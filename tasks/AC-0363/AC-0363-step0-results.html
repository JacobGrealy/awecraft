5. The ticket's causal hypothesis — refuted in mechanism, confirmed in shape

The hypothesis to confirm-or-refute: "the fill is a queue whose drain is paced BY TIME PER UNIT rather than by unit count, so doubling a unit's cost halves the units discharged per frame and roughly doubles the under-built window and the storm's DURATION — more frames spent in an expensive state, not a bigger single frame."

5.1 What the drain actually is (world.gd, current tree — code reading)

  • Dispatch (_drain_build_queue, the DRAIN stage): ONE wall-clock unit budget — LOW_WAVE_PACE_MS = 3.5 ms of WALL CLOCK per dispatch unit (gen-enqueue + high-slab + far-emit all ride it), per-frame catch-up cap LOW_WAVE_FRAME_CAP = 8, plus a drain_budget_ms = 30 time cap and a windowed bucket scan. The 3.5 ms is wall clock spent per unit dispatched — it is fixed by the constant, and the unit's COST is not an input. The per-frame unit count (≈ 4-5 at 60 fps, capped at 8) does not depend on how expensive a chunk is to generate.
  • Generation: runs on the TG worker threads (threadgen_max = 3; 8 in the loading window) — the 5,319 µs/chunk is paid there, off the main thread, and its rate is ∝ 1/cost-per-chunk.
  • Handoff (threadmesh_poll): COUNT-capped at stream_ho_cap (base 3 × speed_factor × radius_factor, clamped 1-100; at R24 walking ≈ 4-5 chunks/frame) — the loading window is time-budgeted (LOAD_HO_BUDGET_MS = 100) but the R24 storm runs steady state. Count-capped again: landing cost does not reduce the count.

So the literal mechanism is REFUTED: the drain is not "time per unit of cost" — it is a fixed wall-clock pace per dispatched unit + per-frame count caps, and the per-chunk generation cost enters none of that arithmetic. Doubling the unit cost would NOT halve the units dispatched or landed per frame.

5.2 But the shape is CONFIRMED, through the TG rate instead

The 5,319 µs/chunk is paid by the TG worker threads, whose chunk production rate is ∝ 1/cost. At 1.84× cost (vs the 2,884 baseline), the in-radius BUILT set fills 1.84× slower — so the under-built window (the walk through ~1%-built terrain) lasts ~1.84× longer, while the per-frame main-thread cost (DRAIN's fixed ~3.5 ms/unit pace × the same ~4-5 units, the same count-capped handoff, the same MISC bookkeeping) is UNCHANGED. That is exactly "more frames spent in an expensive state, not a bigger single frame" — the duration stretches, the frame shape doesn't. AC-0352's own worst frames are consistent with a data-limited, dispatch-capped state: tm/tg pinned at 8/2 (pools saturated — the drain is waiting on data, not throttling cost), the queue deep at 1,306-1,352, in-radius built 22-34 of 2,401, all 20 worst frames in one ~3 s burst.

What distinguishes the two failure shapes — the observable for STEP 1's R24 walk: (i) "one stage got slower per call" → the per-frame stage ms GROWS for the same unit count — a current run would show DRAIN at ~1.84× AC-0352's 20-40 ms (≈ 40-70 ms) on equivalent frames, with the storm window length about the same. (ii) "more frames in the expensive state" (the TG-rate shape this run's evidence supports) → the per-frame split is UNCHANGED (DRAIN still 20-40 ms, same units/frame, same handoff count) but the storm window STRETCHES: more over-30 ms frames (storm_walk_n up), the queue deep for more seconds, in_radius_built_final lower, storm_walk_p99_ms about the same. A current R24 walk (STEP 1, coordinator's heavy stage — ~14 min, not this run) reads exactly those fields and settles it. This run's contribution: the cost side is measured (5,319-class, unchanged since AC-0360) and the code reading says (ii).
