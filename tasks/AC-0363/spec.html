2) Technical Details

THE OBSERVATION AND THE TIMELINE (this is the whole reason the ticket exists):
- AC-0352 (the R24 storm-tail attribution) ran on a tree dated **2026-09-23**. The cave series had not started: the CARVER (AC-0290) landed **2026-09-24 13:59**, the Voronoi AQUIFERS (AC-0291) **09-24 20:43**, caves-P4 contents (AC-0292) **09-25 02:34**, the tunnel gate (AC-0360) **09-25 07:50**. The planet pieces landed **09-25** (P1a grid lock 09:45, P2 placement 12:23, P3 consumers 16:55).
- Per-chunk generation cost, from the commit/standing records (all same-box measurements):
  - AC-0359 (pre-carver baseline): **2,884 us/chunk**
  - AC-0291: **4,532 us/chunk** (+57%; the Voronoi aquifer's per-block 4-nearest search is ~1.6 ms/chunk on its own, fill 515 -> 1,910 us)
  - AC-0292: **5,711 us/chunk** (+26%; field 1502 / scan 1630 / fill 2129 / drip 238)
  - AC-0360: **5,319 us/chunk** (the deep-only tunnel gate removed scan work, as predicted)
- Net across the cave series: **2,884 -> 5,319 us/chunk = 1.84x**, and against the ARCHITECTURE-documented pre-series full-path figure (~1.7 ms/col) it is **~3.1x**.
- SO: the clean attribution in AC-0352 (MISC 59.3% / DRAIN 26.7%, worst frames 66-156 ms `_process`) was measured on a world whose per-column generation was roughly HALF of today's. Every streaming measurement in the R24 row predates the cave series and is now a historical reference, not a current one.

WHY PER-CHUNK COST IS THE RIGHT SUSPECT FOR FRAME TIME (the causal loop, to be confirmed not assumed):
- The fill is a QUEUE (AC-0352 read queue 1,306-1,352 with `in_radius_built` 22-34 of 2,401). The drain is paced BY TIME per unit, not by unit count. So when the cost of a unit doubles, the number of units discharged per frame halves and the under-built window (and the storm's duration) roughly doubles - more frames spent in the expensive state, not a bigger single frame.
- That is a different failure shape from "one stage got slower per call" and the instrument must be able to tell them apart. Do not assume the loop; measure both halves.

STEP 0 - the cheap first measurement (do this before any profiling work):
- `GENMS` / the genhash arm already report per-chunk generation time. Read it on the CURRENT tree and compare directly against the 2,884 / 4,532 / 5,711 / 5,319 sequence above. If the current reading is materially above 5,319 us/chunk, something AFTER AC-0360 (AC-0342's fluid-before-carve, AC-0347 P1-P3, the planet pieces) added cost and that is the first finding.
- Name the delta terms rather than the total: the C++ side already tracks `g_t_carve_us` (~20 us/chunk) and `g_t_drip_us` (~238 us/chunk) class counters; read the full per-stage set (field build / scan / fill / drip / fluid) and report which term MOVED versus the sequence above. A term that grew is the target; a term that is unchanged should be named as cleared.

STEP 1 - attribute the frame-time side (the other half of the loop):
- Re-run the R24 walk arm shape (same knobs as AC-0352: AWECRAFT_RADIUS=24 AWECRAFT_WALK=10 AWECRAFT_TICKTIME=1, seed 44) on the CURRENT tree and compare against AC-0352's readings as the pre-cave-series reference: worst-frame split, `storm_walk_p99_ms` (was 151/141), p95/max, `in_radius_built_final`, `queue_size`, `resident_final`, and the new `crossing_*` fields.
- The comparison is the deliverable: does the CURRENT tree show (a) the same split with a longer tail, (b) a different split (a stage that was small in AC-0352 now large), or (c) the same frames with a deeper queue and a lower built count (the throughput loop)? Each answer points at a different fix.
- Record the tree SHA and the date for both sides. The AC-0352 numbers are only usable as a reference with their date attached, because the generation cost beneath them has since changed by 1.84x.

STEP 2 - the planet pieces specifically (the user's hypothesis deserves a measurement, not a dismissal):
- The planet commits touch `core/sphere_math.gd` (+67/+126 lines), `player/player.gd` (+68/+145), `world/world.gd` (~22 lines each) and `chunk.gd` (+5). Check whether any per-chunk or per-frame work was ADDED on the hot paths: sphere/tangent-plane math evaluated per column during placement or streaming, per-frame player placement, or a new per-chunk transform. Two of those commits touch `world.gd`, whose streaming loops are the ones under measurement.
- ALSO check `player.gd`: AC-0308 (P3 consumers) put +145 lines through the player's physics path, and AC-0352 measured a near-CONSTANT 16-17 ms/frame engine-side gap (physics over 453 collision bodies, render-server bookkeeping, scene-tree work) that the partition cannot see. If the planet consumers added per-frame player work, it lands in exactly that unmeasured gap and would present as "worse since the planet stuff" while being invisible to every existing counter.
- Report the planet contribution as a MEASURED number or an explicit "not measurable with the current instruments" - not as an assumption in either direction.

ADDITION (2026-09-26) - A SHARPER INSTRUMENT FOR STEP 1, from a question worth answering exactly: is the cave-series 3D noise being paid on the FAR LODs too? It is NOT, and the measurement to prove it per run is already exposed.

WHAT THE CODE DOES (`gdext/src/gen.cpp`, `generate_resl` -> `gen_flat`):
- The skip gate is at ~2220: `if (skip) { g_t_cols_skip += 1; ... } else { g_t_cols_full += 1; ... }`.
- Inside the per-column fill the solid test is the SAME gate (~2372): `if (skip) { he = H; }` - verbatim: "the 150-pt density evaluation is skipped free - solid exactly 0..H (the heightmap surface), no caves, no hidden caves built (no f_cheese read, no scan, no lava pocket)".
- Every expensive builder sits in the `else` (full-path) branch: the cave lattice fields (`build_field_c(f_spag/f_nood/f_gate)`, `build_field_vn_c(f_layer)`), the cheese density scan, the aquifer table (`g_t_aquifer_us`, full path only - "the lazy fill and the far payload never read them"), the AC-0292 pillar/vein/biome fields, and the drip pass (`g_t_drip_us`).
- Therefore skip 1 (band-A materialization) and skip 2 (far h-only) both pay NONE of the cave-series cost. The far LODs are not running the new 3D noise; nor is band A.

SO THE REGRESSION IS THE OPPOSITE SHAPE, and this is the thing to measure: the 3D noise got expensive on the FULL path (2,884 -> 5,319 us/chunk across the cave series), and the streaming load is dominated by how many FULL-PATH columns per second the drain has to produce. The far tier stays cheap (~92 us/col) - it is not the consumer; it is the thing whose existence makes the full path's cost matter.

STEP 1 ADDITION - report the FULL-vs-SKIP generation mix per run:
- `AweGen.p4_stats()` already returns `cols_full` and `cols_skip` (gen.cpp ~3107; reset by ~3138). Read them at arm start and end to get COLUMNS/SECOND PER LANE, and report that split next to the per-chunk cost.
- Deliverable: full-path columns/second, skip columns/second, and the generation-time share each lane accounts for. If the storm's generation load is mostly full-path columns, the cave-series cost lands directly on the storm window and the attribution is closed in one number. If it is mostly skip columns, that contradicts the code reading above and is itself a finding worth chasing before any optimization.
- Cross-check against the cost sequence in this ticket's step 0 (2,884 / 4,532 / 5,711 / 5,319 us/chunk) by multiplying out: columns/second x us/column should reconcile with the wall time the arm spends generating. A reconciliation that does not close means one of the two numbers is measured wrong - say which.

This does not add scope: it is a read of counters that already exist, and it turns "the cave series made generation 1.84x more expensive" into "here is how much of the storm window that costs, per second."
