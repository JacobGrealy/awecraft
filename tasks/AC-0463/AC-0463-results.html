2.4 THE FIRST FAILURE The single most likely breakage of a naive unification: STALE FACE LIGHT AFTER AN EDIT. The face lane's re-bake trigger is a COMPARE-AND-ERASE one-shot (world.gd:14967-14976): it fires only when the settled star arr differs from last_eff, then erases the owed key. The home edit path un-settles in HOME world coords (star.on_edit(x,y,z,id), world.gd:12999 — a face cell has no such coordinate). A naive unification that routes a face edit there un-settles the WRONG column: the face column's star arr never changes, the trigger never fires, the owed key is already erased, and the mesh keeps its PRE-EDIT light permanently (until the next landing). The twin feed-side failure is the AC-0358 class: a face slab re-baked from a payload captured outside its own settle state, or with a window that does not match what its bake consumes — the applied mesh drifts from the same-input reference even when the light is cell-identical (window, not light, drives the bake; AC-0358 C4, 5,094-7,867 margin cells). THE ARM / INVARIANT THAT CATCHES IT: - the invariant: the AC-0358 FEED invariant (HARNESS.md:396) — applied bake == settled payload == fresh same-input reference, payload path authoritative (eng_mism + mesh_pa_mism + mesh_qa_mism). It is the right gate for this failure — and it is currently enforced on HOME chunks only (brightslab C1-C6, R16 near the spawn). - the only face-side light gate in the battery: crossface C4 (harness.gd:34999-35060) — light_never_unlit_ok = eff_home >= 1 AND eff_face >= 1 (35059), reading last_eff at ONE seam air cell (35046-35054). It catches a seam light that goes to ZERO (a clobbered key space, a mis-seeded engine) but NOT a wrong-but-lit bake. - CONSEQUENCE: a wrong-but-lit face bake is INVISIBLE to the current gate set (genhash is terrain-only; light/lightstate are home-only at R16/r4). A face-side FEED arm (brightslab-shaped, on a face site) must be BUILT FIRST — the instrument precedes the change — before the feed step (2.5 step 4) lands. The other candidates, ruled in/out: a face engine seeded with the wrong orientation (a (face,cx,cz) clobber or a mirror flip) = light against the wrong neighbors, caught only by crossface C4's weak eff>=1 — the SECOND likely breakage; the far/h-only transition is HOME-ONLY (face chunks are never far, world.gd:13108) and is guarded there by the halo arm (HARNESS.md:398) — giving face chunks a far tier would be a NEW behaviour, not a merge; the AC-0358 re-bake itself (a settled-payload re-bake with a mismatched window) is caught by brightslab on home (same-window reference leg) and by nothing on faces.

2.6 THE COST OF NOT DOING IT The engine DUPLICATION itself is cheap, with evidence: C++ cost zero (the same class, the per-instance key space is the stated reason for the split, world.gd:14919-14920); the per-frame face-side cost is bounded — the step runs only while a face is pending (14942-14943), the steady-state owed scan is ~free (owed ~ 0), and the worst case (~4 faces x 3 ms at a cube corner + the home 3 ms) is ALREADY ABSORBED on this tree (boundary r4 p95 38 ms and planetwalk are green with it — tasks/AC-0469/continuity.md:153, 265). So: two engines are safe to keep TODAY. But the split is not zero-cost — the debt, with evidence: 1. WASTED PAYLOAD: per settled face column per settle window, slab_light_payload + column_light_dict are computed and discarded (14956-14962, chunk.gd:1995), while a comment claims a feed the code does not perform (14973-14974). 2. COARSE FACE EDITS: every face edit un-settles ALL 24 sections via the whole-column reseed (15985) instead of the contained 3x3 x sections 0..si+1 two-phase (starlight.cpp:42-78) — the fallback cost, paid per edit, forever. 3. TWO DRAIN IMPLEMENTATIONS to keep in sync (6206-6232 vs 14944-14976) — the exact bug surface AC-0469 stage F ranked the riskiest slice of the migration. 4. A VISIBLE LIGHT DIVERGENCE: the face subsurface light is the own-column pull — neighbor-blind. A torch in an adjacent face chunk changes the star arr, triggers the re-bake, re-pulls the SAME own-data light, and the mesh never shows the crossed light (home shows it — the payload's strips, mesh.cpp:3596-3621). A feature gap only the eyes (or the owed face-side FEED arm) can see. VERDICT: the split is not "cheap and safe enough that it is not debt" — it is debt, but the honest terminal states are STAGED, not naive: step 3 (one engine, per-face keys, contained edit path, pull feed preserved) kills costs 1-3 with NO visible change and is the cheap safe option; steps 3+4+5 (one feed) also kill cost 4 but require the face-side FEED arm built first and a re-baseline of the face light. A merge justified only by tidiness (jumping to step 4 with no new arm) is worse than keeping two engines — the plan's §6 warning holds, and the evidence here says the risk sits in the feed, not in the engine count.
