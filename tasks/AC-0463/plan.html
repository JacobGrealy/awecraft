1. Goal

A baseline of what each lane holds, evicts and pools over a real traverse — the numbers a unified residency model must reproduce. Without them, slice 2b is unfalsifiable.

2. What is already known (from the code, round 33)

  • Both lanes have windows and eviction; they differ in policy, not in existence. Home: banded residency + drain queue, async worker generation. Face: _face_stream (world.gd:15008) with a window from sim_dist ×16 face cells, FACE_STREAM_BUDGET_MS = 12.0 (14995), eviction past the expanded window via _face_free_chunk (15125, called at 15123), star evict + pooled-column checkin, sync WorldGen.generate_face.
  • So the slice is NOT "give faces residency" — it is "make the two policies one", which is why the baseline matters.

4. What to report

  • A home-only traverse (walk away from the boundary, never crossing): home resident chunk count over time, evictions, pooled columns reused vs created, peak memory if a counter exists.
  • A crossing traverse (the planetwalk route): the same counts PLUS face resident chunks and face evictions, sampled before, at and after the crossing.
  • The steady state: after the traverse settles, how many home and face chunks are resident, and whether that number is stable across repeated samples (a growing count is a leak finding, not a number to record quietly).
  • Report the policy parameters each lane actually used on the run (bands, sim_dist, the expanded window, the budget) so slice 2b has the current settings, not a guess.
  • RESULT keys: ok, home {resident, evictions, pooled_new, pooled_reused, peak}, face {resident, evictions, window_cells, budget_ms}, samples [{t, home_resident, face_resident}], steady {home_resident, face_resident, stable}, fails.
