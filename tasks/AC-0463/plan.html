AC-0463 stage L6 — the face lane consumes its payload (the one visible change)

Coordinator contract. High-effort builder applies it with tasks/templates/implement.md. This is the only stage in the whole light migration that intentionally changes what the player sees. Every earlier stage was proved by identity; this one cannot be, so its gates are built to accept the intended change and catch unintended ones.

1. Goal

A chart-face chunk's mesh is built from the light payload's window — the same authoritative path the home pair already uses — instead of the own-column pull that discards the payload.

2. What is measured, and what it says

  • The payload is obtainable on faces (payload_ok=true everywhere) but not consumable: it carries eff while build_mesh_face requires arr (chunk.gd:1995 vs starlight.cpp:822-884), so the build's has_payload is false at every point. Home sets pl["star"]=true and bakes from the payload; faces never do.
  • Measured with the facefeed arm (L5): at settle a==b==c (d=0) — the own-column pull and the payload agree when settled. Transiently, b lags a by 313 cells (x face) / 82 (z face), converging to 0.
  • Neighbour-blindness measured ZERO on open terrain (sky-saturated at the boundary rows). So this stage is not about adding neighbour light — it is about the payload's window-plus-strips versus the build's empty strips (AC-0358 C4: the window drives the mesh).

3. The honest expectation, stated before the edit

Because a==b at settle, this change should be nearly invisible in steady state and should show up mainly (a) during transients, where the payload carries the corrected light the pull lags behind, and (b) at the strips, where the build currently feeds nothing. If the change turns out to alter steady-state light broadly, that is a signal something is wrong with the window, not a success. Write this expectation down before editing and check it afterwards.

6. Acceptance

The face build consumes the payload (d_a_b zero everywhere), light stays coherent with no leaks and no seams, the render shows no boundary artefacts and is described, and the steady-state change is as small as predicted.

7. Risks

(1) If d_a_b goes to zero by making the arm's two sides agree rather than by making the build read the payload, the gate is worthless — so state how you know the build is reading it, e.g. by changing a payload value and seeing the mesh change. (2) A window mismatch produces visible chunk-border bands; that is what the render is for. (3) If the steady-state light changes broadly, you have a window bug — stop and report rather than tuning until it looks right.

8. Fences

  • No edits outside §4. Do not change the window semantics or tune light values to make a gate pass.
