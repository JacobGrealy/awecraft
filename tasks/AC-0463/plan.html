AC-0463 stage L1 — what would one light-ownership model require?

Coordinator contract. Medium builder applies it with tasks/templates/implement.md. Diagnosis and design only — no behaviour change. Light is the last structural split: _star_faces holds per-face engines while the home path lights differently. AC-0469's stage F ranked this the riskiest slice of the whole migration, gated by AC-0358's feed invariant and the lightstate arm — so it is diagnosed before anything moves.

1. Goal

A written, evidence-backed answer to: what exactly differs between the two light paths, can one ownership model serve faces 0–11, what would break first, and in what order could it be changed while keeping the world lit.

2. What to establish (each with file:line evidence)

  • 2.1 The two paths, precisely. How the home path owns and feeds light (the star engine, its seed/feed/re-bake cycle) versus _star_faces (per-face AweStarlight instances, D4). What is per-face that would have to become per-world, and what is per-world that is currently duplicated per-face?
  • 2.2 The FEED invariant (AC-0358) and what it constrains. Read what AC-0358 established — the measured bakes, the strip window the payload carries, the reference the arm compares against — and state exactly which assumption a unified model would have to preserve. This is the part that will silently break lighting if it is missed.
  • 2.3 The per-face machinery that is genuinely per-face. The migration has already established the pattern: some face-lane behaviours are geometric and must survive as rules (the edge-normal gate, the edge bands, the mirror chart). Do the same classification here — which light behaviours are (a) identical across faces and can unify, (b) genuinely per-face (orientation, the mirror class, the chart's own normal) and must survive as rules, or (c) only exist because there are two engines.
  • 2.4 The first failure. Name the single most likely breakage of a naive unification and the arm or invariant that would catch it. Consider: stale light after an edit, a face whose engine is seeded with the wrong orientation, the far/h-only transition, the AC-0358 re-bake.
  • 2.5 A staged order that keeps the world lit after each step, with the gate that proves each step. Step 1 should be the one that changes no behaviour, as in the residency merge.
  • 2.6 The cost of NOT doing it. If the answer is that two engines are cheap and safe to keep, say so with evidence — a split that costs nothing is not debt worth risk.

5. Acceptance

A design note answering §2.1–§2.6 with file:line evidence and a staged order, and a tree provably untouched.

6. Risks

The honest answer may be "keep two engines" — that is a finding, and a better one than a risky merge justified only by tidiness. A note that concludes "unify" without naming the AC-0358 constraint and the first failure would be worse than no note.

7. Fences

  • No git commit/push/add; no tasks/TASKS.yaml; no new tickets.
  • No code changes at all. This stage writes a design note and runs the gates to prove the tree is untouched.
  • If the plan cannot be applied — anchor missing, symbol absent, steps contradict, or a design decision this plan does not make — write PLAN-INSUFFICIENT: <what is missing, file:line> and EXIT. Do not invent the design.

8. Resume point

Everything except light is unified: one grid (1 m cubic, AC-0471), one placement, one key shape, one node path, one landing, one generation queue and drain, one travel gate and window, one residency model (AC-0469 G1–G4).
