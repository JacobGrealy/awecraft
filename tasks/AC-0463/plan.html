AC-0463 stage L5 — the face-side FEED arm (the instrument step 4 needs)

Coordinator contract. Medium builder applies it with tasks/templates/implement.md. A measurement instrument, not a behaviour change. Stage L1 established that step 4 (one feed) is the only visible change in this migration and that it must not be attempted before a face-side FEED arm exists — because the face path's light is currently unverified against the payload it ignores. This stage builds that arm.

1. Goal

An arm that answers, for a chart-face chunk: does the light the mesh is built with equal the settled light the payload carries, and does that equal a fresh same-input reference bake — the AC-0358 test, applied to faces.

2. What the home side already does (the model to mirror)

AC-0358's invariant, recorded in godot/HARNESS.md: applied bake == settled payload == fresh same-input reference, with the payload path authoritative, and the payload's w_lo/w_hi strip window (2-row overhang, starlight.cpp:797-803) plus zero-filled/unseeded-zero strips being exactly what the bake consumes — the window, not the light, drives the applied mesh (AC-0358 C4). Read the home arm's implementation and follow its structure rather than inventing one.

3. What stage L1 established about the face path (do not re-derive)

  • The face "re-bake on the payload" discards the payload: build_mesh_face requires an arr key (chunk.gd:1995) while slab_light_payload produces eff (starlight.cpp:822-884) and never sets pl["star"]=true. Face mesh light is therefore always an own-column pull.
  • Consequently the arm must be able to distinguish three things, not two: (a) the own-column pull the mesh uses today, (b) the settled payload, (c) a fresh reference bake. If (a) and (b) legitimately differ today, that difference is the finding — the arm should report it, not fail on it.
  • The engines live in _star_faces (14915, 14921-14927); star_for(face) (14938) answers ownership; face seeding happens at _face_land (15875).

5. Edit shape

  • 5.1 Report numbers, not a verdict. For each sampled face chunk: the applied-light checksum, the payload's eff checksum over the window, the reference-bake checksum, and the window bounds used. The arm's ok should assert only what is true today; anything currently divergent gets reported as a measured delta with a flag, so that step 4's change can be judged against a real "before".
  • 5.2 Sample across both chart classes. At least one x face (4-7) and one z face (8-11), because they differ in mirror class and the halved axis — the class where L1's other findings clustered.
  • 5.3 Deterministic. Same inputs, same numbers. If a value wanders between runs, say so and give both runs — OPS.md §7 applies to the arm being built, not just to arms being used.
  • 5.4 The arm must be able to fail. Include one deliberately-chosen chunk whose light is known settled and one that is not, so a green result is not simply "the arm never looked". State how you know it can fail.

7. Acceptance

A documented arm that reports applied/payload/reference light for face chunks on both chart classes, shows its own numbers and whether they can fail, with no product code changed.

8. Risks

An arm that only ever reports "ok" is worthless — §5.4 exists because that is the likeliest failure of an instrument built by someone expecting a pass. If the payload cannot be obtained for a face chunk at all (because the face path never carries one), report exactly that: it is the strongest possible evidence for step 4's necessity.
