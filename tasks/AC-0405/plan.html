AC-0405 plan — raymarched-volumetric-clouds

2026-10-07 · builder run (plan + implement in one turn). Redirect from the user: "look at how voluminous clouds are done and implement them, forget how we currently do it." Four rounds of patterned-surface work failed because a single surface at a single radius has no parallax and no internal depth.

Goal

Replace the look of the cloud deck with a raymarched density volume: step a view ray through a 3-D density field in the annulus R+275…R+400 about (0,−R,0) (the same verified shell extent), accumulate Beer's-law transmittance, and light each sample by marching a short ray toward the sun through the same field. That light march is the single thing the patterned surface cannot do: it produces lit tops, shaded undersides and a brightness range. Acceptance (the user's two complaints, measured): (a) a frame where one mass is visibly behind another + a descent passing through distinct structure; (b) the 700 m lower-mid-band luminance σ (the assessment's instrument, .scratch/AC-0384-final-run/analyze2.py, band lower_mid) measured against the 16.9 (deck ON) vs 32.4 (clouds OFF) baseline — plus cost, measured and reported, because this box runs 2–5 FPS and a cheap convincing result beats an expensive one.

Technique and why

References read before designing (per ticket, in order of usefulness):

  • Guerrilla SIGGRAPH ARTR "The Real-Time Volumetric Cloudscapes of Horizon Zero Dawn" (Schneider & Vos) — the canonical model: density = thresholded FBM; Beer accumulation with adaptive steps; self-shadow by a light march toward the sun; Henyey–Greenstein phase for forward scattering; a powder/dark-edge term to keep boundaries from reading as grey mush (guerrilla-games.com talk + advances.realtimerendering.com ARTR slides).
  • godotshaders.com "Volumetric Raymarched (animated) Clouds v2" (thepathgame) — the working Godot-4 fragment-shader implementation: sphere/box slab intersection, a fixed-count step loop, 3-D density sampling by position, self-shadowing inside the march (fetched via the Wayback Machine; the live page is behind a browser check). Its shadow math is ad hoc; I keep its structure (slab intersection + count-based steps) and the HZD/Heckel lighting model instead.
  • NUBIS / meteoros and Heckel's walkthrough — the same technique family; not needed further once the Godot one was read.

Why a fragment-shader march on the existing outer shell (rather than a new mesh, a 3-D texture, or compute): it reuses the verified geometry (radii/centre untouched), needs no texture memory (analytic FBM — the same ahash/anv the deck already uses, so the pattern's character is directly inherited), compiles on the shipped Forward+ path, and the OFF state is a uniform branch that short-circuits before any new work — provably the old look. The marching shell is the outer shell (R+400, the one with u_phase 0): its fragment shader intersects the annulus [R+275, R+400] with the pixel ray (up to two segments — the near side and the far side of the limb) and marches both; the two inner shells are hidden (node visible — geometry never moves) while the volume is ON. The silhouette against the sky becomes soft (alpha = 1 − transmittance fades) — this also retires D2, the crisp deck edge at the limb the assessment measured.

Density field

q     = wind-rotate-Y(u_drift*u_cloud_time) of (p - u_center) / R     // planet-frame unit sphere
f0    = u_scale3 * R / u_vol_rmax          // = exactly the 256 m base period of the top shell
base  = fbm3(q * sc3)        (3 octaves, lacunarity 2.03, the existing anv noise)
mid   = fbm3(q * sc3 * 2.2 + off)
cl    = the EXISTING deck window chain, byte-identical constants (smoothstep window,
        contrast, band floor, latitude band 0.5+0.5*sin(qy*5 + 2.2*base), soft edge)
        with u_deck selecting the re-characterised deck params (x1/3 frequency, tighter window,
        0.60 band floor) exactly as the 2-D path does
density = cl in 0..1;  light-march and edge taps use a COARSE field (base octave + band only)

So cloud_deck keeps working and keeps meaning: it re-parameterises the field (1/3 frequency = fewer, bigger masses; tighter window = fewer). Feature sizes: ~256 m base masses (deck OFF) / ~768 m (deck ON, the AC-0401 character).

Lighting per accepted sample (d > 0.015)

sh      = exp(-sum of 6 coarse taps toward the sun, step 80 m, early exit at optical depth 3)
cosSun  = dot(u_sun, rd)                     // +1 looking toward the sun
phIn    = HG(cosSun, 0.65)    (in-scatter: bright rim around the sun — the NMS approach look)
phOut   = HG(-cosSun, 0.65)   (out-scatter: faint rim opposite the sun)
edge    = clamp(d - coarseDensity(p - rd*e), 0, 1)      // 1 tap toward the CAMERA
darkEdge= 1 - u_vol_edge * smoothstep(0.08,0.4,edge) * (1 - 0.85*smoothstep(-0.3,0.7,cosSun))
         // darkens camera-facing boundaries unless the sun is in front (forward scatter)
inscatter += T * d * phIn * sh * darkEdge
outscatter += T * d * phOut
T        *= exp(-d * dl * sigma)            // Beer, sigma = 0.01 /m at d=1 (opaque core ~250 m)
ALPHA   = 1 - T
ALBEDO  = u_cloud_tint * u_day * (2.2*inscatter + 0.35*outscatter)   // then the existing srgb_pre
         // u_day = 0.18+0.82*day (the deck's own day/night weight); the directional part of the
         // lighting IS the shadow: a top sample's sun march exits the cloud (bright), an underside
         // sample's stays inside (dark)

Ray/segment construction (per fragment)

ro = CAMERA_POSITION_WORLD, rd = normalize(v_wp - ro), w = ro - u_center, rc = |w|
roots of |w + rd*t| = rmax / rmin  (quadratics, the standard form)
rc > rmax : seg1 = [tO1, tI1], seg2 = [tI2, tO2]   (or [tO1,tO2] if the ray misses the inner ball)
rmin < rc < rmax : seg1 = [0, tI1], seg2 = [tI2, tOf]   (camera in the annulus)
rc < rmin : seg1 = [tIf, tOf]                        (camera inside the inner ball; both roots
                                                     are the forward exits, tIf < tOf)
march seg1 then seg2, carrying T.  Steps per segment = u_vol_steps (24): the step is
length/count, so it is distance-adaptive by construction (2600 m limb: ~70 m steps;
120 m interior: ~6 m) — the r5 grain problem cannot happen: at distance the march
over-integrates the fine octaves instead of aliasing them.
One-hemisphere rule: camera outside the outer sphere -> discard back faces (the existing
rule, verbatim); camera inside -> keep only the NEAR hemisphere (dot(n,V) < 0) so each pixel
is marched exactly once (no double-blend of the same volume).

The switch

Settings.cloud_volume (menu row "Clouds: raymarched volume (real depth)"), default ON — the user ordered the rework in their own words ("forget how we currently do it"), the modern_light/cloud_deck precedent: default conservative only when the user has not asked. AWECRAFT_CLOUDVOL=0 env for the A/B renders. OFF = all three shells draw the exact AC-0401 path (the shader short-circuits on the uniform before any volume work; the inner shells are visible again). The two switches compose: CLOUDVOL×CLOUDDECK = 4 states; volume + deck OFF gives the r9 character in 3-D, volume + deck ON the AC-0401 character in 3-D.

Cost budget (the real constraint — measured, not assumed)

  • View march: 24 steps/segment, max 2 segments (limb views) = ≤ 48 full-field taps (3 octaves) per pixel; early exit when T < 1/255.
  • Light march: 6 coarse taps (1 octave) per accepted sample only (d > 0.015), early exit at optical depth 3.
  • Dark-edge: 1 coarse tap per accepted sample.
  • Worst-case pixel (2600 m grazing limb): ~48×3 + 48×7 ≈ 430 noise taps. Typical 2600 m pixel: ~1 segment, ~24×3 + ~12×7 ≈ 156. 120 m interior pixel: ~24×3 + 24×7 ≈ 240 (short 139 m path).
  • Budget: the 1200-frame snapshot drain must stay under the 1200 s/run cap. Baseline (AC-0384 §25, user R24/F83): ~210–240 s per run at ~5 FPS. Target: ≤ ~360 s (+50%) with volume ON. Measured with wall clock + AWECRAFT_DSSTATS=1 (the overlay's FPS read) on the 700 m run, plus an ON/OFF A/B pair at 700 m. If a frame blows the budget, the fallback is 640×360 for that frame (documented), not silently shipping slow.
