3. The two bugs found by the probe (both fixed, both C++-side)

#symptomroot causefix
B173/1,348 bottom-face records sl exactly 1/15 too bright; ±1-quad c/u driftport typo in s_face_light: the n.z==0 branch's second probe read (nx, ny-1, nz) instead of (nx, ny, nz-1) — it sampled one row BELOW instead of the −z neighbor. In-function trace (FL/EF lines) proved the extra ny-1 call; the box was byte-identical, so only the probe coordinate was wrong.nz - 1 (now verbatim with chunk.gd:1154).
B23 records in one chunk: C++ face mask 1 vs GDScript 0 (r/g channel swap, s=0.08 both)The GDScript original itself diverges from its own light function: _face_mask (chunk.gd:675) samples (nx, ny-1, nz) in the n.z==0 branch while _s_face_light (chunk.gd:1154) samples (nx, ny, nz-1). My first port wrote face_mask "clean" (nz−1) — matching the light function but NOT the shipped GDScript mesh. RECMASK trace showed every GD mask sample by name (the nz−1 byte was 1, the ny−1 byte 0) — the shipped behavior is the quirky one and must be preserved to be lossless.C++ face_mask re-verbatim to the chunk.gd:675 quirk, with a comment pinning the provenance.

Method note: both bugs were invisible to output-level A/B until instrumented per-sample (each probe's 5 s_effl/mask_sample calls with coordinates + lmn + buffer pointer, thread-local to avoid worker interleaving, gated on a d_off==-999 probe sentinel so the world's worker threads never touched the dumps). All instrumentation was removed before the final build (0 references in mesh.cpp; probe debug blocks gone, _acc_diag kept — it does no file I/O).
