Registry notes (verbatim, quoted):

1) User Story

The frame drops are attributed now, but the single biggest share of them is a bucket labelled "other" that nobody can break down, so "we know what is slow" is only two-thirds true. I want that bucket opened so the next ticket can be aimed at a named consumer instead of at the residual.

2) Technical Details

PREREQUISITE - READ AC-0363's RESULTS FIRST. If AC-0363 shows the tail is dominated by a named stage on the current tree, this ticket's shape changes (the residual may shrink or grow with the post-cave-series generation cost). If AC-0363 reports the same split AC-0352 did, this ticket is the direct follow-up. Either way, take the current MISC share as the baseline to move, do not reuse AC-0352's 59.3% as if it were today's number.

WHAT IS KNOWN (AC-0352, R24, worst-20 frames, 1,973 ms total):
- **MISC 1,170.4 ms = 59.3%** of the worst-frame cost. It is the in-process RESIDUAL of the wprof partition - everything inside `World._process` that no stage bracket covers.
- Named candidates, listed by that ticket but never measured: save-queue writes, the 20 Hz tick, fluid dispatch, atlas/cull checks, and GC-class pauses.
- The rest of the split for reference: DRAIN 26.7%, HANDOFF 6.6%, STAR 5.8%, RECENTER 5.7%, COLLIDE 2.1%, LOW 1.7%, and MESHATTACH / FACELIGHT / IO at 0.0.
- Separately and NOT part of this ticket: the arm-side frame wall exceeds the `_process` total by a near-constant 16-17 ms (physics over 453 collision bodies, render-server bookkeeping over 882 MIs, scene-tree work) - ~15.5% of the mean worst frame and 68% of the run's 353 ms max. That is the ENGINE-SIDE gap and it is a different instrument problem (see step 2).

STEP 0 - sub-bracket the residual (the whole ticket):
- Add sub-brackets inside `World._process` for each named consumer: save-queue writes, the 20 Hz tick, fluid dispatch, the atlas/cull checks, and a GC proxy. Keep them cheap and keep them in the residual's own idiom - this must not itself become a per-frame cost that shows up in the numbers it measures.
- Report the split over the SAME population AC-0352 used: the worst-N frames above the threshold, not an average over all frames. A consumer that is 2% on average and 40% on the worst frames is the interesting one, and averaging hides exactly that.
- Report per-consumer p50/p95/max over those frames plus the aggregate share, so one dominant consumer is distinguishable from five small ones.

STEP 1 - the two hypotheses worth naming in advance (so the result is interpreted, not just tabulated):
- **The 20 Hz tick may fire more than once inside a long frame.** If the tick is driven by accumulated time rather than frame count, a 150 ms frame can run it several times, which makes it a candidate that SCALES WITH the stall rather than merely contributing to it. Check the call count per captured frame explicitly - if it is >1, that is a finding.
- **GC is the classic explanation for a bursty p50-2ms/p95-57ms tail** and has never been measured. A GC proxy (object count deltas, or the engine's own counters where available) belongs in the capture even if it is crude. If GC dominates, the fix is allocation reduction in the streaming path, which is a very different ticket from tuning a consumer.
- A third possibility to record honestly: the brackets may show the residual is genuinely diffuse (five consumers each 5-15%) with no owner. That is a legitimate result - say so rather than picking the largest and calling it the cause.

STEP 2 - report the engine-side gap as a number, not a footnote (and do NOT try to fix it here):
- `World._process` cannot see the physics step, the physics server, the render server or scene-tree work. AC-0352 measured that gap at 16-17 ms/frame on the worst frames and 68% of the run's max frame. Record whether the per-consumer brackets change that reading, and if the gap is unchanged, state that this ticket deliberately leaves it to a separate one - an engine-side fix needs a different instrument (FrameTime-style profiling or a custom physics-step bracket) and should not be smuggled in here.

FENCES: instrumentation only. No allocation rewrites, no consumer optimization, no touching the engine-side gap. Deliverable is the split plus the recommendation of which named consumer (or which diffuse finding) the follow-up should target. Keep the standing values held - this adds brackets inside an existing partition, so boundary r4, the R24 crossing row and storm_walk_p99_ms must not move.



ADDITION (2026-09-26) - FLAG NATIVE-PORT CANDIDATES IN THE SPLIT. When a sub-bracket names a consumer, also record whether that consumer is main-thread GDScript, and if so whether it looks like a port candidate. The reason this clause exists: a GDScript hotspot on the main thread is invisible to a stage partition - it lands in MISC and reads as "bookkeeping" - so without this flag a real native-port case would be reported as an anonymous residual and lost.

For each named consumer, record three extra fields:
- **lane**: C++ (gdext) / GDScript main thread / engine-side (not in `World._process` at all).
- **call shape**: per-frame, per-column, per-slab, per-cell, or per-event. THIS IS THE DECIDING FIELD - a consumer called per frame is a port candidate at almost any size; one called per column is usually not worth the marshalling.
- **port candidate**: yes / no / unclear, one line why.

Worked examples so the builder does not have to guess what "candidate" means (these are illustrative, not a worklist - do NOT port anything in this ticket):
- `world.gd`'s pool/score path (`_collect_pool` and the scored picks) rebuilds an array of up to `PICK_POOL_CAP` (512) entries and re-scores it, and `world.gd:466` documents that it used to run every frame before AC-0233/AC-0250 added the version-gated debounce. It is main-thread GDScript, PER-FRAME in shape - so if it appears in the MISC split, flag it as a candidate with its measured share.
- `core/sphere_math.gd` is pure float math with no SceneTree dependency (a natural native port) but its call sites are per-column for placement and a couple of operations per frame for movement - so it is main-thread GDScript with a PER-COLUMN/PER-FRAME-MINOR shape. Flag it, but say plainly that its frequency is low; porting it on structure alone would be a guess.
- Anything in `scenes/harness.gd` is dev-only and must NOT be flagged as a shipped-work port candidate, even when it is expensive (the `seamcensus` reverse-map is the current example).

WHAT THIS DOES NOT CHANGE: the ticket stays instrumentation-only. The flag is a REPORT, not a work item - no consumer may be optimized or ported here. If the split names a per-frame GDScript consumer with a material share, that is the finding this ticket was worth running for, and the port becomes its own ticket with the measured number attached.
