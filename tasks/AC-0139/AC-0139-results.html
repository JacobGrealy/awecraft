1. Design choice (decided + documented)

Minimum-change: main.tscn stays the project main scene. The gameplay root instantiates the new scenes/menu.tscn as a child in menu state; Start/Play and New World free-hide the menu and enter play — exactly the behavior every harness arm sees today. project.godot and main.tscn are untouched (no main-scene change needed ⇒ no env-var or boot-path change for any of the ~20 AWECRAFT_LOGIC arms, the AWECRAFT_SNAPSHOT/AWECRAFT_AIM/AWECRAFT_CAM snapshot flow, the battery, or the menu arms). Making menu.tscn the main scene + change_scene_to_file to gameplay would have forced every arm to re-route through a scene transition = a much bigger behavior change with no benefit; not chosen.

Root class per spec = Control, with a CanvasLayer child inside the scene. The old menu root was a CanvasLayer at layer = 20 (drawn above HUD/world). To keep that draw order exactly while satisfying "root Control + ui/menu.gd attached", the scene is Menu (Control) → Layer (CanvasLayer, layer 20) → boxes. The root Control's visible propagates to the whole subtree, so menu_ui.visible (asserted by the mainmenuexit arm) and the "ingame = hidden" semantics are unchanged. The root Control is 0×0, mouse_filter = IGNORE — no input change.

Menu UI construction lives in the .tscn (visually editable), not code. The whole node tree (3 boxes, ColorRect backgrounds, CenterContainer/VBox columns, all Labels/Buttons/LineEdit/HSliders/CheckBox/OptionButton, bottom help strip, FileDialog) is declared in menu.tscn; all 22 signal connections are declared in the .tscn (incl. bound args: slot rows → continue_clicked(n)/_clear_slot(n), options source → open_options("main"/"pause")). ui/menu.gd keeps the state machine (_state), the 5 external callables, slot/refresh/sync logic and handlers; _ready() collects node refs and does the small dynamic init (Build.ID version label, seed text, FileDialog file_mode/access/filter + its one connect).

Investigation finding (shapes the diff): the menu state/logic already lived in ui/menu.gd (a prior task extracted it; main.gd only wired it). So "extract menu state out of main.gd" was already satisfied; this task moved the remaining menu construction out of code into the scene and switched main.gd from MenuScript.new() to MenuRes.instantiate(). That is why the main.gd diff is deliberately tiny (4 changed lines) and the menu-code line delta is concentrated in ui/menu.gd (−242) + new menu.tscn (+462).
