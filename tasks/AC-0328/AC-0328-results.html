1.4 The one result=0 run, stated honestly

Round 5's B-09 (line 79 of campaign.log) read rc=0 gdb_stopped=1 sig=[] handler=0 result=0 — the engine exited 0, raised no signal, and the crash handler never fired, but the arm's RESULT line was absent. That run's per-run gdb log (.scratch/AC-0323-repro/gdb-B-09.log) was overwritten by later rounds (loopB reuses one filename per run index), so the missing RESULT cannot be inspected — only the recorded summary line survives. It is recorded here rather than swept under: it is the one imperfect data point in an otherwise uniform 99-run table, and a future run of the same shape should re-capture per-run logs under unique names if it recurs.

1.5 What this does and does not prove

Does not prove the crash is gone. At a true 1-in-10 rate, 99 clean runs would be 0.999 ≈ 3×10−5-likely — so either the rate on this tree/host state is far below 1 in 10, or the fault needs a condition loopB does not reproduce. Combined with AC-0323's 43 clean runs on the 2026-09-18 tree, that is ~142 clean runs — a bounded negative result on this host state, the ticket's valid "1 in N, well-characterised" outcome (item d), not an exoneration. The fault family predates the far-band work by ~90 tickets (identical banner + the single frame libc.so.6(+0x45f60) = the rt_sigreturn stub in .scratch/ac0231-r16-inrpass.log, .scratch/ac0236-bat-smoke.log, .scratch/batt192.log …) and its signature is a corrupted-signal-frame class, not a logic branch — so it must be assumed to still exist until a capture or a mechanism-level fix.

2.3 Raw stderr — the complete capture, and the explicit answer

The stderr stream (r50gdb.err) is 132 bytes in total. The engine contributed 0 of them. Every byte is gdb's own output, produced after the process had already exited (gdb's bt and info sharedlibrary commands, run on a dead inferior):

No stack.
warning: Could not load shared library symbols for linux-vdso.so.1.
Do you need "set solib-search-path" or "set sysroot"?

Was there a Rust panic message: NO. The engine's stderr was completely empty — no thread '…' panicked at …, no note: run with RUST_BACKTRACE=…, no abort message, not even an ordinary error line. A pattern grep (panicked at | RUST_BACKTRACE | thread … panicked | rust panic | abort, case-insensitive) over r50gdb.err returns 0 matches; the same grep over the entire combined log (r50gdb.log: gdb output + engine stdout + engine stderr) also returns 0. Since a Rust panic/abort in the engine's statically linked Rust runtime would print to stderr and/or raise SIGABRT, this run shows neither the message nor the signal. (A caveat stated plainly: one run is one sample. The engine's stderr was also empty in the 99 campaign runs' shape — the crash handler's banner is a stderr writer that never fired — so "no message" here is the expected shape of a non-panicking run, and it rules nothing out on other runs.)

3. What a future investigator should try (this hunt did not)

The surviving suspect list (carried from AC-0323): the uncapped 25-element burst group task (now RETIRED by AC-0293 — the 5×5 spawn burst was the only add_group_task caller; it is a historical suspect, and its retirement is one concrete change the load-arm crash could react to), the EditPool raw thread (a bare Thread outside the pool — confirmed live in the process by AC-0323 Phase E), engine pool internals (incl. the statically linked Rust runtime — the SIGABRT-no-message shape), and scheduler-state interleaving (host-dependent timing). The loopB scenario (lightstate R16, ~45 s, t≤12 s first-wave shape) exercises none of these in their heavy-streaming form. Not tried in this hunt, in order of expected value:

  1. Repeat the R50 load arm under gdb until a stop — this is the ticket's named reliable reproducer (3/3 in the AC-0322/AC-0293 era), and this hunt ran it only ONCE (item c's scope). The loop is the campaign pattern: r50gdb.sh already does one run; wrap it in a round loop with unique per-run filenames (fixing the §1.4 overwrite gap). ~13 min/run.
  2. Add RUST_BACKTRACE=1 (then =full) to the env of such runs: the engine's Rust runtime is Godot's, but a panic hook that prints a backtrace on stderr will do so if the environment variable is honoured — it turns the "SIGABRT with no message" variant into a named-frame capture at zero code change.
  3. Sustained heavy streaming at play scale under gdb — boundary R24/R50 storm runs (the AC-0348/AC-0352 ~20-min storm class) rather than the load arm, if the load-arm loop stays clean: the fault family was filed from r16/boundary-era logs, and the EditPool raw thread gets far more churn under sustained editing/streaming.
  4. Core dumps — ulimit -c unlimited plus a gdb post-mortem of the core (the ticket's item b names this path); a core of a SIGABRT gives the aborting thread's stack even where the in-process unwinder produced the one-frame dump.
  5. Windows — the product is Windows-only (AC-0124) and this hunt (like AC-0323) ran entirely on this Linux dev box; a scheduler/interleaving or Rust-runtime fault can be platform-specific. The repro recipe here (arm + env + gdb) transfers.
  6. A loaded host state — every run here had 18–45 GB free and an otherwise quiet box; AC-0323's filing-era box had ~47 GB used. The scheduler-interleaving suspect wants contention: run the loop under CPU load (or on the busy box) to widen the interleaving envelope.
