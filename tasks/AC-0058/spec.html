AC-0058 — web view: game renders to only ~2/3 of the screen

User report (2026-08-20, verbatim)

"now in web view the game is only rendering to like 2/3 of the screen"

Facts (coordinator-verified before launch)

  • godot/project.godot: display/window/size/viewport_width=1280, viewport_height=720. 1280×720 is exactly 2/3 of a 1920×1080 window — strong match for the symptom.
  • web/index.html (build artifact from ./build_web.sh → godot --export-release "Web") sets GODOT_CONFIG = {... "canvasResizePolicy":2 ...}. The canvas appears to stay at 1280×720 in a larger browser window instead of filling it.
  • web/ is a BUILD ARTIFACT, regenerated by build_web.sh on every build. The fix must live in godot/ (project settings / export_presets.cfg) and/or build_web.sh (post-export step). NEVER hand-edit web/ files directly — they get overwritten.
  • The current served build (19:01) already contains the aero look (AC-0056), so verification screenshots will show the aero sky — keep aero on in shots.

Diagnosis (first, in the browser with playwright on https://localhost:8443, ignore self-signed cert)

  1. Open at a fixed viewport (e.g. 1920×1080), wait for world load, then measure and record: window.innerWidth/innerHeight, canvas.id="canvas" clientWidth/clientHeight, canvas.width/height (drawing buffer), getBoundingClientRect().
  2. Resize the page (e.g. to 1366×768), wait, re-measure. Determine: does the canvas ever track the window? (initial-load-only, resize-broken, or both)
  3. Record the exact root cause in the report (which policy/settings combination produced the stuck size).

Fix (pick the cleanest that works; keep it reproducible through build_web.sh)

  1. Preferred: Godot-side only — export_presets.cfg web options (check what the 4.7.1 preset exposes for canvas resize, e.g. "resize on demand") and/or project settings display/window/stretch/mode (e.g. canvas_items + aspect expand) so the exported page auto-scales the canvas to the window. Desktop behavior must stay identical (normal windowed run).
  2. Accepted fallback: post-export step in build_web.sh (we own the script): rewrite the generated web/index.html — e.g. set canvasResizePolicy to the resize-everything value and/or inject CSS html,body{width:100%;height:100%} #canvas{width:100vw;height:100vh} — so every build self-heals. Document the injected block in a comment in build_web.sh (comments allowed in shell build scripts).
  3. Either way, input must still map correctly: after the fix, a click at the rendered crosshair center must hit world-center (mouse scale). Verify by playing 10 s in playwright: move mouse, look changes proportionally; click places/mine-hits where the crosshair points (or at minimum: mouse movement drives the camera without offset).

Verify gates (ALL; zero script errors is a hard gate)

  1. Headless: ~/tools/godot/godot --headless --path godot --quit → 0 script errors (if you touch project.godot/preset settings).
  2. Full battery green (player interact light fluids buckets craft guiclick combat swing settings; 0 script errors).
  3. ./build_web.sh exit 0 (fresh export with the fix baked in).
  4. Browser (playwright, https://localhost:8443): (a) 1920×1080 viewport → canvas fills the window (clientWidth≈innerWidth, clientHeight≈innerHeight, buffer size tracked); (b) resize to 1366×768 → still fills; (c) no console errors; (d) full-window screenshot(s) saved to tasks/AC-0058/ (aero look should be visible, full frame). View your own screenshots before reporting.
  5. tasks/AC-0058/AC-0058-results.html: root cause, measurement table (before/after, both viewports), fix location (file:line), screenshots embedded. Report to coordinator MAX 20 lines: root cause one-liner, fix + file, measurement values, screenshot paths.
