Registry notes (verbatim, quoted):

1) User Story: As a player, the planet should already be there when I enter a world and fly up - not minutes later, and not only if I happen to stand still long enough for the background work to get a turn. Today a world whose seed is not the one shipped with the game bakes its whole-planet texture while I am playing, on one background thread that the streaming work outranks, so the satellite planet reads as "lod not loading at any height" until it eventually appears (user report 2026-10-09, live Windows build 222b1d6, seed 5432: it did finally load, but only after waiting / moving around). It should bake BEFORE the world is handed over, on all the cores, with the loading screen saying what it is doing.

2) Technical Details:

CURRENT BEHAVIOUR (all in godot/world/satellite_body.gd):
- configure() (L313) picks the source: the (1) user:// cache `user://satellite/p{pid}_r{R}_s{seed}_h` (_cache_dir L363), else (2) the shipped res:// textures which exist for CANONICAL_SEED 44 ONLY (L110, the seed==CANONICAL_SEED guard L330), else (3) _start_bake() (L419).
- The bake is ONE WorkerThreadPool task: `Engine.get_singleton("WorkerThreadPool").add_task(_bake_worker.bind(g), false)` (L444). The `false` is high_priority=false, and the line above it states the intent: "LOW priority so the streaming HIGH tasks are never starved". The consequence is the reported symptom: the low-priority lane only gets a worker when the high-priority queue is empty, and the streaming lanes keep that queue busy whenever the player is moving, so the bake waits for the world to go quiet. VERIFY this pool-priority claim against the engine source before relying on it; the observed timing (appears only after idling, never while flying) is what the ticket reports either way.
- Main-thread cost is NOT the problem: _bake_main_step (L471) is a poll in WORK phase and one face per frame in LOAD phase; AC-0382 already moved the pipeline off the main thread. The problem is WHEN the worker runs and how LONG it takes.
- The work, measured: 196,196 generate_far calls (HOME_CHUNKS 155,236 + 10 x FACE_CHUNKS 4,096, L105-109) at the standing ~92 us/column (AC-0284b) = ~18 s of pure generation; then the per-face colour pass over 12 x 1024^2 = 12,582,912 texels of per-texel GDScript (_step_face L814 / _pixel L892 / _l2s L919 / _byte L927); then 12 PNG deflates + writes; then the read-back + variance guard (_guard_check L983) and the 12 geometries (_geom_for_face L1032). AC-0384 r2 measured ~13 min of worker wall for seed 5432 on the dsh-web box (HARNESS.md section 2, the AWECRAFT_SNAPSHOT row). All of it single-threaded.

WHAT IT SHOULD DO:
1. START THE BAKE AT BOOT and await it inside the existing loading window, before the player is handed the world. The window already exists and is quiet: the world activates on the sim taxi diamond being mesh_built (_await_sim_band, world.gd; AC-0313), which is a deliberate wait already. Kick the bake from satellite configure() (or boot) and gate the release on the body's phase, instead of racing it against a live streaming world. A bounded timeout with a LOUD line is acceptable only if it is measured and stated; silently releasing the player to a late planet is what this ticket removes.
2. MULTI-THREAD IT. Both halves are independent and both already have worker-thread precedent:
   - the payload census: 196,196 independent generate_far calls, and the file's own header (L57-61) records that generate_far is "a pure const C++ call the thread-gen pool already runs from worker threads" (world.gd _threadgen_worker) - so sharding it across the pool needs no new C++ and no new task type;
   - the 12 faces: independent per face, each with its own H grid and texture; _geom_for_face is documented "pure SphereMath, thread-safe" (L635).
   Keep the single-writer discipline the class header states: pay/_out/_h2/_t2/guard/_geom are written only by the worker side before bake_done and read by the main thread only after - so shard into per-shard buffers and merge once at bake_done, never into shared arrays.
3. SAY WHAT IT IS DOING: one progress line (seed, face k/12, or payload x/N) on the loading screen / console, so this class of report ("the planet is missing") is self-answering.

ACCEPTANCE (what proves it):
- Cold start on a NON-canonical seed (the user's 5432): the bake completes before the player is released, and the measured wall is reported before/after in the results page (the field is the worker wall plus the frame the body lands on). The bake must not be starved by streaming in the same run.
- genhash 25/25 byte-identical - this ticket is scheduling and threading only; the far payloads and the baked pixels must come out BIT-IDENTICAL to today's single-thread path (the shipped 12 face PNGs are the reference: the satellite arm's AWECRAFT_SATELLITE_REBAKE=1 pixel compare, max_abs_diff <= 1 / diff_px <= 1%).
- The `satellite` arm stays green (12/12 faces, the variance guard, the derived h_first/h_full thresholds, the 0.25 angular ratio), G0 zero SCRIPT/SHADER ERROR, the boundary r4 one-shot for the loading-window interaction (the bake must not move the documented walk p50/p95 bands), and the cache path still short-circuits the bake on a second launch of the same seed.
- The result must be stated in the units the user feels: seconds from launch to "the planet is there", for a cold (uncached) non-canonical seed.

SWITCH (decided here, per the filing rule): the user asked for the bake to happen before the world loads, so that IS the default. It trades load time for a later-appearing planet, which is a real player choice, so it ships as a player-facing setting in Options > Settings, persisted like the others, plus an env override for the arms; OFF reproduces today's behaviour exactly (the world is released first and the body may appear late). The arm asserts both states and that OFF is the pre-change path.

OUT OF SCOPE / DEFERRED:
- The bake's visual quality - the 16 m faceting and the vertical streaks are AC-0412, a separate ticket, and must not be folded in here.
- Shipping or pre-generating texture packs for more seeds (the other way to make a cold start cheap). Worth recording as an option in the results page; not this ticket's acceptance.
- Any change to the ladder thresholds or to the fog-wall/haze contract (the open question about the far world at play altitudes is separate).



ADDENDUM (filed from the same session's frames, 2026-10-09 21:2x):

EVIDENCE THAT NAMES THE FAILURE MODE THIS TICKET REMOVES. In the pre-load window the user does
not see "no planet" - they see a CONVINCING FAKE ONE, and the tell is the sun sitting inside it.
From orbit (live build 222b1d6, first-person, seed 5432) the frame is a smooth blue ball with a
soft glowing rim and the sky's sun disc floating INSIDE the ball. Both are the sky pass:

- the sun is a term in the sky shader, not an object: aero_sky_gradient.gdshader (shader_type sky)
  L123-128, `sd = dot(dir, sun_dir)`, `disc = smoothstep(0.99894, 0.99985, sd) * sun_amount`, plus
  the scattering glow that dies with `(1.0 - u_space)`. A sky term is BACKGROUND: it is visible
  only where no geometry covers the pixel. So a visible sun disc inside the ball is PROOF that
  nothing is drawn there - the body is not in the frame. (With the body LOADED and opaque the sun
  is hidden: the body's material writes ALPHA, so it draws in the transparent pass over the sky,
  and `op = 1` at orbital distance.)
- the ball itself is the same shader's atmospheric limb: `b = length(cross(u_limb_center, dir))`,
  `limb = exp(-(b - u_limb_radius)/300.0)` with the explicit `if (limb > 1.0) limb = 1.0;` clamp
  (L104-121). The clamp makes the term a FLAT 1.0 everywhere inside the planet's tangent direction
  - a FILLED DISC, not a rim - and `sun_side = 0.55 + 0.45 * pow(dot(dir, sun_dir), 2.0)` gives it
  exactly the brighter-toward-the-sun gradient the frame shows. `mix(1.0, u_space, u_limb_gate)`
  with the AC-0401 gate DEFAULT ON evaluates to `u_space`, so the disc is at FULL strength from
  orbit by design ("the rim is an orbit instrument"). Its silhouette has the same angular size as
  the body, so with the body absent the result is a fake planet that reads as a real one.

SECOND CLAUSE (in scope here because it is the same window): WHILE THE BODY IS NOT LOADED, THE SKY
MUST NOT PRESENT A PLANET. Gate the limb term on the body's own state (the LOADED phase / the
visible flag that satellite_body.gd already computes, pushed like the other limb uniforms) so the
orbit view during a bake is honest - either a rim with no body under it, or nothing - instead of a
smooth blue ball. A fake planet is worse than a missing one: it cost this project a full
investigation cycle (the "pale ball" family) and, in this frame, it hides the very failure the
first clause fixes. This does NOT change the gate's altitude behaviour (AC-0401): at ground level
`u_space = 0` keeps the term off in both states.

REJECTED, with the reason recorded: a ticket for "the sun is drawn over the planet". The sun needs
no occlusion test - being a sky term it is occluded by geometry by construction (unlike the stars,
which AC-0386 had to give an explicit ray-sphere test at R+SEA precisely because they are
camera-anchored geometry in a 320 m shell drawn in front of everything). If a sun disc is ever
observed over a LOADED body, that is a different defect and needs its own frame and ticket.
