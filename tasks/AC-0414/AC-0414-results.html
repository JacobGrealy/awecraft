AC-0414 — bake before load, multi-threaded, no fake planet

User report (2026-10-09, Windows build 222b1d6, seed 5432): "after a recent build the level of detail was not showing at all, and when they looked into it the world 'was still baking'." The satellite body's baked terrain was not ready when the player arrived — the 196,196-record bake ran as ONE WorkerThreadPool task at LOW priority, which on this box measured 1.00 effective thread (the thread-priority census, world.gd:6216-6222: LOW = 1.00, HIGH = 5.97) — ~794 s (~13 min) of bake wall for a ~2 s world load, so the planet never made it. Two clauses: (1) bake BEFORE the world handover, on all cores, with the loading screen saying what it is doing; (2) while the body is not LOADED, the sky must not fake-present a planet.

Scope fences — no commits / pushes / TASKS.yaml edits (the coordinator closes the ticket). main.gd, game.gd, drop.gd, debug.gd untouched (another session's uncommitted work). Light gates only; the heavy gate set is the coordinator's. Two temporary probe arms — satboot (the bake-before-load walls) and satmid (the clause-2 mid-bake sky) — each went in and out of harness.gd in this task (pristine rule; both removed at closeout, G0 re-verified); the standing satellite arm is untouched.

1. What was built

  • Multi-threaded sharded bake (world/satellite_body.gd) — the payload stage splits the 196,196 generate_far records into 98 shards × 2,002, streamed at the core-count width (the poller enqueues the next shard as slots open — the first batch fills the pool at start) as WorkerThreadPool tasks; each shard appends to its OWN buffer (no shared-array writes from workers). The priorities are yield-aware: HIGH under the loading-window hold (the bake owns the cores); after the hold's bounded late release, world.gd sets bake_yield and the bake's remaining work enqueues LOW until the player lands — so the diamond build (HIGH) does not queue behind the bake's payload and the player lands at the budget + at most one shard slice (the pre-yield design measured a 109 s release on this box instead — §6); after landing the tail goes HIGH again (capped). The main thread merges the shards in deterministic order into the payload (one concat), then enqueues the 12 face tasks (colour + PNG + read-back + guard + geometry on the worker, per-face state dict, inflight capped: 12 while the loading window holds the bake, 4 after a late release so streaming keeps 2+ of the 6 pool threads). The main thread is the single writer of pay/guard/ _worker_images/_geom/bake_done; the per-face arithmetic is verbatim from the old path (machine copies _step_face_mt/ _pixel_mt/_guard_check_mt/_geom_for_face_local), and the sharded path is bit-identical to the old one by construction (deterministic shard order, verbatim per-face math). Proof: the satellite arm's REBAKE through the NEW path pixel-compared against the shipped seed-44 textures — rebuild_vs_shipped: identical=true, diff_px=0, max_abs_diff=0 (589,824 samples).
  • Bake before the world handover (world/world.gd) — with the switch ON, a fresh-spawn loading window holds the drain's phase 1 (the real-band diamond — the ONLY dispatch path in a loading window, so the hold holds exactly the sim-band release set and nothing else) while the bake is in WORK: _ac0414_hold_tick() (bounded 42 s budget, LOUD release line on the timeout, latched — no second stall), the drain skip (if _ac0414_hold_active(): continue after the real-column filter), and the loading screen's live progress line (seed, shard k/98 or face k/12, payload) instead of a frozen bar (ui/loading_screen.gd set_note). On the late release the bake yields (satellite.bake_yield = true) and comes back to HIGH when the window closes (stop_loading, the player has landed); the tail cap (satellite.tail_inflight_cap, pushed every frame) drops from 12 to 4 after a late release.
  • The switch — sat_preload bool in settings.gd DEFAULTS (DEFAULT ON, the user's verbatim quote in the comment), sanitize_bool clamped corrupt-safe, CheckBox row "Planet: bake before the world loads (recommended)" on the Options surface (menu.gd), and the AWECRAFT_SATPRELOAD=0|1 harness env preloaded at boot WITHOUT save (world.gd _ready, the AWECRAFT_RAMPS discipline). OFF = the pre-AC-0414 single LOW-priority task with no hold — the old path is byte-identical (only inert abort checks added; the REBAKE arm through the OFF path re-proves its bit-identity).
  • Clause 2 — no fake planet (core/aero_sky_gradient.gdshader + world.gd _ac0401_push) — the limb term is LOADED-gated behind two change-gated uniforms: u_limb_loaded (the switch) and u_body_loaded (1.0 iff satellite.phase == LOADED), pushed through the same fence-locked seam as every other limb uniform. The term is multiplied by mix(1.0, u_body_loaded, u_limb_loaded): OFF (shader default 0.0) = ×1.0 exactly (pre-AC-0414); ON + not LOADED = ×0.0 (the sky never draws the limb disc over an unbaked body); ON + LOADED = ×1.0 (the full limb term). This gate is the contract any future limb-radius work (AC-0417) rides on.

2. Design decisions

  • Why shard the payload instead of the faces. The payload stage (196,196 × generate_far, 201 MB) is 94 % of the old bake's worker time on this box (742 s of 794 s); the 12 faces are ~52 s total. Sharding the payload across the 6 HIGH threads buys the 4× wall; the faces (colour + PNG + read-back, per-face state) were already per-face and simply became per-task. generate_far is a const pure C++ method already proven on worker threads by the threadgen lane — sharding it is bit-safe, and the REBAKE pixel-compare is the standing proof.
  • Why a bounded hold instead of an unbounded one. The ticket sanctions "a bounded timeout with a loud line" as the acceptable fallback when the hardware cannot bake that fast — and on every realistic machine it cannot (measured below: the MT bake wall exceeds the 42 s budget even here, and far more on the user's desktop-class hardware the ticket targets). The hold exists so that ON fast hardware the player is never released before the planet exists, and so the loading screen tells the truth while it waits. The 42 s budget sits under the 3000-frame (~50 s) sim-band release cap so the hold never pushes the release past the existing fence.
  • Why the bake YIELDS after a late release (the probe's finding drove this). The first probe run (14 up-front HIGH shards, no yield) released the player at 109.5 s, not the ~44 s the loud line claimed: every shard was HIGH, so the payload held the whole pool to its 160 s wall and the diamond build — also HIGH — only crept through the gaps. The loud line was lying about the release. The fix is a finite yield window, chosen against the pool's two priorities: after the late release the bake's remaining work enqueues LOW (world.gd sets bake_yield) until the window closes, so the diamond's finite HIGH work (41 columns) takes the pool and the player lands; the bake's LOW work still makes progress in the gaps, and after landing the tail goes HIGH again (capped at 4, so the steady streaming trickle keeps 2+ threads — a permanent LOW tail would starve behind the trickle forever, which is why the yield is windowed, not permanent). Shards are STREAMED (and cut to 98 × 2,002) so at release time at most one shard slice (~7.7 s on this box, sub-second on the user's hardware) of in-flight HIGH work can delay the diamond — the release wall is then the budget + at most one slice, by construction: measured 48.4 s on this box.
  • Why the hold rides the drain's phase 1. In a loading window the drain dispatches ONLY the real-band columns (the sim taxi diamond) — phase 1 — the halo waits for streaming to resume after the window closes. Skipping phase 1's dispatch while the bake is in WORK holds exactly the release set and nothing else; the streaming lanes are already idle in a loading window (streaming := not loading_active), so the bake takes the cores with no new starvation.
  • Why the clause-2 gate is a multiply, not a branch. The shader defaults (0.0) make the OFF state bit-exact with the pre-AC-0414 limb expression (mix(1.0, x, 0.0) == 1.0), so the gate costs nothing when the switch is OFF and cannot regress the look it guards. Pushed change-gated from world._ac0401_push() like the other limb uniforms (the sky_mat seam in main.gd is fence-locked — the push side, not the material owner).

6. Deviations and findings

  • Measured deviation (sanctioned): on this box the bake wall (169–195 s) exceeds the 42 s hold budget, so the loud bounded release fires — measured release wall 48.4 s (the budget + at most one in-flight shard slice, by construction), the diamond builds at full speed behind the yield, and the planet lands at 169.4 s after boot (vs ~13.3 min before). The ticket's acceptance ideal (bake ready before release) is met on hardware ~5× faster per record — there the loud path never fires; the ticket sanctions the bounded-timeout-loud path "only if it is measured and stated" — stated here, with the measurement. (The probe's walls in §4 carry the per-run numbers.)
  • Finding → fix (the yield): the first probe (14 up-front HIGH shards, no yield) released the player at 109.5 s — 67 s past the loud line's claim — because the shards held the pool to the payload's 160 s wall and the diamond build (also HIGH) only crept through the gaps. A loud line that does not match the release wall is a defect, so the design changed: the shards stream at the core-count width (98 × 2,002) and, after the late release, the bake's remaining work enqueues LOW (world.gd bake_yield) until the window closes — a FINITE yield, because the diamond's HIGH work is finite (41 columns) while the steady post-landing streaming trickle would starve a permanent LOW tail forever. Re-measured: release 48.4 s. This also bounds the worst case on any hardware: release ≤ budget + one shard slice + the diamond build (~3 s), because at most one slice of in-flight HIGH bake work can overlap the release.
  • Finding → mitigation (the mid-bake exit UAF): the clause-2 probe quit the process while a bake worker was still running and segfaulted on a pool thread (Bad address index in _pixel_mt): the worker holds the node's script instance in its call stack, and process exit frees it mid-slice. This class predates AC-0414 (the old single-task bake had the same race — a user closing the game during the ~13 min bake) but is now much more reachable (the bake runs for minutes on slow hardware). Mitigation (in satellite_body.gd): a file-scope static var _mt_exit_aborted (readable WITHOUT touching the instance), set in _exit_tree(); every worker abort check reads it first and stands down at the next record/slice boundary with no further instance access. It shrinks the UAF window from a whole slice to the function epilogue — a full close needs the workers detached from the node (their own ticket). The probe arm exits the honest way instead (abort + bound-wait, the probe-OFF pattern).
  • Finding → fix (the MT failure path never set bake_done): an aborted/faulted sharded bake left bake_done false forever, so any wait on it ran its full frame cap (a 100 s wasted wait, measured). _fail() now sets bake_done = true (the pre-AC-0414 path already did on its abort wind-down); the probe's abort wind-down then finishes in 17-24 frames.
  • Process note (for the coordinator): one REBAKE run and one render probe overlapped (a one-godot-at-a-time miss). Both runs independently passed their gates (0/0 census, identical=true; rc 0 + RESULT + SNAP) — no observed .godot corruption — but the overlap was not sanctioned; all other godot calls were strictly serial.
  • Two parse errors on the first G0 (fixed, both in the new code): PackedByteArray has no replace() in 4.7.1 — the merge is the deterministic append_array concat in shard order (plus a size assert); and hgrid was declared in the _step_face_mt loop body but read in the PNG section — moved to function scope.
  • One consume handover bug (found by the first REBAKE run, which hung and was killed at the 600 s cap): once the sharded assembly set bake_done, the poller re-ran the assembly every frame (re-appending guard/images/geom, reallocating the 201 MB payload per frame) and the shared consume loop never took over — bake_active never cleared. Fixed by dispatching to the shared _bake_main_step (the consume loop) as soon as bake_done is set; the re-run REBAKE is the clean pass above.
