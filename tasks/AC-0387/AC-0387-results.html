AC-0387 — carve missing from the low and medium LODs

Tree: 0b4d9d68af16f6396e69b10c7c346654ba62d1bc · 2026-10-01 · headless 4.7.1, ulimit -v 8388608, one godot at a time, seed 44 default.
User report (2026-10-01, Windows, while playing): “the low and medium LODs are much taller than they should be after they have valleys carved into them” — the ground visibly drops as the detail streams in.

Verdict (mechanism, established by code reading before any measurement): (b) — the carve is a full-path-only pass and the coarse tiers genuinely skip it. The far (h-only) lane gen_far computes each column's H as surface_h (the three coarse surface fields f_sc/f_sh/f_sr, no density, no carver). The real/full path (skip=0) is the ONLY lane that runs the two carve mechanisms — the density router (dens_at, AC-0347 P2 / AC-0367) in the top-down scan, and the classic carver (carver_carve_column, AC-0290) as a post-density pass. Both only ever REMOVE material, so the full path's effective top heff ≤ H. The far LOD therefore draws the un-carved heightmap (a ceiling) and the real band draws the carved surface: on a far→full promotion the terrain drops by the carved depth. This is not (a) — the far lane does not run dens_at at all, it is a deliberate H-only lane (the cave lattice is “never by gen_far / gen_veg_cells / column_heights16”) — and it is not (c): the far uses the SAME surface_h at the SAME resolution as the full path's heightmap, so no valley is missed by sample spacing.

1. The contract under test

godot/world/AGENTS.md (bit-exactness): “a far/h-only column's H IS the height the full path would produce, because promotion must never shift terrain. Never re-derive or round a value another lane computes independently — compare and assert equality, the way the arms do.”

The existing farab h_mismatch gate (harness.gd _farab_test, line 11472) checks generate_far().slice(0,512) == column_heights16(). Both sides are the un-carved surface_h — the far payload's H and the heights pass are the same function. So h_mismatch 0 passes by construction and never sees the carve. That is why the standing gate is green while the player sees the ground move: the instrument compares the far's H to the un-carved reference, not to the full path's carved top. §2 measures the carve depth the standing gate cannot see.

Why the standing proof did not catch it: ARCHITECTURE.md §6 records AC-0347 P2 “proved H byte-identical before/after” the cave tuning, and the “he ≤ H … holds by construction” pillar gate. Those prove the heightmap H (surface_h) is bit-exact and the carved top never exceeds it. They do NOT require heff == H — the carve legitimately lowers the top below the heightmap. The far LOD draws H; the real band draws heff. The gap H − heff is the carved depth, and it is the ground the player sees drop.

4. Fix or price it

The measurement says the carve is genuinely absent from the far lane (866 columns, up to 91 blocks), so a correctness fix is warranted to satisfy the promotion contract (“a far column's H IS the height the full path would produce”). I did not implement it — I price it — because the fix is a real cost trade, not a one-liner, and the measurement says the effect is localized (0.85% of columns, concentrated in the sparse canyons).

The fix (the correct one): make gen_far (gen.cpp 2767) compute the carved top instead of surface_h. That means the far lane must build the cave lattice (cheese + the 4 tunnel sources + layer + entrance, 2401-pt C48 lattice each), the pillar field, run the top-down dens_at scan, and run carver_carve_column — i.e. it must do what gen_flat skip=0 does for the height, which is the expensive half of generation. The far lane is currently the cheap lane (3 surface fields + the heights pass, “the H's physics”); making it carve-aware folds the full path's density/cave cost into every far column.

5. Cost against the 5,502 / 4,880 µs/chunk references

Reference prices (the full path, gen_flat skip=0): AC-0366 = 5,502 µs/chunk (price list); AC-0381 = 4,880–4,960 µs/chunk (re-measured after AC-0367, −10 to −11%). The far lane today is a small fraction of that (only the 3 surface fields + heights pass). The fix moves the cave-lattice build + the dens_at scan + the carver into the far lane — the stages that dominate the full path's price (the cave lattice's per-point 4-nearest/aquifer work is the single largest item in the 5,502 breakdown; the dens_at scan is the 1,291 µs/chunk stage). So the far lane's per-chunk cost would climb by on the order of the full path's density/cave share — plausibly +3,000–4,500 µs/chunk on the far lane, i.e. a far lane that was ~1/5 the full path becoming ~the full path, paid on every far column (the whole draw band + the offscreen interior collar), not just the 0.85% that actually carry a surface carve.

Verdict on the trade: the fix is a correctness win for the promotion contract and removes the visible ground-drop, but it prices a correctness fix for a 0.85%-of-columns effect by roughly quadrupling the far lane's per-chunk cost (measured against the 5,502 / 4,880 references, not discovered later) plus a native rebuild + re-stage. Two cheaper alternatives the coordinator should weigh before the C++ change: (1) a coarser carve-aware far H — run the dens_at scan (1,291 µs) but skip the carver on the far lane; the 752 deep columns are mostly carver canyons, so this still leaves the worst 91-block case, but it is the cheapest carve-aware option; (2) accept + document that the far tiers show the un-carved heightmap (a ceiling) and the real band shows the carved surface — the honest LOD-shape answer, which the promotion retain-swap does NOT hide (it is an atomic flip, not a crossfade), so the player still sees the drop. Recommendation: file a follow-up for the carve-aware far H (option 1, cheapest carve-aware) with the §5 price attached, rather than silently shipping the mismatch or paying the full carve cost here.
