Issue 1 — "something is wrong with the texture mapping"

Requirement: a strip block (the merged atlas gives it a 512×128 strip) samples its texture repeating — 4× across a 4-block quad (31px per block from the strip origin, the qwrite_merged convention; NOT stretched); a strip-less block samples one 32px tile for any quad size.

Root cause (game code): the atlas identity changes on every re-bake (tint bake at startup, texture-pack import) → _merge_atlas() re-runs → the strip table's positions move. Highs recover (the tex_refresh drain re-pushes every chunk), fog is flat color — but the lows are main-thread MeshInstance3Ds that kept the old strip UVs: a quad whose origin now points into another block's strip region (the "wrong texture" the user saw; R16 showed mesh origins offset by whole strip rows, e.g. dirt UVs at cobble's strip). Fix: world._low_reset_all(), called from BOTH atlas-swap sites (the _process identity guard + refresh_textures()): drop every low, re-ensure its fog box (both are honest placeholders), clear the per-slab stamps and the _low_tl tile cache — the slab wave then re-lowers everything against the new table. The wave now runs even while the heavy pipeline is idle, so the re-lower drains instead of waiting for the player to move.

Root cause (probe, also fixed): the R16 UV gate re-derives each quad's block id from the coarse grid with a single flat index u + v*4 + k*16 — only valid for the Y faces. For the side faces (±X: u=z,v=y,n=x; ±Z: u=x,v=y,n=z) it read the transposed cell — often air — producing phantom mismatches (the "dirt/cobble swap" pattern). Forensics (direct get_local read at the emitter's sample point + reverse UV→id lookup) proved the mesh was right: cell_direct == uv_id on every failing quad. Fix: per-face (u,v,normal)→(x,z,y) mapping in the probe.

Evidence. LODUV probe (loduv3.log, isolated single-slab builds): ok:true — grass slab 24/24 quads: 16-block quads span 496px / 124px (16×31 / 4×31 — repeating, not stretched), 4-block quads 124/124, every origin at strip-rect + 0.5, every UV inside its 512×128 strip; single-leaf slab 6/6 quads each exactly one 31px tile (plain path). R16 final (r16f.log): uv_repeat_ok TRUE at both sample instants — 29,224/29,224 + 14,699/14,699 = 43,923/43,923 quads with 0 mismatches (25,917 + 14,251 strip quads at 31px/block from their strip origins; 3,307 + 448 plain quads each one 32px tile from their rect origin), 0 stale slabs, 0 zero-UV (every block in this terrain is tiled; tileless blocks would be (0,0) like the high mesh).

Issue 2 — "it's still doing columns fully then next columns fully rather than all fog → all low → all high"

Root cause: the low wave looped per column (one column's slabs fully, then the next) — and the chunk-level low_stamp made partially-lowered chunks look stale forever (their built slabs got re-picked: low_rebuilds_n 23,622 in the first fix attempt). Fix (game code): a global slab wave — _low_pick_slab() scans the band buckets (cap 2048) for the smallest-si pending slab across all columns (tie = band/rank order), builds LOW_WAVE_PER_FRAME = 4 slabs/frame (≈1–3 ms, half the old per-column cost). Staleness is now per slab: c.low_stamps[si] = c.stamp() when that slab's low builds (a chunk-level stamp re-picked already-built slabs forever); terminal-fog verdicts live in c.low_failed[si] = data_gen (all-air samples keep their fog and are not re-picked until the data generation moves). No-candidate verdicts are cached against pool_ver|last_pcx|last_pcz, so a drained wave costs a couple of dict ops per frame. Wave 3 (high from the AC-0233 tiers) is unchanged; the stale check there is per-slab too.

Evidence. Live wave sequence (r16b.log, the run where pending slabs were still owed at sample time): _r16_wave_test() drained 854 pending slabs uncapped — si_monotone_ok: true (non-decreasing si = global bottom-up), first si-layer spans 15 distinct columns (15 si-3 slabs, one per column — interleaved, not column-major; si-4..8 layers 136 each = a full layer of all columns before the next si), layer histogram si3:15 / si4–8:136×5 / si9:112 / si10:47. Final run (r16f.log): wave_ok: true — drained_at_sample: true, i.e. by first sight the wave had already completed: far0 = 1,352 low + 30 fog + 0 high = 1,382/1,382 (every far non-air slab covered the moment it could be seen; the 30 fog = terminal all-air slabs). The three-wave shape holds: all fog at data landing (unchanged, 5 landing sites) → all low by first sight → all high fills per tier during the run (far_high 0 → 1,128, low_upgrades_n 2,281).
