AC-0403 — segfault in the chunk block read (get_local, chunk.gd:657)

Builder: subagent. 2026-10-08. Tree at 30b8775 (AC-0406) + one other session's in-flight godot/* changes (main.gd / game.gd / debug.gd / drop.gd / shaders) — fenced files untouched by this task.

Bottom line. The crash is not reproduced (14/14 clean runs of the exact crashing recipe). Static analysis pins the proven mechanism at slab-object memory death (UAF / engine-level corruption), not malformed slab data — a read-site structural guard cannot catch that class (freed memory reads as plausible garbage). The one genuinely unguarded read in the lookup — slab_getbits' i[bo] with no bound on bo — is now bounds-checked in C++ (the only change shipped). Its cost is measured, not assumed: a same-box A/B (baseline .so vs guard .so) shows the per-frame player step at 0.82 ms → 0.81 ms p50 — unmeasurable — and every arm's behaviour fields are bit-identical across the A/B (genhash 25/25, lightstate exact match, mobs / player / interact all fields equal). A clear map of the failure conditions is below; the UAF class remains open and needs a reproduction or an AddressSanitizer build to find the concurrent free.

2. What the code path does under each condition (the failure-condition map)

get_local (chunk.gd:650-657, unchanged since AC-0205) does var s = data[y>>4]; if s == null: return 0 then int(ChunkIO.io_cpp().slab_cell(s, pos)). The C++ slab_cell (chunk_io.cpp:643) bounds-checks p_pos, the n==1 read (p[0]) and the n==0 read (i[p_pos]) — and the n≥2 p[idx] read. Its only unguarded read was slab_getbits' i[bo]/i[bo+1].

Why C6 is the proven mechanism, not a hypothesis: the pre-port crash (ac0231-r16-inrpass.log) faulted at the identical line while the slab read was pure GDScript (s["n"], s["p"][0], s["i"][pos], _slab_getbits). The GDScript VM is bounds-safe on live objects — an OOB index or a malformed-but-live dictionary cannot segfault through it. A pre-port segfault at that line can only mean the slab object (or its buffers) was dead memory. Malformed-slab (C5) would have crashed the mesh decodes just as readily as the player path (meshing reads every cell of every slab — weeks of heavy meshing, zero mesh-side crashes). So C5 is not the demonstrated crash class; C6 is. A read-site structural guard cannot fix C6 — freed memory reads as plausible garbage, so any structural check either passes (no protection) or reads the same dead memory (crash unchanged). This is why the shipped guard is the C5 hardening (the one real unguarded read), and why the C6 finding is reported as a condition map + recommended next steps rather than a fix.

Concurrency audit (current tree): every worker lane (threadgen ≤3, threadmesh ≤6, IO read/write/compact, satellite bake) receives value copies at dispatch (slab_copy / snap_rings / entry-dup), writes only its own slot entry, and every handoff (threadgen_poll / threadmesh_poll / io_poll) runs on the main thread inside World._process. The shared C++ singletons (AweMesh, AweGen, ChunkIOPalette, AweStrips) are stateless (atomic counters / value tables). Lighting._att/_glow are frozen value copies of size 48; Data.atlas_rects (the live reference shared into worker entries via _low_ms_snap_get) is only ever whole-reassigned (data.gd _ready / apply_atlas — texture-pack swap, a user action that never happens in headless arms), never mutated in place. Raw-pointer retention was audited in the C++ (the AweStrips SlabDesc pointers outlive their local PBA only within a single C++ call whose input array keeps the buffers alive — safe). The design forbids C6; the crash persists; static analysis is exhausted. The residual candidates (an engine/wrapper-level free, a refcount edge in the PBA wrapper's shallow-handle semantics documented at AC-0214, or a race this audit cannot see from the outside) need a reproduction or an AddressSanitizer/valgrind run to localize.

4. What changed (shipped)

One file change class, both copies: a bounds check in slab_getbits — the choke point of every paletted slab read (slab_cell, slab_cell_of, the mesh/IO decode lanes):

 // gdext/src/awe_common.cpp (awecommon) and gdext/src/chunk_io.cpp (private copy)
 int slab_getbits(const uint8_t *i, int isize, int bits, int pos) {
+	// AC-0403: bounds check. The i[bo] read below was the ONLY unguarded read in the slab
+	// decode: bo = (pos*bits) >> 3 had no bound, so a slab entry whose b disagrees with its
+	// i buffer (or an empty/dead buffer) read out of the heap — the signal-11 crash family at
+	// chunk.gd get_local -> slab_cell (tasks/AC-0403). Valid codec data never trips this:
+	// paletted slabs carry bits in 1..4 and an i buffer sized exactly ceil(S3*bits/8) by
+	// bitpack, so pos*bits + bits <= isize*8 for every pos < S3 — a no-op on the happy path.
+	if (i == nullptr || isize <= 0 || bits < 1 || bits > 8 || pos < 0
+			|| (int64_t)pos * bits + bits > (int64_t)isize * 8)
+		return 0;
 	int bo = (pos * bits) >> 3;
 	... // unchanged
  • Files: gdext/src/awe_common.cpp +13, gdext/src/chunk_io.cpp +13. Nothing else touched (the GDScript read path, player, mob, world, and all arms are byte-identical).
  • Valid-data invariant verified against the codec: bitpack emits exactly (S3*bits+7)/8 bytes; palettize_flat, slab_set and the wire decode all build i for exactly S3 cells; paletted slabs carry bits 1..4 (n==1 uses b=0 with a p-only path, n==0 uses b=8 with a raw path — neither calls slab_getbits). So for every valid slab the guard's condition is false: zero behaviour change on valid data (asserted in §5, not assumed).
  • Malformed input now reads as palette index 0 (a plausible value; slab_cell' existing idx < p.size() check then returns the normal defensive -1 for an empty palette) instead of faulting.

What was deliberately NOT done, and why:

  • No GDScript read-site guard (per-frame slab-invariant checks in get_local/get_block): it would cost measurable work on the every-frame player path to protect against a class (C5) a live object cannot exhibit, and it would not stop C6 at all. Rejected up front (plan.html).
  • The C6 (UAF) class: unfixable from the read site by construction; unreproducible here. Reported as the condition map + next steps (§6).
  • mesh.cpp decode p[] reads (917/945/978): unguarded palette reads on the worker decode lane — same C5 class. Left untouched: perf-critical per-cell loops, no mesh-side crash has ever been observed, and a shotgun change there is exactly the "quietly changes behaviour" risk the ticket forbids. Documented residual; the crash-site read (C5's i-buffer OOB) is closed.
  • Windows .dll rebuild: the product build lane — python3 -m SCons -C gdext platform=windows / build_windows.sh must re-run on the coordinator's side (SCons is not installed on this box at all — see deviations). The linux .so in godot/bin/ is the guard build now.
  • HEAVY battery / r50 / full r4 walk: coordinator's tier, out of scope (one boundary r4 used as the builder self-check).

A guard I almost shipped — and the bug that killed it (documented per the ticket's honesty rule): a first build also added palette-size / isize guards to slab_unpack and slab_nz_count (a new psiz parameter, 9 call sites). The condition psiz < (1<<bits) was wrong: palettize emits n palette entries where n ≤ 2^bits (n=3,5,6,7,9–15 are the norm, not the exception), so the guard rejected most valid palettes and zero-filled their decode — lightstate went leaks 0→81 / vc_common 393→0 / waited 19→240 and the mobs arm went red. The A/B caught it before delivery (genhash stayed 25/25 because it hashes the encode path; the decode-path arms showed the break). All of it was reverted to HEAD and only the slab_getbits guard remains. Lesson for the ticket's own warning: the A/B arm set is what stands between a "hardening" and a regression.

7. If it crashes again — the starting map for the next occurrence

  1. The innermost frame will still be the slab read line (that is the reliable evidence; the C++ backtrace is a dumper artifact — do not chase the __sigaction frame).
  2. C1–C4 are handled and provably safe — the suspect set is C6 (slab-object death), with C5 as the documented residual (its i-buffer OOB is now impossible; the mesh-lane palette OOB is the remaining C5 corner, §4).
  3. Candidates the audit could not close: (a) the PBA wrapper's shallow-handle semantics (AC-0214 note: raw ptrw() on a shared handle "doesn't propagate" — an engine-side refcount edge would present exactly as this); (b) a free ordering in the chunk pool / handoff path under a scheduling this box never hit; (c) engine-level (the 4.7.1 build) — a one-run valgrind/ASan build would localize (a)/(b) definitively and rule (c) in or out. Suggested next ticket: an AddressSanitizer-instrumented libchunkio + a soak of the crash recipe (this box ran the recipe 14× clean, so the soak budget is the constraint).
  4. Every future gate on this code path must pair the census with the exit status (§6).
