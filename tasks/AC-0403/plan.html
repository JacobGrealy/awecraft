AC-0403 — segfault in the chunk block read (get_local, chunk.gd:657)

Goal

Find the window in which a chunk is absent / freed / mid-rebuild when get_local reads it, reproduce the signal-11, or guard the lookup with a measured cost. Mob and player behaviour must be asserted unchanged when the guard does not trigger.

Reading of the failure conditions (static audit, before any run)

Fits the symptom exactly: the C++ backtrace in every captured log is ONE libc frame at main+45f60 (= __sigaction — the backtrace dumper itself faults while dumping, a classic corrupted-state signature); the GDScript backtrace (the VM state at first fault) is the reliable part. UNGUARDED (native)

Key dating evidence: the same signature predates the C++ port (AC-0214). The AC-0231-era log (.scratch/ac0231-r16-inrpass.log) crashed with the identical shape while the slab read was pure GDScript (ChunkIO._slab_cell). The GDScript VM is bounds-safe on live objects — an OOB index or a malformed-but-live dict cannot segfault through it. So a pre-port crash at that line can only mean the slab object (or its buffers) was dead memory: C6 is the proven mechanism, not a hypothesis. Occurrences found in .scratch/: ac0231-r16-inrpass (chunk.gd:367), skymin2 (chunk.gd:441), batt192 (chunk.gd:464 — the C++ slab_cell line), AC-0402-gates/lightstate (chunk.gd:657 — current), plus the AC-0384 round-12 mob-tick report. This is a weeks-old chronic defect, not a new one.

Concurrency audit result (current tree): every worker lane (threadgen, threadmesh incl. edit pool, IO read/write/compact, satellite bake) receives value copies at dispatch (slab_copy / snap_rings / entry-dup), writes only its own slot entry, and every handoff (threadgen_poll / threadmesh_poll / io_poll) runs on the main thread inside World._process. Shared C++ singletons (AweMesh, AweGen, ChunkIOPalette) are stateless (atomic counters only). No worker body touches the chunks dict or live slab objects. The design forbids C6 — yet the crash persists, so either an unseen cross-thread reference exists or the corruption is at the engine/wrapper level. Static analysis is exhausted; the next step is empirical.

Approach

  1. Reproduce. Loop the exact crashing recipe (AWECRAFT_LOGIC=lightstate AWECRAFT_LS_RADIUS=16, headless, 12 GB cap, ~1 min/run) until rc=134 or the budget is spent. This is the arm that aborted in AC-0402-gates.
  2. If reproduced: bisect the worker lanes on the same recipe (threadgen off → sync gen; threadmesh off → sync mesh; COLSTAGE=0) to identify the lane whose presence makes the crash possible, then fix at the reference-holding site. If not reproduced: state that plainly and ship the C5 hardening (bounds-check slab_getbits, zero happy-path cost) + the G0 blind-spot note, with the failure-condition map above as the starting point for the next occurrence.
  3. Guard decision (made up front): a read-site guard cannot catch C6 — freed memory reads as plausible garbage, so any structural check either passes (no protection) or reads the same dead memory (crash unchanged). The guard that can be proven behaviour-identical and that removes a real unguarded read is the C5 C++ bounds check. A per-frame GDScript slab-invariant check is rejected: it costs measurable work on the every-frame player path while protecting against a class (C5) that a live object cannot exhibit — and it would not stop C6. If reproduction yields a reproducible trigger, the fix goes where the reference is dropped, not at the read site.
