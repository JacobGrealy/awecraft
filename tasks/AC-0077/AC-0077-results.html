G4 verdict: FAIL as written (plan D4 honest-FAIL clause) — with the spec's primary objective met.
Met: forward-drain p95 improved on both post runs (best-of 4291 < 5148, median 4562 < 5182) and per-crossing light computes went 9 → (0 self + 1 batch pass) in steady state — both halves of the spec G4 statement ("forward-drain p95 r4 must IMPROVE … Per-crossing light computes: 9 → 1"). Not met: the plan D4 walk-regression line (walk-frame p95 ≤ 26 / max ≤ 68): measured 33 / 71–72 in both post runs. Root cause (quantified, instrumented): plan D1 estimated contained per-chunk light at ~6 ms; the byte-identical kernel (G2-verified) measures 17–34 ms/chunk (glow/lava-heavy chunks at the top). 9 new chunks per crossing ⇒ ~150–300 ms of new main-thread work per crossing (pre-AC-0077: zero on main — AC-0107 workers did the light). Even at the plan's own D4 parenthetical budget ("batch slice ≤ 18 ms/frame"), ~9 boosted frames/crossing × 13 steady crossings ≈ 110–120 walk frames ≥ 26 ms ≈ 10% of the ~1170 walk frames ⇒ p95 ≥ ~30 ms is mathematically unreachable with on-main contained light at this build pace. D1's arithmetic was wrong twice: the chunk cost is ~3× its estimate, and a 2-chunk slice at measured cost is 36–68 ms per call (contradicting D4's own "≤ 18 ms/frame"). The frame profiler (temporarily instrumented, then removed) attributed the slow frames to the batch component (avg 24 ms on ≥26 ms frames; recenter/fluid overlap ≤ 1 frame). Fixing it belongs to a follow-up task (off-main batch light or a faster contained kernel) — out of scope here by the spec's design constraints.

Design notes / deviations (documented)

  • Nearest-first batch order: _bl_batch_step sorts ready want-set chunks by Chebyshev distance to the player (matches the scored build-pick order) so the build units right after the batch hit the eff cache instead of self-computing.
  • Batch counter = per-pass (plan D4 semantics). Plan D1/D4 both state the expectation as "one batch per crossing (9 chunks ≈ 9 drain frames)" and gate on light_batches_per_crossing ≈ 1; the counter therefore increments once when a want-set pass completes (_bl_want empties), not once per drain call. Measured: exactly 1 per steady-state crossing. light_batch_chunks counts every chunk light-computed through the batch (~251–253/walk).
  • On-the-spot single-item batch in _build_unit (serving D4's "≤ 2 self + 1 batch call"): a want-set chunk that reaches a build pick before the batch step gets a 1-item batch on the spot (same contained kernel, cached) so the worker still skips its own light; cache is the arbiter — no double compute. In steady state it rarely fires (the pacing fix below makes the batch pass finish before build picks reach most want chunks).
  • Drain-loop pacing fix — gen pick skips in-flight chunks (root-cause fix beyond D1–D6 literal scope). The scored data pick re-picked the same gen-in-flight no-data entry every iteration (threadgen enqueue dedup no-op still counted as a consumed unit, u=1), burning the frame budget — measured ~1 real enqueue per 5–6 frames — which starved the batch pass: 3–4 chunks per crossing had no data when the next recenter replaced _bl_want, and later self-computed (the 2–6 warmup self-computes). Fix: skip _tg_inflight_keys entries when scoring the data pick (and cursor-park only on a truly empty pool). Effect: 10–12 data enqueues per crossing window, pass completes inside every steady-state crossing, steady-state self-computes = 0. Also improved forward drain (part of the −15% fwd p95).
  • 18 ms/frame compute budget lives INSIDE the batch compute loop (deviation from D1's literal "≤2 per drain call" — bound by D4's own "batch slice ≤ 18 ms/frame"): a naive append-loop budget checked before appending items (microseconds) and still computed 2 chunks = 36–68 ms/call (measured 34.2 ms worst); the budget now checks elapsed compute time between items, so a drain call computes the first chunk plus any further chunks that fit in 18 ms (in practice 1 at 17–34 ms/chunk). Leftover items stay in _bl_want for the next drain call.
  • Batch slice yields to the recenter slice: _bl_batch_step is skipped while _rec_pending (AC-0118's 8 ms/frame recenter budget takes the frame). The pass completes a few frames later, still well inside the 85-frame crossing window — measured 1 batch/crossing unchanged.
  • eff cache stores only CONTAINED effs. Worker handoffs cache only when eff_trust is true; flush/bulk effs (eff_trust=false) and last_eff-sourced remesh dispatches never enter the cache, so a cross-chunk bulk eff can never pollute a per-chunk data-signature entry. Sync fallback builds never cache (rare paths; their rebuilds self-compute as today).
  • _enter_candidate does NOT evict the eff cache (deviation from plan's "free paths erase cache"): candidacy keeps the chunk data, so the cached contained light stays valid on re-entry; only the stale staged-body entry is removed. True free (to_free loop) evicts cache + _bl_want + staging.
  • col_dirty semantic extended to "body needs (re)building, including staged": deferred chunks keep it true until the staging drain builds the body. Verified safe for the fluids-test col_dirty wait (its fix chunks are ±1 of the player = always immediate).
  • Drain placement: batch step runs at the head of _drain_build_queue (before the unit loop) and collision drain at its tail; the queue_size == 0 branch also runs both (so crossings finish their batch after the last unit) without touching unit bookkeeping.
  • queue_size 93 vs 95 (deviation, not a regression): the pacing fix accelerated far data_only consumption — 2 extra far-ring entries got data + were consumed during the walk, so the final residual is 93 instead of 95. The queue shrank; no build backlog grew. All other queue-adjacent gates (ok/flap/marker/remesh/built counts) unchanged.
  • Staging 1-frame body gap (accepted by plan design): a chunk staged at build time and only then reached by the player is drained within 1–2 frames (nearest-first, ≤2/frame) rather than in the same frame as the crossing. The player's own chunk and ±1 neighbors are always col_immediate at dispatch time, so the only gap is a just-reached previously-far chunk for ≤2 frames; no chunk lacks a body at the end of any phase (G5b evidence).
