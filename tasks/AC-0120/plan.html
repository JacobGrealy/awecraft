2.4 Cache design (owner / creation / key / lifetime / worker path)

godot/world/chunk.gd — inserted after the _ms_* statics (chunk.gd:42-44):

static var _mat_atlas: Texture2D = null   # Data.atlas_tex identity at last build
static var _mat_ms: Texture2D = null      # merged-atlas texture identity at last build
static var _mat_cache: Dictionary = {}    # kind -> Material (opaque/cutout/flower/fluid)
static var _mat_alloc_count := 0          # G3 build-path counter (total since boot)

# Static like _merge_atlas (chunk.gd:47-49): main-thread-only in practice
# (build_mesh sync + apply_accs handoff both run on the main thread).
static func _get_mat(kind: String, ms_tex: Texture2D = null) -> Material:
	if _mat_atlas != Data.atlas_tex or _mat_ms != ms_tex:
		_mat_cache.clear()                 # texture swap / merge rebuild -> fresh set
		_mat_atlas = Data.atlas_tex
		_mat_ms = ms_tex
	if _mat_cache.has(kind):
		return _mat_cache[kind]
	var m: StandardMaterial3D
	match kind:
		"opaque": m = _opaque_material(ms_tex)
		"cutout": m = _cutout_material()
		"flower": m = _flower_material()
		_: m = _fluid_material()
	_mat_cache[kind] = m
	_mat_alloc_count += 1
	return m
  • Owner / creation: statics in chunk.gd, lazy-created on first build per kind (no eager world-ready creation needed; the first 81-chunk build creates at most 4 — amortized O(1), 0 per crossing thereafter). Chosen over a world.gd var / autoload because: (1) chunk.gd is the ONLY consumer (zero material refs in world.gd); (2) the file's existing atlas cache (_ms_key/_ms_tex/_ms_rects, chunk.gd:42-44) already sets the idiom AND the lifetime precedent; (3) zero wiring through world.gd — the fence shrinks to the two files that already own the material and the probe; (4) ChunkScript = preload("res://world/chunk.gd") (world.gd:3) already treats chunk.gd as a static namespace the world pre-warms (world.gd:191-192).
  • Key format: kind ∈ {"opaque","cutout","flower","fluid"}; opaque additionally identity-keyed on (Data.atlas_tex, ms_tex) so a texture-pack swap (Data.apply_atlas data.gd:210-215 → refresh_textures world.gd:326-334 → _tm_ms_full rebuilt) or an AWECRAFT_MERGE=0 run invalidates and rebuilds the 4-entry set (4 allocs once per texture generation, never per crossing). Live cache size ≤ 4; key space is kind-only — no per-chunk/per-coord/per-tint keys (fence: bounded).
  • Lifetime across New/Continue: materials reference only global textures (the res://-cached atlas + the static merged atlas) and no per-world data, so the static cache survives world recenter/Continue/New harmlessly — Data is an autoload (persistent), load("res://assets/blocks_atlas.png") (data.gd:178) returns the same engine-cached resource across worlds, and recenter frees/re-adds chunk nodes but the cached materials simply get referenced by the new chunks (chunk.gd:1503/1508-1510/1531-1541 parenting). Texture swap = lazy clear + 4 fresh allocs; stale entries are refcounted by their (soon-freed) meshes and die with them — no leak. Stated: the cache outlives worlds by design and survives harmlessly; it is rebuilt only on texture-generation change.
  • Worker compatibility (AC-0107) — mechanism + thread-safety verdict: workers never touch the cache. The worker body (world.gd:526-534) runs only ChunkScript.build_accs(...) — a pure-static pipeline over Packed*Array copies and the ctx/ms snapshots, with ms containing ONLY rects (a duplicated dict) + h — no Texture2D, no Material, no Data (chunk.gd:1135-1225 has zero material references; world.gd:643-647 builds ms_w without textures). Material assignment happens EXCLUSIVELY on the main thread: sync build_mesh (world.gd:610/623/638) and apply_accs via threadmesh_handoff (world.gd:589, driven by threadmesh_poll world.gd:536 from the main loop world.gd:321). So the shared Material objects are read/written only ever from the main thread; no material object crosses a thread boundary, no per-worker lookup, no serialization point needed — safe by construction. (Had the design passed materials to workers, Godot ref-counted objects are NOT safe for concurrent mutation and would have needed a per-build main-thread handoff — unnecessary here; the AC-0107 handoff pattern already does the assignment on main.)

godot/scenes/main.gd — helper (harness-only):

func _matinfo_counts() -> Dictionary:
	var mat_ids := {}
	var std_ids := {}
	var built_n := 0
	for key in world.chunks:
		var c: Node3D = world.chunks[key]
		if not c.mesh_built:
			continue
		built_n += 1
		for inst in [c.mesh_instance, c.fluid_instance, c.flora_instance]:
			if inst == null or inst.mesh == null:
				continue
			var am: ArrayMesh = inst.mesh
			for s in range(am.get_surface_count()):
				var mat = am.surface_get_material(s)
				if mat == null:
					continue
				mat_ids[mat.get_instance_id()] = true
				if mat is StandardMaterial3D:
					std_ids[mat.get_instance_id()] = true
	return {"built_chunks": built_n, "distinct_std": std_ids.size(),
			"distinct_all": mat_ids.size(), "total_allocs": int(_ChunkScriptM._mat_alloc_count)}

7. Risks / edge cases

  • (a) Shared material + per-chunk mesh in Godot's renderer: no per-instance material state exists in this tree — grep-verified: materials are set only at the 8 chunk.gd call sites; no material_override on chunk MeshInstance3Ds, no post-construction property mutation (the only material-property mutations in the tree are the player hand/highlight probes, main.gd:4616-4638 — different objects). StandardMaterial3D uniforms are per-Material; per-object variation here is entirely in per-vertex data (position/normal/color/UV), and the atlas texture is ALREADY shared across all chunks via the _ms_* statics (chunk.gd:42-44) — sharing the material changes no render state. Confirmed: no per-chunk material property (shading/fog/transparency) — fog is global (DayNight), transparency mode is part of the kind key.
  • (b) Transparent water/lava sorting: water/lava already use the ONE shared Data.fluid_anim_mats ShaderMaterial today (chunk.gd:1511/1514/1581/1584) — no change at all. The alpha-blended fluid material (torches only) goes from per-chunk-instance to shared: Godot's transparent sorting is per-MeshInstance3D (object depth), not per-Material, so sharing changes NOTHING about sort order — and a natural world has no torch chunks anyway (kind never created, alloc count 3 not 4).
  • (c) Worker thread safety (the big one) — VERDICT: safe by construction, no mechanism needed. Material objects never cross a thread boundary: the worker runs only build_accs (pure-static, Packed*Arrays + ctx/ms snapshots, zero Material/Data/Texture access — chunk.gd:1135-1225, world.gd:526-534); assignment is main-thread-only in build_mesh (world.gd:610/623/638) and apply_accs via threadmesh_handoff (world.gd:589). The cache dict is therefore read/written by exactly one thread. (If a future change DID pass materials to workers: Godot ref-counted objects are safe for concurrent READ but not concurrent WRITE — a worker-side read of an immutable material would be OK, but the cache's lazy CREATE path mutates the dict, so that design would need main-thread lookup; not applicable here.)
  • (d) Cache lifetime across New/Continue/texture-swap: statics outlive worlds by design — materials reference only global textures (engine-cached atlas + static merged atlas) and no world data, so New/Continue/recenter is harmless (new chunks reference the same 4 materials; freed chunks' meshes free their refs, the cache keeps the 4 alive). Texture-pack swap (apply_atlas → refresh_textures world.gd:326-334) changes Data.atlas_tex and _tm_ms_full → first subsequent build sees the identity key mismatch → _mat_cache.clear() + up to 4 fresh allocs (once per texture generation). Stale entries stay alive only while their meshes do (refcounted) — bounded, no leak, key space kind-only (fence satisfied).
