Implement: look-priority scoring in the drain unit pick

Key design constraint (learned from AC-0076/0080 timing): the score must NOT require any bulk re-score pass. Score is a pure function of (entry position, player position, look direction) — compute it on demand, per-entry, only for the small pick pool the drain actually considers each unit. Recenter stays exactly as today (O(n) rebuild, no scoring), and look changes cost zero (the look vector is refreshed lazily). This keeps recenter_ms r=50 at its 97-105 ms baseline and adds no frame spikes at r=50 (n≈13k entries — a bulk pass would be a 30-60 ms spike per look change: forbidden).
  1. Score: for an entry at chunk (cx,cz): d = manhattan to player chunk (band index for pool entries), a = clamp(dot(normalize(chunkCenter − playerPos), lookDir), 0, 1) (chunkCenter = world (cx·16+8, y=spawn-ish const irrelevant — use 2D: (cx·16+8, cz·16+8); lookDir = player's horizontal look vector), cheby = max(|cx−pcx|,|cz−pcz|). score = d + (1 − a)·0.75·d − (cheby ≤ 1 ? 2.0 : 0) — lower is faster. (Forward chunks at distance d tie with forward chunks at d−0 → sort first; backward chunks pay up to 0.75·d effective extra distance; the ≤1-Chebyshev boost keeps the player's own ring absolutely first. Document the formula + any tuning you apply in the results html.) Look vector: cache it; refresh on demand when yaw changed >10° from the cached yaw (the pick pool is ≤ a few hundred entries so the dot products are trivial — the only per-frame cost is the refresh check).
  2. Drain pick pool: replace "mq head ready? / dq head" with a bounded scan: each unit pick, consider near bands mq_b .. min(mq_b+2, last) (3 Manhattan bands — a 16-block crossing shifts d by 1-2, so 3 bands always contain the leading edge + current ring):
    • collect the pool: non-data_only entries in those bands (cap the scan at, say, 256 entries — if a band is enormous at r=50 far bands are never in the pool anyway) + for the data phase: the same window's data_only entries (the r+1 ring) up to the same cap.
    • Build pick: among pool entries whose chunk exists, has data, !mesh_built, and (if in-radius) _build_ready → build the LOWEST score. (This is the look priority: the forward leading-edge chunk gets built before equally-distant sideways/back chunks.)
    • Data pick (when no build pick / gen budget allows): among pool entries whose chunk has no data (stub if node missing, as today) → generate the LOWEST score.
    • After building/generating, advance the cursors past the consumed entry (remove it from its band array like today) so the next pick doesn't re-examine it. Keep queue_size bookkeeping exact (the _process idle check depends on it).
    • The pool scan is O(pool) ≤ ~256 lightweight dict ops per unit ≤ 3-10 units/frame → <1 ms even at r=50. If a pick finds nothing buildable in the pool and no data pick either, break the frame (as today) — but do NOT let a blocked forward lead starve the data wave: if the build pick is empty, the data pick still runs (existing structure already does this).
    • Keep _startup_pending (3 units while spawn 3×3 unbuilt) exactly; scoring makes the forward half of the 3×3 fill first — first-draw gate unchanged.
  3. Harness (main.gd, allowed): (a) during the boundary walk, explicitly set the player's yaw to face +X (the walk direction) every few frames if needed; (b) new RESULT fields: per crossing, forward_wall_ms = crossing → all in-radius chunks with (cx − pcx_crossing) > 0 become mesh_built (dx==0 column excluded; −1 if never during the harness) and trailing_wall_ms = same for < 0; plus forward_p95_ms/trailing_p95_ms. Keep ALL existing fields/semantics.
