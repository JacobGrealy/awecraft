AC-0079 (revised) — look-priority drain scoring: bug-fix + re-verification

Status: COMPLETE (with gate failures honestly reported). Two bugs found and fixed from the prior "G3 PASS" (false green). G1, G2, G4, G5 pass. G3 has genuine gate failures at r=2 and r=4 (forward_p95 > trailing_p95, forward_p95 > 3500 ms, in_radius_built_max < 60). G6 deferred to coordinator. No python processes touched. Godot run strictly one-at-a-time. git = no.

Bugs found and fixed

BUG 1 — wrong look-vector convention (world.gd _refresh_look_dir)

Old code: var d := Vector2(cos(yaw), sin(yaw)) — this gives d=(0,−1) at yaw=−π/2 (the harness's facing), i.e. sideways, not forward. The player's real forward is Basis.from_euler(pitch,yaw,0)·(0,0,−1) = (−sin(yaw), −cos(yaw)) in (x,z), which gives d=(1,0) at yaw=−π/2 = +X (the walk direction).

Fix: var d := Vector2(-sin(yaw), -cos(yaw)) (one-line change, world.gd:419).

Effect: the scorer now prioritizes the correct direction. Before the fix, forward chunks were never prioritized (the scorer was pointing sideways), so the forward wall had no benefit and the gate was a false green because the wall check used the wrong column reference (BUG 2).

BUG 2 — asymmetric wall reference (main.gd boundary harness)

Old code: crossings recorded cross_cx = cx_now + r (the frontier column r ahead). The forward wall then checked columns ccx+1..ccx+r = 2r+1..2r ahead of the player at crossing — outside the render radius until the player walked on. The trailing wall checked ccx−r..ccx−1 = in-radius at crossing. Asymmetric: forward wall = 2r ahead (only enters radius as the player walks on), trailing wall = in-radius at crossing. Result: forward p95 8907 ms vs trailing 3896 ms at r=4 (prior false-green numbers).

Spec definition: pcx_crossing = the player's chunk at crossing. Forward = columns ref+1..ref+r (dx>0, dx==0 column excluded), trailing = ref−r..ref−1. Both symmetric, both in-radius at crossing.

Fix: added cross_pcx/cross_pcz arrays (player chunk at crossing). Wall check helper _ac0079_wall_built() uses these. All existing fields preserved (cross_burst, irb, flap, remesh_ok, etc.).

BUG 3 — trailing chunks hysteresis-freed → wall never resolves (main.gd)

Old code: ch == null or not ch.mesh_built → −1 forever. Trailing chunks fall out of radius while the player keeps walking and get hysteresis-freed (mesh freed) → ch == null → wall never resolves → −1.

Spec intent: "the wall got built while it was in radius."

Fix: per-key ever_built set updated each frame for tracked wall keys. A chunk counts as built if currently mesh_built OR was observed mesh_built at any earlier frame. Trailing walls now resolve (e.g. r=4: trailing p95 64/3244/33 ms instead of −1). Documented in results.

Score formula (as implemented, unchanged from prior)

score = d + (1 - a) * 0.75 * d - boost
  d     = |cx - pcx| + |cz - pcz|          (Manhattan distance)
  a     = clamp(dot(look_dir, to_center_norm), 0, 1)
  boost = 2.0 if cheby <= 1 else 0.0

  look_dir = Vector2(-sin(yaw), -cos(yaw))   [FIXED: was (cos, sin)]
  to_center = chunk_center - player_xz       (normalized for dot)

Pool cap: PICK_POOL_CAP = 512. Look refresh: lazy, gated by PICK_LOOK_REFRESH_DEG = 10.0° on player._yaw.

The trailing wall (40 chunks, 2r+1 columns behind) is already built from the spawn fill — it just needs to survive hysteresis (ever_built) and resolves in 33–3244 ms. The spec gate "forward_p95 ≤ trailing_p95" assumes the forward wall should be faster than trailing because look-priority prioritizes forward — but at the current drain rate, the forward wall is the long pole (it's the leading edge that has to be generated + meshed from scratch), while trailing is pre-built. Round 3 — scored DATA pick (the real bottleneck)

Status: COMPLETE. Coordinator code review (rounds 1–2) correctly diagnosed the remaining G3 failure: the data pick was still FIFO while only the mesh pick was scored. Without a scored data pick, forward leading-edge chunks (band r) only get data after all nearer-band data drains FIFO, and _build_ready (4 axial neighbors need data) blocks the forward mesh until that data exists — so look-priority on the mesh side alone cannot make the forward wall fast. This round makes the data pick scored, exactly as spec §2 "Data pick" requires. Changes are confined to godot/world/world.gd.

What changed (minimal diffs, world.gd only)

  1. Scored DATA pick. The data phase (the if u == 0 ... block) now reuses _collect_pool(build=false) (no-data entries, cap PICK_POOL_CAP = 512, same as today), scores each candidate with the existing _entry_score, and generates the LOWEST score. It keeps everything the FIFO path did for the chosen entry: stub_chunk when the node is missing (same out-of-radius skip guard), then _gen_unit (desktop threadgen enqueue — dedup/cap/stale-drop untouched) or the sync web path. _gen_unit is called when c != null and c.data.is_empty(), whether the node pre-existed or was just stubbed (this matches the original control flow exactly — an early draft that nested the generate inside the c == null branch silently starved generation and was caught + fixed by a debug trace).
  2. Cursor bookkeeping kept consistent. New helper _advance_dq_past(cx,cz) advances dq_b/dq_i past the consumed entry exactly as the old FIFO scan did, so entries are never re-picked and queue_size stays exact (the _process idle check depends on it). _remove_entry is unchanged (build pick). The cursors are pure fallback bookkeeping now — the pick itself is score-driven.
  3. Pool scan is cursor-independent. _collect_pool now scans every band (capped at PICK_POOL_CAP) instead of clipping at dq_b/mq_b. A stale sticky cursor (e.g. dq_b parked past the last band by the exhaustion branch after a recenter) would otherwise empty the pool and starve the drain forever — this is the bug that made the first attempt do 0 units. The pool stays O(cap) ≤ 512 lightweight dict ops per pick.

Scored data-pick mechanics (1 line): data pick = lowest _entry_score among _collect_pool(false) (all no-data entries, cap 512), stub-if-missing then _gen_unit; dq_b/dq_i advanced past the consumed entry as bookkeeping; pool scan ignores the sticky cursors.

Why the data pick was the bottleneck

At r=4 the forward wall is 8 columns × 9 rows = 72 chunks ahead of the crossing chunk. Each needs (a) data generated and (b) a mesh. _build_ready requires the 4 axial neighbors to have data, so a forward chunk cannot be meshed until its neighbors' data exists. Under the FIFO data pick, band-1..r−1 data (the ~30 nearer chunks) drained before any band-r (forward) data, so the forward wall waited for all nearer data to generate first — a serial dependency that added ~5 s. The scored data pick generates the forward band-r data first (lowest score = closest to the look direction), so the forward mesh ring can start filling as soon as the leading-edge data lands. This is why in_radius_built_max rose from 55 (round 2) to 67–68 (round 3): more in-radius chunks are built while walking because the forward leading edge is no longer starved.

Remaining bottleneck — why r=4 forward is still > 3500 ms (honest analysis)

The scored data pick works (irb_max 55 → 67–68 proves the forward leading edge now fills in-radius), but the r=4 forward wall p95 is still 5107–5145 ms (runs 1–2; run 3 was 11218 with a pacing spike where the trailing wall also jumped to 6495). This is a drain throughput limitation, not a scoring bug:

  • Data gen throughput. The drain budget is 3 units (spawn 3×3 pending) then 2/1 by last-build cost, capped by drain_budget_ms = 30 ms. The r=4 forward wall = 72 chunks ahead. Even generating data in look order, 72 chunks of data + 72 meshes at the current ~20 units/s drain rate ≈ 4.9 s — matching the measured 5.1 s. The threadgen pool (max 3 inflight) pipelines data off-thread, but the mesh step is serial on the main thread (_build_unit → build_mesh ≈ 4–6 ms each); the long pole is the serial data→mesh dependency ring plus the per-frame unit budget.
  • _build_ready ring. Each forward chunk needs its 4 axial neighbors' data before it can mesh. The leading-edge chunks sit at the front of the generation wave, so their neighbors' data is only available as the wave advances — a serial dependency that scoring prioritizes but cannot parallelize (meshing is main-thread serial).
  • Drain budget. At 2 units/frame (last_build fast) and 30 ms/frame cap, the drain processes ~2 data + up to 2 mesh units per frame. Raising the budget (or allowing a 2nd data unit in the same frame when the build pick found nothing — the spec's optional §2) would speed the forward wall, but risks the walk frame-time gate (r4 p95 ≤ 80 / max ≤ 150), which is currently passing at 64–66 / 100–115 with headroom. Per the round-3 instructions, I did not add a hack to force fwd ≤ 3500; I report the measured number and the analysis.

Conclusion: the scored data pick is correct and is the intended fix (spec §2 "Data pick"). It crosses the r=4 in_radius_built_max ≥ 60 gate (67–68). The r=4 forward_p95 ≤ 3500 gate still fails at the current drain throughput — that requires a higher drain rate (AC-0077 bulk batch / a 2nd-per-frame data unit / a higher drain_budget_ms), which is a separate decision for the coordinator. No further world.gd hack added this round.
