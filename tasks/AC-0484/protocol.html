AC-0484 — the generation-cost measurement protocol

The reusable procedure for measuring where the native generation time actually goes, split from meshing / lighting / I/O / queue wait. Written so a later ticket in the continent series — and the user on Windows — can re-run it exactly. The Linux numbers in AC-0484-results.html are the first run of this protocol.

DEVELOPMENT-ONLY. Linux headless numbers (including every number this protocol produces on this box) are development evidence on a box that renders through llvmpipe. Shipping Windows is the acceptance platform (the shared plan, §08: “Linux headless runs are development evidence, not a substitute”). Label every quoted figure accordingly. No speedup claims and no atlas layout are decided by any run of this protocol — it only produces a baseline.

0. What is being separated (the one fatal error to avoid)

Total per-chunk cost is a sum of five buckets that must never be blended: generation (the C++ native stages), meshing, lighting, I/O, and queue wait (time a request sits before a worker starts it). A number like “a chunk costs 29 ms” is useless if it silently includes queue wait or mesh time (AC-0474’s “the fill stalls” was an instrument watching one lane while the other landed 16,320 chunks). This protocol measures each bucket with its OWN clock at its OWN call site, and states the attribution below.

2. The fixed corpus

Pin the exact requests BEFORE measuring; write them down; never let a re-run measure different work. See corpus.txt for the pinned sets:

  • C1 — generation: 25 full-column generate_resl(cx, cz, 44, 384, 126, 0, empty, 0, 4000) requests, (cx,cz) over the genhash arm’s own 5×5 window — so the measured work and the byte-identity gate cover the same geography. One unrecorded warmup pass, then the trials.
  • C2 — production pipeline: one real boot, seed 44, the harness battery’s player mode (new world, spawn recenter, sim-band wait, scripted walk) with AWECRAFT_TIMING=1. The streamed set is whatever the scheduler enqueues; record it from the TGENW lines.
  • C3 — I/O: the standing colbytes arm (25 columns, seed 44, the arm’s fixed ring).

3. The trial design (5 INTERLEAVED, not back-to-back)

  1. At least five trials per bucket that is re-measurable in-process (the C1 driver). Run at least five paired/interleaved trials and more if variance obscures the outcome (shared plan §08).
  2. Interleaved means: for corpus position i, its five samples are ADJACENT calls (global k = 5·i + tr). Back-to-back trials let thermal / page-cache drift masquerade as variance (trial 1 cold, trial 5 warm). Interleaved, drift hits every trial evenly, and the per-chunk spread becomes a real per-chunk effect size. (This project was bitten by single-sample thresholds: an earlier p95 was fitted to two samples on an arm that wanders 37–40.)
  3. Report median, p95, p99 AND the spread (min–max) per stage, per-chunk sample counts (n, and n>0 for stages that are sparse — the carver is ~15%/chunk), plus per-trial aggregates (their spread shows the interleaving worked: at 7731c0d the five trial medions were 5329–5350 µs, a 0.4% spread).
  4. Contention is disqualifying, not averageable. Before every engine call record: date, loadavg, the top processes, and whether another engine is running (the slot guard). A contended trial is invalid — drop it and say so; never average it in. Timing runs are the most contention-sensitive work on a shared box.

4. The timer negative control (an instrument never shown to be sensitive is not evidence)

  1. Build with AC0484_GEN_TIMING=1 (SConstruct opt-in, default off — the plain build is bit-identical, verified by md5 against the pre-instrument build).
  2. Run the driver once with AC0484_INJECT_US=5000: a known 5000 µs delay slept inside generate_resl, AFTER the work.
  3. Pass = the per-call WALL grows by ≈ the injected amount (observed at 7731c0d: median 5346 → 10399 µs, delta 5053 µs) AND the stage counters do NOT absorb it (stage-sum stays ~5.2 ms) — the injection lands in the wall, not in the work, so both the wall clock and the stage diff are proven to register differences.
  4. No pass on the control = no evidence from the measurement; fix the instrument before quoting anything.

5. Output identity (the instrumentation must be inert when off)

  1. Rebuild WITHOUT the flag; the .so must be bit-reproducible against the pre-instrument build (md5) — the AC-0480 pattern. At 7731c0d it was: 8feae1e8… both sides.
  2. Run AWECRAFT_LOGIC=genhash twice; both runs must print 25/25 identical GENHASH lines, and they must equal the standing reference set in godot/HARNESS.md §3 (at 7731c0d: .scratch/AC-0311-gates/p2_genhash_r1.log). The hash set bakes in caves, aquifer, carver, drip, decoration — 25/25 against the reference is the “features intact” proof. Never rebase a surprise mismatch: it is a finding.

6. The metadata block (a timing table without it is not reproducible)

Record with every result: git revision; build (target, flags, the instrumentation flag on/off, the .so md5); CPU model + core count; memory; worker counts (gen/mesh, and whether auto-split); the settings in force (seed, HEIGHT/SEA, render radius, blur OFF, default-settings loader); the corpus id; the contention snapshot of the run; and the engine version.

7. The runs, in order (Linux)

# 1. instrumented build (the driver measurements)
AC0484_GEN_TIMING=1 <scons> -C gdext platform=linux target=template_release
cp gdext/bin/libchunkio.so godot/bin/libchunkio.so

# 2. negative control, then the 5 interleaved trials (driver; corpus C1)
bash .scratch/AC-0484/run_engine.sh negctrl
bash .scratch/AC-0484/run_engine.sh trials

# 3. default build (everything else runs INSTRUMENT-OFF)
<scons> -C gdext platform=linux target=template_release
cp gdext/bin/libchunkio.so godot/bin/libchunkio.so    # md5 must match the pre-instrument .so

# 4. output identity (genhash 25/25 x2 vs the standing reference)
python3 tasks/scripts/gate_run.py AC-NNNN --arms g0,genhash

# 5. production buckets (corpus C2) + I/O (C3)
bash .scratch/AC-0484/run_engine.sh prod      # AWECRAFT_TIMING=1 AWECRAFT_BATTERY=player
python3 tasks/scripts/gate_run.py AC-NNNN --arms colbytes

(The runners slot-guard on the engine binary path, memory-cap the engine, record the contention snapshot, and never kill a process they did not start. The driver and runners live in .scratch/AC-0484/ — copy them for the next ticket or into the Windows box; they are plain bash + one GDScript SceneTree script with no repo dependencies.)

8. Running it on Windows (the handover)

This ticket did NOT run the Windows numbers — the acceptance platform needs its own execution window. To run the protocol there:

  1. Build: python3 -m SCons -C gdext platform=windows target=template_release (the MinGW cross path works from Linux too — gdext/AGENTS.md), or the native Windows build. Do it TWICE: once plain (record the .dll md5), once with AC0484_GEN_TIMING=1.
  2. Engine: the Windows 4.7.1 engine + the game export or the editor with --path. The driver is a headless SceneTree script: godot.exe --headless --path <game> -s <absolute>\driver.gd with AC0484_TRIALS=5 and AC0484_TIMING_FILE set. (If -s does not load the GDExtension in a given engine build, the fallback is a temporary harness arm calling the same driver body — add and REMOVE it in the same task, harness.gd stays pristine after.)
  3. Runs: the same five runs in §7 (negctrl / trials / identity / prod / colbytes). The prod run needs the shipped build, not the cross-build, for honest product numbers.
  4. Quiet box: a Windows dev box is usually quieter than a shared Linux one — still record the contention snapshot per run; the rule (contended = invalid) does not relax.
  5. Report: the same table shape, same statistics, same attribution text, and the same label: the Linux column stays development-only; the Windows column is the acceptance data. No speedup claim until the series’ optimization tickets have re-run this protocol and shown a repeatable reduction beyond run-to-run noise on the same corpus.

9. What a result of this protocol is allowed to say

  • “Stage X is N% of generation” (ranked, per the measured stages) — with the metadata block attached.
  • “Generation costs A; meshing B; lighting C; I/O D; queue wait E — measured separately this way.”
  • Nothing else. No “we should remove Y to be faster”, no “the new generator will be 20% faster”, no atlas layout. Those belong to the tickets that cite this baseline.
