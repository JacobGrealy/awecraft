AC-0484 — where the native generation time actually goes (measurement only)

Coordinator contract (written by me; the ticket was filed by another agent). Medium builder applies it with tasks/templates/implement.md. MEASUREMENT ONLY — no optimisations, no planet changes, no speedup claims. The deliverable is a ranked, reproducible bottleneck table plus a reusable protocol.

1. The requirement, from the filing

"generation improvements should address the work that actually costs time, without removing caves, decoration or other features to make the numbers look better." So the output is a truthful cost breakdown of native generation, split from everything that is not generation.

2. What must be separated (this is the hard part, not the timing)

Total frame cost is a sum of things that must not be blended: generation, meshing, lighting, I/O, and queue wait. A number like "a chunk costs 29 ms" is useless if it silently includes queue wait or mesh time — and this session has already been burned by exactly that class of measurement (AC-0474's "the fill stalls" was an instrument watching one lane while the other landed 16,320 chunks). Report each bucket separately, and state how you attributed time to it.

4. The method (the filing specifies it; follow it exactly)

  1. 4a METADATA, RECORDED. Revision, build type, hardware, worker count, and the settings in force. A timing table without these is not reproducible.
  2. 4b A FIXED REPRESENTATIVE REQUEST CORPUS. Pin the exact set of chunk requests used, so every trial and every future re-run measures the same work. Write the corpus down — it is part of the reusable protocol.
  3. 4c AT LEAST FIVE INTERLEAVED TRIALS, reporting median, p95, p99 AND the spread. Interleaved matters: running five trials back-to-back lets thermal or page-cache drift masquerade as variance. This project has repeatedly been bitten by single-sample thresholds (an earlier p95 was fitted to two samples on an arm that wanders 37–40), so the spread is part of the finding.
  4. 4d NEGATIVE CONTROL FOR THE TIMER. Prove the counters can register a difference: instrument something known-costly and show the number moves, or inject a known delay and show it appears. An instrument never shown to be sensitive is not evidence — this is the same rule that made the halo arm's negative control mandatory last round.
  5. 4e GENHASH 25/25 WITH THE INSTRUMENT OFF. The instrumentation must not change output: with it disabled, genhash must read 25/25 byte-identical. Output and enabled features must be unchanged — no cave, decoration or feature removed to flatter the numbers (the filing is explicit).

5. Honesty requirements the filing calls out

  • LINUX NUMBERS ARE DEVELOPMENT-ONLY and must be labelled as such, in the results page and wherever they are quoted. This box renders through llvmpipe and is not the product.
  • Windows native timing may need its own execution window — if it cannot be done here, say so and hand the user a protocol they can run, rather than dressing Linux numbers as product numbers.
  • NO speedup claim and NO atlas layout frozen here. This ticket produces a baseline and a protocol; the following tickets use them.

8. Acceptance

A ranked per-stage cost table over five interleaved trials on a written corpus, with generation separated from meshing/lighting/IO/queue wait; a timer negative control; instrument-off genhash 25/25; unchanged features; every number labelled development-only; and a reusable protocol for the Windows run.

9. Risks

(1) Blending queue wait or mesh time into "generation" — the one fatal error here. (2) Five back-to-back trials instead of interleaved, turning drift into false variance. (3) An instrument never shown to be sensitive. (4) Instrumentation that changes output or drops a feature. (5) Presenting Linux numbers as product numbers. (6) Timing on a box contended by the parallel session. (7) Reading gen.cpp whole and burning the context budget.
