1. What the change does

The task's file pointer (lighting.gd :: _data_landed) is stale — that function was removed in AC-0119. The real "new-column neighbor marking" is _eff_landed in godot/world/world.gd: when a chunk's light lands, each built axial neighbor whose import from that chunk may have changed is evicted + re-enqueued into light_pending (the E2 wave = the dirty spike; each re-enqueue is a full re-light + remesh handoff).

The per-side gate now does the border compare (cheap edge-value scan vs the full rebuild):

  • First landing (old_eff empty = the new column): the before-state is exactly known — every built neighbor read an EMPTY strip from that side while the column was missing (margin 0, no injection — _strips_for), i.e. all-zero edge values. New gate _frame_nonzero(new_arr, side) scans the 2-deep eff frame toward that side (same cell set as _frame_changed): mark the neighbor only when the edge values differ from the all-zero before-state.
  • A zero frame is a provable no-op for the neighbor: the bake box pre-zeros its margin (an all-zero strip writes zeros), and eff = max(sky, blk) so a zero frame means zero block light on the border — the settled face row is inside the 2-deep frame (no separate face scan needed) and cand = 0 − att ≤ 0 can never raise — so the neighbor's light and mesh stay byte-identical; its full re-light + remesh is skipped.
  • Steady-state landings (old_eff non-empty): unchanged — the existing per-side _frame_changed(old_arr, new_arr, side) gate, which is the before/after border compare for re-lights.
  • Late border changes cannot be masked: any frame value rising 0→n requires a re-light, whose _eff_landed re-runs the steady-state gate (eff only ever increases — the AC-0134 no-staleness argument).
  • Cost of the compare: one top-down byte scan, 12288 B worst case, early-exit after the first row on surface chunks (open-sky rows are eff 15) — ≈0.1–0.2 ms vs the 2–10 ms full rebuild it can skip.

Instrumentation (R16 dirty-count evidence): world counters perf_lightdirty_marks (new light_dirty marks in the 3×3 edit ring — the task's "all eight"), perf_e2_marks (unique built-neighbor re-enqueues), perf_e2_first_marks/ perf_e2_first_skips (first-landing border-compare verdicts), perf_e2_side_changed/perf_e2_side_unchanged (steady-state gate verdicts), perf_lightpend_retrigger; the R16 arm reports them as a per-phase dirty block in RESULT (static/moving/settle/fly4/fly50).

5. Honest analysis: why the skip count is 0 on this world

The border compare is exact, but on seed 44 (open-sky grassland) a new column's border light always differs from the before-state, so no first-landing mark is eligible to skip:

  • The frame is never all-zero on this world. Rows above a column's top are air open to the sky → eff 15 (C++ pull kernel: for (y = hact; y < h; y++) eff = SKY_FULL; GDScript reference identical; pullprobe-verified). The topmost frame row (y = 383) is therefore 15 for every chunk — a fully-dark enclosed frame cannot occur here, so _frame_nonzero early-exits on the first row and the skip path (perf_e2_first_skips) is measured but fires 0 times. The mechanism is live and would fire on a genuinely all-dark border (e.g. a column enclosed with no block light).
  • Every first-landing mark is legitimate under the task's own rule. "Only mark when the edge values differ" — they do: the margin the neighbor read goes 0 → 15 (sky) at the surface, so the neighbor's frontier faces are genuinely re-lit dark → lit (the AC-0119 frontier pop). Skipping those would leave dark cliff faces along chunk boundaries — a visible lighting regression, which the task explicitly forbids ("the light is still correct").
  • The steady-state half of the ask is already the frame gate (old frame vs new frame per side) — it keeps skipping ~45% of re-light sides in fly4 (701→715 unchanged sides in the after run), unchanged by this task.

Remaining lever (out of scope, flagged as follow-up): the fly-phase re-enqueue wave (1020/chunk-run) is margin-fill work that is visible wherever the new column's boundary has air (cliff/step/cave faces). It could be reduced only by a mesh-level check — "does any visible face exist on the neighbor toward this column" (neighbor's boundary solid vs new column's air cells) — which is a data/mesh analysis, not a cheap border-light compare, and needs its own correctness case. Not attempted here.
