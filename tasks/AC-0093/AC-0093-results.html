AC-0093 — drop-spin-in-place-not-orbit

User story: broken-block drops must spin in place while they sit on the ground. Bug as filed: they orbit (a circle) instead of spinning. Verdict: FIXED — numeric invariant proven

Root cause — it is case (d): the pivot, not the rotation

The spin itself (_mesh.rotation.y += dt * 2.0, original drop.gd:129) is a legitimate local Y-rotation. The bug is where that rotation is anchored. The box/cross geometry is built in [0,1]³ with its center at (0.5,0.5,0.5) in mesh-local space, but the mesh's origin (the pivot the rotation is applied about) sits at the box's corner:

  • godot/core/held_mesh.gd:3-4 — the cross quads XQ_A/XQ_B are corners in [0,1]³, centered at (0.5,0.5,0.5).
  • godot/core/held_mesh.gd:83-117 — _build_box emits VoxelMath.FACES corners (the unit cube [0,1]³, core/math.gd:3), also centered at (0.5,0.5,0.5).
  • Original drop.gd:23 add_child(_mesh) + drop.gd:128 _mesh.position = Vector3(0, 0.16+bob, 0) — the mesh origin is the box's corner, and the _mesh.scale = 0.3 puts the geometry center 0.3·(0.5,0.5,0.5) = (0.15,0.15,0.15) away from it.

Rotating _mesh about its own origin therefore sweeps the box center in a circle of radius 0.3·√(0.5²+0.5²) = 0.3·√0.5 ≈ 0.212. That is the orbit. Per the ticket's own rule, the correct fix is the pivot / mesh offset — not the rotation (the rotation was already correct).

The fix (drop.gd)

Reparent the mesh under a _pivot node whose origin is the box center, recenter the geometry on it, and spin the pivot:

# _ready()  (was: add_child(_mesh))
_mesh.position = Vector3(-0.15, -0.15, -0.15)   # recenter the [0,1]³ geometry on the pivot
_pivot = Node3D.new()
_pivot.add_child(_mesh)
add_child(_pivot)

# _process()  (was: _mesh.position = (0,0.16+bob,0); _mesh.rotation.y += dt*2.0)
_pivot.position = Vector3(0.15, 0.31 + sin(_age*3.0)*0.06, 0.15)  # box center in drop space
_pivot.rotation.y += dt * 2.0                                     # spin about the box center

Consequences, verified by construction + the numeric arm:

  • The box fills the exact same region as before (x:[0,0.3], y:[0.16+bob,0.46+bob], z:[0,0.3] in drop space) — look unchanged.
  • The drop node's position is untouched — fall/settle and the pickup magnet read only it, so those move it (legit) and nothing else does.
  • Bob preserved: same sin(_age·3.0)·0.06 term (0.06 amp, 3.0 rad/s), now on the pivot (0.31 = 0.16 hover + 0.15 half-block center).
  • Spin rate preserved: still dt·2.0 (2.0 rad/s).
  • The Area3D/collision sphere stays a direct child of the drop node — physics unchanged.

Verification — the numeric form of "spins without circling"

Method: a drop at rest (pre-grounded; a far-away player stub so the magnet dist < 2.5 never fires; Game.world = null so the ground-snap branch is skipped) is driven with a fixed dt = 1/60 for 200 ticks. Each tick records: (a) the drop node position, (b) the rendered box-center world XZ (the (0.5,0.5,0.5) mesh point composed through the node chain), (c) the mesh's world Y-rotation (unwrapped). Invariant of "spins in place": the box-center XZ and the node position stay fixed while the Y-rotation advances. The orbit (the bug) is the box-center XZ drifting in a circle whose radius is the off-origin offset.
