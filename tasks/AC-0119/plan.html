Post-change (whole body replaced):

func _chunk_data(cx: int, cz: int) -> Node3D:
	return chunks.get(_key(cx, cz))

Pure lookup — returns null for a missing chunk, the stub (empty data) for a stubbed one, the chunk for a generated one. No generation, no enqueue, no build enqueue. Every chunk that needs data has (or gets) a drain entry: in-band chunks get WANT build entries at every recenter (_rec_want_step :1266-1269 re-queues c == null or not c.mesh_built), the r+1 ring gets data_only entries at every recenter (_rec_merge_ring_step :1342-1378), and freed-then-re-entered chunks are re-stubbed + re-queued the same way. Nothing the read path ever speculatively generated is left without a drain entry. The ONDEMANDGEN print dies with the branch (G4 probe = RESULT fields, §2.5).

2.2 Convergence mechanism — how air-frontier builds rebuild when neighbor data lands

Facts (current tree): a built chunk is never re-queued by the drain (_collect_pool :706-731 skips mesh_built chunks) and the recenter WANT phase skips meshed chunks (:1265-1269) — so no existing mechanism re-meshes a chunk whose data is fine but whose diagonal neighbor was ungenerated at build time. The spec requires convergence "via the existing dirty/remesh mechanism" — that mechanism is the light_dirty → light-flush → _mesh_dispatch path (the same path an edit takes: _mark_light_around :1414-1421 → light_dirty → flush → rebuild). So the new hook feeds that path; it changes no dispatch or drain internals.

New helper (world.gd, additive):

func _data_landed(cx: int, cz: int) -> void:
	for dx in range(-1, 2):
		for dz in range(-1, 2):
			if (dx == 0) and (dz == 0):
				continue
			var nkey := _key(cx + dx, cz + dz)
			var nc = chunks.get(nkey)
			if nc != null and nc.mesh_built and not light_pending_set.has(nkey) and _build_ready(int(nc.cx), int(nc.cz)):
				light_dirty[nkey] = true

Call sites (exactly two, both at "data just landed" moments): threadgen_handoff after :501 (c.data = data; c.init_fl(); _apply_edits_to_chunk(c)) and _gen_unit sync branch after :428. create_chunk (harness boot / spawn boot) does NOT need the hook: in recenter(false) battery runs no chunk is meshed yet (light/fluids modes build no meshes), and the spawn-boot call happens before the first build.

Proof chain (decision #3):

  1. No permanent air holes. Every chunk with Chebyshev distance ≤ r+1 from the player chunk has a drain entry after every recenter: in-band chunks get WANT build entries (_rec_want_step :1266-1269, re-queues everything c == null or not c.mesh_built) and the r+1 ring gets data_only entries (_rec_merge_ring_step :1342-1378, added unless the chunk already has data). The drain processes every band bucket to completion (empirically: all_meshed true pre-change in perf r4; AC-0118 r50 completion; queue_size data_only residual ~93-95 is the known ring remnant, A/B’d in G5). So every diagonal neighbor of every in-band chunk receives data. threadgen_handoff re-applies recorded edits on landing (:501), so player edits in re-entered chunks survive (the boundary re-entry remesh check relies on this and passed pre-change).
  2. Air-frontier faces get replaced. Chunk A builds with missing/empty diagonal D (renders air on that edge). When D’s data lands, _data_landed(D) marks A (built, _build_ready(A) true — its 4 orthogonals had data when A built and are closer to the player than D) light_dirty; the existing flush loop re-meshes A via _mesh_dispatch — worker path if all 8 diagonals now have data, sync path (air for any still-missing diagonal) otherwise.
  3. Readiness ordering. If A is not 4-ortho-ready when D lands (an outer orthogonal E is also still ungenerated — possible at the band edge), A is not marked (the _build_ready guard in the hook prevents the flush loop’s light_pending re-append spin). When E lands, _data_landed(E) marks A (now ready) — induction on landing order: the moment the last missing orthogonal lands, A is marked and re-meshed. A chunk is re-meshed at most once per later-landing diagonal (bounded ≤ 8, in practice 1-2) — transient, no spin, no permanent state.
  4. Final state byte-identical. A chunk’s mesh depends only on its own data + the 8 diagonal neighbors’ data/fl (the 18×H×18 snapshot). When all 8 diagonals have data, the re-mesh snapshot is content-identical to a build that had them from the start (same seed → same data; edits re-applied identically via _apply_edits_to_chunk on landing). G5(c) asserts the settled state (all_meshed, in_radius_built_final 81) and the A/B boundary anchors cover the per-crossing timing.

The hook is a new mechanism (additive helper + 2 call lines in world.gd only) — flagged in the box at top for coordinator scope approval. It does not touch _drain_build_queue :733, _collect_pool :706, _mesh_dispatch :583, threadgen dispatch :435-504, threadmesh dispatch, AC-0077 eff cache (_eff_cache_evict :882 / _eff_cache keyed on c.data identity — a missing chunk simply has no entry; no fake signature), or the flush loop itself.
