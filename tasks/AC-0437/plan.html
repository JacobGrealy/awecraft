AC-0437 — plan (PLAN + IMPLEMENT in one turn)

Date: 2026-10-16 · Spec: tasks/TASKS.yaml AC-0437 · Found by: AC-0384 §29 whole-experience assessment (the interface is product-shaped; it stops one polish step short; the menu still shows developer scaffolding).

Goal

Address exactly the four assessment findings, in the visual language that is already there — a polish pass, not a redesign:

  1. Crosshair (nowhere in the code) — a pixel plus in the HUD's own border/label language. No switch (the ticket's stated exception: the absence of a feature in a first-person game — its presence is simply correct).
  2. Stat rows (health + hunger rows look identical, read as debug output) — captions + the existing order carry the hierarchy. Behind a switch (look change).
  3. Inventory open (the panel competes with the scene) — dim the world behind the panel. Behind a switch (look change).
  4. Menu (flat black + developer scaffolding: the dev tag and a test range entry) — the developer entries gated out of the shipping path, the mechanism named. The assessment's menu frame is the before image.

What I found about the gating (item 4)

Finding: there is no runtime dev/shipped distinction anywhere in the code. is_debug_build() has zero usages in the tree. The only dev/shipped mechanism on the shipping path is AC-0248: build_windows.sh rewrites the const in godot/core/build_id.gd from "dev" to "<stamp> <sha>" immediately before export (git-checkout trap restores it afterwards). That mechanism covers the version string only. Consequences:
• AweCraft[dev] does NOT leak into a stamped build — the assessment frame showing it is a dev-provenance render (a git archive of the working tree, where Build.ID == "dev" by design). The tag's gate works; the provenance just isn't a shipped build.
• The Test Range button is declared unconditionally in scenes/menu.tscn and menu.gd checks no build flag — no gate exists at all. That is why a shipped build shows it: the gate isn't failing, it was never there. Nothing in the shipping path removes a UI entry.
The fix reuses the project's single source of truth for "is this a shipped artifact": the build stamp. menu.gd hides RangeButton when Build.ID != "dev". Harness runs and dev/local-tree runs (ID "dev") keep the entry; any export stamped by build_windows.sh hides it. Proof: apply the build script's exact sed to build_id.gd temporarily, capture the menu shot (its RESULT JSON reports "build": "<stamp>"), revert.
