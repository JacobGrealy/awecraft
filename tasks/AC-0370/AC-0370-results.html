1. What the code is (read, not re-derived)

World._game_tick() (world.gd:3777) fires at 20 Hz with catch-up ≤ 4 (TICK_MAX_CATCHUP) and runs, per fired tick: _random_tick_pass(tick_index) → tick_fluids() (if enabled) → _leaf_decay_tick() (if enabled).

  • _random_tick_pass (world.gd:12291) — scans the resident chunks dict for the band-0 columns with non-empty data (the 41-column taxicab diamond), then per column: one _rt_colhash (3× _rt_mix64) + 24 sub-chunks × (1× _rt_mix64 + 3 unpack shifts). Each position goes to _apply_random_tick (world.gd:12317) which does exactly two things: random_tick_total += 1 and random_tick_map[base*24+sub] = int(random_tick_map.get(…, 0)) + 1 — the consumer hook is a STUB (a comment: "decode cx/cz, world cell (cx*16+lx, sub*16+ly, cz*16+lz)"). AC-0365 flagged this ("pure hash+dict bookkeeping, consumer hook is a stub"). The "per-block work the pass dispatches" does not exist yet — there is no dispatched work to be non-portable.
  • _leaf_decay_tick (world.gd:11930) — per band-0 column: skip if c.leaf_decay.is_empty(); else keys() + per-timer has/int/erase/write-back, and a fired timer does c.get_local + set_block(wx, ly, wz, 0) (a real edit). On a WALK arm no tree is broken, so the maps are empty and this is a per-tick column iteration (≈ resident-set property reads) plus ~0 timer work. It is NOT dispatched from the random pass — it is a sibling inside the same tick.
  • tick_fluids (world.gd:12108) — already bracketed by AC-0365 (33.8 ms / 27.2% of the tick over the worst-20). Its per-cell work is real set_fluid/set_block + star batched edits — the non-portable class; out of this ticket's split decision (it is in scope only in that the fluids arms must stay green, since tick_fluids sits in the same tick).

Only consumer of random_tick_map/random_tick_total/random_tick_seq outside world.gd is the tick arm (harness.gd:21887, AWECRAFT_LOGIC=tick, W=120): it resets the state, runs 120 real 20 Hz ticks over the full 41-set, verifies scope (41 cols, band 0), per-subchunk counts == W, recomputes every logged position with the GDScript _rt_colhash/_rt_mix64 and requires recompute_mismatch == 0, and reports window_md5 (md5 of all logged positions across the window — "byte-identical across fresh runs", the arm's own determinism gate). It is NOT in the 7-mode battery. This arm is the bit-identity proof: BEFORE-vs-AFTER window_md5 + the recompute check (which, after the port, compares the NATIVE output against the GDScript reference — strictly stronger than before).

Native lane shape (for the port): one GDExtension library libchunkio (entry chunkio_library_init, gdext/src/chunk_io.cpp), one RefCounted class per src/*.cpp (SCons glob), ClassDB::bind_method(D_METHOD(…)) registration, GDREGISTER_CLASS + the register_classes() call in the entry symbol. AC-0356's pattern = a synchronous batched call (star.begin/end_edit_batch). The port is one synchronous call per fired tick: the per-tick work is ≈ 1100 mix64 + 984 map increments — a few µs in C++, no queue needed. Constants: c1 = 0x9E3779B97F4A7C15, c2 = 0xBF58476D1CE4E5B9, c3 = 0x94D049BB133111EB (GDScript int64 two's-complement bit patterns; C++ replicates with int64_t so >> stays arithmetic and +/* wrap mod 2⁶⁴ — bit-identical; -O2 -ffp-contract=off untouched, integers are not FMA candidates).

4. The route: (a) PORT — and exactly what goes

Chosen: (a) PORT the hash + the random_tick_map bookkeeping to the native lane (one synchronous call per fired tick), for the measured reasons:

  1. The bookkeeping dominates and is pure. 43% of the hot cost is hash math + dict updates with a stub consumer — the AC-0356 shape exactly (a per-tick main-thread cost that is wholesale portable, no SceneTree dependency, no world edits). Throttling would remove at most the per-sub part of it (mix+map+ colhash ≈ 1.2 ms/tick → ~2.4–3.6 ms per multi-fire frame) while changing behaviour (see §6 for the cost that would have been stated); the port removes the same work with zero game-behaviour change.
  2. The lane has the headroom. Per the ticket, threadgen is starved at 1–2 inflight against 545/s; ≈ 1100 mix64 + 984 map increments is a few µs in C++ — a synchronous call, no queue, no drain pacing. AC-0356's begin/end_edit_batch is the precedent for a synchronous batched call on this lane.
  3. The bit-identity proof exists and gets stronger. The tick arm recomputes every logged position with the GDScript reference (_rt_colhash/_rt_mix64 stay in world.gd as the reference) and gates recompute_mismatch == 0 + the window md5. AFTER the port, that check compares the native output against the GDScript reference — cross-lane, strictly stronger than the before.

Scope of the port (deliberately narrow): the per-column colhash + the 24× per-sub mix64 + the map increments move to C++ (AweRandomTick.random_tick_pass); the map itself becomes C++ state (map_dict() exposes it on demand — the only reader is the tick arm, two-line edit, its core recompute check untouched). The column scan stays in GDScript with exact semantics (same filter, same order, sort only when random_tick_log) but allocation-free (reused PackedInt32Arrays instead of 41 fresh Arrays per tick). Leaf decay stays in GDScript: its measured cost is a column scan (the edit work is zero here) and its fires do set_block (world edits — the non-portable class); porting its scan would owe a cross-lane state-sync contract for ~0.6 ms/tick. Named residual (a follow-up, not this ticket): the two column scans (rtp 0.87 + leaf 0.59 ms/tick) — the band-0 set is the 41-column taxicab diamond, so a diamond-anchored lookup (41 keys, not ≈1450) or a native column mirror would remove them; both need a band-anchoring equivalence proof the budget does not carry safely. Expected after (from the split): rtp ≈ 0.75 ms/tick (≈ 0.7 scan + ≈ 0.05 native call) vs 2.15 before — the tick drops ~35–40% and the multi-fire multiplier weakens by the same factor; the acceptance run in §6 says whether the expectation holds.
