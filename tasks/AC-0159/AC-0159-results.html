Status: DONE (builder scope). Linux .so rebuilt + staged; all standing gates re-run after the change (table in §7). Windows .dll rebuild + full battery = the coordinator's.

1. What the mesh build actually is (where the feature lands)

The ticket names godot/world/world.gd "mesh build", but since AC-0190/AC-0208 the high-band mesh build is C++-only: AweMesh.build_accs in gdext/src/mesh.cpp (the GDScript ChunkScript.build_accs fallback was removed in AC-0208 — the C++ extension is required, no GDScript lane survives). world.gd only dispatches (_tm_worker_run → mc.build_accs(...), world.gd:6298). Smooth lighting therefore lands in mesh.cpp, the lane where the light is already sampled (s_face_light, mesh.cpp:392). This is the deviation from the ticket's file pointer, recorded here; the ticket's shape (sample 3 neighbours + the block's light per face corner, interpolate 0–15 into the vertex colour, AO 0.2 per occluding solid, multipliers 1.0/0.8/0.6/0.4) is implemented as specified.

Consequences: the Linux .so rebuild + re-stage is mandatory and done in this task (gdext/AGENTS.md); the Windows .dll rebuild is the coordinator's (same C++ source, same flags).

1.1 The light data the mesh already has

  • The per-chunk light is the AweStarlight settled payload (AC-0283 P2/P4): one combined 0–15 intensity per cell (eff bytes) + a per-cell block-light evidence mask (blk > 0). There is no separate per-corner sky/block split in the data — the combined value is what Java's fancy averaging would consume too (Java averages max(sky, block) per sample cell). Sky vs block only matters for the channel the value is packed into (below).
  • bake_box expands it to a 20×20 (2-cell margin) light box barr; the block-id box snap is 18×18 (1-cell margin, edge rings from the 4 edge neighbours; the 4 corner margin cells stay 0 = air).
  • Vertex colour repack (AC-0128): with atlas → r = s (sky channel) or g = s (block channel, when the face has block-light evidence, the mask), b = face shade (FSH: 0.8/0.8/1.0/0.5/0.8/0.8). The opaque shader (chunk_lit_opaque.gdshader) computes L = 0.20 + 0.80 * max(u_day * r, g) and ALBEDO = tex * b * L — the 0.20 floor / 0.80 gain is the standing user-directed curve (AC-0135) and is not part of this change.

1.2 The Java Fancy formula implemented (per face corner)

Face block B, normal n, corner vertex at in-plane offsets (du, dv) ∈ {0, +1, −1} (per the FCV corner table); O = B + du·ê_u + dv·ê_v (the inside block the corner touches); directions d_u, d_v ∈ {+1, −1} away from the face's own origin (the corner's far side). Then, per corner:

// 4 light samples (3 neighbours + the block's own light), each a combined 0-15 int
S0 = O                        (the corner block itself)
S1 = O + d_u·ê_u              (in-plane neighbour, axis u)
S2 = O + d_v·ê_v              (in-plane neighbour, axis v)
S3 = O + d_u·ê_u + d_v·ê_v + n (the OUTSIDE diagonal)
Lc = (L(S0)+L(S1)+L(S2)+L(S3)) / 4      // integer sum / 4 — EXACT in binary FP (no rounding)
// 3 AO occluders (outside of the face, at the corner)
A1 = O + d_u·ê_u + n    A2 = O + d_v·ê_v + n    A3 = S3 (shared)
ao = count(solid(A1), solid(A2), solid(A3))      // solid = C.stab[id] > 0 (the face-cull solid test)
vertex light sl = clamp(Lc/15, 0.08, 1.0) * {1.0, 0.8, 0.6, 0.4}[ao]   // ticket's multipliers, verbatim

Channel choice per corner: chan = OR(mask(S0..S3)) — if any of the 4 sample cells has block-light evidence the corner's light is packed into g (stays bright at night, u_day-independent), else into r (fades with the day cycle). This is the per-corner generalisation of the standing face-level face_mask decision: a sky-lit corner of a partly-torched face now fades at night, as in Java (where the sky portion of a corner's light is recomputed per corner), instead of the whole face inheriting one channel.

Rounding/determinism (the prompt's subtle part): the 4-sample average is integerSum / 4.0f — a power-of-two division of an exact small integer, so it is exactly representable in binary FP32, no rounding at all (unlike e.g. /15 or /60). The remaining arithmetic is the standing light→float conversion (/15.0f, one IEEE rounding, same as today's flat path) and the AO table (1.0f, 0.8f, 0.6f, 0.4f — the ticket's literal constants; 0.8/0.6/0.4 are not binary-exact but are display-side constants applied identically by the single C++ code path that emits vertex colours). There is no second lane computing the same per-vertex value: the far lane has no per-vertex light (it is per-cell average colour, §2), so no cross-lane bit agreement is owed on the per-vertex values themselves — what is owed is §2's light-field agreement, which this change leaves untouched (same larr, same starlight engine). -ffp-contract=off is unaffected (no new float multiply-add chains; the divisions are exactly representable or the standing single-rounding form).

Scope of application (matching Java, where fancy lighting applies to full blocks only): the opaque face path ro (solids incl. leaves) and rc_o (tinted xtab faces, the opaque-drawn leaves) get per-vertex light + AO. Cutout (rk, glass/flowers), cross-quad (rq, plants/torches) and fluid faces stay flat-lit exactly as before.

1.3 Merging with per-vertex colour (the perf-critical shape)

The high path greedy-merges coplanar faces (up to 16×4) into one quad with ONE colour (qwrite_merged). A per-vertex colour would make any merge across a gradient incorrect (the merged quad bilinearly interpolates only its 4 outer corners; the per-face union would show interior dips). Java's answer: fancy lighting disables merging entirely (one quad per face). This implementation is at least as fast as Java's: a region may still merge when every face in it is uniform — all of its 4 corners carry the same (L-sum, ao, chan) triple — because then every per-face quad in the region is a flat quad of one colour, and the merged quad (whose 4 vertices are 4 of those same uniform colours) is exactly equal to the per-face union. In a fully-lit open ground (all samples 15, no occluders) the 16×4 merge survives byte-for-byte; gradients and AO corners fall back to per-face quads, exactly where the new detail lives. Implementation: the merge key grows from (id, fni, shade) to (id, fni, uniform, L, ao, chan); uniform faces emit through the unchanged qwrite_merged (one colour), non-uniform faces through a new 4-colour qwrite twin.

2. The far lane: what it produces and what this change owes it

  • Does the far lane produce light? Yes — per coarse cell, not per vertex. Bands B/C draw the average-colour emits (h_avg_emit / low_emit_avg, 8×8×8 med / 4×4×4 low). Their light is the heightmap sky (AC-0283 P3): per cell, 15 strictly above the carved terrain top, 0 at/below; no block light, no cave carving, no interpolation. The vertex colour of those meshes is (1.0-flat sky, 0 block, per-face shade) — a filler.
  • Granularity: one light per 2×2×2 (med) or 4×4×4 (low) cell — 2–16× coarser than the full lane's per-cell starlight, before any vertex interpolation.
  • What this change owes it: the far lane's light is an independent approximation of the same physical field (heightmap sky, its own C++ compute — gen_far/sky payload). Smooth lighting does not change the field: it redistributes the same per-cell starlight values onto face corners (a convex combination — interpolation cannot create or destroy light), so the far lane's approximation remains equally valid, and its emitted bytes are untouched. The promotion seam (far → full) already changes the light model today (0/15 heightmap sky → true starlight with caves and block light); this change adds no new seam class — the promoted column gets the same field it would have gotten flat-lit, just distributed smoothly across faces. No far-lane value is re-derived or rounded by this change: h_avg_emit, low_emit_avg and the sky payload are byte-untouched, which the farab gate (1080/1080 byte-identity + h_mismatch 0) and halo re-prove after the change.

6.1 FINDING — the 20×20 light box's corner margin is dark (pre-existing, now visible per corner)

While instrumenting the merged path it came out that bake_box fills the 20×20 box's four 2×2 corner-margin cells only for row 0 (the corner-strip write keeps the GDScript write order with no row offset — "every y overwrites, y_hi last wins — byte-exact", mesh.cpp bake_box); for rows > 0 those four cells stay at their 0 init. The smooth path's S3 sample (the outside diagonal) lands in those cells for the 4 edge faces of each corner column of a chunk, so exactly one corner of such a face reads light 0 → the face is non-uniform → it falls back to a per-face quad with one darkened corner. This is not new light: the old flat path read the same box through s_effl and got the same 0 (its in-plane max-probe sampled these cells too, just masked by the max); smooth lighting merely makes the single-cell dark corner visible instead of averaged away. At a chunk boundary the same corner point is darkened from both sides (symmetric across the seam), it is one vertex at the exact corner of a chunk edge, and it is bounded to faces whose outside diagonal is a chunk corner — classified as an acceptable boundary artifact (same class as AO missing the diagonal occluder at chunk corners). Re-fixing the box (per-row corner cells) would change the light field the flat path also consumes — that is a separate light-ticket decision, not this mesh ticket.

Frame cost: no frame-cost regression in the standing arms — r16: static p50 7 / p95 9 / max 31 ms, moving p50 8 / p95 9 / max 22 ms (the moving-vs-static A/B is the arm's own gate, green; the vertex census delta lands on the worker-thread build, not the frame). boundary r4 (one-shot): crossing frame p50 29 / p95 42 (the standing 35–42 band), crossing sweep p50 4.3 ms / p95 10.7 ms with one 15.2 ms single-sample max (the documented single-sample class — the sweep is scan-dominated, 5.4 ms); resident 93, 20/20 crossings. Standing-picture context: R24 crossing-frame p95 ~52 ms and the crossing burst ~4–5 ms vs the 10 ms gate (AC-0388) — the r4 sweep p50 4.3 ms is inside that class, i.e. no regression at the seam this change could affect (mesh attach after a rebuild).

If the census ever matters on real terrain, the cheaper shapes are, in order: (i) a per-cell corner-tag table (each cell is a corner for up to 3 neighbours — cut the ~11 reads/face to 4 table hits at the price of a 16×16×h scratch table), (ii) merging adjacent non-uniform faces when their 4 corner tags agree pairwise (extends the §1.3 uniform merge). Not taken: the measured +2–4 ms sits on the worker thread and the R6 column is a synthetic worst case.
