3. The lifetime hypothesis — tested and refuted

Hypothesis (the ticket's): a chunk dropped from staging while something still holds a reference to it would be BOTH a rising drop counter AND a use-after-free. Test, in the order the evidence lands:

  1. Static — the queue holds keys, not references. _col_pending holds "cx,cz" strings (_stage_check: _col_pending.append(key)). A dropped entry frees nothing and dereferences nothing. "A dropped stage leaves a live reference" is false at the staging layer by construction — the staging lane cannot be the UAF's reference holder.
  2. Static — the free path tells every holder. _free_chunk_key (world.gd 10333–10383) erases the chunk's key from every key-indexed holder in one synchronous pass (queued_keys, fluid_dirty, tex_refresh, _eff_cache, _face_blk, _bl_want, star_owed/star_remesh/star_seed_count/star_seed_us, promo_* counts, _far_promo_owed, _promo_build, _stream_outside, _real_demote_owed, and the staging queue itself), then _col_checkin (1405–1426) detaches the high MIs to the pool and queue_free()s the StaticBody3D collision bodies before _pool_reset() drops the slab data. _enter_candidate (the r+1 candidacy, 10278–10302) does the same for the maps a candidate must not keep.
  3. Runtime — the two new censuses, from the one-shot boundary r4 (20 crossings, full walk): staged_drop_stale 0 (the free path never failed to erase before the drain saw the dead chunk) and staged_drop_holder_residue 0 (at every chunk death and every stale drop, none of the 18 key-indexed holders retained the dead chunk's key; zero STGPROBE detail lines in the log). The "something still holds a reference" case did not occur once in a full r4 walk.
  4. The crash site is not reachable from the queue. The AC-0403 read is a main-thread slab_cell → slab_getbits i[bo] on a live chunk's slab PBA buffer (the chunk is in the chunks map; a dead chunk node would give a GDScript script error, not a silent SIGSEGV). The queue never touches slab data. The UAF's proven class (C6: slab-object memory death / engine-level corruption) lives in the slab-buffer lifetime — the PBA-wrapper refcount edge (AC-0214's shallow-handle note) or the engine itself — a layer the staging drop cannot reach. Shared lane (chunk lifecycle churn), no shared mechanism.

Verdict: not one bug. The counter rose because the carve-era world stages more in-progress builds (benign, now permanently diagnosable via the cause split); the UAF is a separate defect in the slab-buffer lifetime that the read-site guard cannot catch — as AC-0403 already stated.

5. The sanitizer question

  • ASan — infeasible on this box, verified both ways (the "only the extension needs instrumenting" reading was correct in scope but not in outcome): 
    $ g++ … -fsanitize=address … libchunkio-asan.so   # builds fine in 41 s (needs -DASAN_ENABLED —
                                          # godot-cpp defs.hpp #errors without it: first-class support)
$ godot --headless --quit                     # rc=1: "ASan runtime does not come first in initial
                                              # library list" (the .so is dlopen'd late)
$ LD_PRELOAD=$(g++ -print-file-name=libasan.so) godot …
                                              # rc=1: "trying to dlopen libchunkio.so with RTLD_DEEPBIND
                                              # flag which is incompatible with sanitizer runtime"
                                              # (sanitizers issue 611)
    Godot loads GDExtensions with RTLD_DEEPBIND; the ASan runtime refuses to back a DEEPBIND library. The only ASan route left is an ASan-built engine (out of scope for this turn; a coordinator-lane decision).
  • Valgrind memcheck — the substitute (no instrumentation, works on the real binary). Soak script .scratch/AC-0408-asan/vg_soak.sh (resumable, per-run DONE markers, 90-min caps): the exact AC-0402/AC-0403 crash recipe AWECRAFT_LOGIC=lightstate AWECRAFT_LS_RADIUS=16 ×4 + the player arm (the other crash caller) ×1, --tool=memcheck --leak-check=no --track-origins=yes --num-callers=50 --error-exitcode=99, production .so. Launched as a managed background job; state at delivery in §7 (the soak is the slow part: valgrind runs the 27-s recipe at roughly 15–20× wall).
