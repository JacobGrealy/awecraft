AC-0460 stage 4 — the warp, in native code

Coordinator contract. Medium builder applies it with tasks/templates/implement.md. Stage 3 measured the warp at 8.8 ms per chunk / 1.231 us per vertex — 73% of the 12 ms FACE_STREAM_BUDGET_MS for one chunk — so it is not shippable as a GDScript loop. This stage moves the same mapping into the native lane as a drop-in post-pass: same place in the pipeline, same data, native speed. The emitters are not touched.

1. Goal

The identical warp output, computed in C++, materially faster, with a measured before/after and a parity proof against the GDScript reference.

2. Toolchain (verified by the coordinator, 2026-10-20)

Build with PYTHONPATH=.scratch/scons-target python3 -m SCons -C gdext platform=linux target=template_release — SCons is installed at .scratch/scons-target and an incremental build takes ~24 s. godot/bin/libchunkio.so is a build output: never commit it, and never edit it by hand.

4. Edit shape

  • The native method. static PackedVector3Array warp_face_verts(PackedVector3Array verts, int face, int ccx, int ccz, double R), bound as warp_face_verts. For each vertex (lx, ly, lz) it must reproduce EXACTLY the GDScript mapping that stage 1-3 validated, including the deviation the builder corrected at AC-0458: the chart coordinate is the continuous inverse of the legacy local-X layout — non-mirror u1024 = ccx*16 + lx, mirror u1024 = ccx*16 + 16 - lx — with u = u1024 / 1024, v = (ccz*16 + lz) / 1024, and the position (R + ly) * normalize(sm_uv_to_world(face, u, v, R)) - (0, R, 0). Use the double-precision helpers so the parity tolerance is met.
  • The call site. In _warp_face_slabs, when the extension exposes warp_face_verts, call it per surface and write the result back; otherwise fall back to the existing GDScript loop. Keep the stage-3 timing statics around whichever path runs, so the comparison is like-for-like.
  • Nothing else changes: flag off still does nothing at all; the node identity assignment, the occluder derivation and the warp's inputs/outputs stay exactly as they are.

5. Parity probe (tasks/AC-0460/native_parity_probe.gd)

  • Load the extension the same way the game does; for a sample of face chunks (faces 2..11, both mirror classes), build a deterministic pseudo-random vertex set in local metres covering the chunk's extent.
  • Compute the reference in GDScript with the stage-3 _warp_cell_point-equivalent formula, and the native result, and report the max per-vertex distance.
  • Expected: max parity error <= 1e-4 m. Also assert the native function returns the same array size it was given.
  • Negative control: perturb one input vertex and confirm parity breaks (negative_detected).

RESULT keys: ok, chunks, verts, max_parity_m, negative_detected, fails (JSON).

7. Acceptance

The native warp reproduces the validated mapping within 1e-4 m, the measured cost drops materially, and the flag-off path stays untouched. A stale or missing extension must degrade to the GDScript path rather than crash.

8. Risks

(1) Double vs float: the GDScript reference is float32 Vector3 while the C++ path can use doubles — that is exactly why the parity bound is 1e-4 m and not 0. (2) A stale .so would silently use the fallback: the probe must assert the native method EXISTS, not just that the result looks right. (3) Do not "optimise" by interpolating a coarse grid — the seam guarantee depends on evaluating every vertex exactly.
