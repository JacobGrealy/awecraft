AC-0311 RE-BAKE — the satellite body textures, re-baked from the current (post-port) world and re-shipped

Bounded piece: the RE-BAKE + RE-SHIP of the 12 per-face satellite textures owed by AC-0311 piece 3. Seed 44 (canonical), R = 4000, W = πR/2 = 6283.185, SEA = 126, HMAX = 384. No render tier, no streaming change, no product-behaviour change — this is an asset regeneration. Evidence is numeric by construction (the builder does not open images; the coordinator views the 12 PNGs against the stated expectations in §6). All runs: HOME=/tmp/dsh_home, ulimit -v 8388608, one godot at a time, no R50, no load arm, no 3-D renders. No commits, no TASKS.yaml edits.

WHAT THIS CLOWS. Piece 3's verdict was mechanism-only, no REBAKE (AC-0311-results.html §12.5): the salt fix made the in-engine bake salt-consistent with the world, but the 12 shipped seed-44 textures in godot/assets/satellite/ were PRE-PORT (baked by AC-0310 from the flat-frame world, with the per-face seed salt still on faces 2–11). The sphere-domain port changed the far generation lane, so they were owed a re-bake + re-ship. This run regenerates all 12 from the current world, re-ships them to godot/assets/satellite/, and proves the result against the engine. Outcome: the 12 re-baked textures are byte-identical to the in-engine bake on all 12,582,912 pixels (§4), the permanent variance guard passes on every face on the written bytes (§3), and the game now loads the new textures via a re-import (§7).

1. What was re-baked, from what, and how

Twelve 1024×1024 per-face satellite textures (satellite_face00.png … satellite_face11.png, RGB8 PNG) were re-baked from the far column payload of the current, post-port world — exactly the same pipeline AC-0310 used, reused rather than rewritten:

  • Dump (godot): .scratch/AC-0311/ac0311_far_dump.gd (adapted from .scratch/AC-0310/ac0310_far_dump.gd) instantiated AweGen via ClassDB and called generate_far for all 196,196 chunks — the same call the demotion path and the satellite bake make. The only change vs the AC-0310 tool is the keying, now mirroring satellite_body.gd:_gen_one (post-port): one seed everywhere (the per-face salt seed^(face*1000003) is dropped) and (face, R) threaded raw into both lanes — generate_far(cx,cz,seed,384,126,0,R) for the home pair, generate_far(f*64+ccx, f*64+ccz, seed,384,126,f,R) for faces 2–11. Output .scratch/AC-0311/far_dump.bin (44-byte header + 196,196 × 1036-byte records, magic AC0311F1, identical layout).
  • Bake (python, numpy): tasks/AC-0311/ac0311_rebake_satellite.py (adapted minimally from tasks/AC-0310/ac0310_bake_satellite.py). Only paths/metadata moved: DUMP → the new dump, OUTDIR → godot/assets/satellite/ (the shipped location), STATS → tasks/AC-0311/ac0311_rebake_stats.json, FCC_JSON → the AC-0310 fcc probe, cost log → the new dump log. The pixel convention, the colour/shade recipe, the census, the roundness checks and the permanent variance guard are byte-identical to the P2 script (including the P2 index/gradient fixes). Colours reuse tasks/AC-0310/ac0310_fcc_probe.json — the fcc top-face colours are an atlas-tile property (atlas + data.gd web tints), untouched by the generation-lane port.

numpy: taken from the workspace-local venv .scratch/pylib (numpy 2.5.3 — the same one AC-0310 used, PYTHONPATH=.scratch/pylib). Nothing was installed.

Per chunk the payload is [H u16×256 LE][biome x256][top x256] (slot = lz·16+lx). The bake maps each texture pixel to one surface column and writes: ocean (H < SEA) flat unshaded water colour (the water surface is the plane S = max(H, sea)); land (H ≥ SEA) fcc top colour × lambert, lambert = 0.45 + 0.55·max(0, N·L), N = normalize(−∂H/∂u, 1, −∂H/∂v) (clamped central differences, 1 m spacing on the home pair; s·(1, ½|½, 1) on faces 2–11), fixed sun L = normalize(0.4, 1.0, 0.2). Stored = linear_to_srgb(colour) — an unlit bake the render tier modulates. Pixel convention: pixel (i, j) = chart point ((i+0.5)/1024, (j+0.5)/1024); faces 2–11 one cell per pixel (with the face_mirror_x lx flip on faces 2–5, 8–9); faces 0/1 the 1 m column at the pixel centre's flat position (floor of the home_uv inverse). Face 0: i-axis = flat +x (left = midline x=0, spawn at left edge mid-height); face 1: i = x from −3141 (left) to 0 (right).

4. DIFFED AGAINST THE ENGINE — the in-engine bake is the canonical reference

It was diffed against the in-engine bake — the GDScript SatelliteBody bake the game itself runs, which is the canonical reference (it was correct in AC-0310 and the one the shipped PNGs are compared to).

Which faces moved most: by fraction of pixels changed — face 3 (95.3 %), then 9, 11, 10 (93–92.7 %); by mean per-pixel shift — face 9 (93.0), then 5, 11, 3 (~87–91). Faces 0/1 are the clear outliers at the small end (66–67 % of pixels touched, mean |Δ| ≈ 6, about 2.5 % of full scale) — the home pair never carried the salt, so only the (d,δ) substitution moved them. Concrete class-level example: face 10's snow-grass pixel count jumped from 119,707 (pre-port) to 405,106 — it is now the snowiest face on the planet, where before it read as a flat green plain.

Player-visible? Yes, on faces 2–11: with ~90 % of pixels shifted by 18–36 % of full scale, those faces are plainly different terrain — a full re-roll, not a re-light. The home pair (0/1) reads as the same planet (mean Δ ≈ 6/255) with a faint re-shade. At the satellite's 4 m texel size the home-pair change is below the eye; the side faces are not.

6.1 What a viewer should expect to see on each face (the 12 PNGs in godot/assets/satellite/)

Files: satellite_face00.png … satellite_face11.png (1024×1024 RGB8, 418–568 KB each — up from the pre-port 252–449 KB, a real 2-D texture is less compressible). A viewer checking them should see exactly this (the builder did not open them; §4 proves the bytes are the engine's own bake):

White/cream snow fields, tan sand speckle, and thin flat-blue ocean veins. Still not a blue marble: the post-port planet is 98.88 % land (ocean 560,350 of 50,226,176 columns = 1.12 %, up slightly from pre-port 1.07 %); ocean is 0.88–2.74 % per face as flat unshaded veins, not deep seas. Nothing is a flat plain or a set of bands.
  • face 0 (home, +Y even): left edge = the x = 0 midline (spawn at left edge, mid-height); the finest 1 m grain of the set. 1.0 % ocean veins, 268,953 snow px (upper/negative-z side), 94,324 sand px; H 109–212. Visually near-identical to the pre-port face 0 (the §6 subtle class).
  • face 1 (home, +Y odd): mirror across the left edge (x −3141 → 0); 1.0 % ocean, 217,416 snow px; H 102–212 (one of the two faces touching the global H floor 102). Also the subtle class.

7. Re-ship — the assets the game loads are the new ones

The 12 re-baked PNGs were written to godot/assets/satellite/ (the shipped location) and the project was re-imported (godot --headless --path godot --import, 8 GB cap, one godot, rc 0). The import re-imported all 12 satellite PNGs; 12/12 .godot/imported/*.md5 sidecars now track the new PNG source md5 (e.g. face 00: source_md5="84f04068…" = the new file), and the .ctex payloads were rewritten (dest md5 changed). So a game load of res://assets/satellite/satellite_faceNN.png remaps to the re-imported .ctex = the new bytes, not the pre-port ones. This is a re-ship, and the loaded assets are the re-baked ones. (The .import sidecar path= lines are unchanged — the .ctex filename is derived from the source name + a stable hash — but the payload behind them is the new texture.)
