AC-0051 - user bugs: tools have no held 3D model AND no pixel-art icon

Report (user 2026-08-20)

"when i use my axe or pick it does not even look like im swinging my axe or pickaxe" + "the axe does not even have an icon, nor do any of the other tools i think. it should look like a pixel art representation of the 3d pixel model in the item list"

Reference

MC-exact rule (AGENTS.md §Game semantics reference; minecraft.wiki/w/Tool, /w/Item). Icons should be the pack's actual pixel art: the Faithful mcpack ships real item textures at textures/item/*.png (806 of them, verified present), already extractable via the existing atlas pipeline.

Root cause (AC-0049 research G3 - tasks/AC-0049/AC-0049-research.html - READ IT FIRST)

  • Held non-block items render as a flat solid-color billboard: _update_held (godot/player/player.gd ~357-377) -> held_sprite with _tint_tex(item["icon"]); held_box is only used for blocks.
  • UI icons: _setup_icon (godot/ui/inventory.gd ~447-465) fills with the item's flat color; Data.tiles is empty (data.gd:143); blocks_atlas.{png,json} has block tiles only.
  • No per-tool 3D model exists at all.

Existing infra (reuse - do not reinvent)

  • Atlas pipeline: godot/core/atlas.gd - Atlas.import_pack(pack_path) extracts mcpack (repo root Faithful-32x-1.21.11.mcpack) into res://assets/minecraft/textures/..., then builds assets/blocks_atlas.png + .json of 32x32 tiles (json: id -> {top/side/bottom: [x,y,w,h]}). Item textures live at textures/item/ in the pack.
  • Held viewmodel: player.gd hand_root / held_box (block) / held_sprite (flat item billboard) / held_fist; swing system animates hand_root (SWING_DURATION 0.1, AC-0048 loop) - anything parented to hand_root swings for free.
  • Item ids live in godot/autoload/data.gd (100 stick, 104 leather, 105 iron ingot, 107 diamond, 109 iron sword, 111-114 pickaxes wood/stone/iron/diamond, 115-118 axes, 119-122 shovels, 123-125 wood/stone/diamond swords, 127-138 armor 3 materials x 4 pieces, 139 bucket, 140 water bucket, 141 lava bucket, 142 bow, 143 arrow, 145 string, food ids, etc - READ data.gd for the authoritative list; item display color is items[id]["icon"] or similar). Tool types are already known to the matcher (data.gd TOOL_BLOCKS / block_tool).

Part A - pixel icons (all items, from pack textures)

  1. New import step (extend atlas.gd or a sibling script, same style): extract textures/item/*.png, build assets/items_atlas.png + items_atlas.json: {item_id: [x, y, w, h]} single-sprite-per-item. Map every item id in data.gd to its mcpack texture name (wooden_pickaxe, stone_axe, ..., iron_sword, leather_chestplate, bucket, water_bucket, bow, arrow, ...). Items whose texture is missing fall back to flat color (never crash). 32x32 native tiles, same as blocks.
  2. Expose lookup (e.g. Atlas.item_rect(item_id) or Atlas autoload var) - single source of truth.
  3. UI icon path: _setup_icon (inventory.gd) - if item has an atlas tile, draw it (texture-region on the slot Control, scaled to fit the slot like block tiles already work); else keep flat color fallback. This covers the E-inventory, storage, hotbar, armor slots AND the left "Craftable" recipe list for free (they all route through _setup_icon).
  4. Held non-tool items (food, buckets, arrows, bow, armor in hand): replace the flat _tint_tex sprite with a textured sprite (ItemTexture from items_atlas tile; keep the same quad size/position). Blocks keep held_box; tools go to Part B.

Part B - voxel 3D held tools (pickaxes/axes/shovels/swords, all 4 tiers)

  1. New: a per-tool-type voxel viewmodel built from plain BoxMeshes (1 voxel = 1x1x1 box, ~0.12 scale) parented to hand_root (sibling of held_box/held_sprite) so the EXISTING swing animation drives it - no new anim code.
    • Handle: 3 voxels vertical (1x3), wood-brown for wood, gray/white/diamond-colored shaft tint is fine (keep one handle color + tool head tinted per tier via items[id]["icon"] color - simplest honest approach).
    • Pickaxe head: 3 voxels across the TOP of the handle (x -1..1 at handle top), tier tint.
    • Axe head: 2 voxels at handle top (one directly above the top, one to the +x side), tier tint.
    • Shovel head: 1 voxel (slightly taller/wider, 1x2 acceptable) at the BOTTOM of the handle, tier tint.
    • Sword: 3-voxel vertical blade, bottom 2 = handle tint (leather brown), top = tier tint (slightly brighter acceptable).
    • Bow (142): no 3D model needed - textured icon sprite is fine (MC bow held model is complex); document it.
  2. _update_held routing: selected item is a tool (pick/axe/shovel/sword family by id range/type in data.gd) -> show voxel tool (correct type + tier), hide held_box/held_sprite/fist; block -> held_box as today; non-tool item -> textured sprite (Part A); empty -> fist. Selection/tier must update correctly when switching hotbar slots (the existing _held_key change mechanism already fires - reuse it).
  3. Orientation: static pose matching "held at 45deg" look (rotate the tool group so the handle points up-back-right like MC's first-person items); per-tool minor position offsets to keep it centered in the bottom-right viewmodel area. First-person only is correct (external cameras show whatever the model is - fine).
