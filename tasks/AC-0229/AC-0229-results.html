AC-0229 — dynamic per-frame mesh budget (speed + render distance) — results

GDScript task (no C++/.so touched). The AC-0224/0225 drain cap (stream_ho_cap, godot/world/world.gd threadmesh_poll) now reads the AC-0225 chunks_per_frame slider value (1-100, default 3) as the BASE burst and scales it by the player's horizontal speed and the render radius — higher when moving fast or at a large render, lower when still — clamped back into the slider range (1-100) so the manual slider still bounds the burst from above. Spec: tasks/AC-0229/spec.html. Gate logs: .scratch/AC-0229-gates/.

The dynamic scaling (what it does)

stream_ho_cap = clampi( roundi( base × speed_factor × radius_factor ), 1, 100 )

base           = Settings "chunks_per_frame" (the AC-0225 slider, read every
                 process frame exactly as before; AWECRAFT_TM_HO preloads it)
speed_factor   = 0.5          while still  (player < 0.5 m/s, or no player)
                 s / 4.3      (s = smoothed horizontal speed, 0.3 lerp —
                               converges ~200 ms, ~250 ms back to still after
                               stopping; WALK reference = player.gd WALK 4.3)
                 clamped [0.5, 12.0]   (50x flight = 215 m/s saturates 12.0)
radius_factor  = render_radius / 16 clamped [1.0, 2.0]   (the ahead-ring width
                 grows ~linearly with R: ~14 new chunks per chunk moved at
                 R16 vs ~32 at R50; R≤16 keeps 1.0 — every r4 arm unchanged)

Speed is sampled once per process frame from the player's POSITION delta
(not player.velocity — that is input-driven and stays ~0 while harness fly
phases teleport player.position directly, so the position delta is the only
signal that sees harness motion).

Reference points (base = 3 default):
  R16 still -> 2 | R16 walk -> 3 (AC-0225 no-op point) | R16 4x fly -> 12
  R16 50x fly -> 36 | R50 still -> 3 (AC-0224/0227 drain profile untouched)
  R50 walk -> 6 | R50 50x fly -> 72 | slider 100 anywhere -> clamps to 100
Why the two standing arms are provably p95-stable: the R16 arm's measured phases sit at the walk reference (speed factor 1.0, radius factor 1.0 → cap = base = 3, the AC-0225 behavior) and the perf R50 arm has no player (speed 0 → 0.5 × radius_factor 2.0 = exactly 1.0 → cap = base = 3). Both standing gates run the IDENTICAL cap as before; the dynamic budget only moves the cap in the fast / large-render scenarios the task targets. The loading-window pace (LOAD_TM_HANDOFF), the UNCAPPED shutdown poll-drain, the edit-lane exemption and the hb_max 64 bound are all untouched.
