Registry notes (verbatim, quoted):

1) User Story: The single biggest share of our longest frames is time we cannot account for - our own profiler does not see the flying, the planet drawn from orbit, or the hundreds of physics bodies - so "we know what is slow" is false for the largest piece of it.

2) Technical Details:
FOUND BY AC-0381's re-review (2026-10-01, tree f6dd516): the engine-side gap is **62.6-71.9% of the longest frames** (the max frames measured at 85 and 160 ms), the same shape AC-0352 measured at 68% - and the new and important part is that its interior is now SUSPECTED-UNMEASURED rather than merely unattributed: **no counter in this project sees the 6-DOF flight path, the satellite body draw, or the 466 collision bodies**. All three are new or newly-prominent since the last review (AC-0145, AC-0310, and the body count from the collision work), so the largest share of the worst frames grew exactly where our instrumentation does not reach.
WHY THIS IS A TICKET AND NOT A FOOTNOTE: every other bottleneck in this project has a counter and a history - DRAIN, HANDOFF, RECENTER, MISC, COLLIDE, the storm ring, GENMS. The one that now dominates is the one with no instrument, which means the next performance ticket cannot be aimed at it and any change to those three systems is unmeasurable in the tail. This is the same class of defect as the four stale or flapping instruments this session repaired, except here the instrument does not exist yet rather than being wrong.
THE JOB: build the missing counters, then use them. Determine what CAN be measured in-process (the wprof partition brackets code we control) versus what is genuinely engine-side (Godot's physics server stepping 466 bodies, the render server drawing the in-tree instances, the satellite draw) - the second class needs either engine-side instrumentation the project already knows about (the AC-0338 standing row's labelled derivation, the RS/PS timing questions the storm work ran into) or an external sampler (the AC-0372 work built a /proc-based main-thread sampler and it is kept and re-runnable; extend it if in-process brackets cannot reach). Then attribute the gap with the same discipline AC-0381 used: state the tree SHA, state the REGION, distinguish a share from an absolute cost, and say which values are stable across runs.
A CAUTION FROM THIS SESSION, so the new instrument does not repeat an old mistake: do not build a gate that everything passes or a field that rides a variable process. Whatever you add should be able to FAIL visibly - negative-test it the way the AC-0310 bake guard and the AC-0379 straddler assertion were negative-tested, because those two are the only instruments added this session that demonstrably bite.
CONSTRAINTS: instrumentation-only - no behaviour change, genhash 25/25 byte-identical, G0 zero SCRIPT ERROR (not rc=0), the standing set green (ladder 20/20, meshprobe 1.0, halo ok, lightstate 0/0, r16 all sub-flags with far_holes 0/0 both bands, boundary r4 in band, the battery), and any new field or row goes into tasks/harness_data.yaml with the doc re-rendered and --check clean.
CONTEXT: read tasks/AC-0381/AC-0381-results.html (the split, the could-not-measure list and the instruments it says are needed), tasks/AC-0372/AC-0372-results.html (the kept /proc sampler), and the AC-0352 page for the original 68% figure.
