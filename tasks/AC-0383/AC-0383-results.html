1. Negative test — how the counters were made to fail

Pattern: AC-0310 bake guard / AC-0379 straddler assertion. Each counter carries a GUARD that trips if the counter silently stops seeing the work it is supposed to see: AWECRAFT_AC0383=blind arms the guards and disables the brackets — the code paths run, the counters record nothing, and each guard must print AC0383_GUARD FAIL … once after 60 frames. The cumulative-0-over-N-frames form is what makes it safe: a healthy run (bracket total > 0 µs over dozens of frames) can never trip it, while a blinded one must. The 60-frame threshold keeps it out of startup transients.

4. Engine-side: the per-frame gap split (runs A/B/C; worst-20 arm frames each)

Per-frame definition: gap = arm_ms − wp_ms (arm-side frame − the World._process frame inside it — one arm frame = one main-loop iteration = exactly one committed wprof row); eng = gap − plr − wphys (what remains is the physics-server step over N bodies + the render-server flush (headless no-op class) + remaining node callbacks + engine bookkeeping). The sampler's window = the arm frame's wall window (anchor: Δ = wall(result line) − t_ms_at_result; the script clock starts ~0.73 s after process start, expected — Time.get_ticks_msec() is the script clock). cpu_ms = main-thread utime+stime delta across the window, quantized to 10 ms jiffies — read the cpu% column as a bound class, and fracR/wchan as the classification.

The honest residual — what the instrument still cannot split: 95.0–97.3% of the gap is attributed to "main-thread CPU inside the engine" as a CLASS (proven CPU-bound by the external sampler), but the split inside that class — physics server over N bodies vs render-server bookkeeping vs other node callbacks vs main-loop bookkeeping — is NOT measured: in-process brackets structurally stop at the engine boundary, and /proc sampling sees the main thread but not its call stack. On this headless arm the render half is a no-op class by construction (the labeled-derivation convention), so the residual is expected to be dominated by the physics-server step of the 501–534 bodies — but "expected by construction" is not a measurement, and on a Forward+ build the split would be different. The instrument it would need: engine-internal RS/PS timing (the exact question the storm work hit — the project's standing answer is the AC-0338 row's labeled derivation, which is an instance-count argument, not a time) or perf record -g / a profiler build for the symbol level. Stated as a fraction of the gap: ~95–97% is class-attributed (main-thread engine CPU); within it, the physics-vs-render split is 100% unmeasured; the other ~3–5% (flight model) + ~0% (world physics) are fully attributed to named in-process code. That is the expected honest partial attribution for this ticket.

Caveats on the sampler columns: (a) cpu_ms is 10 ms jiffies-quantized (±10–20 ms per window — per-frame cpu% reads 90–116%); (b) the sampler attaches ~7.5 s after boot, so worst frames earlier than that (12 of 20 in run A, 9 of 20 in run B) have no CPU classification (their gap/eng split is still exact — it comes from the in-process clocks); (c) one arm frame can contain several physics steps (fixed 16.67 ms step) — the player/world per-window sums cover ALL steps in the window, so the split stays exact.
