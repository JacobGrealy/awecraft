AC-0458 — warp the face-lane placement onto shared vertices (flag off by default)

Coordinator contract, first ticket of the AC-0433 migration series. Medium builder applies it with tasks/templates/implement.md. Scope is deliberately narrow: the face lane only, behind a flag that defaults OFF, so the shipped game is byte-identical until a later ticket flips it.

1. Goal

Give the face lane's meshes a pointwise placement so two chunks that meet at a seam evaluate the same surface point, replacing the per-chunk least-squares fit that leaves the 2.19 m crossing / 3.73 m corner disagreement.

3. Edit shape

3.1 The flag. Read once per build: OS.get_environment("AWECRAFT_WARP") == "1" (an env var, like the project's other switches), defaulting OFF. Build a cached static var _warp_on resolved on first use. With the flag off the code path must be exactly the current one — no changed arithmetic, no reordering, so G0, genhash and every standing arm stay identical.

3.2 What the warp does (face lane only). After the C++ emitter returns a slab's arrays and before they are committed to the ArrayMesh, when the flag is on, rewrite each vertex from chunk-local metres to world metres and set the chunk node's placement to identity for that build:

  • For a vertex at local (lx, ly, lz) in face chunk (face, ccx, ccz): the chart cell is iu = ccx*16 + (15 - floor(lx) if mirror else floor(lx)) using the SAME mirror convention SM.face_local_x uses, and iv = ccz*16 + floor(lz); the sub-cell fractions are the fractional parts of lx and lz. Use u = (iu + frac_x) / 1024.0, v = (iv + frac_z) / 1024.0.
  • World position = (R + ly) * normalize(SM.uv_to_world(face, u, v, R)) - Vector3(0, R, 0), with R = Game.planet_R. Note the height axis: the legacy lane treats local Y as metres of height, so it enters as the radial offset, exactly as cell_to_world does. State in the code comment that this is the same construction as PlanetGrid.cell_to_world, on the legacy 1024 chart.
  • Normals: rotate each emitted normal by the same pointwise frame? Decision: leave normals untouched in this ticket and record it as a known limitation — the meshes here are voxel faces whose shading is vertex-colour/AO driven, and normal correction is part of the later tessellation ticket. Do not invent a normal transform.
  • Set the node's transform to identity for warped builds only (position 0, Basis.IDENTITY), because the vertices are now world-space.

3.3 Guard rails. The warp must not run for any lane, mode or call site other than the face build. If face < 2 or the face is not a face-lane build, log one line and skip warping (do not silently warp the home pair — that is AC-0460's job).

3.4 The probe (new tasks/AC-0433/warp_probe.gd). Pure SphereMath, no world: prove that under the warp construction, two adjacent face chunks' shared edge evaluates identically.

  • For a grid of adjacent chunk pairs on faces 2..11 (including the mirror class), take the 17 shared-edge vertices of both chunks, compute each side's world position by the §3.2 formula from its OWN local coordinates, and report the max gap.
  • Expected: max gap exactly 0 (the same chart point, the same evaluation). Report pairs and max_gap_m.
  • Report the same measurement under the LEGACY construction (SM.face_chunk_transform per chunk, local centres) for contrast, so the log shows what the warp buys. Expected: non-zero, order 1-2 m.
  • Negative control: perturb one side's v by one cell and confirm the gap becomes non-zero (negative_detected).

RESULT keys: ok, pairs, warp_max_gap_m, legacy_max_gap_m, negative_detected, fails (JSON).

5. Acceptance

With the flag off nothing moves (proven by the standing gates). With it on, the face lane's shared edges agree exactly across chunk joins, the probe shows the legacy gap it replaces, and the flag is the only thing standing between the game and the new placement.

6. Risks

(1) Cost: the warp evaluates uv_to_world per vertex, which is trig — the plan requires a cheap guard (only when the flag is on) but a frame-time measurement belongs to the later streaming ticket; do not optimise speculatively. (2) Flood fill/light: node transform identity changes the culling AABB, so the flag-on path may mis-cull; if an arm shows missing geometry with the flag on, record it as a finding for AC-0460 rather than patching the culler here. (3) The mirror convention is the easy mistake — the probe's negative control exists for exactly that.
