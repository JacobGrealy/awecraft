AC-0513 — prove the HDR/depth transition works BEFORE it replaces the renderer

Coordinator contract (written by me; filed by another agent). Medium builder applies it with tasks/templates/implement.md. AN ISOLATED FIXTURE, NOT A PRODUCTION CHANGE. The deliverable is a feasibility verdict backed by measured proofs, and "this API cannot do X" is a perfectly good result.

1. The requirement

"a transition technique proven to preserve depth, water and performance before it replaces the working renderer." So this ticket exists to de-risk: if the technique cannot do one of the nine things below in Godot 4.7.1, that must be discovered here, in a fixture, not after the working renderer has been replaced.

2. ⚠ USE THE SHARED PLAN'S CONCRETE PROTOTYPE, NOT ONE YOU INVENT

The filing is explicit: "Apply the shared plan's concrete two-source HDR/depth prototype, not an implementer-selected architecture." So read docs/satellite-lod-handover-plan.html first — sections p0, pipeline, blend, exceptions — and implement the architecture described there. If the plan's description is ambiguous or contradicts the 4.7.1 API, that is a finding to report, not an invitation to design your own.

3. The nine things that must be proved (each is a gate, not a checklist item)

  1. Same-frame SubViewport dependencies — the second source must be readable in the same frame it was rendered, not one frame stale.
  2. Pre-tonemap HDR — the fixture must prove it is compositing before tonemapping (values above 1.0 survive to the blend). This is the one most likely to fail silently: a post-tonemap blend still "works" and looks plausible while destroying the whole point.
  3. Reverse-Z — correct depth comparison under the engine's depth convention.
  4. Actor occlusion in BOTH draw orders — test each order; a technique that only works in one is not usable.
  5. Main screen-depth readers — whatever reads depth on the main screen continues to read it correctly.
  6. Alpha-tested foliage — transparent cutout geometry must not break the depth composite.
  7. Water / refraction channel choice — water reads a colour/depth channel for refraction; prove which channel, and that the composite does not corrupt it.
  8. Resize — the technique must survive a window/resolution change (render-target recreation).
  9. Teardown — clean destruction, no leaked resources or dangling buffers.

4. The numeric acceptance the filing specifies

  • Linear 0/1 midpoint = 0.5 ± 0.002. Blend two sources whose linear values are exactly 0 and exactly 1 and measure the midpoint. This single number is the proof that the blend is linear and pre-tonemap — if the fixture is post-tonemap or in sRGB, the midpoint will not be 0.5 and the ±0.002 tolerance is what makes it a proof rather than an impression.
  • Selected depth error ≤ 1 mm on the defined case.

5. What "isolated" means here

Production behaviour unchanged. Build the fixture as a separate scene or an env-gated mode that the game never enters by default. Do not modify the game's render pipeline. If the fixture needs a CompositorEffect, it is added to the fixture, not to the shipped scene. At the end, the product must behave byte-identically — state how you proved that (genhash and a render comparison).

8. Acceptance

A verdict on all nine capabilities with evidence; the linear midpoint at 0.5 ± 0.002 with the post-tonemap contrast reported; the ≤1 mm depth error on a defined case; production provably untouched and the fixture provably unreachable by default.

9. Risks

(1) Inventing an architecture instead of applying the shared plan's — explicitly forbidden. (2) A post-tonemap or sRGB blend that looks right and passes every qualitative check; the ±0.002 midpoint is the only thing that catches it, so measure it. (3) Quietly skipping a capability that does not work, which defeats the entire purpose of a spike. (4) Touching the shipped pipeline "just to make the fixture run". (5) Treating llvmpipe's behaviour as the product's (label it).

10. Fences

  • No git commit/push/add; no tasks/TASKS.yaml (another session writes it); no new tickets.
  • No production pipeline changes. No edits outside §6. No self-designed architecture.
  • If the shared plan's prototype cannot be applied as written — ambiguous, missing, or contradictory to the 4.7.1 API — write PLAN-INSUFFICIENT: <what is missing, file:line> and EXIT with what you established. Do not substitute your own design.
