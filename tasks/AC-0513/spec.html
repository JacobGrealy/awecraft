# AC-0513 — HDR/depth prototype feasibility (journal)

## Coordinator pre-work (round 121): the 4.7.1 API REFLECTED FROM THE ENGINE, not from docs

The filing and the shared plan both demand that API semantics be "recorded from Godot 4.7.1, not inferred from an older documentation page". Done before handing to a builder, because it is cheap (a headless reflection probe, no render) and it decides whether the whole technique is even available.

**Probe:** `.scratch/AC-0513/apiprobe.gd`, run as `godot --headless --path godot -s ../.scratch/AC-0513/apiprobe.gd`. Engine reports **`4.7.1-stable (official)`**, hash `a13da4fe…`.

**Results — the three classes the prototype depends on all EXIST:**
- **`CompositorEffect` EXISTS, 15 methods:** `_render_callback`, `set_effect_callback_type`, `set_access_resolved_color`, `set_access_resolved_depth`, `set_needs_motion_vectors`, `set_needs_normal_roughness`, `set_needs_separate_specular`, plus the enabled accessors. **So both "access resolved colour" and "access resolved depth" are first-class switches** — which is the good case for the plan's pre-tonemap requirement: the engine offers the resolved-colour/depth access the prototype needs rather than requiring a guess.
- **`RenderSceneBuffersRD` EXISTS, 27 methods**, including `create_texture`, `create_texture_view`, `get_color_texture`, `get_depth_texture`, `get_render_target`, `get_internal_size`, `get_target_size`, `get_texture_slice`, `clear_context`, and the scaling/AA/taa/debanding accessors. So owned-export copies (the plan's "copy borrowed scene buffers into stable render-thread-owned exports") are supported by `create_texture`/`create_texture_view`.
- **`Compositor` EXISTS** (`set_compositor_effects`, `get_compositor_effects`) — so attaching an effect to a viewport is possible.
- `RenderSceneDataRD` reported **0 methods** through `ClassDB.class_get_method_list(cls, true)`; that is likely an introspection quirk (a singleton-ish or abstract class) rather than proof it has no API. **The builder should probe it directly rather than trusting this line.**

**What this does NOT settle, and the builder must still measure:** the actual **callback enum semantics** (`set_effect_callback_type` — which point is pre-tonemap), whether the resolved colour/depth are genuinely pre-tonemap at that callback, **reverse-Z depth convention**, same-frame SubViewport dependency ordering, and everything about water/refraction channel reading. Existence of the API is not proof of the *semantics* the plan requires — that distinction is the whole reason this ticket exists.

**The 0.5 ± 0.002 midpoint test remains the decisive measurement** and is unaffected by any of the above.


## Coordinator note (round 122): the spike ran, verdicts are recorded, and the ticket is NOT closeable yet
The builder ran and produced the full evidence page plus deviations D9-D14. Two of the nine capabilities **fail as implemented**, and its own open list (a)-(d) are FIXTURE repairs that could change the verdicts — so closing now would be premature and would record a half-answer as an answer.
WHAT THE SPIKE ESTABLISHED, and it is genuinely useful: the pre-tonemap HDR read **channel works** (compute copy to an owned RGBA16F, read back ok at 0.186 ms/frame at 640x360); reverse-Z is **confirmed**; main-pass depth readers work; alpha-tested foliage is **proven both ways**; the water colour composite **resolves** (mm solved -0.36/+0.098/+1.46); **100 resize cycles** ran with the export copy intact each time; teardown is clean (objects 1706 -> 1683, resources 27 -> 26, clean exit).
THE TWO REAL FAILURES, which are exactly what this ticket existed to discover: (1) **SAME-FRAME READ FAILS** — with `UPDATE_ALWAYS` the census shows a ONE-FRAME LAG (det 598/599 inverted, sat 299/599 alternating), i.e. the resolve is reading the previous frame, which is the "merely coincidental child-node order is not a render graph" trap the shared plan warned about; (2) **<=1 mm DEPTH FAILS** — reverse-Z itself is confirmed, but a TRANSPARENT FULLSCREEN PASS PUBLISHES ITS GEOMETRIC DEPTH RATHER THAN THE `DEPTH` VALUE IT ASSIGNS, so the resolve cannot hand a chosen depth downstream. The midpoint gate also did not produce a number because the fixture's blend band carries 0 in the satellite half — a WIRING DEFECT in the fixture, not yet a verdict on the technique.
SIX API FACTS THE RUN SETTLED, worth harvesting rather than rediscovering: GDGLSL markers are rejected by `shader_compile_spirv_from_source` (raw GLSL only); compute lists are handle-based and `compute_list_end()` takes no handle; `RDUniform` has only type/binding/add_id; `return` is illegal inside `fragment()`; the scene colour RID is sampleable but NOT copyable; and — the one that costs hours if missed — **a `SubViewport` must be given its shared `World3D` AFTER `add_child`**, because setting it before makes the viewport render its own empty world and every source sample reads 0.
OWED BEFORE THIS CAN CLOSE: (a) repair the blend-band wiring so the midpoint produces a number at all; (b) close the same-frame dependency and re-measure the parity census; (c) publish terrain depth through geometry (a depth prepass) and re-run the <=1 mm case against the 24-bit quantum (0.0954 mm at 40 m); (d) swap the fixture's leaf/hole sample points, which are labelled inverted against the 4x4 texture layout. THEN every number needs a hardware-GPU re-measure — llvmpipe cannot answer timing, depth-buffer format or leak counts, and `get_driver_allocation_count` returns 0 here.

CLOSED (round 122). THE SPIKE ANSWERED, AND THE ANSWER IS **P0 REJECTS THE TECHNIQUE AS SPECIFIED** — which is precisely the outcome the shared plan pre-authorised ("P0 is explicitly allowed to reject it") and the reason it existed: to discover this BEFORE it replaced the working renderer.
THE ONE GATE THAT PASSED IS THE ONE THAT PROVES THE INSTRUMENT: **linear 0/1 midpoint = 0.500000, 8 of 8 samples**, in the pre-tonemap `R16G16B16A16_SFLOAT` export. And the contrast values make it a proof rather than a number: an **sRGB-domain blend of the same endpoints reads 0.214041**, an **AGX post-tonemap blend reads 0.398039 against the pre-tonemap 0.674510 (-0.2765)**, and the 8-bit display reads 188/255 = 0.502886 decoded. So the fixture demonstrably measured the pre-tonemap linear stage and would have FAILED had it measured any other. The round-2 wiring defect (satellite half reading 0) was repaired by bounding satellite coverage to +/-150 m with a source probe proving each half.
**BLOCKER 1 — THE SAME-FRAME SOURCE TEXTURE CANNOT BE OBTAINED IN 4.7.1.** Lag census after repairing round 2's echo instrument (which had been missing the sampled pixel): **lag-0 in 0 of 599 frames, from BOTH sources, with parity 599/599** — and the echo matches a CPU-read texel exactly, so the instrument is sound. Camera creation order moves the failure mode (7 -> 25). `POST_SKY`, `POST_TRANSPARENT`, `SubViewport.update`, `render_priority`, cull masks and a shared WorldRoot **all failed to produce a single lag-0 frame**. The conclusion is at the API level: **4.7.1 exposes no handle on "this frame's source texture"**, and a one-frame-stale resolve is exactly the "coincidental child-node order is not a render graph" failure the plan warned about. This is not a wiring bug to fix; it is the API saying no.
**BLOCKER 2 — A FULLSCREEN PASS PUBLISHES GEOMETRIC DEPTH, NEVER THE `DEPTH` IT ASSIGNS.** With an opaque prepass quad at -40.000 and `depth_draw_never`, the reader sees **41.16 m, a +1.16 m error, in EVERY sub-case** — including the decisive one where the pass explicitly assigns DEPTH 40.000 while its geometry sits 1 m away. So the resolve can never hand a chosen depth downstream, which defeats the plan's requirement that the resolve "write selected `DEPTH`" at all. The 24-bit quantum (0.0954 mm at 40 m) is not the limiting factor — the semantics are.
EVERYTHING ELSE, RECORDED SO THE WORK IS NOT LOST: alpha-tested foliage colour **passes** (and the correct alpha mode is `TRANSPARENCY_DISABLED` + `alpha_scissor_threshold` — with `TRANSPARENCY_ALPHA_SCISSOR` the leaves vanish entirely), with its **depth side failing at -919 mm** because an alpha-scissored plane writes no depth. Main-pass depth readers pass **with a transparent-reader requirement**. Water colour composite resolves. **100 resize cycles** ran clean. Teardown is clean. Actor occlusion is **partial** — far actors occluded in both orders, near actors only in the late order.
A BUILDER THAT VERIFIED INSTEAD OF COMPLYING, WHICH IS WORTH RECORDING: my predecessor run's own task (d) said to swap the leaf/hole sample points because its labels were "inverted". This run **measured instead** and found the labels were RIGHT and the requested swap would have CREATED the inversion (leaf colour at (-51,+2)/(-47,-2) against satellite at (-49,+2)/(-51,-2)). An instruction from a previous run is not evidence.
TWO CORRECTIONS TO EARLIER CONCLUSIONS: **4.7.1 has 29 sRGB DataFormats of 233** — round 2's "no sRGB format exists" was wrong; and round 2's echo instrument was defective, so its lag census was not trustworthy until repaired here.
ISOLATION HELD: g0 rc=0, **genhash 25/25 byte-identical to `genhash-r1.log`**, the fixture lives in untracked `godot/fixtures/` and is **unreachable from `main.tscn`**. Product unchanged.
STILL UNPROVEN BECAUSE LLVMPIPE CANNOT ANSWER IT: timing, the depth-buffer format behind the +1.16 m offset, leak counts (`get_driver_allocation_count` returns 0/-1 here), and whether real hardware can show lag 0. **Both blockers are stated as API-level findings with the configurations tried, so they can be re-tested on hardware rather than assumed permanent** — but on this engine version, with these APIs, the architecture as specified does not work.
