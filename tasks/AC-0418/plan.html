AC-0418 — plan: workers that hold no reference to the node

Builder: subagent. 2026-10-12. Tree at b5b1d5c (AC-0414 + AC-0417 + AC-0421 committed; the mitigation from AC-0414 §6 is in the tree). Fenced files untouched: main.gd / game.gd / debug.gd / drop.gd.

1. Goal

Close the mid-bake-exit use-after-free the AC-0414 run measured: a pool thread is inside a call to a method of the SatelliteBody node (the worker callables are the node's own methods), so when the process exits the scene-tree teardown frees the node's script instance under the running worker. The shipped mitigation (file-scope _mt_exit_aborted + the _exit_tree hook) only shrinks the window to the function epilogue — the worker is still inside the node's instance until it returns. The fix, per the ticket: workers that hold no reference to the node, shown to prevent the crash by counting deliberate mid-bake exits before and after (the exit status is the primary signal — the defect leaves a clean log), with the bake output proven byte-identical and its speed unchanged. Also: test the link to the AC-0403 stochastic slab-read crash and report the verdict with reasoning.

4. Reproducing the crash before the fix (on demand, counted)

The temporary satexit arm: boots a non-canonical seed (AWECRAFT_SEED=5432 → the bake is forced, sat_preload default ON → the sharded path), the AC-0414 hold engages, the sim band releases at the capped await (~48-50 s, loud line at 42 s), the player spawns, then — exit mode (AWECRAFT_SATEXIT=exit) — the arm waits until the requested stage (1 = a shard in flight, 2 = a face in flight, read from bake_progress_line()) plus a delay (AWECRAFT_SATEXIT_DELAY, default 5 s) and the dispatch quits: the process exits while bake workers are in flight. complete mode (AWECRAFT_SATEXIT=complete) instead waits for the boot bake to LOADED and reports its walls (the speed A/B + the bake-before-presentation proof) before a clean quit. Each attempt is one godot invocation; the exit status is the verdict (rc 0 = clean; rc 134/139 or a handle_crash line = crash), logged per attempt.

  • Pre-mitigation baseline (establishes "reliably reproducible before", the ticket's premise): the AC-0414 flag-set is temporarily disabled (one-line scratch edit of _exit_tree, restored before any measurement of the fix) — 5 stage-1 exit attempts.
  • As-shipped baseline (the tree this ticket starts from — mitigation in): 10 stage-1 + 2 stage-2 attempts.
  • After the fix: 15 stage-1 + 3 stage-2 attempts, expected 0 crashes. The before number is what makes the after number mean anything (the ticket's own clause).

7. The AC-0403 link — pre-registered verdict logic

  • AC-0403's crash ran on the canonical seed (default 44 → the res:// texture path → no bake in flight), at t≈27 s of normal play, with the faulting frame a main-thread slab read from the player's physics step / mob tick. AC-0418's fault is a pool thread inside a bake worker method at process exit. For this defect to be the cause of that one, the worker's VM/instance use would have had to corrupt slab memory in a run where no bake worker was running — it was not. Refuted as specific cause.
  • Same failure class, though: both are use-after-free / data-race shapes around pool threads + the node's script instance, with the class's signature (clean log, stochastic, a read site, multiple callers, no stable reproducer). The remaining candidates for AC-0403 are the streaming workers' concurrent VM use (threadgen/threadmesh run node methods from pool threads the whole time) and the PBA shallow-handle edge (AC-0403 §7) — this fix does not touch either (bake scope). Verdict wording decided by the measurements: link confirmed / refuted / still open, with the reasoning above either way.
  • Noted residual (not this ticket's scope): the streaming workers carry the same exit-race class at a much lower in-flight fraction (short calls vs the bake's minutes-long ones) — thousands of clean arm exits are the empirical bound; a follow-up ticket is the honest home if it ever surfaces.
