AC-0485 — what startup and the caches actually cost, in bytes and seconds

DEVELOPMENT-ONLY. Every figure on this page is Linux headless (llvmpipe box, 6-core i5-9400F, 64 GB RAM, git f37a66a, Godot 4.7.1) — development proxy evidence for the Windows-only product (AC-0124). The Windows acceptance run is specified in AC-0485-windows-protocol.html. No product number is claimed here. Measurement only: no cache, eviction or behaviour change; product code untouched — the generation hash of the 25-column corpus is byte-identical to the AC-0484 reference (25/25), and g0 is 0 script / 0 shader errors (gate section below).
THE §2 NUMBER, MEASURED AND STATED EARLY. The shared plan's provisional targets (3 s atlas bake / 8 MiB disk / 16 MiB resident / 64 MiB scratch / 64 MiB global cache) sit two to three orders of magnitude below the existing far-tier bake's IN-MEMORY working set: AC-0469 stage D measured that bake at 1,699,726 records = 1,740,519,424 B (1,659.0 MiB) of payload with a 4,823,572 KB (4,710.5 MiB) peak process RSS and a ~21-min wall per seed; this ticket re-measures the seed-45 path in the bake section below. Against the 8 MiB disk target that in-memory payload is a ~207× multiple (1,740,519,424 / 8,388,608 = 207.5×). But the 1.62 GiB is the IN-MEMORY bake payload, not the disk cache: what the far tier actually puts on disk is 12 × 1024² RGBA PNGs — 10,834,903 B (10.33 MiB) shipped for the canonical seed, and one comparable copy per non-canonical baked world in user://, i.e. ~1.3× the 8 MiB target on disk. So the reconciliation the coordinator owes is narrower than a raw 100–200×: the disk cache modestly exceeds the disk target (1.3×); the two-to-three-orders-of-magnitude gap is between the bake's IN-MEMORY payload / peak RSS and the disk/scratch targets (scratch: ~59×, bake wall: ~266–423×). Either the provisional targets describe the planned continent atlas (a different artefact than the shipping far-tier bake) — most likely — or the shipping bake cannot meet them. This ticket measures and quantifies; the decision is above it.

6. The meter negative control (E) — PASSES

Method: the stamped child process sleeps a known duration, then execs the engine (the sleep sits on the pipe's left side AFTER the stamp wrapper starts, so the meter's origin is unaffected and only the engine start is delayed — a placement bug that would have made the control a no-op was caught on the first sanity run). The actual sleep is self-reported in-log (@AC0485-INJECT nominal_us=… measured_us=…) because sleep(1) adds ~2–12 ms of fork/exec/jitter on this box. The engine's in-process t= clock starts at the engine's exec, so a pre-exec delay moves every wrapper-relative stamp and NONE of the t0-relative engine-internal numbers — exactly what the data shows.

The meter is sensitive 1:1: a known 56 ms startup delay moved the launch→milestone wall by 59 ms (the residual 3.1 ms is the exec overhead after the self-report point — constant across both injections). AC-0484 precedent for scale: its 5000 µs in-process injection moved the wall median 5,346 → 10,399 µs. The LD_PRELOAD shim route was investigated and set aside (deviations): strace proved the engine opens project files with DIRECT openat(2) syscalls — libc symbol interposition never sees them — and the shim fired in both the timeout wrapper and the engine (two processes inherit LD_PRELOAD), making the injected total ambiguous. The sleep wrapper is unambiguous. (Note for the Windows protocol: Windows user code takes file I/O through the CRT/kernel32, so the instrumented-.dll route there has no syscall-bypass problem.)
