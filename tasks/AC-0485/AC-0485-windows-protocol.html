AC-0485 — the Windows acceptance protocol

The handover for running this ticket's measurement on the target Windows machine. The Linux figures in AC-0485-results.html are development-only proxy evidence (llvmpipe box, AC-0124's Windows-only product); this protocol produces the acceptance column. It re-uses AC-0484's protocol (tasks/AC-0484/protocol.html, §8 is its Windows handover) and this ticket's corpus. The runners live in .scratch/AC-0485/ (plain bash + one Python stamp wrapper + one C shim — copy them over; the bash layer needs no adaptation, only the meter and the shim, per §5).

DEVELOPMENT-ONLY / ACCEPTANCE split. Every figure quoted from the Linux box is development evidence. The numbers this protocol produces on Windows are the ones the shared plan's provisional targets (docs/continent-biome-generation-plan.html §budgets: 3 s atlas / 8 MiB disk / 16 MiB resident / 64 MiB scratch / 64 MiB global cache) are set against. No speedup or budget claim is valid on the Linux column.

3. The trial design (identical to the Linux run)

  1. Five A PAIRS: pair i = (cold run, warm run) ADJACENT — cold deletes the user dir first, warm keeps the cold run's state. Drift hits both sides of the pair. Report median, p95, p99 and spread (min–max) per milestone, plus the within-pair cold−warm deltas (the paired comparison).
  2. Cache-state metadata with every run: the runner snapshots the user dir (file list + sizes + total) before and after each run, plus a contention snapshot (date, load, top processes, whether another engine was running) before each engine call. A contended run is INVALID — drop it, record it, never average it in. The Windows box is usually quieter; the rule does not relax.
  3. One engine at a time. On Windows the slot guard is: no second AweCraft process (Task Manager / Get-Process) while a measured run is in flight.
  4. Milestones (per A run): t0 (first stdout line / process start) → world created (SATDIAG configure) → first drawable: planet body (phase=LOADED) and first ground (first TMESHW) → first playable (the 41st first-TMESHW over the diamond keys |dx|+|dz| ≤ 4 around the spawn/continue chunk — the exact set the loading screen gates on) → save file written (cold runs). The parse is .scratch/AC-0485/parse.py (pure Python, runs on Windows).
  5. Wait buckets (AC-0484 attribution, re-used verbatim): TGENW wms = generation wall, TGENW wait = queue wait (wt − tenq), TMESHW wus = mesh build wall (includes the per-slab static-light pull — the C++ build self-lights and the pull is not separable without new instrumentation, the same honesty clause as AC-0484), STSEED wus = starlight seed wall. I/O is the colbytes arm (F) + the on-disk bytes (F1/F2). State the method; do not blend the buckets.

5. The meter and its negative control on Windows

  1. The meter: wrap the process stdout with a line-stamper (the Linux run used stamp.py; on Windows a 15-line PowerShell/C# equivalent: read the child's stdout line by line, prefix [<usec since child start>]). The engine's own t= fields (ms since process start, on GENCHUNK/TGENW/POOLCACHE lines) are the in-process cross-check — record the stamp↔t offset once per run; a large or drifting offset invalidates the run.
  2. The negative control (primary: the pre-engine sleep, same as the Linux run): a tiny launcher (C/PowerShell: Sleep(µs/1000000) then CreateProcess/start the engine as the stamped child, after the stamp wrapper's own start) injects a KNOWN delay into process startup — the stamped child sleeps, then launches the engine. The actual delay is self-reported in the log (query the sleep's wall) because the launcher's own start adds overhead. Run E at 5000 µs and 50000 µs nominal. Pass = t0 (the engine's first stamped line) moves by ≈ the self-reported amount (the Linux run: 11.1 ms and 56.0 ms measured injections moved t0 by +14.2 ms and +59.1 ms, the residual being a constant exec overhead) AND the engine-internal (t0-relative) milestones move NONE — a pre-exec delay must not touch the engine's own clock.
  3. The negative control (in-process alternative: AC-0484's instrumented .dll): build the gdext extension TWICE — plain (record the .dll md5) and with an env-gated AC0485_WIN_INJECT_US delay (µs, std::this_thread::sleep_for) fired ONCE at the extension's first entry, logging the fired path to stderr. Preferable if the launcher route proves noisy on the target box. Pass = the t0→milestone stamps grow by ≈ the injected amount AND the plain build is bit-identical (md5) to the shipping .dll (or to the same-source plain build). No pass = no evidence from the meter; fix the instrument before quoting. (Context from Linux: an LD_PRELOAD shim was tried and abandoned — this engine opens its project files with DIRECT openat(2) syscalls, so libc symbol interposition is blind to them, and LD_PRELOAD fires in both the timeout wrapper and the engine. On Windows the in-process .dll route has no such bypass — user file I/O goes through the CRT/kernel32.)
  4. Do not present the injected run's numbers anywhere else — it is the control, not a trial.

6. What the result must contain (the deliverable shape)

  • The per-family byte inventory (F1–F4 + shipped F3(a)) summing to the combined footprint, with the duplicate called out.
  • The cold/warm/first-drawable/first-playable tables with median/p95/p99/spread + cache-state metadata, all labelled.
  • The wait-bucket tables with the attribution text.
  • The target comparison table: for each provisional target (3 s atlas bake p95 / 8 MiB disk atlas / 16 MiB resident atlas / 64 MiB peak bake memory / 64 MiB global cache cap), the MEASURED current value and the multiple — including the far-tier gap (AC-0469 stage D: 1,699,726 records / 1,740,519,424 B payload in memory, 4,823,572 KB peak RSS, ~21 min bake on the 6-core Linux box) vs the 8 MiB disk target. That comparison is the deliverable; the design decision it feeds belongs to the coordinator.
  • The meter control (injection + observed delta) and the contention record (any invalid run, named).
  • Every figure labelled: Linux column = development-only; Windows column = acceptance.

7. Fences (same as the ticket)

Measurement only: no cache/eviction/behaviour changes, no rebaseline, no extrapolation from one platform to the other. The product code stays untouched; the only build artifact allowed is the env-gated instrumented .dll for the negative control, removed from the tree afterwards (the plain build re-verified bit-identical).
