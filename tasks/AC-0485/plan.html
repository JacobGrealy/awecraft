AC-0485 — what startup and the caches actually cost, in bytes and seconds

Coordinator contract (written by me; filed by another agent). Medium builder applies it with tasks/templates/implement.md. MEASUREMENT ONLY — no new cache, no eviction, no behaviour change, no optimistic extrapolation.

1. The requirement

"faster generation to mean getting into and exploring a world sooner, rather than waiting through a new bake or accumulating large hidden caches." So this ticket answers two questions with numbers: how long from launch to playable, and how many bytes the caches hold — by family, not as one total.

2. ⚠ A NUMBER THAT WILL DOMINATE EVERYTHING — check it first and build the report around it

AC-0469 stage D measured the existing far-tier bake at 1.62 GiB of records and 4.60 GiB PEAK RSS, taking 1,198–1,269 s per seed. The shared plan's provisional targets quoted in this ticket are a 3-second atlas, 8 MiB of disk, 16 MiB resident and 64 MiB of scratch.

Those two sets of numbers differ by roughly two to three ORDERS OF MAGNITUDE. So the inventory's most likely finding is not a marginal overrun — it is that the existing far-tier cache is 100–200× the provisional disk target before anything new is added. State that explicitly and early, with the measured bytes, because it reframes the whole series: either the provisional targets describe a different artefact than what ships, or the shipping bake cannot meet them. Reconciling that gap is a coordinator/design decision, not the builder's — measure it, quantify it, and stop.

3. What to inventory (bytes AND peak memory, BY CACHE FAMILY)

  • Cache ownership: godot/autoload/save.gd — who owns what is written, and where. Recheck the exact paths before running; the filing says to, and this session has had three plans with stale anchors.
  • Far/orbital cache consumers: godot/world/world.gd — what actually reads the far tier's data at runtime (the three-phase source: user:// cache, shipped res:// textures, bake — note AC-0478 regenerated the shipped textures this session).
  • Per family: existing far-tier data, temporary files, and DUPLICATE data — duplicates are explicitly called out and are the cheapest win to find, so look for them (e.g. the same bake stored both in user:// and shipped in res://).
  • Combined current disk footprint — one reconciled total, plus the per-family breakdown that sums to it.

4. What to time

  1. 4a COLD CREATION — first launch with no cache present, to playable.
  2. 4b WARM STARTUP — subsequent launch with the cache present.
  3. 4c FIRST DRAWABLE AND FIRST PLAYABLE FOOTPRINT — two distinct moments; report both.
  4. 4d FIXED TRAVEL / PROMOTION SCENARIOS — pinned movements, so the numbers are comparable.
  5. 4e SEPARATE generation from I/O, mesh and lighting wait explicitly, as AC-0484 did, and reuse its attribution method (counters around the driver, single-threaded where exactness matters).

5. The method

  • AT LEAST FIVE PAIRED TRIALS — paired, so cold/warm and generation/wait can be compared within a trial rather than across drift. Report median, p95, p99 AND spread.
  • CACHE-STATE METADATA recorded with every trial: what was present before, what the run created, what it read. A timing without the cache state is unreproducible.
  • REUSE AC-0484's PROTOCOL AND CORPUS (tasks/AC-0484/protocol.html, corpus.txt) and its revision — the filing names it as a dependency. Say where you deviated and why.
  • A TIMER/METER NEGATIVE CONTROL, as AC-0484 did: prove the instruments can register a difference (its 5000 µs injection moved the wall median 5346 → 10399). An instrument never shown to be sensitive is not evidence.

6. Windows versus Linux — the honesty clause

"Measure ... on the target Windows machine, with Linux proxy evidence labeled separately." This box is Linux and cannot run the product. So: do the Linux proxy work, LABEL EVERY FIGURE as proxy/development-only, and hand over a protocol for the Windows run — do not present Linux numbers as product numbers. AC-0484 established exactly this pattern and its protocol.html §8 is the model to follow.

7. The deliverable the filing asks for

"Logs sufficient to set the shared plan's provisional 3-second atlas / 8-MiB disk / 16-MiB resident / 64-MiB scratch and global-cache targets against real hardware." So the report must be structured so a target can be set from it: for each provisional target, the measured current value and the multiple. That comparison is the deliverable — not a recommendation about what the target should be, which is a design decision above this ticket.

10. Acceptance

A per-family byte and peak-memory inventory that reconciles to a combined disk footprint with duplicates identified; five paired trials covering cold creation, warm startup, first drawable, first playable and pinned travel, with distribution statistics and cache-state metadata; waits separated across generation/IO/mesh/lighting; a proven-sensitive meter; every figure labelled development-only with a Windows protocol; and an explicit measured-versus-provisional target table.

11. Risks

(1) Reporting one total instead of families, which hides the duplicate and the far-tier dominance. (2) Deleting the wrong thing between cold trials — a build output or another session's work. (3) Presenting Linux proxy numbers as product numbers. (4) Extrapolating a target rather than measuring the current multiple. (5) Timing on a contended box. (6) Not noticing the §2 magnitude gap and instead reporting a tidy table that looks fine.
