Re-derived consequence (the factual correction to RUN 1): a chunk with no local light source (a dark cave chunk) seeds an EMPTY queue (:974 finds no blk cell > 0) → the v-loop iterates empty buckets → the flood body — including the cross-chunk pull at :982–996 — never executes → the chunk never imports the neighbor's light; and the pull can never write into a cell that is 0 in our own array (queue membership requires > 0 at seed or import). recomputeLightAround (edit, 9-chunk box) recomputes the dark neighbor from scratch (blk.fill(0) :1011, own sources only) → the neighbor's boundary stays 0. ⇒ The web's per-chunk blk arrays have exactly the user-reported "lit next to pitch black" cliff at chunk boundaries: torch at chunk-A local (15,y) → A's boundary cell eff 14, chunk-B local (0,y) eff 0 — the (14, 0) pair the user reported EXISTS in the web too. The web's pull is a PARTIAL exchange: it fires only where our own flood already reached the boundary (our boundary cell > 0) AND the neighbor is brighter by ≥ 2 (nv > v+1) — two adjacent torch-lit chunks do trade boundary light; a dark neighbor chunk is never lit by the pull. RUN 1's "web parity / web shows no cliffs" framing was wrong and is corrected here.

Therefore the fix target is NOT web parity for this mechanism. The web (frozen artifact — seed :974 + pull :982–996 are the web's own flaw) HAS this cliff; the target is the Minecraft semantics (the canonical reference per AGENTS.md, and the user's explicit "should fade smooth 14→0"): block light must cross the boundary INTO dark cells (that is the fix), while sky must NOT leak full-bright into enclosed caves (that is why a naive ungated COMBINED-eff injection is wrong: a surface neighbor's sky-15 would flood our cave boundary → glowing cave walls, a NEW artifact). Resolution: the injection strip carries the neighbor's block-light-only value per boundary cell (derivation in §2.C.1) and the injection DROPS the eff[B] > 0 gate (it fires into dark cells too; sky-leak prevention moves from the gate to the strip content). This task is a user-directed spec correction going beyond the web — a documented deviation.

Known web deviations (three, all documented): (i) the web does NOT re-light old neighbors when a NEW chunk lands (remesh ≠ re-light, :1295–1326) — Godot's E2 hook (§2.C.4) goes beyond the web here (strictly fewer cliffs; the web gap is a web bug, not a spec feature). (ii) The web renders sky/blk as separate color channels (buildChunkMesh :1254–1267 cr=[ls/15,lb/15,…]); Godot's bake uses the combined value — pre-existing divergence, out of scope (AC-0128 territory). (iii) NEW: the web has the block-light boundary cliff itself (per-chunk arrays seeded from local sources only, :974; the partial queue-gated pull :982–996 never lights a dark chunk) — Godot implements the full Minecraft cross-boundary block-light fade (the user-directed correction).

Max-distributivity note: RUN 1 justified a COMBINED-eff pull via max-BFS distributivity (max(a−c, b−c) = max(a,b) − c). That argument is no longer load-bearing: the injection now propagates a SINGLE kind (block light only), so no cross-kind distribution is needed. It remains TRUE and is kept only as a historical note for the combined bake-box sampling (a rendering approximation in AC-0128 territory — not a propagation claim).
