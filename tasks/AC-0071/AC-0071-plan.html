1. Current-pipeline audit (what runs today)

1.1 The pipeline, as it exists

  • Chunk model — each chunk is a Node3D with raw data (block ids, 256×80 bytes, index (y<<8)|(lz<<4)|lx, chunk.gd:35-40) + fl (fluid level, same layout, chunk.gd:43-48) + up to three MeshInstance3D (opaque+cutout, fluid, flora, chunk.gd:20-22, 581-615) + one StaticBody3D with a single ConcavePolygonShape3D (chunk.gd:23, 625-645). World.HEIGHT=80 (data.gd:4).
  • World manager (world/world.gd) — chunks{} keyed "cx,cz" (world.gd:25, 335-341), per-chunk edits{} deltas (world.gd:27, 486-490), a sorted build_queue (world.gd:44, 183-212) with two entry kinds: data (ring, radius+1) and build (radius), and three per-frame drains run from _process: light flush (world.gd:75-149), then _drain_build_queue (world.gd:148, 261-332), then texture refresh (world.gd:149, 156-172).
  • Recenter (world.gd:385-436) — called when the player's chunk changes (player.gd:890-897, 273), at first load (main.gd:257, 295, 694), on settings change (settings.gd:96-100) or Debug.teleport (debug.gd:97, 105). With the play-path default mesh_now=true it never generates or meshes: it stub-creates nodes for the new radius squares (world.gd:415-420) and the outer data ring (world.gd:421-428), queue-frees anything beyond r+1 (world.gd:390-402), and re-enqueues all unbuilt chunks by Manhattan distance (world.gd:429-436, 201). The synchronous generate-all path (create_chunk(…,false) in a loop, world.gd:403-414) is only used by logic tests via mesh_now=false.
  • The drain (world.gd:261-332) — per-frame budget: 3 units while the spawn 3×3 has any unbuilt chunk (_startup_pending, world.gd:232-238), else 2 if the last build took <15 ms (BUILD_FAST_US, world.gd:19, 265), else 1; hard-capped at 30 ms of work per frame (DRAIN_FRAME_BUDGET_US, world.gd:20, 267-269). One "unit" = one data generation or one mesh build. A build is only eligible when its 4 axial neighbor chunks have data (_build_ready, world.gd:215-220), so the drain naturally does a BFS: spawn data → neighbor data → spawn mesh → … "spawn chunk first" falls out of the distance sort (world.gd:201).
  • One data unit — WorldGen.generate(cx,cz,seed) (world.gd:306; generator.gd:85-334: 5 fbm2 grids, column fill, 2-column cave noise, 4-column ore/hash noise, trees in a ±2 block margin, flora) + init_fl (world.gd:307) + edit re-apply (world.gd:308 → 493-510).
  • One build unit — build_mesh(get_block) (world.gd:319 → chunk.gd:454-622): standalone light compute over the 16×16×80 box because no light cache is passed (chunk.gd:466-472; Lighting.compute_light_flat, lighting.gd:146) → 18×18×80 snapshot incl. 8-neighbor bands, with a hidden on-demand generate of missing diagonal neighbors inside the snapshot (chunk.gd:364-397, 372-374 → world._chunk_data:369-382) → face scan over 16×16×80 (chunk.gd:533-562) → quad emission into 6 surfaces (chunk.gd:563-580) → new ArrayMesh + a new material object per surface (chunk.gd:581-615, 400-433) → mesh_built=true (chunk.gd:616) → if col_dirty, full collision rebuild: copy every opaque-surface vertex, ConcavePolygonShape3D.set_faces(all triangles), new StaticBody3D+CollisionShape3D (chunk.gd:617-622, 625-645). col_dirty is set only by block/fluid writes and edit re-apply (world.gd:467, 508; chunk.gd:17), so light/fluid/texture flush rebuilds do not rebuild collision.
  • Edit flush (AC-0034's original target) — a set_block marks a 3×3 light_dirty (world.gd:7, 474-478); _process rebuilds ≤2 chunks/frame under a 40 ms frame budget (FLUSH_MAX_PER_FRAME/FLUSH_FRAME_BUDGET_MS, world.gd:8-9, 112-138), with a bulk shared light pass when the pending box is ≤3000 columns (BULK_LIGHT_CELLS_MAX, world.gd:10, 101-107, 524-536). This staggering (PERF3a) already cut the 9–17 s one-frame block to ~54 ms worst build frame (CONTINUITY §6, PERF3a line).
  • Fluids — every 0.2 s (FLUID_TICK_INTERVAL, world.gd:11, 70-72) tick_fluids scans a column window of ±fluid_tick_radius blocks around the player (world.gd:700-718; default sim_dist=1 → 16 blocks, settings.gd:7, 90-93). Sleep (PERF3d): after 3 write-free ticks it returns in ≈0 ms (world.gd:725-733) — but the "stability" signature is the window's size + first column (world.gd:719-723), so every time the ±16-block window slides across a chunk boundary it resets stability and re-wakes a full scan of ~20 k cells per chunk in the window (world.gd:735-799). Pre-sleep that tick cost 175–520 ms (CONTINUITY §6, PERF3d line).
  • Unload today — only inside recenter: chunks beyond r+1 are collected and queue_free'd (deferred to frame end), with queue + light-pending entries removed (world.gd:390-402). fluid_dirty and tex_refresh for freed chunks are not cleared there (they are harmlessly skipped later, world.gd:97-99, 165-167).

1.4 What a boundary crossing does today (walking 1 chunk east, r=4)

  1. Frame in which the player crosses x = k·16: player.gd:273 → _recenter (player.gd:890-897) → world.recenter (world.gd:385-436): 9 new stubs (+ring stubs), 9 chunks freed on the far side (world.gd:390-402), queue re-sorted. ~<1 ms.
  2. Next ~15–30 frames: the drain processes up to 1–3 units/frame (world.gd:265-269) = the 9 new chunks' data→build→collision, interleaved with whatever else is pending (edit flush, tex refresh). Each unit ≈31 ms (gen) or ≈10–40 ms (build, headless).
  3. Every 0.2 s, the fluid tick possibly does a full window scan (re-woken by the window shift, world.gd:719-723, 730-733).

Net: the crossing is spread over many frames already — the problem is that each unit still costs 1.5–30+ frames' worth of work (headless vs wasm), and nothing about ordering (look direction), unloading (hysteresis), light reuse, or collision staging reduces the per-unit cost. That is what this plan changes.

2. Problem statement

  • First-load pop (New world). Player appears on a 16×16-block island (main.gd:296, 3241-3250 waits only for the spawn chunk) while 80 more chunks stream in at ≤3 units/frame, each unit 1.5–30+ frames of work. r=4 fully drains in ≈8 s headless / long-er in wasm; the last chunks of the radius pop in visibly mid-gameplay.
  • First-load blank (Continue). The opposite: _await_world_build (main.gd:258) blocks on the entire radius before the player exists — the whole drain as a loading stall.
  • Boundary hitches. Every 16-block crossing enqueues 9 gen+build units and re-wakes the fluid window; at 1–3 budgeted units/frame with 30 ms unit costs (headless) / 100–300 ms (wasm), the player gets several visibly heavy frames per crossing, worst when diagonal ring data is missing (hidden generates, chunk.gd:372-374) or the fluid window is awake (CONTINUITY §6 suspects 2+3, both still live, §1.5).
  • AC-0034 block-break flushes share the same main-thread budget as streaming — the two must coexist (flush 40 ms guard, world.gd:8-9; drain 30 ms guard, world.gd:20; one frame has both, plus physics + render). No double-work when a chunk is being unloaded (partially true today: flush skips freed chunks, world.gd:81-84, 97-99, 165-167 — made explicit in §3.4).

3. Proposed design

3.1 Streaming policy

  • Target chunk set — keep the current square (Chebyshev) radius, render_radius 1–8 (settings.gd:41-42); it is what the fog edge math already relies on (fog_far(r) < (r+1)·16 asserted in the perf RESULT, main.gd:3373-3380). Add an outer data ring at r+1 (already exists, world.gd:421-428) and — new — an optional r+2 data ring in low-memory mode: generating data (≈41 KB/chunk, no mesh) is cheap insurance that mesh build-ready (_build_ready, world.gd:215-220) is never data-starved at the leading edge.
  • Load priority — replace the pure Manhattan-score (d, world.gd:183-212, 201) with a composite entry score, recomputed at recenter and (throttled to ~2×/s) on look change: score = distManhattan + lookPenalty + collPenalty, where
    • lookPenalty = (1 − angleAlignment)·K: chunks within ~±70° of the camera look direction sort first (K ≈ 0.75·distScale), so the view fills before the periphery;
    • collPenalty: chunks at Chebyshev ≤ player-radius get full-priority (they can be stood on); r+1 ring entries are data-only and sort behind everything in-radius;
    • the drain keeps its "first eligible entry" scan (world.gd:270-298), so build-readiness can't be starved — priority only orders the queue (n ≤ 361 entries at r=8; re-sort <1 ms).
  • Unload with hysteresis — today: hard free at r+1, decided once per crossing (world.gd:390-395). New:
    • a chunk becomes candidate at Chebyshev r+1 (keep data, kill mesh+collision now — frees the expensive GPU/physics memory immediately) and freed only after r+2 for 2 consecutive recenter events (~1.1 s at sprint, 3.7 s at walk);
    • no flap: a chunk inside r again clears candidate state at once; max churn for boundary jitter = 0 frees;
    • on free, clear all per-chunk maps: build_queue/queued_keys (already, world.gd:399), light_pending/set (already, world.gd:400-401), and — new — fluid_dirty + tex_refresh entries;
    • memory-pressure mode (optional, Phase 1 item): if resident built chunks exceed a cap, evict oldest data-only ring chunks first (LRU), never built in-radius ones.
  • First-load fast path — keep the two-stage design but make it explicit:
    • sync core: spawn chunk + 3×3 (≤9 chunks) data-then-mesh before the player spawns. New-world: _await_spawn_floor (main.gd:3241-3250) waits only for the spawn chunk today; [PROPOSAL — decision item 6] widen to the 3×3 (bounded extra cost ≈ 8 × (gen+build) ≈ 0.3–2 s) so the first view is a 48×48-block solid area, then the rest streams. Continue: stop waiting for the full radius (main.gd:258) — wait for the 3×3 around the saved position instead; the rest streams in around an already-existing player.
    • the rest of the radius streams with the startup budget (3 units/frame while `_startup_pending`, world.gd:265) — unchanged; look-bias makes the forward view fill first.

3.2 Execution model — comparison for THIS engine

Hard constraints, verified: (i) the Web export preset has variant/thread_support=false (godot/export_presets.cfg:25) and Godot 4.3+ web exports are single-threaded by default and recommended; a threaded web export would require cross-origin isolation headers (COOP/COEP) and "the project will not run" without them (Godot docs, "Exporting for the Web", Thread support + Serving the files sections). Our canonical server serve_web.py does not send those headers. ⇒ Web = budgeted main-thread, full stop. (ii) Godot scene-tree APIs (node add/remove, MeshInstance3D, StaticBody3D/CollisionShape3D, ArrayMesh, RenderingServer mesh registration) must run on the main thread; worker threads may only touch pure data (Godot docs, "Thread and task manipulation" / using multiple threads — node & RenderingServer calls are main-thread; Task/WorkerThreadPool are the supported 4.x work-stealing primitives). Godot-4 Task (allocate/run/await) and the engine's WorkerThreadPool (≤ OS.get_core_count() workers, here 6) are available in 4.7.

3.3 Collision staging (the heavy part of a build)

  • Current trigger surface: initial build, any set_block/set_fluid/_apply_edits_to_chunk via col_dirty (world.gd:467, 508, chunk.gd:17, 617-622); light/fluid/tex flushes already skip collision (col_dirty gate, chunk.gd:617).
  • [PROPOSAL] Staged rule for stream-in builds:
    • chunks at Chebyshev ≤ 1 from the player: collision immediate in the same build unit (player can be there this second);
    • chunks at 2…r: mesh first (visible immediately), collision in the next budget slot (a dedicated low-priority "collision" unit type) — the mesh pop and the physics pop are decoupled, and the worst build frame loses its set_faces cost (chunk.gd:638-639);
    • bounded exposure: the 1-slot delay = ≤1 frame where a far chunk is walkable — the player is never within 1 frame of such a chunk unless flying at the leading edge; covered by a sprint-into-terrain gate in the boundary harness (§5). If that ever matters: per-y-band CollisionShape3D sub-shapes added incrementally (a StaticBody3D may carry many shapes) — listed as fallback option 4, only if measurements demand it.
  • [PROPOSAL] Measure first: the Phase 1 harness reports collision_ms per build unit (instrument around chunk.gd:625-645) before/after — if set_faces cost turns out small on modern desktop, option 4 never gets built.

3.4 Lighting + fluid integration with streaming (no double work)

  • Bulk batch light for stream-in. Today every queued build does its own standalone 16×16×80 light compute (world.gd:319 passes no cache → chunk.gd:466-472). The flush already has the shared-box pattern (_bulk_light/_build_batch, world.gd:524-561, margin 2, world.gd:6). New: a re-center batch (≤ the 9 new chunks) computes one compute_light_flat over their union box + margin and hands the per-chunk slice into build_mesh(…, eff) (the eff parameter already exists, chunk.gd:454, 466-472). 9 light computes → 1 per crossing.
  • No work for chunks being unloaded. recenter-freed keys are removed from build_queue + light_pending today (world.gd:399-401); extend to fluid_dirty/tex_refresh, and the flush loops additionally skip chunks beyond r+1 (one-line checks beside the existing null checks, world.gd:81-84, 97-99). A chunk that is candidate-for-unload (§3.1) gets its mesh+collision killed immediately and its pending light work dropped — its data stays for the hysteresis window, so a re-entry costs a rebuild (with edits re-applied, §3.5) not a re-generate.
  • Fluids (suspect 3 fix). Inside tick_fluids (world.gd:700-802):
    • prescreen per chunk: scan the chunk's fl (20 KB, trivial) — skip chunks with no fluid at all (dry biomes cost ~0; the 20 224-iteration column loop, world.gd:749-799, only runs on fluid-bearing chunks);
    • coarser sleep signature: round the window to 32-block cells (world.gd:719-723 currently changes on every chunk-column shift) so small walks don't reset stability;
    • keep the existing wake sources (fluid writes, _fluid_write, world.gd:725-727) — the sim results must stay bit-identical to the current AWECRAFT_LOGIC=fluids/fluidsettle RESULTs (gate: FLUIDSTAT unchanged, CONTINUITY PERF3d).

3.5 Save integration (AC-0062) — why streaming is transparent, + 1 hardening

  • Edits live at world level, keyed by chunk-coord string ("cx,cz" → cell → {b,f}) — world.gd:27, 486-490. They never move with a chunk node, so stream-out keeps them; every generation path re-applies them before first mesh: queue drain (world.gd:308), create_chunk (world.gd:359), on-demand gen (world.gd:379) → _apply_edits_to_chunk (world.gd:493-510, also sets col_dirty + light/fluid dirty, world.gd:508-510).
  • Save persists exactly {"edits": w.edits, player, seed, time"} (save.gd:73-89), and restore injects world.edits before recenter (main.gd:249, 257) — regen-not-dump by design. Streaming adds no new failure mode here. Phase 1 keeps exactly these invariants and adds a boundary-harness round-trip assertion (edit → walk 20 chunks away and back → cell matches), so a regression is caught by the gate, not by the user.
  • One existing sharp edge to harden (1 line): set_fluid(…, create=false) is the default (world.gd:648), so player-initiated placement onto a not-resident chunk silently no-ops (world.gd:658-660). Player bucket placement (player.gd:820) should pass create=true (matches set_block's create=true, player.gd:788 / world.gd:446, 452-453). Unreachable in practice today (reach < one chunk at r≥1) but it must stay true once streaming means chunks are deliberately absent.

3.7 Resulting per-frame work (proposed steady state, playing at r=4, crossing a boundary)

  1. player.gd:273 → recenter: stubs, candidate-mark freed side, score+resort queue, clear dead map entries (≈1 ms).
  2. Drain (budgeted, 30 ms guard kept): up to 3 scored units — a build unit now = shared-batch light slice + mesh (+collision only if player-adjacent); a gen unit ≈31 ms main-thread (web) or off-main completion handoff (desktop Phase 2).
  3. Collision-staging slot: 1 deferred collision unit (low priority, never competes with a pending edit flush of the same chunk).
  4. Edit flush: unchanged ≤2 chunks/40 ms (world.gd:8-9) — a chunk that is being unloaded is skipped (§3.4).
  5. Fluid tick (0.2 s): per-chunk prescreen; asleep unless the window actually holds fluid and something wrote (world.gd:730-733 as improved).
