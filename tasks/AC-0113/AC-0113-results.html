3. The toolpose arm's re-established assertion (and its twin in the held arm)

The red: _toolpose_test asserted held_box_scale_x/held_sprite_scale_x ≈ 0.70 — the AC-0073-era HELD_ITEM_SCALE. AC-0097 replaced it with 0.33, so the arm's top-level ok had been false on the main tree while every tool row was green: an instrument reporting a failure that no longer meant anything (the second stale instrument currently red this session). The fix, with attribution, in this task:

# AC-0113: RE-ESTABLISHED a stale assertion. … (full comment in harness.gd)
var exp_box_scale := float(p.HELD_POSE["block"]["scale"])
var exp_spr_scale := float(p.HELD_POSE["sprite"]["scale"])
var scale_ok := absf(held_box_scale_x − exp_box_scale) ≤ 0.001 and absf(held_sprite_scale_x − exp_spr_scale) ≤ 0.001
res["scale_expect"] = [exp_box_scale, exp_spr_scale]   # new: the expectations are visible in the RESULT

The expectation now reads the player's HELD_POSE rows instead of a copied constant, so the instrument tracks the source of the scale (tolerance tightened 0.05 → 0.001 — the node scale is the table value; 0.05 would have let a future per-branch retune silently go unreported). Result: scale_ok:true, scale_expect:[0.33, 0.33], top-level ok:true — the toolpose arm is GREEN at the end, which was the point.

Related finding, fixed with the same attribution: _held_test (line 19925) carried the same stale 0.70 expectation (it reported scale_ok:false without gating a top-level ok). It now asserts the HELD_POSE block/sprite rows too; the held arm reports scale_ok:true. Note: the held arm's result_fields row in harness_data.yaml was already stale before this task (it lists fields the arm no longer emits and omits cross_ok/scale_ok/depth) — pre-existing doc debt, not re-written here; the toolpose row (whose fields this task changed) was updated, harness_doc.py --render + --check clean.

4. The bow decision: DEFERRED (stays in the sprite branch, explicitly)

Item 142 ({"name": "Bow", …, "tool": "bow"}, data.gd:105) carries a tool tag but is not in the four-tool list [pick, axe, shovel, sword], so it falls through to the sprite branch. Chosen: keep it in the sprite branch, explicitly, for now. Why:

  1. The tool branch is a voxel-geometry domain. Its four types exist as 32×32 TOOL_GRIDS with per-type TOOL_TARGET_DIAG and a tuned pose — a bow there would mean designing a new grid, a target diagonal and a retuned pose: net-new weapon content, not pose plumbing.
  2. The bow is a placeholder by its own documentation. _fire_bow (player.gd, AC-0191) is "a placeholder bow — a hitscan … the procedural gun picker is a follow-up once the weapon system exists." Its tool:"bow" tag drives fire behaviour (start_mine dispatches it to _fire_bow, :1653) — it is not a mining/attack voxel tool. Re-arming it as a voxel tool would be a design decision this ticket was not given.
  3. This ticket's contract is a behavior-preserving split. Moving the bow to the tool branch would change what it renders (sprite → voxel) — exactly the class of change that is invisible until someone plays and unverifiable here (renders infeasible). A pose split must not smuggle in an appearance change.

The deferral is marked where it will be seen: the sprite row's comment in HELD_POSE names the bow and the deferral, so the finding is tracked rather than hidden. The bow's viewmodel is byte-identical to before (sprite row pos (0,0,0) scale 0.33 = the old shared values).
