AC-0477 — a battery compare that fails on status, not only on values

Coordinator contract. Medium builder applies it with tasks/templates/implement.md. Tooling ticket. The point is not to patch one script — it is that the script that would have caught this debt does not exist as a maintained tool.

1. Why this exists (measured while closing AC-0330)

The battery compare diffs VALUES only, so an arm returning ok:false in both the baseline and the current run looks "identical" and passes silently. That is why water and trees stayed red for months with nobody noticing.

AND THE SCOPE IS LARGER THAN THE FILING ASSUMED: the compare scripts are per-ticket ad-hoc copies — .scratch/AC-0287-gates/battery_compare.py, .scratch/AC-0288-gates/battery_compare.py, .scratch/ac0284a/battery_compare_a.py, plus unrelated ones for other arms. Each ticket rewrote its own. So there is no single place to fix, which is the real reason this class of debt recurs — and a fix that only edits one copy will be re-lost the next time someone writes their own.

2. What to build

  • 2.1 One maintained tool at tasks/scripts/battery_compare.py — a real script with a documented CLI, not another .scratch artifact. Model its diff on the most complete existing copy (read .scratch/AC-0287-gates/battery_compare.py and .scratch/AC-0288-gates/battery_compare.py and say which you based it on and what you added).
  • 2.2 STATUS-AWARE. It must fail (or loudly warn, your call — stated) when an arm's pass/fail status CHANGES in either direction, and it must report arms whose status is red in the BASELINE, so a long-standing red is visible instead of normalised. That second half is the actual fix: the debt was a red that never moved.
  • 2.3 DECLARED ok-LESS ARMS ARE NOT RED. AC-0330 declared atlas, buckets, player, interact as value-reporting BY DESIGN, with that contract recorded in godot/harness_data.yaml §1. Read the declaration rather than assuming every arm has an ok — otherwise the new check will cry wolf on four arms on its first run, which is how a good check gets disabled.
  • 2.4 Do not weaken the value diff. It is what catches terrain/behaviour drift; status is an ADDITION, not a replacement.

5. Acceptance

A maintained status-aware compare exists, it flags the two real reds and any status change, it stays quiet on the four declared arms and on unchanged input, the value diff is intact, and the prior art it came from is named.

6. Risks

(1) Editing one .scratch copy instead of creating the maintained tool — that re-loses the fix. (2) Crying wolf on the four value-reporting arms, which would get the check disabled by the next person. (3) An untested status-change branch, which is precisely the "test that cannot fail" pattern.

7. Fences

  • No git commit/push/add; no tasks/TASKS.yaml; no new tickets.
  • No edits outside §3. Do not change any arm or the battery.
  • If the plan cannot be applied — anchor missing, symbol absent, steps contradict, or a design decision this plan does not make — write PLAN-INSUFFICIENT: <what is missing, file:line> and EXIT. Do not invent the design.

8. Resume point

AC-0330 classified the seven battery arms and left water/trees deliberately red; this makes red visible in future comparisons, which is the reason that debt survived for months.
