AC-0459 — one chunk-key format, and a save version that says so

Coordinator contract. Medium builder applies it with tasks/templates/implement.md. Measured blast radius: 120 call sites of _key() but only ~5 key PARSERS, so the format changes in one producer and a handful of readers. That is what makes this ticket bounded.

1. Goal

Every chunk key in the game has the same shape — face:ccx:ccz — for the home pair (0:…) and for chart faces (4:…) alike, and the save version records the change so an old save is rejected cleanly.

3. Edit shape

3.1 Producer. _key(cx, cz) returns "0:%d:%d" % [cx, cz]. The cache key (cx * 65536 + cz) and its lazy fill stay as they are; only the string changes. Home chunks are one flat space, so the 0 is a constant — do not invent a second home index.

3.2 Save version. SAVE_VERSION 4 → 5, comment naming AC-0459. main.gd:628 already rejects a mismatch cleanly (edits + player pose dropped, fresh world at the same seed, one log line) — do not change that rejection path, and confirm in the gates that it still fires.

3.3 Parsers. Each site must extract face, ccx, ccz from face:ccx:ccz and from the legacy cx,cz (which means home, face 0). Keep a legacy branch only where the string can originate outside this process (a save loaded from disk); the version bump makes that impossible in practice, so a legacy branch is allowed but must be commented as defensive. Do not silently treat a mis-shaped key as chunk 0 — an unparseable key must return a clearly invalid result (e.g. null/empty) and be reported by the caller as it is today.

3.4 What must NOT move. Which chunk a coordinate maps to. This is a pure relabelling: the same (cx,cz) must resolve to the same node before and after. genhash 25/25 and the light set are the evidence.

6. Risks

If a parser is found that the plan did not list, STOP and report it rather than improvising a sixth edit.
