Deciding evidence chain (the true layer)

  1. The line is the body. One render with the body’s ALBEDO forced to zero (everything else untouched): row 358 goes (179,210,95) → (0,0,0); the line is gone; rows 350–368 all (0,0,0). Not fog, not atmosphere, not clouds, not HUD.  (.scratch/AC-0438/blackbody.png)
  2. The line is a texture-sample brightness, UV-independent.
    • texv probe (ALBEDO = vec3(texv)): row 358 = (179,210,95) vs neighbours (41,157,0) — the sampled texture term itself is ~4× brighter in R on that row (.scratch/AC-0438/texvfield.png).
    • Three sample-UV sources rendered at the r24 recipe — (a) the mesh UV attribute, (b) fragment-stage chart UV from the radial normal, (c) vertex-stage chart UV with the authoritative per-face index (exact inverse of SphereMath.uv_to_world, face from a per-material float, not re-derived from the normal): the disc is pixel-identical in all three and the line is present in all three. The line therefore does not depend on which texel the UV addresses — it is a sub-texel rasterization/sampling artifact at the chart’s coincident face seam (1 px ≈ 5.5 m < 1 texel at this render distance), not a UV-content error.
  3. Not the bake. All 12 face textures scanned for spike rows (row vs neighbour mean, Δ>40): zero. The x=0 seam columns are identical between faces (mean Δ=0, gapless bake). No bright feature exists for the row to sample.
  4. Not haze/relief/sun. Term-field probe (ALBEDO = vec3(haz, sun_l, texs.a)): haz uniform across the disc, sun_l uniform, relief alpha near-flat — no spike at row 358 (.scratch/AC-0438/termfield.png). The line’s hue (179,210,95) is not reproducible from any bake texel × day/relief factor, nor from a haz mix toward u_air (B=95 is below both mix parents).
  5. Minification ruled out. All 12 face imports flipped to mipmaps/generate=true + re-import + re-render → frame pixel-identical to r24. (Imports reverted; the tree carries no import change.)
  6. Stale shader cache ruled out. godot/.godot wipe + --headless --import + re-render → byte-identical.
  7. Normal/geometry sanity. Light-cancelled normal probes (engine lighting cancelled via a reference channel, saturation-safe) show a coherent radial normal field over the disc; the disc centre sits in the +Z/x>0 face territory; the normal field shows no sign flip at the line row at the disc centre — the line is not a face-boundary normal discontinuity either.

Recommendation / follow-up

  1. Confirm on the Windows build (the shipped forward_plus/D3D11 renderer): take the same r24 nadir recipe and check rows 357–358. If the line is absent there, it is a llvmpipe (software Vulkan) sub-texel rasterization artifact — document as a verification-box caveat in godot/OPS.md and close the ticket as environmental. If present there too, it is a real mesh-seam rendering defect.
  2. If real: file a follow-up targeting the 12-face chart’s coincident boundary edges — a sub-texel per-face radial offset in the body’s vertex stage (shader-only, genhash-safe) to break the coplanar seam, or a seam-UV nudge in the bake worker (world/*, owes a deliberate genhash rebase). Either is a geometry-level change; nothing at the sample-UV level can fix it (proven above).
