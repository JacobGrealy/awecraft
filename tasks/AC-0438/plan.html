AC-0438 — chart-seam-line-across-the-planet-disc

Goal

Find the true layer of the 1–2 px hard pale line across the planet disc in the spawn-nadir orbit view (r24 assessment: rows 357–358, 254 pts Δ≥6, mean step 68), then implement a conservative fix behind a switch and verify with light gates only (heavy gates are the coordinator’s). The mandate: do not assume the bake is at fault — identify the layer first.

Files to touch

  • godot/core/satellite_body.gdshader — the satellite body’s 12-face great-circle-chart fragment (the candidate layer for the disc’s pixels).
  • godot/world/satellite_body.gd — per-face material build + uniform pushes (the A/B switch home, the house pattern of u_srgb_pre).

No world/* generation file is touched by the fix (mesh construction is unchanged; only the shader’s sample-source selection moves) — so genhash 25/25 must hold, and any drift is a finding.

Harness gates (light only)

  • G0 via tasks/scripts/gate_census.py — zero SCRIPT ERROR + zero SHADER ERROR and process exit status 0 (AC-0396/AC-0403 paired rule).
  • SMOKE — dependency-mapped modes on the changed area (the body render path).
  • genhash — 25/25 byte-identical (a move = a finding to report).
  • shaderforce — only if a shader change lands (it does not in the final tree — see results).
  • No AWECRAFT_LOGIC arm for the renders (the arm would own the shot); AWECRAFT_SIZE=1280,720 (comma), xvfb-run + lavapipe + --rendering-driver vulkan.

Which layer + the deciding evidence

The line is in the satellite body (the 12-face chart mesh), proven by the black-body render: setting the body’s ALBEDO to zero removes the line (the frame’s row 358 goes from (179,210,95) to (0,0,0)). It is not the fog, the atmosphere, the cloud shell, or the HUD.

The line is a sub-texel sampling artifact and is UV-independent. Three independent sample-UV sources were rendered at the exact r24 recipe and the disc is pixel-identical in all three:

  1. the mesh’s stored UV attribute (the pre-AC-0438 path);
  2. a fragment-stage chart UV recomputed from the radial normal;
  3. a vertex-stage chart UV with the authoritative per-face index (the exact inverse of SphereMath.uv_to_world, face not re-derived from the normal).

All three leave the line byte-for-byte (seam rows 357→358: 444 pts≥6, mean 75.5, max 229 — identical to r24; disc stats identical). So the line is not a UV-content error: whatever UV the sampler receives, the same 1-px row reads a bright texel.

Also ruled out, each by a decisive A/B on this box:

  • bake content — no face texture has a bright spike row (all 12 scanned); the seam columns are identical between faces (gapless bake, mean Δ=0);
  • minification aliasing — mipmaps on (12 imports flipped + re-import) → frame pixel-identical to r24;
  • haze / relief / sun light — term-field probes: haz uniform across the disc, sun_l uniform, relief alpha near-flat — none spikes at row 358;
  • stale shader cache — .godot wipe + re-import → byte-identical.

Verdict: the line is a sub-texel (1 px ≈ 5.5 m < 1 texel at the r24 render distance) rasterization/sampling artifact at the chart’s coincident face seam, present on the llvmpipe verification box. It is in the body but is not removable by any UV change, bake change, or shader-term change. The honest resolution is a FINDING (see AC-0438-results.html): the conservative fix (computed chart UV behind a switch) was implemented and proven inert, then reverted to keep the tree minimal; the coordinator is asked to confirm on the Windows build whether the artifact is renderer-specific.
