AC-0061 — Tiered verify pipeline (results)

Task type: process/tooling — single-process multi-mode battery harness in godot/scenes/main.gd + coordinator-ready tiered-verify protocol. No game-visual changes, no renders.

Deliverable A — battery mechanics

AWECRAFT_BATTERY=player;interact;light;fluids;buckets (semicolon-separated AWECRAFT_LOGIC mode names) runs every listed mode sequentially in ONE godot process. Each mode is driven through the same entry points the standalone AWECRAFT_LOGIC=<mode> path uses — the runner calls the existing per-mode dispatch (and, for the player/interact/buckets tests, the newly-extracted _<mode>_test_body() so the standalone wrapper keeps its own get_tree().quit()). Each mode's RESULT {...} is emitted verbatim (as today), then a final combined line:

RESULT {"battery":{mode:{...,"ms":<per-mode ms>},...},"ok":true|false,"total_ms":<in-process total>}

BATTMODE <name> ms=<n> is printed after each mode so per-mode cost is measurable. genhash is a first-class battery mode (prints the same 25 GENHASH lines + GENMS; no RESULT of its own). The single-mode AWECRAFT_LOGIC path is untouched and still quits after one mode.

Defect-fix round (2026-08-24, after independent verification)

Verification found two defects in the uncommitted battery harness; both fixed in godot/scenes/main.gd only (drop.gd untouched — it already gates _process on Game.mode != "play", so the existing pause toggle is the freeze mechanism). Re-verified per the gates below.

  1. genhash battery arm truncated + seed ignored. The inline battery "genhash" arm printed only 16 hex chars (range(8)) vs the standalone arm's 32, and skipped the AWECRAFT_SEED reseed, so AWECRAFT_BATTERY=genhash never matched standalone. Fix: extracted the shared _genhash_print(seed_env) (main.gd:150-165, 32 hex via range(16) + seed override) and made BOTH arms delegate to it — standalone (main.gd:922-925) and battery (main.gd:198-199; _batt_run_mode now takes seed_env, main.gd:168).
  2. interact drop_spawned flaky in battery runs. After _mine, the drop entity's _process ran during the battery's 4-frame settle (main.gd:1642-1644); the drop's 2.5-chest attract lerp (drop.gd:66-76) sometimes pulled it into pickup range and inv_add freed it before the drop_spawned count (main.gd:1647) — a race that made the battery intermittently print drop_spawned:false. Fix (deterministic): the battery pre-settle now freezes drops via the existing Game.mode = "pause" toggle — set in _batt_reset_state (main.gd:123-125), resumed after every mode (main.gd:239-240) and again at the top of _interact_test_body (main.gd:1622-1623) so the test itself runs in play and standalone is untouched. drop.gd required no change.

Reset between modes (documented)

_batt_reset_state() does, in order:

  1. nulls Game.player and free()s the old player node (the player is respawned fresh each mode — this clears inventory, selected slot, fly state, swing/sway, look);
  2. zero-fills every resident chunk's data and fl arrays (reverts every block edit, fluid placement and reaction the previous mode made — the world is deterministic, so the next mode's recenter regenerates the same terrain);
  3. clears the drops container and the world's light/fluid/tex pending + dirty accumulators;
  4. forces fluid_sim_enabled=false and render_radius=4 (standalone default) and releases any held WASD input actions;
  5. resets Game.time_of_day=0.3;
  6. world.recenter(spawn.x, spawn.z, true) + awaits the spawn region building so the next mode starts from a clean, fully-built world.

The world node itself is not freed/recreated (that path triggered 20 script errors and added no parity benefit); the per-mode world is recreated at the top of each battery iteration instead. AWECRAFT_ONLY (the chunk-visibility filter) is NOT reused or renamed.

Reading: per-mode, the battery is cheaper than standalone — in-process mode sum 11141 ms vs standalone sum 15387 ms (−27.6%), because each standalone launch re-pays ~800 ms of engine start / world-import overhead that the battery amortizes once. The battery's wall time (33209 ms) is ~2.16× the standalone sum — this is NOT a regression in the modes themselves; it is the cost of state isolation: between the 4 mode transitions the reset (zero-fill 121 chunks + synchronous recenter that rebuilds every chunk mesh in mesh_now=true) costs ~4–7 s each (~21 s total). The spec's G2 asks for honest numbers + analysis: the tool is not slower per-mode, and it is the only way to get a single-process sequential run; the isolation overhead is the price of the "one launch" guarantee. Documented cost characteristic: the smoke tier (2–4 modes, 1 launch) is the primary savings path; the 5-mode full battery pays the per-mode world reset (~21 s total).

Deviations / known limits

  • script_errors count removed from combined RESULT. Godot 4.7.1 exposes no engine-side script-error counter (no Engine.get_script_error_count(), no Node.set_errors(), no relevant Engine signal) — verified empirically. The G0 zero-script-errors guarantee is instead enforced by grepping the run's stderr for SCRIPT ERROR (0 in every battery/standalone run here), which is the same method the project's existing headless gate uses. The combined RESULT therefore carries ok (all mode RESULTs ok) + total_ms.
  • G2 wall time is higher than the standalone sum — analyzed above as isolation overhead (synchronous recenter mesh-rebuild per transition), not a per-mode slowdown. The isolation step is what makes each mode's RESULT byte-identical to standalone (the G1 guarantee).
  • Only godot/scenes/main.gd changed (runner + reset + 3 test-function bodies extracted so standalone wrappers keep their own quit). No world/*, player.gd, chunk.gd, generator, mesh/light/fluid changes; no renders; no UI; no git.
