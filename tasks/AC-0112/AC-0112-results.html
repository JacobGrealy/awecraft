AC-0112 — held-item positioning per-type catalogue (REVIEW, audit only — no code change)

Review of godot/player/player.gd _update_held + the sway_root/hand_root/held-node transforms, per the ticket notes (verbatim in spec.html). Rendered evidence is infeasible on this box (degraded llvmpipe); all numbers below are headless. Line references are to godot/player/player.gd at HEAD unless stated otherwise.

TL;DR — The hand has 4 render nodes covering 5 held-item branches: empty fist; block (box mesh); cross/flower (shares the box node); flat item sprite (~35 item ids, incl. the bow, which has a tool key but falls through to the sprite branch); voxel tool (4 tool types, 16 item ids). Five values couple the branches: HAND_BASE_POS+sway and the hand_root swing (all branches), HELD_ITEM_SCALE (block+sprite), the hard-coded held_box.position (0,0,−0.18) (block+cross, same node), and TOOL_POSE_POS/TOOL_POSE_ROT (all 4 tool types). The regression history (AC-0073 → AC-0085 → AC-0097) shows each tool-centric ticket moving the other branches through exactly those shared values. Recommended split: a per-branch pose table (one row per branch/tool-type) consumed by _update_held/_setup_held_tool; the hand hierarchy, sway, swing timing and viewmodel lighting stay shared. A numeric baseline table (live run + independent constant-based recomputation agreeing to ≤1.2 mm) is in §5 for AC-0113 to assert against.

3. Regression history — what each ticket changed and what it disturbed (cited)

AC-0073 — "held tool orientation + held scale ×2" (tasks/AC-0073/AC-0073-results.html)

Aimed at: the four voxel tools (head toward crosshair, swing arcs through center) and the held items generally (×2 scale, per its title). Changed (results page "What changed" table): TOOL_TARGET_DIAG ×2 (per-type dict); TOOL_POSE_ROT (−0.42, 0.55, −0.9) → (0.467168, 2.956413, −0.394178); TOOL_POSE_POS (0.03, −0.03, −0.02) → (0, 0, 0); _apply_swing tool branch; HELD_ITEM_SCALE 0.35 → 0.70 (the shared constant); and held_box.position — "(never set; geometry 0..1 anchored at hand origin)" → (0, 0, −0.18), which the page marks as a required "near-clip fix … to make ×2 flowers/blocks actually render". Disturbed: every block and every sprite (both scaled 2× and re-centered in z through shared values, with no per-type alternative), while the fist was explicitly left unchanged ("reads fine next to ×2 items" — deviations section). The tool pose was tuned on the same two shared constants the next ticket would re-tune.

AC-0085 — "swing = rotate, vertical at rest, handle off camera" (tasks/AC-0085/AC-0085-results.html)

Aimed at: the four voxel tools (rest pose vertical, handle below viewport; swing as a rotation about the shoulder). Changed (results page "Files changed"): HAND_BASE_POS (0.45, −0.42, −0.8) → (0.45, −0.62, −0.7); TOOL_POSE_ROT (0.467, 2.956, −0.394) → (0.632, 2.639, −0.2); TOOL_POSE_POS (0, 0, 0) → (0.2, −0.3, 0); _apply_swing position-lerp → rotation-arc; hand_pose_rot() accessor; plus harness re-tuning in main.gd (swing arm: position → rotation thresholds; toolpose arm: rot_delta/vert_ok/below_ok). Disturbed: the page documents it itself — "Held cubes lower. Same HAND_BASE_POS lowering moves the held box/fist/sprite down with the hand." Fist, block, cross and sprite all moved 0.2 m down / 0.1 m in z because of a tool-pose ticket, and the swing motion of all item types changed character (translation → rotation) because the pivot is shared. Its "before" numbers also cite AC-0070/AC-0073's toolpose outputs as the baseline it replaced.

AC-0097 — depth-on-top + scale per user (git commit 3816ad1; no tasks/AC-0097/ folder exists in the repo)

Changed (commit message): no_depth_test on all viewmodel materials; sprite material_override now carries the tile; HELD_ITEM_SCALE 0.70 → 0.33 "(block + sprite) per user". Disturbed: the third move of the same shared scale in three tickets (0.35 → 0.70 → 0.33); block and sprite moved together by definition. Evidence is the commit message only — the results folder is absent.

The pattern, as evidence: three consecutive tickets, each aiming at the tools (or the viewmodel generally), each reaching for the same ≤5 shared values in §2, each moving the branches it was not about — and each re-tuning the harness arms in lockstep (AC-0085's "Harness re-tuning notes"), so the instruments track the shared constants rather than the types. A fourth live observation from this review: the toolpose arm still asserts the AC-0073-era scale — harness.gd:20063 expects held_box_scale_x/held_sprite_scale_x ≈ 0.70, while the code is 0.33 since AC-0097. My live run (below) reads the top-level ok:false with scale_ok:false while all four tool rows are ok:true: the stale expectation sits inside the instrument. Fixing that row (to 0.33, or to a per-branch value once AC-0113 lands) belongs with AC-0113 or a hygiene ticket.

4. Recommended split — per-type knobs without duplicating the chain (do NOT implement; this is AC-0113's baseline)

The smallest change is a per-branch pose table in player.gd, e.g. a HELD_POSE dictionary with one row per branch — fist, block, cross, sprite, pick, axe, shovel, sword — each row carrying pos, rot (for the tool rows) and scale — consumed at the two points where branches already branch: _update_held (sets the node's local transform from its row, replacing the shared HELD_ITEM_SCALE and the hard-coded (0, 0, −0.18); box and cross get separate rows, so no node split is needed — only one node is visible at a time) and _setup_held_tool (replaces the two TOOL_POSE_* constants with the per-type row, sitting next to the already-per-type TOOL_GRIDS/TOOL_TARGET_DIAG).

  • Moves (per-type): scale of box / cross / sprite (splits HELD_ITEM_SCALE into three rows); local position of box and cross (currently one hard-coded value for both); TOOL_POSE_POS/TOOL_POSE_ROT become four rows; optionally the swing arc amplitude per branch in _apply_swing (it already has two kinds — punch vs item — the table just generalizes the existing split).
  • Stays shared: the sway_root/hand_root hierarchy and HAND_BASE_POS (that is the hand, not the item — one hand in the scene, and it is where AC-0085's fix correctly belongs as a hand-level value), the sway function and its constants, swing timing (SWING_DURATION, loop logic, swing_kind_for_selected), _vm_mats lighting, the no_depth_test material handling, and the HeldMeshes builders. Also stays: the dispatch at :219-225.
  • Invariant it establishes: tuning any type = editing that type's row; no other row reads the same constant. Then re-baseline the numbers in §5 per row, and have the headless arms assert them (extend the existing toolpose/held arm pattern to all five branches, and fix the stale 0.70 at harness.gd:20063 in the same change).

5. Numeric transform baseline (for AC-0113 to assert unchanged per type)

Convention: camera space, metres, at rest (no swing, no walk sway) and at swing apex (hand arc at its peak, a = sin(π/2) = 1). Tool part positions are part-mesh AABB centers — the convention of the existing instrument (_toolpose_centroid, godot/scenes/harness.gd:20040-20045: mesh.get_aabb().get_center() through the part's global transform, into cam space). Euler convention verified as Godot's default YXZ by matching live data (§5.2). Camera frame at spawn is identity for this chain (the chain is a pure camera-relative parent chain; camera position and the player basis cancel in cam.to_local).

5.2 Provenance — the numbers came from a REAL run, and independently from reading the constants

The table above is from an actual headless run of the pre-existing toolpose arm on this tree (no probe, no edits). Separately, I recomputed every tool centroid purely from the code (HAND_BASE_POS + TOOL_POSE_POS/ROT composed as YXZ basis, part centers = union-AABB midpoint of the per-type grid in the combined head+handle bbox frame that :1357-1372 uses, voxel = TOOL_TARGET_DIAG ÷ √(bw²+bh²+1)): all 8 vectors (4 tools × idle head/handle) and the apex heads match the live run to ≤ 0.0012 m (sum 0.0043). Two implications: (a) the pose is fully determined by the player.gd constants + grids — there is no hidden runtime state in the chain, so AC-0113 can assert these numbers headlessly per type; (b) the YXZ + AABB-center + combined-bbox-center combination is the exact convention to reuse in any new arm. What the run does not cover: near-plane culling (needs a real renderer; documented phenomenon in AC-0073), on-screen projection (camera FOV/aspect), and walk sway (time-varying, ≤ 0.006 m x / ≤ 0.015 m y per SWAY_AMP_*).

5.3 Note on AC-0085's reported numbers

AC-0085's results page reports e.g. pick idle head [0.559, −0.859, −0.801] vs today's live [0.583, −0.838, −0.805] — up to ~4 cm apart, while the chain code (grids, pose constants, arm code) is verified byte-identical between AC-0085's commit (28d8960) and HEAD. The difference cannot be pinned down from the repo (the arm moved from main.gd to harness.gd in AC-0140 and transient sway/swing state at capture is a candidate); it does not affect the baseline above, which is self-consistent (live = recomputation) and reproducible by re-running the arm.

6. Evidence gaps — what could not be settled by reading alone

  • Sprite pixel_size: never set anywhere in code → the width 0.1056 m assumes Godot's Sprite3D default of 1/100. A one-line probe (p.held_sprite.pixel_size) in any arm would settle it; nothing else in this review depends on it.
  • Near-plane / FOV: camera near distance and FOV live in the camera setup, not in player.gd; the AC-0073 near-clip incident shows size tuning is coupled to them. A render is infeasible here; a numeric probe of the camera's near/fov values is the cheap substitute if AC-0113 needs the constraint.
  • Holdability of block-only ids: water (5), lava (24), open doors (29/31) have no Data.items entries, so in normal play they likely never occupy a hand slot; the code path treats them uniformly if they did. Not resolvable from the positioning code alone.
  • "TOOL_POSE_RETUNE" (named in the ticket notes) does not exist in the tree — git log -S finds no commit containing it in player.gd; the live symbols are TOOL_POSE_ROT/TOOL_POSE_POS (:1154-1155). Treated as the notes' shorthand for the current constants.
  • AC-0097 evidence: no tasks/AC-0097/ folder in the repo; the scale change is documented only in commit 3816ad1's message.
