1. Step 1 — does the fluid simulation self-heal the pits?

Answer: the question is vacuous on this tree (there is nothing to heal), and by construction the sim could not heal such a column anyway. Two independent proofs, then the measurement.

1.1 Mechanism proof (code)

  1. Natural worldgen water is stationary, fl=0 — the aquifer fill places block id 5 with no flow level (gen.cpp emit loop; the sparse scan in world.gd _tick_fluids_body only processes cells with l != 0).
  2. _tick_fluids_body only processes chunks in fluid_wet, which is populated exclusively by runtime edits (set_fluid lvl>0, set_block on a fluid id, _wake_fluid_around on a block break near water, saved-edit apply) — never by worldgen build. A freshly generated world has fluid_wet = {}, so tick_fluids() is a mathematical no-op.
  3. A dry-below-sea column has no adjacent flowing water cell at all — there is no fl>0 donor anywhere in a fresh world. The sim has nothing to spread. No worldgen defect in the ocean fill can be healed by the fluid sim; only a generation-side fix could.

1.2 Measurement (the pitsettle instrument, temp arm — removed at exit)

Built the 11×11-chunk seed-44 window (chunks −5..5, the exact AC-0342/AC-0371 census window) as FULL-path data (band0_r stretched to 12 so every window chunk is tier-0), verified it against the generator byte-for-byte, censused the ocean/land water classification, then settled the sim exactly the way the ticket names (tick tick_fluids() to 3 quiet ticks / AWECRAFT_SETTLE_TICKS cap) and re-censused. Logs pitsettle_r1..r6.log.

  • Byte verification: 119/121 chunks md5-identical to generate_flat(skip=0); the 2 differing chunks differ only in 33/44 non-water cells (material/texture-class variance in the live path) with identical water counts (767/767, 324/324) and top water at 126 — the full-path data is what the census ran on.
  • Settle census (before → after): fluid_wet 0 → 0; 3 ticks to quiescence; 0 writes (_fp_writes delta). The before/after censuses are field-identical — the sim moved nothing, as the mechanism predicts.
  • Pre/post classification (this is the actual census the ticket asked for): land 29,895 cols (open cave-dropped 110, open water in [he+1, 126]: 0 — the AC-0342 sub-contract holds); ocean 1,081 cols: surface_ok_at_sea 887, flooded_to_sea 887, dry_islets_zero_water 0, water-at-sea-with-solid-above 194 (all capped — §3), water_below_only 0, he<H 0 (no column's solid top carved below lattice H in this window). Total water 28,194, lava 925, max water y 144 — the AC-0371 census totals, reproduced exactly.
Self-heal answer: 0 dry-below-sea columns before settling, 0 after; the sim wrote 0 cells and had 0 wet chunks. Nothing healed because nothing was dry — and a hypothetical dry column would never have healed (stationary fl=0 sources + the empty fluid_wet gate). The generation-side gate is the only guard on this classification — which is precisely why step 3 (the arm field) is the durable deliverable.

2. The "791" — not reproducible, with byte-level evidence

The number came from AC-0371's results page (F2): "791 of the 1,081 lattice-ocean columns are CARVED ISLETS… (measured: H=125, solid top 121–123, zero water); 290 at-sea-or-islet." Its arithmetic is 1,081 − 290, i.e. the complement of an ocean_at_sea field. The byte-verified data refutes the per-column claim outright:

  • Every one of the 1,081 ocean columns has water at y=126 (887 open-surface + 194 capped; dry_zero_water = 0, water_below_only = 0). "Zero water" describes no column in the window.
  • The cited column shape ("H=125, solid top 121–123") matches no column: only 218 of 1,081 ocean columns even have H=125 (distribution 125:218, 124:171, 123:149, 122:129, 121:115, 120:104, 119:95, 118:100), and he == H for all 1,081 — no column's topmost solid is carved below its lattice H in this window at all.
  • The AC-0371 arm's own debug progression shows the field was still being tuned when the number shipped: ocean_at_sea 0 (v1, dense-H variant — ocean 2,947, open water 4,187!) → 74 (v2, lattice H) → 290 (final, census_base3.log in .scratch/AC-0371-gates/). 290 matches neither the water-at-sea count (1,081) nor any per-column subset of the verified data; the arm was removed at AC-0371 closeout, so the exact bug in that field is not recoverable — but the per-column water pass (run here) is the instrument it never did, and it found 0 dry.
  • Its aggregates (land 29,895 / ocean 1,081 / water 28,194 / lava 925 / hidden 24,030 / max_w_y 144) all match the byte-verified census — the arm read the world correctly; only the derived per-column classification was unsound, and it was extrapolated into "791 dry islets" without a per-column water check.

2.1 The ticket's stated mechanism is also impossible in the current code

The ticket says "AC-0342 gates ocean fill on PRE-carve height, so a column the carve drops below sea receives no water." The actual rule (gen.cpp emit loop, the AC-0342 block):

bool solid = skip ? (y <= he) : (solidf[y] != 0);
...
if (y >= he + 1 && y <= sea && H < sea) {
    cell = B_WATER;  // aquifer: ocean fill up to Sea 126, gated on pre-carve H
}

The gate is H < sea — the pre-carve lattice heightmap, a quantity the carve cannot change — and the fill range [he+1, SEA] starts at the post-carve topmost solid, so the carve can only extend the fill (flood a carved opening up to sea level — submarine caves open to the sea still flood, as the AC-0342 comment itself states), never shrink it. For an ocean column (H<126) to stand dry, its post-carve top would need he ≥ 126 — solid at or above sea level inside an ocean lattice cell. The only pass that places terrain above H is the drip pass, and it leaves the water fill intact (the capped columns, §3) — so the mechanism as filed cannot produce an air column in the sea on this tree.

3. Finding F-SPIRE — dripstone spires standing in the sea (the one real visible artifact)

The 194 "capped" columns (seed-44 window; 209/seed-99; 580/25×25-44; 519/ocean-dominant) are a real, visible artifact: dripstone stalagmites rising 1–5 blocks above the intact water surface in ocean columns (column dump, e.g. (−21,76): stone 118–121, dirt 122–124, sand 125, water 126, dripstone 127–130, air above; cap histogram {33: 194} — every cap is dripstone, block 33). The sea surface itself is intact everywhere — these are rock spires, not holes. Mechanism (gen.cpp drip pass, AC-0292): a stalagmite grows 2–6 blocks from a solid floor into an air/water run whose top of the generated slab bounds the run — in an open-sky ocean column there is no ceiling, so the spire anchors 2–6 blocks below the slab-generation margin and pokes above sea whenever H ≈ 122+. Out of scope for this ticket (it is the drip pass's open-run handling, not the water classification) — recommend a follow-up ticket; the permanent arm carries the count as a watch field so it can be tracked without gating.
