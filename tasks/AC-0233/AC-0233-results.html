status: PASS · engine: Godot 4.7.1 · files: godot/world/world.gd, godot/scenes/main.gd (R16 arm probes) · GDScript-only · logs: godot/.scratch/AC-0233-gates/

What changed

The streaming queue is now tiered, two-lane, and debounced:

  • Two queues. streamingQueue = the speculative band_buckets (rewritten on debounced recenter; the 4-tier order lives here). dirtyQueue = edited chunks appended by set_block (_dirty_add, deduped via dirty_set); it drains first, 1 per frame in _process (_dirty_drain → _dirty_dispatch: scoped edit lane when the chunk is meshed, light-wave fallback otherwise), ahead of the streaming drain and the light flush. In-flight ThreadGen (pool 4) / ThreadMesh (pool 6) tasks are never cancelled — stale results drop at handoff (data/band/inst checks) and the chunk re-queues.
  • 4-tier priority. _tier_of(dx,dz): 0 under (the column under the player), 1 ring-1 (chebyshev 1), 2 FOV cone (TIER_CONE_DOT = 0.5, i.e. a 60° half-angle wedge around the look direction), 3 rest. Score is lexicographic (tier, taxi) — tier*10000 + taxi — so every tier-N entry sorts strictly before every tier-(N+1) entry and taxi only breaks ties within a tier (the spec's strict tier order). The first implementation used a tier + taxi*0.1 blend, which let a near tier-3 outrank a far tier-2 and blurred the tier boundary the 180-spin test requires; the lexicographic form fixed that.
  • Separate tiered picks, gen vs mesh. _pick_data_cached (ThreadGen pool-4 feed: entries with no data) and _pick_build_cached (ThreadMesh pool-6: entries with data and all 8 neighbors' data — "mesh only when gen + light flat ready") each sort their own pool by _tier_score; picks are cached against _pool_key (queue version + look direction + maxb + spawn-fast + center) and busted on every membership/readiness change (_pool_touch, 13+ landing sites). A rescore (look change) changes the key, so reordering never rescans needlessly — R16 evidence: 379,051 pick-cache hits / 8,838 misses (97.8%).
  • Debounced rewrite, not every frame. The queue is re-scored only on: a debounced recenter (column cross within the 1000 ms debounce while the walk still covers the player — recenter() → _rescore_kick()), a ≥10° look change (_refresh_look_dir, including the yaw snap of player.look), and the recenter finalize. _rescore_step amortizes the re-stamp pass (2048 entries/frame, stamp-only, no structure mutation). A pre-existing look-gate normalization bug (fposmod(dy + PI, TAU) mapped a 0° delta to 180°) fired 87,939 rescore events / 7.05 s across one run (idle p50 3→5 ms); fixed to the shortest-angle form. R16 evidence: 48 rescore events / 6.4 ms total / 4,414 stamps for the whole arm.
  • Trim to render circle, evict farthest first. _cap_queue_depth() after each recenter finalize evicts the farthest speculative entries first (built/high entries and the edit lane are exempt); the walk itself re-queues only the circle (entries outside the stream set are dropped at merge; built chunks are never re-wanted).
  • Keep-high once built. _rec_want_step keeps a built chunk's band (no downgrade to coarse/low while resident); entries carry e["tier"]/e["rank"] stamps for AC-0231's low-LOD scan (the low placeholder for never-built far chunks is AC-0231's job).
  • Outrun coverage (new in this task). At supersonic speed (215 m/s) the debounced 5x5 pre-warm was outrun: the walked circle lagged 10-30 chunks behind the player, the queue starved on fuel/zombie entries (bscan=0 dscan=0 while the player was 30+ chunks past the walk center), and the ahead-fill collapsed (fly50 ahead-while-moving 58 → 0 risk). Fix: the debounce stands only while the walk center is ≤ REBUILD_COVER_L1 (4) L1 from the player; an outrun recenter parks an escalation target (no restart livelock while a walk is in flight) and the walk finalize chains the next walk; a settle rebuild fires one final walk at the resting position 1 s after the recenter stream goes quiet (fast-then-stop flight). Walking is unaffected (each per-crossing walk anchors cover 0). Result: fly50 ahead-while-moving 58 → 775, under-gap 0, lost 0.
  • Wave entries now carry t_submit (the edit lane already did) — the handoff queue/worker split diagnostics read it, and the R16 edit probe uses it to verify a handoff's task was submitted after the probe's set_block (a pre-edit in-flight handoff does not carry the edit).

Evidence detail

  • spin window (supporting): after the flip, the 8 s window saw 192 further dispatches (the frontier fill kept flowing; the fill is tier-ordered under the new facing since the spin precedes the window — there is no pre-spin dispatch leak). The aggregate new/old-ahead split (0/192) is expected: the +x cone wedge was already built by the flight fill (which feeds the facing cone first, by design), so the remaining pending work sits in the tier-3 rest set — the flip gate above is the deterministic measure, and it passes with the full 85-entry cone set demoted.
  • mini-flight preamble: the spin probe first flies 0.7 s @ 50x (228 ahead-builds while moving, 0 lost) so the queue holds live streaming work at spin time (a stationary probe after the supersonic flight faces an idle queue — the settle rebuild fills the circle in ~2.5 s, faster than any probe reaction).
  • pick cache: 379,051 hits / 8,838 misses (97.8%) — the debounced-rewrite design pays for itself: re-scoring happens on look/center/membership change only.
  • rescore cost: 48 events / 4,414 stamps / 6.4 ms total across the whole arm (the <1 ms reorder budget for 800–7,845 entries is met: 4,414 stamps ≈ 0.15 s of stamp work amortized, < 1 ms per event on average).

Treated as environment flakes, not code defects — no RESULT was ever lost to them except once (the file-backed user://debug_result.json confirmed the arm had not reached the RESULT line in the SIGSEGV case, i.e. it was in the probe's flight, not the shutdown).

  • Walk cost at R16 ≈ 2.5 s wall (STUB phase node creation, ~2.5 ms/node × ~1000 nodes) — inherent to the Godot scene tree; REBUILD_COVER_L1 (4) is the tuning knob if p95 matters at supersonic speeds.
