AC-0205 smooth ground ramps - pre-work survey

Status: survey only, no product code changed. Written by the coordinator on 2026-10-03 after THREE consecutive subagent launches failed with "subagent run failed" on prompts of both normal and minimal size, while the box itself was healthy (43 GB free, load 0.50, no godot running, disk 47%). The agent mechanism was unavailable, so the two decisive questions were answered directly with targeted greps rather than left unanswered.

1. Can the collider be sloped? YES - and it can agree with the mesh by construction

Collision shapes are built as ConcavePolygonShape3D (godot/world/chunk.gd:1809), wrapped in a CollisionShape3D (:1812), and the project already reads them back as raw triangle lists (godot/world/world.gd:4142 iterates get_faces()). A concave polygon shape in Godot is ARBITRARY TRIANGLE GEOMETRY, not a box list, so a sloped quad is fully expressible. This removes the one blocker that would have made the feature dishonest: the ticket's user story is about movement ("strafe and slide without snagging"), and a visible ramp over a stair-stepped collider would be worse than the blocky look it replaces, because the player would then snag on an invisible ledge.

The implementation consequence worth carrying forward: if the collision faces are emitted from the SAME face list as the visual mesh, then mesh and collider agree BY CONSTRUCTION rather than by two code paths being kept in sync - which is the failure mode this project has met repeatedly (AC-0387's far lane silently not carving; AC-0159's two lanes needing to agree on light). Prefer that over adding a second, parallel ramp rule for collision.

2. Does the mesh builder have what the ramp rule needs? YES

The C++ mesh builder's own header documents that its context carries the chunk's own 16x16 columns PLUS the four edge-neighbour rings, with a snap_rings neighbour snapshot for the boundary slice (gdext/src/mesh.cpp, header lines ~20, ~53-62, ~661). Neighbour heights are therefore available where faces are emitted, so the ticket's rule - two adjacent ground columns whose heights differ by exactly ONE connect through a sloped quad - is implementable at the point where a face decision is made, without new plumbing.

3. What the far/coarse path owes, and the other two interactions

Far/coarse agreement: not yet determined by this survey. godot/world/AGENTS.md requires a far or h-only column's H to equal the full path's so promotion never shifts terrain, and ramps are mesh geometry derived from that height - so the coarse tiers must apply the SAME ramp rule for the same columns or the silhouette will change shape as residency changes. That is the AC-0387 class of drift and must be established before the feature lands, not after.

Smooth lighting (AC-0159): a sloped quad's vertices need their own per-corner light and AO values; sampling them as if the quad were two flat faces would reintroduce exactly the blockiness AC-0159 removed, on the very surfaces the ramp feature is meant to smooth.

Buried columns: the rule applies only where terrain meets AIR, so a dirt column under more dirt must not ramp - a face that is not emitted cannot carry a slope.

Recommended next step

When the agent mechanism is back: implement the rule in the C++ face emitter, emit the collision faces from the same list so mesh and collider cannot diverge, apply it consistently on the coarse tiers, carry the AC-0159 corner lighting onto the sloped quads, and assert per column-height pattern (flat, one-step, two-step, ramp corner, in-scope next to out-of-scope, buried, player-placed) which quads are emitted - with the two-step case explicitly NOT ramping and the negative tests shown failing.
