AC-0205 smooth ground ramps - pre-work survey

Status: survey only, no product code changed. Written by the coordinator on 2026-10-03 after THREE consecutive subagent launches failed with "subagent run failed" on prompts of both normal and minimal size, while the box itself was healthy (43 GB free, load 0.50, no godot running, disk 47%). The agent mechanism was unavailable, so the two decisive questions were answered directly with targeted greps rather than left unanswered.

1. Can the collider be sloped? YES - and it can agree with the mesh by construction

Collision shapes are built as ConcavePolygonShape3D (godot/world/chunk.gd:1809), wrapped in a CollisionShape3D (:1812), and the project already reads them back as raw triangle lists (godot/world/world.gd:4142 iterates get_faces()). A concave polygon shape in Godot is ARBITRARY TRIANGLE GEOMETRY, not a box list, so a sloped quad is fully expressible. This removes the one blocker that would have made the feature dishonest: the ticket's user story is about movement ("strafe and slide without snagging"), and a visible ramp over a stair-stepped collider would be worse than the blocky look it replaces, because the player would then snag on an invisible ledge.

The implementation consequence worth carrying forward: if the collision faces are emitted from the SAME face list as the visual mesh, then mesh and collider agree BY CONSTRUCTION rather than by two code paths being kept in sync - which is the failure mode this project has met repeatedly (AC-0387's far lane silently not carving; AC-0159's two lanes needing to agree on light). Prefer that over adding a second, parallel ramp rule for collision.

2. Does the mesh builder have what the ramp rule needs? YES

The C++ mesh builder's own header documents that its context carries the chunk's own 16x16 columns PLUS the four edge-neighbour rings, with a snap_rings neighbour snapshot for the boundary slice (gdext/src/mesh.cpp, header lines ~20, ~53-62, ~661). Neighbour heights are therefore available where faces are emitted, so the ticket's rule - two adjacent ground columns whose heights differ by exactly ONE connect through a sloped quad - is implementable at the point where a face decision is made, without new plumbing.

3. What the far/coarse path owes, and the other two interactions

Far/coarse agreement: not yet determined by this survey. godot/world/AGENTS.md requires a far or h-only column's H to equal the full path's so promotion never shifts terrain, and ramps are mesh geometry derived from that height - so the coarse tiers must apply the SAME ramp rule for the same columns or the silhouette will change shape as residency changes. That is the AC-0387 class of drift and must be established before the feature lands, not after.

Smooth lighting (AC-0159): a sloped quad's vertices need their own per-corner light and AO values; sampling them as if the quad were two flat faces would reintroduce exactly the blockiness AC-0159 removed, on the very surfaces the ramp feature is meant to smooth.

Buried columns: the rule applies only where terrain meets AIR, so a dirt column under more dirt must not ramp - a face that is not emitted cannot carry a slope.

Recommended next step

When the agent mechanism is back: implement the rule in the C++ face emitter, emit the collision faces from the same list so mesh and collider cannot diverge, apply it consistently on the coarse tiers, carry the AC-0159 corner lighting onto the sloped quads, and assert per column-height pattern (flat, one-step, two-step, ramp corner, in-scope next to out-of-scope, buried, player-placed) which quads are emitted - with the two-step case explicitly NOT ramping and the negative tests shown failing.

AC-0205 smooth ground ramps - final results (2026-10-06)

Status: DONE. Feature implemented in the C++ ro scan (mesh.cpp) + the smooth_ramps setting (default OFF, AWECRAFT_RAMPS=0|1 env override), verified by the new ramp harness arm in BOTH toggle states + the extended settings arm + the standing gate set. G0 (zero SCRIPT ERROR) on every run. No commits (task scope); the Windows DLL follows from the coordinator.

1. The rule (as implemented and as asserted)

A ramp is emitted where a rampable solid block (Data "ramp" flag: grass/dirt/sand/snowy-grass, ids 1/2/4/12) has a non-solid cell above (water counts as air; buried ground never ramps) and one of its four horizontal neighbours is non-solid with a rampable solid one below (surface height differs by exactly one). The vertical face is suppressed via rmask in the C++ ro scan and the 45° quad (shade 0.9, the AC-0159 s_corner_tag(2, j, … corner lighting of the riding column, shared edges seamless) is emitted into the same opaque acc as the rest of the slab. Δ2 never ramps (both vertical faces stay); every other block type stays a full cube. Generated terrain AND player-placed blocks ramp (the rule is id-based, not source-based).

2. The toggle

smooth_ramps in settings.gd DEFAULTS (default OFF), sanitize_bool-clamped (corrupt-safe), on the Settings surface (the "Smooth ground ramps (dirt / grass / sand steps)" CheckBox row, name RampCheck, synced by _sync_controls). Change path: Settings.set_value → apply_ramps() → world.note_ramps() (bumps world.geom_epoch - the per-slab collider stamp re-derives the band - and re-dispatches the real band). The harness env AWECRAFT_RAMPS=0|1 preloads into Settings.values WITHOUT save() (the arms never clobber the user cfg). The switch SHORT-CIRCUITS BEFORE geometry: Ctx.ramps off = rmask 0 + empty ramp-record list = the pre-feature byte path. Arm-verified: default_off, saved round-trip, reload, corrupt-clamp, row present + synced (the settings arm's ramps block: all 7 fields true).

3. Byte-identity with the feature OFF

The OFF-state fingerprint of the one_step pattern (canonical %.9f over all 6 accs of all slabs: length/hash/reversed-hash = "331446/3237708432/767103344", captured on the PRE-FEATURE .so) is re-checked every run: ref.mode "checked", ref.ok true, and on_differs true (the ON state provably moves it) - both final runs. The synthetic patterns additionally assert off_nq == nq per pattern (off = same quad count, same layout, no ramps) and off_zero (zero ramp-class quads band-wide off: the toggle flip drives off_count 0).

4. Far/coarse decision

The coarse/far tiers do NOT ramp. The ramp branch is guarded by !C.coarse and the far emitters never enter it (no rmask, no records). Consequence: H stays bit-exact - the ramp is geometry derived from H, never H itself. Verified: genhash 25/25 (chunk (0,0) 46c20b07c95cb03b57772e1531c97f71 = the documented post-AC-0311 reference - the data.gd "ramp" flag is a pure metadata flag, generation untouched) + farab h_mismatch 0 + 1080/1080 slab byte-identical (and 1080/1080 at G=8). No finding.

5. Collider agreement

By construction AND asserted: the ramp quad is emitted into the same opaque acc the collider derives from, so a ramp collider under a cubed mesh (or reverse) is impossible in the emit path. The arm asserts it per ramped slab in BOTH states: the ramp's two triangles present iff on (collider.ramp_tris == ramp_tris_total: 5838/5838), missing_tris 0, whole mesh surface-0 ⊆ collider (mesh_not_in_col 0), bodies_missing 0, 53 ramped slabs checked. The flip test re-derives the collider on each side: OFF mesh has zero ramp tris (off_count 0), and neg_mismatch true - the negative test: a ramp tri present in the ON collider AND absent from the re-derived OFF collider would red the arm (a mismatched build is caught).

7. Corner lighting

The ramp quad rides the AC-0159 smooth-corner machinery: per-corner s_corner_tag(2, j, … of the riding column's top, shade 0.9 - the shared edges sample the same corner tags as the adjacent flat faces, so the ramp is seamless with the surrounding smooth lighting (no per-face sampling of the slope).

8. Cost (gradient terrain, 240 ramps)

992 quads off == 992 quads on - a 1:1 face replacement (each ramp replaces exactly one vertical face; no quad growth). Build cost wms 2-3 off → wms 2-3 on (within noise on this box; the ramp branch adds a record + a 4-corner emit per Δ1 step, no fill-loop or op-order change). The world scan's forced re-mesh wave settles in seconds (the stamp-based wave-landed test - a world-wide ramp-COUNT stability test can never settle: the light re-bake churn remeshes the edge chunks forever with identical geometry; measured: the count never stabilizes 40 frames, the stamp test converges in seconds).

9. Negative tests (the stale-instrument defence)

Collider-agreement check, red on a mismatched build: neg_mismatch true - the flip test re-derives the OFF collider and asserts the ON ramp tris are ABSENT from it; a build where the collider keeps the ramp under a cubed mesh (or vice versa) would red the arm. Both measured true in the final ON run (and the OFF run's collider shows the 5838 expected ramp tris correctly ABSENT).
