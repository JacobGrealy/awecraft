3. The fix

Answers (b) + the measured dry-slab dominance; bit-identical by construction — every d² operand (x, y, z, the cell centers) is an integer and every squared distance is exact in int32 (|x−cx|,|z−cz| ≤ 30, |y−cy| ≤ 23 for the 12 candidates, d² ≤ ~2,329) and was exact in double, so the int math computes the same integers the double version did; the candidate iteration order and the strict insertion-sort comparisons (ties keep the earlier-iterated candidate) are reproduced op-for-op; the INT32_MAX sentinel plays the 1e300 role. All in aqu_block + a per-column POD (AqColState), no file-static state (TG-safe: columns are disjoint across workers):

  1. Per-column precompute (the fill loop is per-column; x, z, he are constant): A[dx][dz] = (x−cx)² + (z−cz)² for the 4 xz combinations — the centers' xz depend only on the cell ix/iz, never the slab. Computed once per column.
  2. Per-slab candidate cache (rebuilt only when the slab ay changes): the 12 slots in the original (dx, dy, dz) iteration order, each {cy, dA, const AquCell *, valid} — the barrier pair pass now dereferences pointers (the idx % 3 / idx / 9 decode is gone).
  3. All-dry early-out (measured 86% of searches): with no fluid among the 12 candidates the search is provably inert (barrier stone needs a fluid pair → p stays 0; the fluid rule needs n0.type > 0) — returns {0,0}, exactly what the original computed there. The caller's y ≤ 10 lava-layer rule is unaffected (it runs on out.block == 0 either way).
  4. Int d²: 12 × (squared-diff table load SQ[y−cy+128] + A add) + the int insertion sort.

Everything downstream of the search — aqu_pressure, aqu_barrier, the fluid/fl-8 rules, the lava layer, the stone-rim y < he gate — is untouched.
