5. Design & mechanism

5.1 Mechanism choice: frame-budgeted SLICED rebuild (web-style) — recommended, over lazy incremental ring expansion

Web wins on behavior, and the port must match its amortization: the web never rebuilds anything on a crossing — each frame it re-scans rings around the fresh center and does bounded work (3 chunks or 8 ms). The Godot equivalent of “bounded per-frame work under a count + time cap” is a resumable sliced rebuild of the structures the crossing must produce (stubs + band_buckets + queued_keys + queue_size).

Why NOT lazy incremental ring expansion: on a 1-chunk crossing, EVERY existing queue entry’s Manhattan distance from the center changes by 1–2, so the entries must be re-bucketed for the new center regardless — a lazy delta either re-walks the whole O(R²) queue anyway (no win) or keeps stale band assignments, which changes the drain’s band/cursor semantics and exposes the AC-0079 look-priority gate (r4 in_radius_built_max 67 / p95 65) to priority-order drift. The spec’s byte-identical-surface requirement (band sticky cursors, queue_size exact, final-set priority order) forces the single-shot rebuild’s exact math; slicing is the only option that spreads that exact math over frames.

Web-parity note (budgets): web caps at 3 full-gen chunks/frame + 8 ms. A Godot stub is a bare node (~5.3 µs, AC-0076 measured) and a queue op is a dict write (~1–2 µs) — ~1/30 of a web ensureChunk. So the Godot count caps are looser (2048 units/frame) while the time cap is the web-matched governor (8 ms/frame); effective per-frame work stays ≤8 ms.

5.5 Why the MERGE_WANT re-check is mandatory (correctness, not optimization)

Today WANT-snapshot and queue-append happen micro-seconds apart in one call — a want chunk cannot become meshed in between. With the slice, frames elapse between phase 0 and phase 3 while the drain keeps consuming the old queue. If a want chunk meshes in that gap, appending its “build” entry would leave a meshed chunk permanently queued: _collect_pool skips meshed chunks (:657 c.mesh_built → continue) without removing the entry → queue_size can never reach 0 → the G5 drain-completeness gate fails and _process never idles. The re-check (skip already-meshed keys at append time) reproduces exactly what today’s single-shot would have produced (it checks mesh_built live in WANT and never re-queues a meshed chunk). No other phase needs a re-check: WANT and MERGE_OLD read live state per unit; MERGE_RING’s checks are live too; freed chunks can never enter WANT (freed = cheby ≥ r+2, outside the in-radius domain).

func _recenter_slice() -> void:
    if not _rec_pending:
        return
    var t0 := Time.get_ticks_msec()
    var units := 0
    while _rec_pending and units < REC_UNITS_PER_FRAME and Time.get_ticks_msec() - t0 < REC_SLICE_BUDGET_MS:
        if _rec_phase == 0: _rec_want_step()
        elif _rec_phase == 1: _rec_stub_step()
        elif _rec_phase == 2: _rec_merge_old_step()
        elif _rec_phase == 3: _rec_merge_want_step()
        else: _rec_merge_ring_step()
        units += 1
    if _rec_pending:
        var fm := float(Time.get_ticks_msec() - t0)
        _rec_slice_total_ms += fm
        _rec_slice_frames += 1
        if fm > _rec_slice_max_ms:
            _rec_slice_max_ms = fm
    elif _recprobe:
        print("RECSLICE r=%d total_ms=%.1f max_ms=%.1f frames=%d new_n=%d stubs=%d queue=%d" % [...])

Each *_step() processes exactly one work unit (one cell/entry) and, on domain exhaustion, advances _rec_phase (phase 4’s exhaustion performs the SWAP). All five step funcs use _rec_pcx/_rec_pcz as the center and render_radius live.

5.7 Crossing mid-slice (player crosses again while a slice is pending) — exact rules

  1. recenter() re-runs: hysteresis/candidacy/frees run synchronously and exactly (they operate on chunks, which the slice has not corrupted), then the setup block resets the pending state to the new center (phase 0, cursor 0, fresh empty _rec_want/_rec_new_buckets). There is exactly ONE pending rebuild at any time — no double-schedule, no stacked cursors, the new center is authoritative from frame 1 (last_pcx/last_pcz already updated, so the drain’s scores use the new center immediately).
  2. Partially created stubs stay (they are valid scene nodes; the fresh STUB walk skips existing chunks via chunks.has). Partial _rec_want/_rec_new_buckets are discarded (recomputed for the new center).
  3. The old band_buckets + queued_keys are untouched until the new SWAP, so work that entered the old queue mid-slice (drain consumption via _remove_entry, new entries via _enqueue_build :319-344 from edits, _convert_data_to_build kind flips, _tm_retrigger re-enqueues) is folded in by MERGE_OLD walking the live old buckets — precisely what today’s single-shot rebuild would have done had that work existed when it ran.
  4. AC-0082 (threadgen) / AC-0107 (threadmesh) dedup stays authoritative throughout: in-flight keys are deduped at dispatch (keyed maps :79-80, :94-95); the slice neither re-enqueues in-flight work nor touches the dispatch state. A handoff landing mid-slice updates the chunk’s data; the next drain pick / SWAP sees it (the _rec_want meshed-re-check and MERGE_RING’s data.is_empty() check both read live state).

5.9 Drain integration — no cap starvation, no re-trigger storm

  • During the slice the drain operates on the old (still valid) buckets: every old entry’s chunk node still exists except freed chunks, whose entries were already stripped/dropped by the synchronous hysteresis+strip before the slice starts; a stray r+1 “data” entry for a freed chunk is skipped out-of-radius by the drain’s data pick (:729) and dropped by the SWAP’s MERGE_OLD — today’s exact behavior.
  • Feed pacing unchanged: the drain’s unit budget (1 unit, or 3 during _startup_pending() :694-698, gated by DRAIN_FRAME_BUDGET_US) and its handoff to threadgen (_gen_unit :386, cap 6) / threadmesh (_mesh_dispatch :546, cap 3, dedup) run on the old queue during the slice, then on the swapped queue — no frame starves the pipeline; the slice only delays availability of the NEW entries by the time-to-SWAP (1-2 frames @r4, ≈15-25 frames @r50 cold start), and the old queue feeds meanwhile. AC-0107’s finding (workers feed-paced, inflight=1) is preserved because the feed rate is unchanged.
  • No re-trigger storm: the slice re-queues only chunks that are not meshed and not already queued_keys=="build" — identical dedup set to today’s single-shot. _tm_retrigger/_tg stale-drop paths see the same per-key in-flight state (untouched).
  • Spawn-chunk sync (threadmesh always builds (0,0) sync, :551-554) is independent of queue timing. First-frame coverage @r50: today ALL stubs exist in the recenter frame but the queue (hence any data gen) is ready at +97 ms; post-change the queue is ready at +time-to-SWAP (≈250-400 ms cold start). Both worlds show identical visuals in the gap (unstubbed/unbuilt = no mesh = invisible; collision/get_block/fluid read 0 either way — a missing in-radius cell, if reached by the drain or player first, is created on demand exactly as today’s _chunk_data :816-836 does). No new holes appear; the final set is identical (it just arrives over more frames, as the spec permits).
