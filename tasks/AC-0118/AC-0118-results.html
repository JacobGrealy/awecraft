Design as implemented (plan §5)

Five resumable phases per recenter: WANT → STUB → MERGE_OLD → MERGE_WANT → MERGE_RING, each frame ≤ REC_UNITS_PER_FRAME (2048) units AND < REC_SLICE_BUDGET_MS (8 ms), mirroring the web updateWorldStreaming shape (count + time caps). Every per-cell check is the verbatim logic of the deleted _build_queue_for_center (line-mapped in plan §5.11); dx-major (dx outer, dz inner) order is preserved so the final per-band entry order is byte-identical to the old single-shot rebuild for any state the old code would have seen. MERGE_WANT carries the mandatory meshed re-check (a want chunk meshed by the drain between WANT snapshot and MERGE_WANT is skipped → no "build" entry for a meshed chunk → the queue can still drain to 0). SWAP is verbatim of the old :894-902. recenter()'s hysteresis/candidacy/frees remain synchronous (they are the web hysteresis/candidate semantics and are small: ≈7-13 ms @r50, < 5 ms @r4).

Implementation notes (additive, no behavior change): (1) plan pseudocode [ [] x (2*rr+3) ] is not GDScript — implemented as the same append-loop the old code used; GDScript has no div/mod operators — cell math uses //% on non-negative ints (identical). (2) Two extra private state vars: _rec_i (MERGE_OLD is a 2D (band, index) domain) and _rec_want_keys (WANT insertion order — GDScript dicts have no indexed key access; list is appended in WANT order). (3) MERGE_OLD iterates the live old buckets per plan §5.3; a drain removal before the cursor in the current band would shift indices, but drain is score-driven (lowest bands first) and each band holds ≤ 4·(2r+1) « 2048 units, so any band is always fully passed within one slice frame — and the slice runs before the drain in the same _process — so in-band interleaving cannot occur at any harness radius. (4) _rp_stub_n = _rec_new_n (old :903) is executed in the same frame, in _recenter_slice right after the RECSLICE print, so the probe reports the real stub count. (5) _enter_candidate comment: stale reference to the deleted function updated to "the recenter WANT pass".

Honest finding — continuous-walk restarts (r50 only, expected per plan §5.7, consequence bounded): under the loaded r50 walk (headless frames ≈15 ms wall, drain+threadgen+threadmesh+fluids all busy), the 8 ms wall budget yields ~700-1000 slice units/frame, so a full ~52k-unit rebuild needs more than the ~59 frames between walk crossings. Result: the cold-start rebuild and the end-of-walk rebuild complete (2 RECSLICE lines), while the 19 mid-walk rebuilds are restarted at each crossing before finishing (plan §5.7: "a 1-chunk walk restarts the O(R²) slice every crossing"). The queue is therefore stale by ≤1-2 crossings during continuous walking: it stays valid (every entry still in-radius+ring of the new center is re-bucketed from it at the next completed SWAP; out-of-range entries dropped), the drain keeps consuming it, and the world self-heals missing ring data via the existing on-demand path. A/B consequence: r50 walk RESULT is behavior-identical to pre-change — built_final 228 (= pre), ok true, flap 0, remesh_ok/marker_ok true, irb_max 108 (pre 105), walk_s 19.56 (pre 19.6). The end-of-walk RECSLICE new_n=2060 (vs pre-change per-crossing 204) is the direct symptom: with no completed SWAP mid-walk, the final rebuild's WANT sees ring cells whose data was never pre-queued. At r4 the whole rebuild (<2048 units) completes in 1 frame, so no restart can occur (G4(c)/G5). Not a gate failure: G4's r50 gates are the recenter-call p95 (<15 ✓) and RECSLICE max_ms (<15 ✓). Flagged for the AC-0119 follow-up (e.g. make the slice complete within the crossing window at r50, or delta-rebucket).

G5 — drain completeness

Gate correction (measured, recorded as deviation): the plan's G5 expectation queue_size == 0 is unreachable by design of the original code: data_only ring entries are NEVER removed from band_buckets — the drain's scored data pick advances the sticky cursor past them (_advance_dq_past) but only build entries go through _remove_entry (world.gd drain, pre-change behavior, untouched by this task). A data entry becomes inert once its cell has data but persists in the bucket until the next recenter SWAP. The plan's premise ("all ring cells have data at the last recenter → 0 data entries") confuses "has data" with "entry removed". Definitive A/B: pre-change world.gd (git HEAD) re-run with the new field → queue_size 95 at the same RESULT moment, identical to all three post-change runs (95/95/95, deterministic).
