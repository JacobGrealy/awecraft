Deviations / known limits

1. Loading-window exit tail: the exit predicate waits for BOTH pools to drain, and the E2 light-convergence re-mesh churn can keep TM tasks in flight past the moment all 7845 unique columns are meshed. Two of four ON runs therefore hit the 45-min arm cap (58 churn tasks in flight at cap) instead of exiting at ~28 min. Not a correctness issue (all arms report the mesh-complete state), but the loading screen can linger on the churn tail. FOLLOW-UP: exclude re-mesh tasks (or a grace window after target-meshed) from the drain predicate.
2. Boundary band moved DOWN (73–89 → 30–37): the group-consumption fix un-sticks the recenter 5×5 burst prune (previously the leaked group stuck the no-new-burst branch for the whole session). Later recenters now re-burst → work is front-loaded into the burst (which is itself smaller: 33–40 s → 17–18 s) and per-frame walk cost drops. Believed mechanism, consistent across boundary ×2 + perf; HARNESS §3 band updated.
3. "Saturation" = in-flight depths, not more engine threads: the WorkerThreadPool thread count is fixed at engine init; the bypass raises the in-flight caps (TG 4→24, TM 6→64) and removes the main-thread drain/handoff/flush/save caps so both pools stay saturated between frames. gen/s: ON 5.0 vs OFF 3.0. The strips (light/effect assembly) stay on the main thread (byte-identity contract) — moving apply_accs/_assemble_slab to workers is a noted follow-up (AC-0165 native codec pairs for the max win).
4. One OFF-baseline run (load_off2, final code) hung with the main thread blocked (log frozen at t≈22.9 min; the 45-min cap is checked in the frame loop, so it never fired). Its data is redundant (load_off on the same code era completed the baseline cleanly); the hung process should be killed for hygiene (pkill -f "godot --headless" on the host — it is outside the agent sandbox).
