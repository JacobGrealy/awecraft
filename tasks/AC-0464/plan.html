AC-0464 — does the boundary chunk still render unlit black?

Coordinator contract. Medium builder applies it with tasks/templates/implement.md. Reproduce first; fix nothing that is already gone. This ticket's coordinates predate both the warp and the 1 m grid, and two changes since could each have removed it.

1. The defect as filed (2026-10-20)

Standing near the edge of the spawn face looking along the boundary, a large block of the world rendered pure black and unlit — a hole or missing chunk that was actually geometry. Reproduced with these settings (kept for fidelity, but treat the aim as suspect, see §2):

xvfbn -a env HOME=/tmp/dsh_home VK_ICD_FILENAMES=/usr/share/vulkan/icd.d/lvp_icd.json \
  AWECRAFT_SNAPSHOT=<abs>.png AWECRAFT_AIM="3133,60,0,0,-0.4" AWECRAFT_NOCLIP=1 \
  AWECRAFT_RADIUS=4 AWECRAFT_TIME=0.5 AWECRAFT_SIZE=1280,720 AWECRAFT_SNAP_DRAIN=300 \
  ~/tools/godot/godot --path godot --rendering-driver vulkan

AWECRAFT_AIM takes FLAT coordinates; x=3133 was just inside the home/face boundary (hw = 3141.59 at R=4000), z=0. Two captures exist in tasks/AC-0464/captures/ — flag off and flag on — visually identical apart from noise, so warp was ruled out at filing time.

2. Why this must be re-measured rather than assumed

  • The recorded aim may no longer be a boundary view. hw is unchanged, but the grid went to 1 m cubic cells (AC-0469/AC-0471), the home pair moved to the CANONICAL CHART PLACEMENT (AC-0467), and chunks are now 16 m of 1 m cells. x=3133 is still ~8 m inside hw, so it is plausibly still a boundary view — verify that arithmetically before rendering, and if the geometry moved, choose a new aim that IS a boundary view and say so.
  • AC-0463 L6 CHANGED HOW FACE CHUNKS ARE LIT: the face build now consumes the star payload (window + 8 neighbour strips) instead of an own-column pull, at all four build sites. An unlit black chunk on the face side of the boundary is exactly the symptom that change could have removed.
  • AC-0469 stage E moved face chunk GENERATION onto the worker queue and its LANDING to _face_land (data, light seed, mesh, collision, occluder) — so a chunk that used to land half-lit may now land whole.

3. What to do

  1. 3.1 Confirm the aim is still a boundary view arithmetically (flat x vs hw, at the 1 m grid) and state it. Fix the aim if not.
  2. 3.2 Render it at the same settings and with the same window/flag pair if a flag still exists (if it does not, say so). Read the frame for a large black unlit region: report the pixel values of any suspicious region and where it sits in the frame.
  3. 3.3 If it is GONE: cancel this ticket with those numbers — do not fix what is not broken, do not close it as done. Say which of the two changes most plausibly removed it and why.
  4. 3.4 If it is STILL THERE: localise it before touching anything — is the black region geometry with zero light (read the light values at those blocks via an existing arm or the debug API) or missing geometry (a hole)? Those are different bugs. Then report and fix only the named one.
