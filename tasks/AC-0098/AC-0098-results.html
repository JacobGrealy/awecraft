AC-0098 — held voxel tools take their per-voxel colour from the icon

status: evidence for coordinator review · builder: delegated subagent · the held pickaxe/axe/shovel/sword voxels (16 items: 109, 111–125) are no longer a flat single tint — every voxel carries the sRGB colour of its own icon pixel in godot/assets/items_atlas.png.

1. Where the icon art lives, and how the voxel colours are derived from it

The icons are per-pixel art: godot/assets/items_atlas.png (1024×1024, 32×32 cells, rects in godot/assets/items_atlas.json), imported with the default sRGB process. Nothing about them is procedural — there is no generator to share, so the ticket's "strongest approach" applies: the icons are sampled programmatically and the voxel build and the icon share one source of truth.

The decisive finding (probed first, before any design): each icon is a per-cell rendering of the very 32×32 TOOL_GRIDS shape the voxel tool uses. The sampler verified the match in BOTH directions for all 16 tool items: every non-. grid cell has an opaque icon pixel, and there are zero spare opaque icon pixels on empty grid cells (0 fallbacks, 0 spares — exact 1:1). So the derivation is per-cell, not per-palette: voxel cell (i, j) takes the colour of icon pixel (i, j). The icon's hand-drawn per-cell shading (highlight / base / shadow / edge tones per material) IS the shading variation — nothing was invented by eye.

The committed sampler tasks/AC-0098/sample_tool_icons.py reads the atlas + the parsed TOOL_GRIDS + the canonical tints (Data.items icon floats, player.gd HANDLE_C) and regenerates the TOOL_ICON_TONES const block in player.gd (marked AC-0098 GENERATED BLOCK — do not hand-edit). If the icon art changes, re-running the script re-projects it into the voxel build.

Two canonical pins, forced by existing gates (not taste):

  • Head anchor — the icon tone closest to Data.item_tint(id) is replaced by the canonical tint float exactly. The toolres arm asserts held_head_color() == Data.item_tint(id); the "head" node must keep reading the canonical tint.
  • Handle anchor — the icon tone closest to HANDLE_C is replaced by HANDLE_C exactly (the existing handle base — no movement of the established tone).

Colour-space handling: icon bytes are sRGB display values, while albedo_color is linear. Non-anchor voxels are sRGB-decoded (the EOTF in player.gd _srgb_lin) so the voxel wall displays exactly what the icon texture displays. Anchor voxels display the sRGB-encode of the linear tint float — the same value the flat era already displayed for that tone (the tint convention is untouched; this ticket does not rebase the game's colour management).

2. The shading rule (stated)

For each tool item, for each TOOL_GRIDS cell (i,j):
  colour = icon pixel (i,j) of the item's atlas cell          # per-cell 1:1
  EXCEPT cells of the head-anchor tone  -> Data.item_tint(id)  (canonical, exact)
  EXCEPT cells of the handle-anchor tone -> HANDLE_C           (canonical, exact)
Material: head voxels are the icon's head tones (tier colour family);
handle voxels the icon's wood tones — the icon art already carries the
highlight (up/sun side), shadow (receding side), base and dark edge
outline per material. No geometric tone assignment was invented;
the icon IS the palette.

So "up faces lighter, down faces darker, edge dark" is not a rule I applied — it is what the Faithful-style icon art already does per cell (e.g. iron pick: white/#d8 highlight on the bar's lit side, #c1 base, #44/#18 shadow + outline; wood: #896727 highlight, #6a501e/#684e1e base, #493615/#372910/#281e0b/#20180a shadow ladder).

5. Poses did not move

The pose plumbing (HELD_POSE rows, the per-type pos/rot/scale assignment, swing arcs, TOOL_GRIDS geometry, voxel count, bbox) is untouched. The one structural risk was real and was caught: splitting the head/handle into per-colour meshes shrank the "head"/"handle" nodes' AABBs to the anchor-tone subset, which moved the toolpose arm's camera-space centroids (measured up to 0.135 m off the pristine baseline). Fixed by keeping "head"/"handle" as invisible full-extent geometry anchors (canonical tint material, as before) with the visible per-colour meshes as *_cN children — the arm's measurement contract is byte-for-byte the old one.

Measured A/B on this tree (same session, same world, toolpose arm): all 16 pose vectors (4 tools × idle/apex × head/handle) drift 0.0000 m between the pristine (stashed) tree and this change; rot_delta 0.858 rad, bbox_diag 1.224/1.10/1.10/0.796, scale_expect [0.33, 0.33] unchanged. AC-0113's 0.0 m baseline therefore holds — any pose movement would be a regression, and there is none.
