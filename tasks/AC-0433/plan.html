3. Edit shape

3.1 Two statics.

  1. chunk_key(face:int, cx:int, cz:int, R:float) -> String — the canonical key of a valid chunk, formatted "%d:%d:%d" % [face, cx, cz] with plain integer formatting (no locale, no padding, no floats). Invalid face/radius/chunk -> "" (empty is never a valid key).
  2. chunk_from_key(key:String, R:float) -> Dictionary — the inverse: {ok:true, face, cx, cz}, or {ok:false}. Accept ONLY the canonical form: split on ":", require exactly three parts, each a non-empty run of ASCII digits, no leading "+"/"-", no spaces, no leading zeros beyond the value zero itself (so "0" is fine but "00" and "007" are not), then validate face/radius/face-domain. A key produced by chunk_key must always parse; anything else must be rejected rather than coerced.

3.2 Why strict parsing. A streaming dictionary keyed on strings silently accepts a second spelling of the same chunk and then holds two copies of one chunk — the classic double-load. Strict canonical parsing is what makes the key a real identity. The probe must show the rejects actually reject.

3.3 Probe (new p2c2_probe.gd; one RESULT line; exit 1 on any failure). Sample chunks on all 12 faces (cx, cz from {0, 1, last} within each face's chunk grid).

  • T1 round trip. For every sampled chunk: chunk_from_key(chunk_key(c)) returns exactly c. Report keys and round_trip_failures (0).
  • T2 uniqueness. All produced keys are distinct, and the count equals the sampled chunk count (duplicates 0). Also assert chunk_key is stable across two calls and across a fresh R of the same value (same string).
  • T3 reject table. These must ALL return ok:false: "", "1", "1:2", "1:2:3:4", "a:b:c", "1::3", ":2:3", "1:2:", " 1:2:3", "1 :2:3", "+1:2:3", "-1:2:3", "1.0:2:3", "01:2:3", "1:02:3", "1:2:03", "12:0:0" (face out of range), "1:-2:3", "1:2:999999", "0x1:2:3". Report reject_cases and reject_failures (0).
  • T4 near-miss control. Take one valid key, delete one character, and confirm it no longer parses (or parses to a DIFFERENT chunk) — proving the parse is not sloppy in the accepting direction (near_miss_detected true).

RESULT keys: ok, keys, round_trip_failures, duplicates, stable, reject_cases, reject_failures, near_miss_detected, fails.

5. Acceptance

One canonical spelling per chunk, exact inverse, non-canonical input rejected, and still no caller and no save-file involvement.

6. Risks

A lenient parse (trimming, int coercion) passes the round trip and fails the job — the reject table is the real test. Do not relax it to make a case pass; report the discrepancy.
