ALL GATES GREEN. R16 (the #1 gate, fresh C++ gen, no disk shortcut): the AC-0219 1-mesh-per-frame handoff cap is tuned to a 3-burst per frame (STREAM_TM_HANDOFF_PER_FRAME 1 → 3, tunable at boot via AWECRAFT_TM_HO, clamped 1..16). ho_max = 3 in both fly phases — the burst is live; flying forward at 4x (17 m/s, 8 s, 9 recenters) still shows ahead while moving: 279 forward chunks first-built during flight (farthest 264 m) — equal to the 1-cap run, and each recenter's ahead ring now lands at 3/frame (~⅓ the frames) instead of 1/frame. The whole-circle initial fill (build phase, ahead ring included) drops 35.9 s → 12.4 s (2.9× faster): at 1/frame the handoff cap throttled the in-flight gate, so builds queued behind it; at 3/frame the pool stays saturated. p95 stable — flat or improved in every phase: static 28→143, moving 143→143, fly4 59→63, fly50 31→40 (fps p95); p50 200/200/250/250 everywhere. No sustained drop: the only max-frame is a single 85–100 ms frame (10–12 fps) — the same one-off class as the 1-cap baseline (82–85 ms). No pop-in: 0 lost chunks / 0 rebuilds in every run; ahead edge reaches the far circle edge (263–264 m) in every run. G0 clean (0 SCRIPT ERROR before + after, every arm); SMOKE ok:true ×4; no regression (chunkiocpp byte-identical md5 8a89…9081, genhash 25/25 == AC-0215 NEW baseline in 2 runs, light standing baseline 15/0/14, meshprobe/stripsprobe/ pullprobe 100% exact, nofallback ok:true).
Finding (fixed): the first R16 run at the 3-burst rate logged 1 SCRIPT ERROR (Invalid access to property or key 'tid' at threadmesh_poll) — a pre-existing AC-0203-class torn read (the pool worker writes entry["t_run"]/["result"] on the worker thread while the poll reads the SAME Dictionary every frame; Dictionaries are not thread-safe) that the 3-burst rate made ~3× more likely to hit in its rarer form: e.has("tid") passed, then e["tid"] threw, aborting the whole poll for that frame. The effect was self-healing (the entry stays in flight, next poll hands it off — 1 frame late, no pop, no corruption), but it is a logged SCRIPT ERROR outside the documented noise classes. Fix: the poll now reads e.get("tid", null) and skips the entry for the frame on a torn read (the AC-0203 skip path, made exception-free). The final R16 run: 0 SCRIPT ERROR. All gates below are from the FINAL code state (cap 3 + guard).

1. What changed

godot/world/world.gd — the AC-0219 cap tuned (cap logic intact: same process-frame counter, same break, same epool exemption)

sitechange
const STREAM_TM_HANDOFF_PER_FRAME 1 → 3 — the steady-state streaming handoff burst per process frame. Minecraft paces chunk builds to a "few per tick with a frame budget", not a hard 1: 1/frame was too slow for 4x–50x flight (a recenter's ahead ring of ~30 ready meshes took a full second of frames to land, so the ahead band filled well behind the player). At 3/frame the same ring lands in ~10 frames. New const STREAM_TM_HANDOFF_MAX := 16 = the clamp ceiling (a bad env value can't disable the cap or burst back into the 64-mesh recenter-burst regime the cap exists to break up).
var stream_ho_cap (new) the effective burst (const default) — the runtime tuning knob, so 2/3 can be A/B'd in the harness without a code change. Set in _ready from AWECRAFT_TM_HO when present: stream_ho_cap = clampi(hoe.to_int(), 1, STREAM_TM_HANDOFF_MAX) (same pattern as drain_budget_ms/AWECRAFT_DRAIN_MS).
threadmesh_poll() (the cap check) the break condition now tests _stream_ho_n >= stream_ho_cap (was the const). Everything else is untouched: the Engine.get_process_frames()-keyed counter _stream_ho_n (resets per process frame — threadmesh_poll runs up to 3×/frame: physics + process + recenter), the per-call hb_max batch, the loading window's separate LOAD_TM_HANDOFF (6) pace, the UNCAPPED shutdown poll-drain, and the edit-lane (epool) exemption.
threadmesh_poll() (torn-read hardening — see the warn box) var tid = int(e["tid"]) → var tidv = e.get("tid", null) + skip-on-null (i += 1; continue). A torn read that slips past the has() guard above can no longer raise a SCRIPT ERROR and abort the poll; the entry stays in threadmesh_inflight and the next poll sees a consistent dict. This is the AC-0203 documented design ("a torn read degrades to a skip, never a corrupted apply") applied to the one read that still threw.

Reading — the gate. (1) Flying forward shows ahead while moving: fly4 — the sustained 4x flight case — lands 279 forward chunks DURING flight (equal to the 1-cap run), the ahead edge reaches 264 m (the far circle edge), and the queue stays bounded (136 total / 31 build vs the 797 cap). ho_max = 3 in both phases proves the tuned cap is live: each recenter's ahead ring (~30 ready meshes at 4x) now lands in ~10 frames at 3/frame instead of ~30 frames — the ahead band fills over a few frames, as intended. The first-fill story is the headline: the whole-circle build phase (ahead ring included) goes 35.9 s → 12.4 s (2.9×), because at 1/frame the handoff cap throttled the in-flight gate and builds queued behind it. (2) p95 stable: p95 fps is flat or improved in every phase (static 28→143 — the landing tail now finishes inside the build phase; moving 143→143; fly4 59→63; fly50 31→40). (3) No sustained drop: p50 is 200–250 everywhere (flat or up); the only outlier is ONE 85–100 ms frame per fly phase (10–12 fps) — the same one-off class the 1-cap baseline had (82–85 ms / 12 fps), not a sustained region.

fly50 ahead 124 → 62 — attribution + variance, not a loss of ahead visibility. The counter measures FIRST appearances of forward-half chunks DURING the 2 s burst. At 3-burst the circle is fully built 2.9× earlier, so by the fly50 start fewer forward chunks are left unbuilt — less is left to first-appear during the burst (the 797/797 total, the 263 m edge reach, and the 0-lost/0-rebuild no-pop check all hold). The metric is also run-noisy at 50x: the two 3-burst runs report 93 and 62 for the same code (the torn-read guard — a one-frame skip on a rare torn read — is the only delta between them), vs 124 for the 1-cap run. Phase-start chunk state + recenter-debounce alignment + scan alignment move the count by ±30. The stable, gate-relevant numbers — fly4 279==279, edge reach 263–264 m in every run, lost 0 / rebuilds 0, built_all true — do not move.

6. Scope notes / caveats

  • R50 was NOT run (PENDING — the .so crashes in the coordinator env, AC-0206); the Windows build was NOT run. The 3-burst only relaxes the handoff side of the drain; the queue-depth cap + farthest-band eviction (AC-0222) are untouched, so the R50 guard holds by construction — the R50 queue-no-stall gate will re-measure when AC-0206 resolves. (At R50 the 3-burst also raises the initial-load handoff rate from 60→180 meshes/s in steady state; the loading window keeps its own LOAD_TM_HANDOFF=6 pace, unchanged.)
  • The torn-read finding is pre-existing, not introduced by the tuning: the worker-side writes (entry["t_run"] line 1511, entry["result"] line 1544) and the main-thread poll reads are the AC-0082 handoff pattern AC-0203 already documented as a race ("the entry's dict is being written on the pool thread"). The 1-cap simply hit the rarer torn form (has() passes, [] throws) ~3× less often — it was never eliminated. The guard makes the one throwing read exception-free; the rest of the poll already uses .get() (non-throwing), and the post-completion handoff reads run after the worker's last write (safe by the is_task_completed ordering).
  • Default choice (3, top of the 2–3 range): 3 = "a few per tick" and gives the 2.9× first-fill win. If the coordinator wants a more conservative default, AWECRAFT_TM_HO=2 (or flipping the const) is a one-value change — no code change needed to A/B it.
  • Fly phases: 4x = 9 recenters (full rebuilds, 17 m/s → ~0.9 s/chunk), 50x = 27 recenters (debounced, AC-0213). Ahead counts FIRST appearances only (reband swaps tracked separately as rebuilds: 0 in every run). The R16 arm's build phase runs with loading_active = false (same as the AC-0222 A/B — controlled).
