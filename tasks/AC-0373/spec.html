Registry notes (verbatim, quoted):

1) User Story: The random-tick pass no longer stutters the frame, but what is left of its cost is spent walking columns to find the ones that can tick at all - work that could be answered by an index instead of a scan.

2) Technical Details:
WHERE THIS COMES FROM (AC-0370, 2026-09-28): porting the random-tick pass to the native lane cut the tick from 8.0/12.8/14.1 ms to 4.0/5.6/5.7 ms, the frame share from 15.1% to 8.9%, and the multi-fire incidence from 16/20 to 10/20 worst frames. The named residual is the **two column scans at 1.48 ms/tick** (of which the main column scan is 0.87 ms), which is now the largest remaining term inside a tick that fires one to three times per frame during the streaming storm - so it is worth 1-3 ms/frame, roughly 10-20% of a storm-phase frame.
THE JOB: replace the scan with something that does not touch every column. The candidates, to be chosen by measurement the way AC-0370 chose its route: (a) maintain a compact per-region index of columns that currently have anything tickable (the random-tick pass only matters where there is foliage, crops, snow, ice or fire - an empty stone column can never produce a tick), invalidated on edit and on load/unload rather than recomputed; (b) if the scan is already bounded by a per-column flag, make the flag hierarchical (a per-slab or per-region "nothing tickable here" bit) so the scan can skip whole regions in one test; (c) hoist the scan out of the per-tick path entirely if the tickable set changes far more slowly than the tick fires. Measure which of these the data supports BEFORE writing one, and report the split the way AC-0370 did.
THE ACCEPTANCE TEST IS AC-0370's OWN INSTRUMENT: the tick arm (`window_md5` byte-identical, `recompute_mismatch` 0 across all 118,080 positions - the port made this a cross-lane oracle, so it is now the strongest behaviour check available) plus the R24 walk's tick ms/frame, frame share, multi-fire count and worst frame. A change that does not move the tick number must be reverted and said so.
CONSTRAINTS: bit-identical behaviour (the md5 oracle is the gate, not a proxy); genhash 25/25 byte-identical; the fluids, trees, leaves and fluidfall/fluidsettle arms byte-identical before and after; r16 all sub-flags with far_holes 0/0 both bands; G0 zero SCRIPT ERROR; the battery green (7 modes in one process need 16 GB); and if the native lane is touched, OPS.md's rebuild plus re-stage procedure, including the Windows DLL because the product is Windows-only.
CONTEXT: read tasks/AC-0370/AC-0370-results.html first - it has the sub-stage brackets, the measured split, and the new `gdext/src/random_tick.cpp` this ticket would extend. DRAIN remains the bigger target (52.5 ms of a 69.8 ms worst frame on my verification run) and is AC-0369's successor work, so this is the secondary lever.
