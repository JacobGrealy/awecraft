1. What the two scans were (read, not re-derived)

AC-0370 moved the hash + random_tick_map bookkeeping to the native lane and named the residual: two GDScript column scans, both walking the ENTIRE resident chunks dict (≈ 1400–1600 entries on the R24 walk):

  • _random_tick_pass — keep face ≤ 1 and band == 0 and !data.is_empty() → the 41-column taxicab diamond → one native call. AC-0370 measured 0.89 ms/tick.
  • _leaf_decay_tick — the SAME filter minus the face test, then per kept column leaf_decay.is_empty() + timer countdown. AC-0370 measured 0.61 ms/tick — on a walk the timer work is ZERO, so the whole cost was the second 1400+ walk.

Mutation-point census (before choosing a route): the filter inputs per resident chunk are exactly membership in chunks, c.band, c.face, c.data empty-vs-not; every write to them funnels through a small set of world.gd sites (§3). Column defaults are band 0 / face 0 / data [] (chunk.gd) — a spawn fails the filter until its data lands, and face chunks (AC-0309 grid) keep band 0 by default, so they sit INSIDE the leaf-decay filter (the random pass excludes them only via the face test). The tick fires at the TOP of World._process, before every streaming pass of the frame; catch-up ticks run back-to-back inside one _game_tick_accumulate.

The measurement also exposed the one place the naive reading is wrong: during the LOAD storm (the worst-20 frames themselves sit at t 4.3–13.4 s), band-0 data landings fire at ~1/tick, so a "stamp on ANY resident mutation" design rebuilds almost every tick there. The stamps must be GATED on "can this mutation move the band-0 set" (§3) — then even the storm rebuilds drop to the 41 diamond landings + a few rebands.

3. THE FIX (world.gd only — the memoized band-0 column list)

One memo, two consumers. _rt_rebuild_if_stale() walks the resident dict with the band-0/data-present filter (the old scans' verbatim filter, verbatim dict order) and caches (cx, cz, node-ref) lists under a stamp _rt_idx_v; it rebuilds only when _rt_stamp moved. _random_tick_pass applies the face test over the cached ≈ 41 nodes; _leaf_decay_tick applies its per-column leaf_decay test over the same 41 (that test stays per-tick — it is edit-sensitive and must see same-frame set_blocks). The per-tick cost drops from two ≈ 1450-walks to two 41-reads; the full walk happens only on a stamp change. Bit-identity is by construction: same filter, same dict order, same columns — the tick arm's cross-lane window_md5 is the gate, and it passed.

The stamp sites are each gated by the "can this move the memo's set" predicate (a far-ring landing or a band 1↔3 reband never rebuilds):
