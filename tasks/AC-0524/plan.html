1. The question, and the two answers it could have

As you fly, the satellite landscape should become detailed terrain without a blue veil, brightness flash, or a different atmosphere around loaded chunks.

AC-0512 measured 151,371 px — 61.4% of the exterior — reading as sky "while the body is drawn". The user has explicitly warned that this figure must NOT be assumed to apply universally, and rightly: it was one pose, one frame, one seed. So the ticket's first job is to find out, per case, which of two very different situations is true:

  • (A) OCCUPIED-BUT-SKY-LIKE — terrain is being drawn at that pixel, in a colour indistinguishable from the sky. Fixable as a colour/lighting problem, in the renderer we already ship.
  • (B) GENUINELY MISSING GEOMETRY — nothing is drawn there. No colour correction can fix this, and attempting one would be the "restore a blue bridge to conceal missing chunks" that the scope forbids.

Reporting an aggregate percentage across cases would repeat the error the user is guarding against. The deliverable is a per-case classification with the evidence that discriminates (A) from (B).

2. The discriminating instrument (this is the ticket)

A pixel that looks like sky cannot tell you whether geometry was drawn there. You need a signal independent of final colour. Use, in this order of preference, and state which you used:

  1. Resolved depth at the candidate pixel — geometry at a terrain distance establishes (A); sky-depth establishes (B). This is the cleanest signal and does not depend on colour at all.
  2. Occupancy/publication counters for the chunk covering that ray, from the existing instrumentation.
  3. If neither is available at that stage, a temporary developer A/B isolation (permitted by scope, on the accepted post-removal baseline) that makes drawn terrain unmistakable — dev-only, not a player-facing switch, and removed before close.

3. What to measure, at MATCHED materials, across time and altitude

The scope names the matrix; do not shrink it silently. Materials: grass, snow, sand, water. Times: day, dusk, night. Vantages: ground and altitude. For each cell of that matrix:

  • the near-tier colour of that material (the reference the far tier must match),
  • the satellite-tier colour of the same material in the same frame,
  • the classification from §2 — (A) occupied-but-sky-like or (B) missing,
  • and the signed difference, in normalized linear space (not sRGB display values, which is what makes later comparisons meaningful).

4. The four suspects the scope names — check each, in linear space

Each is a distinct cause with a distinct fix; the evidence must say which one, or that none applies:

  1. Baked satellite RGB decode vs height data. Does the shipped texture's RGB decode to the same colour the height/bake pipeline believes it does? (AC-0478 regenerated those 12 textures this session and verified height_decode 12/12 byte-exact — re-verify, do not assume.)
  2. Lit satellite vs UNSHADED near endpoints. AC-0480 established these are different shading models (near tier unshaded with L = 0.20 + 0.80*m_direct; far tier engine-shaded on top of its own light). A lit surface matched against an unshaded one cannot agree at all times of day — this is the most likely single mechanism and should be quantified per time-of-day.
  3. Source HDR exports — is anything companding twice, or exporting an already-encoded value?
  4. Single final tone mapping — is tone-mapping applied once, to the composite, or has a source been tone-mapped already?

Name the cause with a measurement before proposing anything. If the measurement says the endpoints differ because one is lit and one is unshaded, then the correction is in the shading endpoint, not in the palette.

5. Hard prohibitions (from the scope — quote them to yourself before editing)

  • "Fterrain remains 0; never reinstate fog, haz_d or a wash to conceal missing chunks." No depth fog, no mist, no wash, no blue handover bridge. AC-0510 removed these by user ruling.
  • Do NOT retune the palette, moon gain, or the bake recipe. Do NOT add a new Options switch.
  • Keep accepted sky / planet-limb / cloud behaviour unless separately authorized.
  • No terrain generation, grid/radius, save/cache format, collision, simulation, light-settle safety or streaming-queue changes in this ticket.
  • A large geometry/lighting redesign requires another plan — return PLAN-INSUFFICIENT instead of scope-creeping.
  • Temporary dev A/B isolation is permitted; it must be removed before close and must not be player-facing.

9. Method and tooling

Locate every anchor by symbol — this repo changes under a parallel session and three of my plans carried dead line numbers. Render set planned up front: ~1200 s per render, serial, so decide the matrix subset you can afford and say what you skipped rather than silently shrinking it.

Engine calls need HOME=/tmp/dsh_home in the same bash command, an absolute engine path, from the repo root, one godot at a time. Run engine work from a script FILE invoked by name — gate_run.py's slot test is pgrep -f "[g]odot", which matches your own shell string. BLUR IS OFF by user ruling — never enable it; it would destroy the colour measurement. Renders: xvfb-run -a env HOME=/tmp/dsh_home VK_ICD_FILENAMES=/usr/share/vulkan/icd.d/lvp_icd.json godot --path godot --rendering-driver vulkan with AWECRAFT_SIZE=1280,720, AWECRAFT_SNAP_DRAIN=600. Another session holds this checkout — take the slot only when pgrep -af '[g]odot' is empty; commit nothing; add named paths only.

10. Acceptance

The (A)/(B) classification per case with a named discriminating signal; the material × time × altitude matrix with signed normalized-linear differences; one of §4's causes demonstrated by measurement before any correction; any correction narrow, colour-domain and tied to that cause with before/after numbers; no fog/mist/wash/palette/bake/switch changes; genhash 25/25 on the same generator; Windows evidence handed over as a protocol with every figure labelled development-only.

11. Risks

(1) Assuming AC-0512's 61.4% is universal — the user explicitly warned against it, and the whole ticket is built to avoid it. (2) Correcting colour where geometry is simply missing, which is the forbidden "blue bridge" by another name. (3) Comparing sRGB display values instead of normalized linear, making the numbers uninterpretable. (4) Reaching for the palette or a switch because it is easy. (5) Silently shrinking the matrix. (6) Trusting a stale anchor or a stale prerequisite.
