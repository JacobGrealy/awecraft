AC-0389 — the ambient sound bed: toggleable, default off

User report (Windows build, 2026-10-02): “there is a background sound that sounds like waves or wind or something, we should remove this or make it Togglable.” The culprit is the ambient bed AC-0039 added to godot/autoload/audio.gd — a 2.0 s seamless loop (integer-cycle sines at 1/2.5/5.5/55 Hz + Hann-windowed noise) on a dedicated looping player outside the 16-voice SFX pool, wired always-on by an auto-play() in _ready().

1. The fix — where the toggle lives and what its default is

LayerFileWhat changed
Settinggodot/autoload/settings.gd New key ambient_enabled in the DEFAULTS table — default false — with a plain bool clamp branch (same shape as fog_enabled). Persists to user://awecraft.cfg through the existing set_value/save/load_settings machinery, so it survives restarts and travels with saves like every other setting.
UIgodot/ui/menu.gd “Ambient sound (background wind bed)” checkbox (AmbientCheck) on the Options → Settings page — the same panel as “Sound volume”, “Enable fog”, “Hunger” — created with the established code-created-checkbox pattern (fog/hunger precedent), synced in _sync_controls, handler calls Settings.set_value("ambient_enabled", on) + Settings.apply_audio(). Not a debug key.
Enginegodot/autoload/audio.gd New Audio.set_ambient(on) (start/stop the dedicated bed player only — the SFX pool is never touched). play() gates only the bed branch on the flag. _ready() no longer auto-plays the bed — the AC-0039 always-on wiring is gone. Settings.apply_audio() (already called from main.gd _ready and the volume slider handler) now pushes volume and the toggle to Audio in one step, so the persisted value applies at startup and on every toggle.

Default off is the right call (per the ticket notes): the user asked for removal rather than tuning, and an always-on loop is something a player cannot un-notice; keeping the toggle means AC-0039’s ticket stays satisfied for anyone who wants ambience.

2. The audit — event-driven vs ambient, all nine sounds

The distinction is the whole issue: event-driven voices need an Audio.play(name) call at an interaction site to fire (they play when the player does something); ambient voices play on their own.

SoundClassWhy
blockEVENTBreak/place/door interactions (alias break/place/door → block). Fired only by player interaction.
stepEVENTFootfall — distance-based cadence on the player’s local frame (STEP_DIST 2.3 m of tangent travel). Needs a step.
hitEVENTDamage thud (alias hurt/pickup → hit). Needs a hit.
eatEVENTEating crunch. Needs the player to eat.
splashEVENTWater interaction. Needs the event.
arrowEVENTArrow shot (arrow.gd). Needs a shot.
bowEVENTBow draw (arrow.gd). Needs a draw.
mobEVENTMob growl (mob.gd; alias gorilla → mob). Needs the mob to act.
ambientAMBIENTThe 2 s seamless loop bed. The only voice with the self-playing property. It was wired always-on via the _ready auto-play (not even via a call site) — exactly the mistake this ticket exists for. No game code calls Audio.play("ambient"); the bed player alone drove it.

Audit result: the ambient bed was the ONLY sound with the always-on property. There is no wind layer, no cave rumble, no altitude/biome-keyed loop anywhere in the tree — the other eight bases are only ever started by interaction-site Audio.play calls (player.gd / arrow.gd / mob.gd), verified by grep (the only other "ambient" hit in the tree is an unrelated lighting readout in main.gd). No other sound needs this treatment; the bed gets it alone.

4. Is the default-off state asserted by an arm?

Yes — in both arms, in the same task:

  • Sound arm (D2): ambient_toggle.default_off asserts Audio.ambient_enabled == false AND Audio.ambient_playing() == false at arm start (nothing has started the bed), then asserts set_ambient(true)/set_ambient(false) drive the toggle, and the events-with-bed-off proof above. Headless caveat honored: the arm asserts the toggle state and the trigger bookkeeping, never the sound (the dummy driver makes .playing driver-dependent, so it is only read for the default check, where nothing has ever started it).
  • Settings arm: ambient {default_off, saved_on, back_off} — the default is false after a fresh load, and the value round-trips through set_value → cfg → load_settings (the same discipline as fog_enabled).

Note on the old expectation: the pre-AC-0389 arm did not assert the bed was PLAYING by default — it asserted the stream’s LOOP_FORWARD mode (ambient_loop), which is a property of the generated AudioStreamWAV, not of the playback state. That expectation was never about the always-on wiring, so nothing had to move: ambient_loop stays green as-is, and the new expectation (default OFF) is the one established above.
