2) Technical Details:
REPORTED BY THE USER FROM THE WINDOWS BUILD (2026-10-01): "the satellite LOD never loads, I just see a white planet". ROOT CAUSE FOUND BY READING THE CODE, and it is a textbook editor-versus-export bug that no headless arm could have caught:
`godot/world/satellite_body.gd::configure` chooses its texture source with **`FileAccess.file_exists()` on `res://assets/satellite/satellite_face%02d.png`** (via `_all_exist(_res_paths())`). In the editor that returns true, because the SOURCE PNGs are on disk. **In an exported build the source `.png` does not exist** - the export contains the imported `.ctex` and `FileAccess` does NOT consult Godot's import remapping the way `ResourceLoader` does. So `_all_exist` returns FALSE, the canonical seed-44 branch is skipped, and the code falls through to **`_start_bake()`**: the body then draws with **unset textures, which is Godot's default WHITE**, for as long as the bake runs. That is exactly the reported symptom.
WHY EVERY GATE PASSED: the arms run from the source tree, where `file_exists` succeeds, so the failing branch was unreachable in every test we own. AC-0311's "0 of 12,582,912 pixels" comparison was between the Python bake and the IN-ENGINE bake - it never exercised the `res://` load path at all. This is the same class of blindness as the engine-side gap AC-0383 just instrumented: a whole code path with no instrument that can reach it.
THE FIX, small and precise: (a) use **`ResourceLoader.exists()`** for `res://` paths - it consults the import system and is the correct predicate for an imported resource - while keeping `FileAccess.file_exists()` for `user://` (the cache dir), where it is right; (b) make a FAILED load LOUD rather than silent: if the res textures are expected but unavailable, log the reason and then bake knowingly, instead of falling through with no signal; (c) consider making the canonical seed take the shipped-textures path without a filesystem probe at all, since for seed 44 those textures ARE shipped, and the probe exists only to decide whether to trust them.
THE VERIFICATION THAT WOULD HAVE CAUGHT IT, which is part of this ticket and not an afterthought: an assertion that exercises the EXPORT CONDITION rather than the editor condition. The honest form is a predicate test - the loader must decide on `ResourceLoader.exists`, and there must be a check that the two predicates are not interchangeable (for example an arm field recording which predicate chose the source, so a run that silently fell through to baking is visible). If a post-export check is feasible on this box, verify that the shipped PCK/exe actually contains the 12 imported textures; if it is not feasible, say so and rely on the predicate test. Either way the white planet must be reproducible-or-excluded BY EVIDENCE, not by the user looking again.
CONSTRAINTS: genhash 25/25 byte-identical (a render tier touches no generation); the satellite arm's ladder (hidden / rim / dissolve at nadir_op 0.5 / full) and the 0.25 texel-to-chunk ratio must stay intact; the piece-1 two-axis variance guard keeps passing; the standing set green (G0 zero SCRIPT ERROR, farab h_mismatch 0, ladder 20/20, meshprobe 1.0, halo ok, lightstate 0/0, r16 all sub-flags with far_holes 0/0 both bands, boundary r4 in band, the battery); ARCHITECTURE.md sync if the load contract changes; and the Windows export must be rebuilt so the user can confirm.
CONTEXT: read godot/world/satellite_body.gd (configure, _res_paths, _all_exist, _phase_load) and tasks/AC-0310/AC-0310-results.html for the tier's design and its ladder.

WHAT WAS ACTUALLY WRONG, because the shape generalises and that is the durable part: satellite_body.gd decided whether the shipped per-face textures existed with `FileAccess.file_exists` on a `res://` path. THE RULE IS IN OPS.md: never decide anything about a res:// resource with FileAccess.file_exists - use ResourceLoader.exists or load - and, more generally, ANY DECISION THAT IS TRUE IN THE EDITOR AND FALSE IN AN EXPORT IS INVISIBLE TO EVERY GATE WE OWN. THEREFORE, with high confidence: (1) THE WHITE PLANET IS A WASHED-OUT HAZE, NOT A MISSING TEXTURE. The body renders, and its colour is the sky's own air colour rather than terrain, because the shader's haze is driven by a DISTANCE ramp - `d = length(VIEW)` pushed through the slant-path and clear-dist terms - and at orbital range that ramp SATURATES, so the haze weight is at maximum across the WHOLE DISC instead of only at the limb. The haze was designed as a limb effect (a long path through the air shell near the horizon) and it has become a full-disc effect at exactly the range the body is meant to be seen from, which is why the body reads as a uniform pale ball with no terrain in it. That also explains why the export fix changed nothing the user could see: the textures were loading all along, and no amount of correct loading can survive being blended into the sky colour. (2) THE CLOUD REPORT IS CONFIRMED EXACTLY as the user described - sparse white PUFFS on a shell rather than a continuous layer wrapping the planet, which is a cloud-system property (AC-0385) and not a satellite-body defect. (3) A THIRD OBSERVATION FALLS OUT OF THE SAME IMAGE and is worth recording before it becomes a mystery: at that altitude only two terrain chunks are drawn at all, so the world below the player is largely absent - which is the far lane's coverage and relates to the LOD work in AC-0387 rather than to the body. THE METHOD LESSON, and it is the same one three times now: the arm measured the ladder (hidden / rim / dissolve / full) and read green because it computes the values the SHADER is handed, not the pixels the shader produces, and a green arm is not a picture. The bake guard measured texture bytes; the arm measured thresholds; the export probe measured loadability - and none of them could see that the body's colour is the sky. When a visual feature cannot be rendered on the build box, the only instrument that reaches it is a human being with a screenshot, and asking for one should have been the FIRST move on this ticket rather than the last.

CLOSED - the shader fix is in the shipped build (fb9644d) and the user has been asked to confirm it, which is the only remaining step and is theirs because renders are infeasible here. WHAT WAS ACTUALLY WRONG, after two wrong diagnoses in a row: the satellite body's fragment shader computed its dissolve opacity from `d = length(VIEW)`, and in Godot's fragment stage `VIEW` is a UNIT vector - `view_highp = -normalize(vertex_interp)` in the 4.7.1 engine source - so `d` was identically 1.0, `op` was identically 0, and the body DISCARDED 100% OF ITS FRAGMENTS. It had never rendered, in any build, at any altitude, and the user's original words "the satellite LOD never loads" were literally exact. The pale ball in their screenshot is the AeroWash layer plus the cloud puffs - a different thing entirely - which is why my first fix (the res:// existence predicate) changed nothing visible even though it was a genuine latent bug, and why my second reading of their screenshot as a "washed-out haze" was a plausible inference from an ambiguous image that happened to be wrong. THE FIX computes the true world-space distance, `d = |(INV_VIEW_MATRIX * VERTEX) - CAMERA_POSITION_WORLD|`, with the limb term evaluated in world space; the physical model is now stated as the ray's impact parameter, and the finding worth keeping is that the term was never mis-scaled - it was evaluated in the wrong space on top of `d` being constant. Haze across the disc now reads centre 0.0000, mid 0.1723, limb 1.0000, monotone, where before NO FRAGMENTS EXISTED AT ALL. THE INSTRUMENT LESSON IS THE THIRD ONE ON THIS TICKET AND THE SHARPEST: the bake guard measured texture BYTES, the arm measured the ladder's THRESHOLDS from GDScript, and the export probe measured LOADABILITY - and not one of them computed what the shader outputs. The new check does, and it was BUILT TO FAIL: replaying the old shader asserts zero fragments, replaying a haze-identically-1 body asserts variance 0.0, and the real fix yields a disc-centre output variance of 23794.3 against the texture-derived 23794.6, a ratio of 1.000. A body that renders as a constant cannot pass it now. A caveat that stays open deliberately: headless never compiles the shader pipeline, so the Windows build is the real GPU-compile check, and if the planet now appears but looks wrong the debug console build will print Godot's own shader error - which is why the user was asked for exactly that text if anything looks off.
