1. plugins/subagent-reasoning.ts (verbatim plan skeleton + 1 documented adaptation)

/**
 * subagent-reasoning — AC-0104
 *
 * Pins the reasoning effort for subagent children. A subagent's LLM call
 * normally inherits the root's `agent-default-model` selection (xhigh in this
 * deployment). This plugin intercepts the `agent/request` waterfall and, for a
 * subagent agent only, replaces the resolved `reasoningEffort` with the
 * deployment-configured `subagentEffort` (any valid effort id, e.g. `low` or
 * `medium`). Non-subagent requests pass through untouched.
 *
 * Wired via $DSH_HOME/cordis.patch.yml. The effort is validated against the
 * provider model's `reasoning.efforts` at the llm service boundary
 * (packages/llm/llm/src/index.ts), which throws UNSUPPORTED_REASONING_EFFORT
 * for a value the model does not support.
 */

import type { Context } from '@deepseek-ai/cordis'
import z from '@deepseek-ai/schemastery'
import { ReasoningEffortId } from '@deepseek-ai/dsh-llm'
// The `agent/request` waterfall + its payload/next signature are declared by
// @deepseek-ai/dsh-agent's `declare module '@deepseek-ai/cordis'` Events merge
// (packages/core/agent/src/runtime-types.ts). Sibling consumers
// (compaction-basic, llm-retry) import a type from dsh-agent to pull that merge
// into scope; without it `ctx.on('agent/request', ...)` is not a known event key.
import type {} from '@deepseek-ai/dsh-agent'

export const name = 'subagent-reasoning'
export const inject = ['agents'] as const

export interface Config { subagentEffort: string }
export const Config: z<Config> = z.object({ subagentEffort: z.string().required() })

function isSubagent(a:any){
  const h=a.session.header as any // SessionHeader.delegationDepth/origin/parentSession packages/core/session/src/types.ts:91
  return (h.delegationDepth??0)>0 || h.origin==='subagent' || !!h.parentSession
}

export function apply(ctx: Context, cfg: Config){
  ctx.on('agent/request', async (payload, next)=>{
    const base = await next() // waterfall: must delegate docs/cordis-primer.md:30
    if(!isSubagent(payload.agent)) return base
    const want = ReasoningEffortId(cfg.subagentEffort) // Branded packages/llm/llm/src/brand.ts:55
    if(base.reasoningEffort===want) return base
    return {...base, reasoningEffort: want} // validated vs reasoning.efforts packages/llm/llm/src/index.ts:793 else UNSUPPORTED_REASONING_EFFORT
  })
}

Adaptation vs the verbatim skeleton: exactly one line added — import type {} from '@deepseek-ai/dsh-agent'. The agent/request event + its payload/next signatures live in @deepseek-ai/dsh-agent's declare module '@deepseek-ai/cordis' Events merge; every sibling consumer (e.g. compaction-basic, llm-retry) imports a type from dsh-agent to pull that merge into scope. Without it, ctx.on('agent/request', …) is TS2345 (not a known event key) and the two listener params become implicit-any (TS7006). The body (isSubagent, apply, the :any annotation, the waterfall, the branded effort) is the user's verbatim code. G1 is clean with this line; removing it re-introduces exactly the 3 errors the brief named.

low / medium flip proof (the user's follow-up)

The subagentEffort config value is a single switchable string — no label-based routing. Flipping that one value flips the applied effort (real apply(), from g3.log):

cfg {subagentEffort:"medium"} -> subagent reasoningEffort "medium"  (case3, new object)
non-subagent payload          -> base returned unchanged (same ref)  (case1)
base already "low" + cfg low  -> SAME reference, no rewrite           (case4)

How DSH actually loads TS plugins (mechanism found)

Direct load via the tsx/esm Node loader — no build step. DSH does not compile user TS plugins; it runs them through the ambient module pipeline. Evidence in the checkout (read-only): packages/sandbox/sandbox-local/src/index.ts:563 → [process.execPath, '--import', 'tsx/esm', sourceEntry] ("the built entry if present, else the package source through tsx (development)"); packages/boot/app-boot/README.md — "The dsh app owns its Node source-launch hook … built consumers continue to use plain Node package resolution"; the root tsconfig.json carries the full paths map "so tsx running examples/ and scripts/ … resolves workspace imports through this file." Relative specifiers in a config "always resolve against the config directory" (why name: ./plugins/subagent-reasoning.ts resolves against the patch file's dir, per README:32). So a user drops a .ts plugin + a cordis.patch.yml and DSH boots it straight — verified end-to-end here by running the real plugin + real schemas through tsx from the checkout root (G2/G3) and by the offline --dump-config composition (G4).
