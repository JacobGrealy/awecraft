AC-0471 — deviations + the per-axis grid census
================================================

THE FIX (one-line form)
-----------------------
The halved axis of each chart face now spans its half-width with HALF the
cells — 3,141 of (W/2)/3141 = 1.000189 m — instead of 6,283 of 0.500015 m.
Single-sourced: SphereMath.cells_u/cells_v (GD) + awesm::sm_cells_u/v (C++),
the AC-0309 halving rule moved from SIZES to COUNTS (x faces 4-7 =
(6283, 3141), every other face = (3141, 6283); home faces 0-1 key flat and
never chart). CELLS_HALF = 3141, chunks_u/v = (count+15)/16 (393/197).
face_cell_scale is DERIVED (axis span / axis count). Chart geometry
IDENTICAL: uv_to_world / world_to_face / face_chunk_transform sample
uv = cell/count, and the (u,v) -> world map itself is count-independent —
what moved is which (u,v) a cell index maps to on the halved axis (the
declared rebase).

DEVIATIONS
----------
D1. Plan §3 applied as anchors, not a boundary (the AC-0469 D1 precedent —
    world.gd is the plan's named anchor region and carries most of the
    sites). Files edited outside the §3 table, and why:
    - world/chunk.gd `_warp_cell_point` — the GD fallback twin of
      mesh.cpp:4199 (§3 names mesh.cpp); left desynced, the GDScript and
      native warps would disagree on every halved-axis vertex.
    - world/generator.gd:245 — comment only (the linearization stride is
      the MAX axis by design).
    - player/player.gd:2840 — comment only (the DDA range note).
    - scenes/harness.gd — the warpcensus extension is plan-named
      (cell_sizes / cubic_ok / face_hashes / fixed_hashes); the
      planetwalk / sphere / residency per-axis sites are owed because the
      sphere arm is neighbor_key's only consumer (a single-count rewrite
      of its range checks would go red at the new counts) and the
      planetwalk/residency arms read the cell scale directly.
    - world/world.gd `_face_rearm_home_neighbors` (15298) — not in the
      plan's site list: it carries the same S*0.5 along-edge unit bug as
      _face_rebake_boundary (the plan's named sibling); left at the old
      8 m/chunk extent, the rearm window would keep the pre-fix size.

D2. Plan §2 inaccuracy — "faces 0-3 -> (s, s) already correct" is true
    only for the HOME PAIR (faces 0-1, the flat 1 m world, flat keying).
    Faces 2-3 (the +/-Y chart faces) use the face grid and their u axis
    charted 6,283 cells over W/2: the measured pre-fix baseline (r2)
    shows cell_sizes face 2 = face 3 = [0.500015, 1.000029]. The fix,
    applied via the plan's own mechanism (the existing halving rule on
    the COUNT), fixes faces 2-3 identically — in scope by mechanism;
    the declared chart rebase therefore covers all 10 chart faces (2-11),
    not only 4-11. Measured: 90/90 fixed generation hashes moved, 9/9 on
    EVERY face 2-11 (pre-fix baseline vs post-fix, same keys).

D3. Plan gate (d) inaccuracy — the `genhash` arm (_genhash_print) hashes
    ONLY the home-pair columns (WorldGen.generate, cx,cz in [-2,3]^2); it
    does not hash chart faces. Home generation consumes no face cell
    counts, so the result is STRONGER than the plan's expectation:
    genhash 25/25 BYTE-IDENTICAL pre/post (genhash-r1.log vs r2.log, diff
    on the GENHASH lines: 0). The chart-face rebase is proven instead by
    warpcensus fixed_hashes (90/90 moved — the pure generate_face A/B,
    same (face, ccx, cz) keys both sides), the expected_center movement
    ([2830.55, -1173.7, 2.83] -> [2830.54, -1173.7, 5.66]) and the
    resident-set reindex (face 5's window: pre 5:388:383..5:392:392,
    post 5:388:191..5:392:196 — the along-edge axis is 197 chunks now).
    World regenerated on chart faces 2-11: stated plainly, no
    byte-identity chased there (the plan's own instruction).

D4. The halved axis cell is 1.000189 m, not 1.000029 m. 6,283 is odd:
    W/2 cannot be split into 3,141.5 cells, and the plan mandates
    3,141 = floor. Residual 1.887e-4 m per cell (~0.019 % of a cell) —
    "1.000 m" at the 3 decimals the plan measures; the cubic_ok gate
    uses the [0.999, 1.001] band. Post-fix measured cell_sizes: faces
    0-3 [1.000189, 1.000029], 4-7 [1.000029, 1.000189], 8-11
    [1.000189, 1.000029] — every chart face 1.000 x 1.000 m at 3 dp,
    cubic_ok TRUE (pre-fix FALSE: the halved axis read 0.500015 on all
    12 chart faces).

D5. THE z-FACE ROWS BUG (a stage-B leftover unit bug, surfaced by the
    fix): _face_stream computed the z faces' edge-NORMAL row cap with the
    HALVED axis' cell size (S*0.5) — but on the z faces the edge-normal
    axis is v, which is FULL (the halved axis is u, the along-edge one).
    Measured: pre-fix policy edge_rows_z = 9 vs edge_rows_x = 5 at the
    64 m window; post-fix both = 5 (rows = min(393, ceil(win/(16*S)) + 1)
    — one formula, both classes, read through face_cell_scale). Face-
    chunk residency follows (warpcensus face_chunks 100 -> 60; residency
    steady face_resident 57).

D6. AC-0470 side effect (the prestream window) — PARTIALLY SELF-FIXED.
    The z faces' raw_idx flag (the +hw chart offset) is correct only for
    the mirror z faces (9/11). Post-fix, faces 9/11's window is CORRECT
    (stride = the true half-axis cell; (x+hw)/stride lands in [0, 3141])
    — the self-fix the plan anticipated. Faces 8/10 stay degenerate:
    their window clamps to the chart's far corner (cc 195-196 at the
    x=+hw end — the same 1-2 column shape as pre-fix's 391-392,
    reindexed; planetwalk lap_0-8/lap_0-10 to_resident_sample shows the
    8/10 band at ccx 193-196). The direction fix is AC-0470's raw_idx
    work — AC-0470 is NOT declared done; its remaining scope is now
    exactly that one flag (+ the stale comment in _face_stream, updated
    here to state the per-sector truth).

D7. The chunk-space linearization stride stays face*CHUNKS_PER_FACE*16
    (6,288) — the MAX axis's span. The halved axis' range (cc <= 196)
    fits inside it with no collisions (max linearized cell =
    11*6288 + 6287 = 75,455, unchanged, int-safe). sm_chart_dir and
    sp_col_index keep the stride; sm_chart_dir's chart divide is
    per-axis now.

D8. Off-chart negative chunks (planetwalk to_resident_sample lists
    9:-1:8 / 7:-1:8): the block API (get/set_block_key ->
    _ensure_face_chunk) does NOT clamp at the chart boundary — a DDA
    step past u=0 on a mirror face generates a ccx = -1 chunk.
    PRE-EXISTING: the identical keys appear in the pre-fix r1 run. The
    linearization slot face*6288 - 1 overlaps the previous face's last
    slot — that class exists pre-fix identically. Separate ticket
    material (block-API chart-edge clamp); out of scope here, reported
    plainly.

D9. Stale legacy arms left as-is (the AC-0469 D3 precedent — none is in
    this ticket's gate set): the crossface arm (N = 6283 hardcoded x2 +
    the um formula), ac0433probe (the iv formula x2), the meshcost arm
    (zedge := 1016 = 63*16+8 — the 1024-cell era's edge row; the true
    row is 392*16+8 = 6280, and z0 = 400 is off-chart on face 8's halved
    u axis post-fix — the arm has been mis-aimed since AC-0469; the
    follow-up owed by AC-0469 D3/D4 covers it).
