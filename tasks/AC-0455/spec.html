Registry notes (verbatim, quoted):

1) User Story: Most of a builder's steps are spent doing things a script could do: reading seven
   documents to find the forty relevant lines, running eight gate commands one at a time and
   reading eight logs, and hand-writing an HTML results page. Each of those is a round trip
   through a 15 tokens/second model. Four small scripts collapse them into three steps, which
   makes every future ticket cheaper to run without making it any less proven.

2) Technical Details:
   Depends on AC-0454 (the implement-to-plan prompt defines the file formats these scripts emit).
   Four new scripts under tasks/scripts/ (tooling rules: tasks/scripts/AGENTS.md):

   (a) context_pack.py AC-NNNN  ->  .scratch/AC-NNNN/context.md
       One file a builder reads instead of seven documents. Contents, in order: the ticket's
       notes; plan.html's goal + file list; for each file in the plan's file list, the grep
       anchors named in the plan with N lines of context (NEVER a whole file); the named
       ARCHITECTURE.md sections only (matched by heading); the HARNESS.md rows for the named
       AWECRAFT_LOGIC modes; the last continuity entry; the frozen constants the plan cites.
       HARD CAP 12k tokens (~48 KB) - over the cap it truncates and says so, it does not grow.
       Must never emit whole harness.gd (36,630 lines / 1.5 MB ~= 430k tokens, larger than the
       250k window) or whole world.gd (15,498 lines) - asserted in a unit test.

   (b) gate_run.py AC-NNNN --arms g0,smoke,probe,genhash,...
       One command runs the ticket's gate set SEQUENTIALLY from the HARNESS.md §4 recipes, with:
       a pgrep -af '[g]odot' guard before every arm (never kill a process it did not start), the
       mandatory `ulimit -v` cap from godot/OPS.md (a runaway gate OOM-kills dsh-web.service),
       HOME=/tmp/dsh_home per call, RSS sampling every 10-15 s for large-radius arms, and output
       to .scratch/AC-NNNN-gates/<arm>-rN.log. Writes summary.json + summary.txt (ONE LINE per
       arm: name, rc, ok, census, the headline value) and touches HEAVY_GATES_DONE at the end.
       --dry-run prints the exact planner without invoking godot (the only mode CI can run).

   (c) results_page.py AC-NNNN --deviations <file>
       Renders tasks/AC-NNNN/AC-NNNN-results.html from summary.json + the deviations text +
       continuity.md. Self-contained HTML, no external refs; carries the G0 output, every RESULT
       JSON, the arm table, the deviations block and the PNG list when visual. Refuses to render
       an arm with no log (the H3 honesty rule: no number that is not in a log).

   (d) builder_stats.py [--since DATE] [--json]
       The scoreboard, from ~/.dsh/sessions/*/session.jsonl.zstd: per builder session duration,
       steps, out/in tokens, tokens per step, implied tok/s, and the wall~out_tokens regression
       with R^2. This is the script that produced the AC-0454 evidence and it is how the change is
       judged: it must reproduce R^2 >= 0.9 and ~15 tok/s on the existing logs.

   GATES for this ticket: no godot arm is required to prove the scripts - they are tooling, not
   engine code. Proof is (i) a unit test per script, (ii) each script run against a real existing
   ticket folder as a fixture (AC-0433 for the pack and gate summary, AC-0450 for a render-heavy
   results page), (iii) builder_stats.py reproducing the measured regression, (iv) gate_run.py
   --dry-run. Do NOT modify godot/scenes/harness.gd (it stays pristine).
   DEFERRED: actually re-running a heavy gate set through gate_run.py is the next real ticket's
   job, not this one's smoke test.
