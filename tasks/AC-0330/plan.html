AC-0330 — make every battery mode usable as a pass/fail gate

Coordinator contract. Medium builder applies it with tasks/templates/implement.md. Per-arm, with evidence. The ticket's rule is explicit: do not flip ok to true, do not delete arms, and do not decide the group as a block.

1. The debt, as filed

Seven of the 31 battery modes cannot be used as pass/fail gates, and that has been true for a long time. The battery compare script only diffs VALUES, so nobody notices status.

  • Three report ok:false in the BASELINE ITSELF and still do: craft, water, trees.
  • Four emit NO ok key at all, so pass/fail is undeclared: atlas, buckets, player, interact.

2. Facts that have MOVED since this was filed — verify, do not assume the filing

  • player has been reporting ok in this session's runs (sprint_ok true, rc=0), and interact reports place_ok — so the "no ok key" claim may be stale for one or both. Establish what each emits TODAY before deciding anything.
  • water was identified at AC-0326 as a third victim of the same dead sea parity (its ±60-cell mirror-ocean scan finds no live water) — so its ok:false likely belongs to outcome (a) with a known cause, not (b).
  • craft was measured byte-equal at AC-0316 and trees' ok:false is documented as stale Aug-19 fixtures (AC-0320 noted genhash_fail 2,2). Both look like (a) with named causes — but confirm per arm.
  • basis and sphere are not in this list only because they are not battery modes — both became green this session (AC-0326/AC-0327), which is the same class of debt being retired elsewhere.

3. What to do, per arm

  1. 3.1 Run each of the seven and record what it ACTUALLY emits today (ok present/absent, its value, and the arm's own sub-flags). Report a table — one row per arm, before any edit.
  2. 3.2 Classify each one with evidence, not as a group: (a) stale expectation or broken scenario setup → fix so it asserts again, using the arm's own RESULT values and the standing values in HARNESS.md §3 as the reference; or (b) value-reporting by design → say so explicitly in its HARNESS.md §1 row, making ok-less a declared contract rather than an oversight.
  3. 3.3 Fix only what 3.2 justifies. For (a), the fix may be in the arm's expectation, its setup, or a product defect the arm correctly caught — if it is a product defect, stop and report it rather than adjusting the arm to match broken behaviour.

7. Risks

(1) Flipping ok to true — forbidden and it would fake the gate. (2) Adjusting an arm's expectation to match genuinely broken product behaviour — that converts a real defect into permanent silence. (3) Treating the seven as one problem; the ticket says per-arm and that is the point.
