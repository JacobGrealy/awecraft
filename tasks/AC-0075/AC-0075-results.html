AC-0075 — chunk-streaming: boundary/first-load harness + r-sweep baseline (AC-0034 child 1/4)

Measurement-only task (plan AC-0071 "step 0: measure first"). Adds the AWECRAFT_LOGIC=boundary harness + extends AWECRAFT_LOGIC=perf, and records the r=2/4/50 baseline that children 2–4 will be judged against. No streaming behavior was changed — the only non-harness code touched is one read-only instrumentation stamp in world.gd (called out below). Everything headless; no renders.

Headline findings for the web-vs-native r=50 decision:
(1) Native r=50 steady-state memory ≈ 7.7 GB at 8 483 chunks → ≈9 GB full radius (~0.86 MB/built chunk). That is 25–90 GB in a wasm/GPU browser tab per the §1.6 3–10× per-chunk multiplier — r=50 is not browser-feasible.
(2) r=50 is dominated by the recenter re-enqueue cost, not meshing: first-draw 7.6 s is almost all an O(n²) initial recenter (7 397 ms); the boundary walk's frame p95 is 841 ms / max 991 ms because every crossing re-inserts ~101 new chunks through _insert_sorted, which walks the ~12 290-entry queue. The plan's "$\lt$1 ms recenter" holds only at r≤8 (≤361 entries).
(3) At a realistic 1 chunk/s walk the drain keeps the radius partially built even at r=4 (in-radius peaked 64/81 during the walk; 11/20 leading edges never finished before streaming out) and is hopelessly behind at r=50 (236/10 201). Phase 1's scored queue / bulk-light / staged collision are required before r≥4 walks are smooth.

What this means for web vs native at r=50 (6-core / ~63 GB box)

First-draw (Play → playable)≈ 7.6 s (O(n²) recenter 7.4 s + spawn mesh)≈ 23 s–76 s (single-threaded wasm, 3–10×)

Reading: r=50 as a native default is "works but stutters" — the world fills slowly (~10 chunks/s) and each chunk-boundary crossing is a ~0.5–1 s hitch; it is playable but not smooth. As a web default it is not feasible at all (memory alone rules it out). The AC-0072 slider default of 50 should therefore stay native-only; the web default should be ≤ 8 (r=4 native is smooth at 60 fps with p95 53 ms first-load frames and 19.2–57 MB memory; r=4 walks keep up mostly with only transient lag). Phase 1 items (scored O(1)-insert queue to kill the O(n²)/O(queue) recenter, bulk batch light, staged collision, fluid prescreen) are what make r≥4 walks smooth and would cut the r=50 recenter from seconds to near-zero — but they do not change the r=50 memory story, which is why the web ceiling must be low.

Instrumentation exceptions (called out)

  • world/world.gd — added var fluid_tick_samples: Array = [] and two fluid_tick_samples.append((Time.get_ticks_usec()-t0)/1000.0) lines at the two existing TICKMS sites in tick_fluids() (early-sleep return + end-of-scan). This is the only non-harness change. It is read-only measurement (nothing reads it for a decision), adds no block writes/reads, and is provably bit-identical to the simulation — the fluids/fluidsettle/fluidfall/webfall/buckets/water battery modes are all byte-identical pre↔post. Rationale: the spec asked for fluid_tick_ms_p95 from the TICKMS signal, but the harness runs in-process and has no stdout capture, so the smallest possible in-process stamp at the exact TICKMS sites was the minimal way to collect those samples.

Deviations / notes

  • Memory API: spec said OS.get_used_memory(); that symbol does not exist in this Godot 4.7.1 build (verified via method probe). Used the available OS.get_static_memory_usage() (returns process heap bytes) — same role for the before/after Δ.
  • Walk speed: AWECRAFT_WALK_SPEED default 16.0 blocks/s = 1.0 chunk/s (in the spec's 0.8–1.2 range). Measured 16.4 blocks/s. At a slower "realistic sprint" (5.6 blocks/s) the drain would keep up better; the 1.0 chunk/s baseline is intentionally a stress case per spec and is what exposes the r≥4 lag.
  • perf frame cap: was a fixed 1200 frames (≈20 s) — far too small for a 10 201-chunk radius. Made it maxi(1200, (2r+1)²·5): r≤8 keeps 1200 (r=2/4 behavior unchanged, §1.6 still matches); r=50 → 51 005 frames (857 s), which still ended with all_meshed:false (full r=50 drain ≈ 18 min > 1 200 s budget) — reported as data, not a failure.
  • burst semantics: measured as time-to-build that crossing's new east-edge column (2r+1 chunks). Crossings whose leading edge never finished before streaming out report −1 — this is a genuine streaming-lag signal (9/20 at r=4, 20/20 at r=50), not a measurement gap.
  • wallshot excluded from the headless G2 battery: it is a render-only mode that hangs on await Debug.snap → frame_post_draw (never fires headless). Pre-existing; unaffected by this change (separate dispatch branch); the task is headless-only. Included in the 31-mode list on both runs (timed out with no RESULT, identically pre and post).
  • G2 timing-field modes: 7 modes (player, swing, survival, hunger, daynight, editperf, perf) carry inherently non-deterministic RESULT fields (wall-clock ms, day/night cycle rate, time-of-day, sway animation samples). They differ pre↔post and post↔post2 (two identical-code runs) in the same field set — proving the variance is intrinsic machine timing, not this change. Every deterministic field in those 7 is byte-identical pre↔post.
