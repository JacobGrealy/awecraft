AC-0469 stage A — take the grid to 1 m blocks, and only the grid

Coordinator contract. High-effort builder applies it with tasks/templates/implement.md. The user has fixed the constraint: blocks are ~1 m × 1 m × 1 m and that is unchangeable gameplay. This stage changes the CHART GRID to 1 m cells planet-wide. It must not touch the payload or save formats, which merely happen to use the number 1024 for something else.

1. Goal

CELLS_PER_FACE = 6,283 so a face cell is 1.000 m at R = 4000, with every grid-class site parameterised by that constant, and the game booting and running green at the new resolution so the cost can be measured for real.

2. The census already taken (round 39 — extend it, do not repeat it)

  • CELLS_PER_FACE: 29 GDScript sites. The literal 1024: 120 GDScript, 33 C++.
  • Three classes, and only ONE may change: (1) GRID — the chart divide and cube-map indexing, e.g. gen.cpp:710-733 ("index is face*1024 + the face's own cell index", then /1024 to recover u,v), the 0..1023 clamps, per-face cell loops, cell→uv→world conversions; (2) PAYLOAD — out(1024) at gen.cpp:2880, p_far->resize(1024) at 3935, the "size is exactly 1024" contract at 4443; that 1,024 is BYTES of block data per 16-high section. MUST NOT CHANGE; (3) OTHER — round numbers, texture sizes, capacities: inspect, do not touch.

4. Edit shape

  • 4.1 Classified list first (deliverable). Table of every 1024/CELLS_PER_FACE site: file:line, class (GRID/PAYLOAD/OTHER), and what you did. That list is the proof this stage did not touch the formats.
  • 4.2 One constant per language. GDScript keeps SphereMath.CELLS_PER_FACE; C++ gets/keeps a single named constant. Grid-class literals become that constant. Do not introduce a second source of truth.
  • 4.3 Send-check any format boundary. Before declaring done, confirm the slab payload and far payload sizes are unchanged (same bytes/column, same 1,024-byte constants, same save version behaviour) — this is the failure mode a blanket sweep would cause.
  • 4.4 Rebuild both binaries (Linux .so; report the Windows .dll status — a cross-compile may be attempted but a failure there is a deviation, not a blocker for this stage).

6. Acceptance

The grid is 1 m everywhere, the game boots and runs, the save/payload formats are provably untouched, and the real cost at 1 m is measured.

7. Risks

(1) Format corruption by blanket replace — the classified list and the save round-trip are the guards. (2) Address-space blowups: index arithmetic that assumed 1024 (bit shifts, & 1023, packed ints) will silently wrap — search for those patterns explicitly and report any you cannot safely widen. (3) Generation cost may make the world unusable; that is a FINDING for the throughput work, not a reason to revert the grid.

8. Fences

  • No git commit/push/add; no tasks/TASKS.yaml; no new tickets.
  • No edits outside §3. Never change a payload/save size.
  • If the plan cannot be applied — anchor missing, symbol absent, steps contradict, or a design decision this plan does not make — write PLAN-INSUFFICIENT: <what is missing, file:line> and EXIT. Do not invent the design.

9. Resume point

1 m blocks are fixed by the user. Stage 0 priced them; the census classified the sites. This lands the grid change so the cost can be measured for real, then the two measured bottlenecks (gen 13.4 ms, mesh 19.2 ms per chunk) are attacked, and the home grid is deleted.
