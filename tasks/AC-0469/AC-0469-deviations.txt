AC-0469 stage 0 — deviations + the projection formula
=======================================================

FORMULA (any cell re-derives; the arm computes it, tasks/AC-0469-deviations.txt is the written form)
-------------------------------------------------------------------
Inputs:
  face_width(R) = pi*R/2                          (R = 4000 -> 6283.185 m, SphereMath)
  cell_m   = face_width(R) / CELLS_PER_FACE       (6283 -> 1.000 m; 3000 -> 2.094 m; 1024 -> 6.136 m)
  D        = view distance in m                   (0.5 / 1 / 2 / 4 km)
  B        = bytes_per_chunk.measure              (MEASURED by the arm on the live tree)
  M        = ms_per_chunk.build = gen_data_ms + mesh_build_ms (sum of two MEASURED parts)

Projection (per cell size c, per view distance D):
  r       = ceil( D / (16 * c) )                  (16-cell chunk footprint = 16*c metres)
  chunks  = (2*r + 1)^2                           (the SQUARE window the residency is — the
                                                   81-chunk radius-4 anchor is (2*4+1)^2; the
                                                   plan's "cover that disc" is read as the
                                                   window the lane actually holds, not a
                                                   geometric disc: disc area pi*r^2 would be
                                                   (pi/4)*chunks if anyone needs it)
  bytes   = chunks * B
  stream_ms = chunks * M                          (the per-pass streaming of the WHOLE window at
                                                   the measured per-chunk build cost)
  fill_s  = stream_ms / 12 / 1000                 (at the existing FACE_STREAM_BUDGET_MS = 12.0 —
                                                   the lane spends at most 12 ms of build work
                                                   per frame, so a full window fill takes
                                                   stream_ms/12 frames at 60 fps)
  x_vs_6m = chunks(c, D) / chunks(6.136, D)       (the trade: at the same view distance, c costs
                                                   (6.136/c)^2 the chunks of the 6.136 m cell
                                                   — 37.6x at 1.000 m, 8.58x at 2.094 m)

60 fps verdict inputs:
  frame constraint : M <= 16.7 ms                 (one build must fit one frame — the pacer budgets
                                                   BETWEEN chunks, a single build runs to
                                                   completion)
  budget constraint: demand(v) = 2*(v/60)/(16*c) * M <= 12.0 ms
                     (chunk-boundary crossings per frame <= 2*(v/60)/(16c), the diagonal worst
                     case, at the top speeds from player.gd: walk WALK 4.3 m/s, cruise-sprint
                     SPRINT 5.6 * cruising_speed 6 = 33.6 m/s)
  The 12 ms budget PACES the fill (fill_s above), it does not cap the view — a window that
  needs 10 minutes of paced build still runs at 60 fps while it fills. The deciding numbers
  are bytes (resident memory) and fill_s (time to a full view), not the frame budget.

DEVIATIONS
----------
1. The plan's "cover that disc" was implemented as the SQUARE window (2r+1)^2 — the shape the
   residency actually is (the plan's own 81-chunk radius-4 anchor is (2*4+1)^2). A geometric
   disc (pi*r^2) would hold (pi/4) the chunks; the square is the conservative (larger) side.
   The formula above is written out so either re-derives.
2. bytes_per_chunk is the MEASURED live-tree census (palettized slab payload p+i bytes for
   c.data AND c.fl + every slab mesh's ArrayMesh array bytes + the ConcavePolygonShape3D face
   bytes). The GDScript node/dict overhead (the per-slab Slab object, the slab dicts, the
   MeshInstance3D/StaticBody3D node overhead) is NOT byte-countable from the API — it is a
   labeled gap, not a hidden zero; it is small against the mesh arrays (the census reports the
   split, so the gap's size is bracketed by the mesh/collision share).
3. ms_per_chunk.build = gen_data_ms + mesh_build_ms — both parts MEASURED on this machine
   (the fresh data-only ensure; the sync build_mesh_face on band chunks with data-live
   in-line neighbours). The sum is DERIVED by addition, labeled as such in the RESULT. The
   warp sub-part is MEASURED from the chunk.gd accumulator delta around the mesh pass
   (warpcensus's own 0.42 ms figure is the warp only, as the plan states).
4. The timed gen ensures run on FACE 8's edge row (ccz = 63, along-edge ccx 47..62; the band
   mesh line is ccx 25..40 on the same row). The measurement had to move off face 4: face 4's
   far rows (ccx 0) sit on the far hemisphere, where face_cell_band's home_flat_ext reads
   d.y <= 0 and returns (INF, INF) — _face_chunk_min_dist then serves the 0.0 sentinel
   ("this face does not border the home patch") and EVERY ensure there builds the mesh
   (build on demand), so face 4 cannot produce a data-only chunk. The first arm attempt
   measured exactly that: the "fresh" face-4 cc 47..62 chunks came back resident+meshed from
   the settle, min_dist 0.0 (the arm keeps a gen_diag {key, resident_before, in_window,
   min_dist_m, mesh_built} in the RESULT so the data-only claim is evidence, not assumption).
   Face 8 is the clean side: _face_stream's edge-normal gate (edge_dist = hw - p.y ~ 3141 m
   > win) never streams it during the settle, and its edge row's distance to the stand is
   REAL (~3.1-3.9 km; gen_diag min_dist_m 3244.0, in_window 0, resident_before false,
   mesh_built 0 after the data-only ensure). The timed mesh builds read data-live in-line
   neighbours (the band line) but absent edge-normal neighbours (solid rings — ccz 62 is
   unstreamed, ccz 64 does not exist); steady-state streaming has all four neighbours
   present, so the mesh cost is expected to be a bound, not an exact steady-state value.
5. Render-side draw-call cost of a large resident set (251,001 meshed chunks at 1 m / 4 km is
   the address space, the resident set at a chosen view distance is what draws) is OUT OF
   SCOPE for this headless measurement — no rasterizer. The 60 fps verdict covers the CPU
   streaming/build budget as the plan defines it (16.7 ms frame, 12 ms face-stream budget).
6. The arm streams 34 extra face chunks at the fixed stand (18 band + 16 gen) and builds 16
   meshes synchronously inside its own process — nothing persists (no save, no world file, no
   CELLS_PER_FACE, no policy, no key, no light). genhash 25/25 is the gate that proves the
   world is unchanged.

AC-0469 stage F — design note: what would it take for banded residency to own faces 0-11?
=======================================================
Diagnosis and design only — this stage changed no code (proof: gates below;

2.1 THE COORDINATE QUESTION
---------------------------
NO — one coordinate space cannot express "the player's surroundings" for all
12 faces without special cases, as long as the band model's predicate is a
taxicab test on flat chunk deltas.

The evidence, in the two facts that decide it:
- The band space is FLAT INTEGER. in_stream_set(dx, dz) (6894-6898) and
  band_of (6908-6918) take integer chunk DELTAS from the recenter center;
  the metric is absi(dx)+absi(dz) (6872-6873, 6898). The player's position
  in that space is _rec_player_wx/wz — flat metres (3416-3417, stored at
  recenter 12013-12014).
- A player on a chart face has NO position of its own in that space:
  _face_player_flat (15178-15191) is _rec_player_wx/wz CLAMPED to the patch
  [-hw, hw] (15191). A player 500 m into face 4 has the same flat position
  as a player standing on the boundary. The extended-flat chart
  (home_flat_ext, sphere_math.gd:628-634) can place CHUNK cells past the
  patch (face_cell_band, sphere_math.gd:650-670) but returns (INF, INF)
  wherever the corner cell's direction has d.y <= 0 (sphere_math.gd:630-631)
  — the far hemisphere — and the world reads that as the is_inf sentinel
  (_face_chunk_min_dist returns 0.0, 15171-15172).
So: the only flat space that contains all face chunks (extended-flat) does
NOT contain the player (the clamp at 15191); the only space that contains
BOTH (the planet frame, world_to_face sphere_math.gd:156; player_anchor
15515-15547) is not the band model's metric — "surroundings" there is an
angular/spherical radius, and band0_r/band1_r/in_stream_set (228, 234,
6898) have no angular form without being redefined.

WHAT THE SPACE WOULD BE, stated precisely, so the next stage is not a guess:
- Option A — keep extended-flat as the shared space. It covers exactly the
  region the face lane streams today (faces 0/1 + the near-hemisphere edge
  cells of faces 4-11, where d.y > 0) and keeps two honest special cases:
  the player clamp (15191) and the is_inf sentinel (15171-15172). This is a
  merge of the RESIDENCY POLICY, not of the coordinate space.
- Option B — move the band model itself to the planet frame: in_stream_set /
  band_of become predicates on per-chunk spherical distance (the player's
  own face/chunk, world_to_face at 15521). Then faces 0-11 are one model
  with zero coordinate special cases — but band0_r/band1_r become angular
  radii, the crossing sweep's band-bounded ring walk (12069-12097, which is
  O(ring) in taxi integers) must be re-derived for a sphere, and every
  standing gate value on the planet moves. That is a change to the band
  model itself, not a merge on top of it.
FINDING (reporting it, not forcing a conclusion): these cannot be one model
without changing the band model itself. Option A is the merge this ticket's
remaining slice describes; Option B is a separate, larger ticket.

2.3 WHAT THE BANDS GUARANTEE

THE SET (no literal `stream_set` function exists — the set IS in_stream_set,
6894-6898): taxisquare(render_radius = 4, 200/6872-6873) UNION
diamond(b1_eff()+1 = 5, 6865-6866/6898) UNION the circle ring (6884-6891),
all around the recenter center. At defaults (render_radius 4, band1_r 96 ->
b1_eff 4, 228/234) it is a taxicab disc of radius ~5 chunks.
THE BANDS (band_of, 6908-6918): taxi <= b0_eff (=4) -> band 0, the only
region with full 16x16x16 + TICKS + collision (206-210); (b0, render] ->
band 1 (full mesh); taxi <= b1_eff+1 outside the circle -> band 3 collar
(data-only); ring -> band 3; else -1.
THE GUARANTEE, stated: after a recenter, every stream-set cell has a data
request in the queue — the crossing sweep is band-bounded and walks exactly
the ring where membership can flip (12062-12097), the in_stream_set checks
gate every fill (7057, 7529, 12184, 12433), the spawn 5x5 prewarm (12425-
12439) feeds the drain — and eviction frees only outside candidates under
the r+1/r+2 two_out hysteresis (12062-12065, 12377-12387). "The chunk under
and around the player exists" = the band-0 sim diamond (taxi <= 4, 41
columns at sim 4, 6566-6568, 6754) held by fill + queue + drain, PLUS the
per-frame synchronous read on the face side (the _ensure_face_chunk sync
fallback, 15651-15672).
PER-FACE? The guarantee is expressible per face, but ONLY in a different
metric: the face lane uses a continuous per-chunk Euclidean distance
(_face_chunk_min_dist, 15165-15176, extended-flat corner cells) with
_sim <= sim_dist*16 (15199) and the is_inf -> 0.0 sentinel (15171-15172),
not the integer taxicab predicate (6898). The RADI differ too: the home
window/evict is (64 m, 96 m) — margin (b1_eff()+2-band0_r)*16 = 32 m at
defaults, 12104 (comment 11959) — while the face window/evict is (64 m,
128 m) — FACE_STREAM_EVICT_MARGIN = 64.0, 14827, applied at 15243/15372.
The WINDOWS agree (64 m, both through _stream_window, 11961-11963); the
EVICT MARGINS do not (32 vs 64 m), because the home evict radius must cover
the band-3 collar and the face lane has no band 3 (its distance is the far
tier, not resident data). Unification must choose one margin per face — a
design decision the next stage's plan must make.

2.4 THE FAILURE THAT WOULD COME FIRST
-------------------------------------
SINGLE MOST LIKELY BREAKAGE: the edge-crossing frame stall from the face
budget disappearing — and its correctness twin, the crossing row unbuilt.
Mechanism: the home lane's only out-of-pass creation path is the recenter
crossing sweep (11972 ff.) — a ONE-SHOT SYNCHRONOUS event, band-bounded
(12062-12097), FLAT-KEYED ONLY (_enqueue_build rejects fully-past chunks,
6925-6931, via _chunk_past_patch 14890-14895), with NO wall-clock budget
(contrast FACE_STREAM_BUDGET_MS, 15234). A naive merge that routes face
chunks through it would create the whole face band at the crossing recenter
(6054) in ONE frame — the ~5-row edge band along the window (the residency
arm's own policy report: face.edge_rows_x/z = 5) plus the band-bounded
walk's per-candidate bookkeeping — instead of O(1) enqueues spread over
many 12 ms passes (15338-15359). And if the merge also drops the sync
fallback (15651-15672) in favor of the home lane's queue-only creation, the
same crossing frame is where the player first stands on a face chunk:
queue-only means the chunk may not be landed yet — a void.
THE ARM THAT CATCHES IT: the BOUNDARY arm (crossing-frame p95/p50 —
standing 38 / 26-31, and face_wall_ms) for the stall; the PLANETWALK
twelve-chart lap (mesh_built + body_present at every crossing, with the
negctrl saw_unbuilt as the negative control) for the void. Both already
exist; no new instrument is needed.
WHY NOT THE OTHER CANDIDATES:
- The 16 m travel gate against the wide band: the gate is an EVICTION-side
  hysteresis (12377, 15365) and a stationary player never sweeping is by
  design (the user chose the travel-gated rule). The real risk it points at
  is a NEW radius mismatch in the merged lane: if creation window and evict
  radius stop coming from the same _stream_window quantity (11961-11963), a
  stationary player re-creates the round-41 leak (face resident 79 -> 499,
  context.md) — caught by RESIDENCY (leak flag).
- The edge band near the home boundary: near the edge, the crossing row IS
  inside the extended-flat disc around the (clamped) player, so a
  coordinate-only merge mis-times rather than voids it there; it breaks
  first on the BUDGET side, not the coordinate side.
