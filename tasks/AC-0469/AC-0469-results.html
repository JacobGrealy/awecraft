2. Deviations

AC-0469 stage 0 — deviations + the projection formula =======================================================

FORMULA (any cell re-derives; the arm computes it, tasks/AC-0469-deviations.txt is the written form) ------------------------------------------------------------------- Inputs: face_width(R) = pi*R/2 (R = 4000 -> 6283.185 m, SphereMath) cell_m = face_width(R) / CELLS_PER_FACE (6283 -> 1.000 m; 3000 -> 2.094 m; 1024 -> 6.136 m) D = view distance in m (0.5 / 1 / 2 / 4 km) B = bytes_per_chunk.measure (MEASURED by the arm on the live tree) M = ms_per_chunk.build = gen_data_ms + mesh_build_ms (sum of two MEASURED parts)

Projection (per cell size c, per view distance D): r = ceil( D / (16 * c) ) (16-cell chunk footprint = 16*c metres) chunks = (2*r + 1)^2 (the SQUARE window the residency is — the 81-chunk radius-4 anchor is (2*4+1)^2; the plan's "cover that disc" is read as the window the lane actually holds, not a geometric disc: disc area pi*r^2 would be (pi/4)*chunks if anyone needs it) bytes = chunks * B stream_ms = chunks * M (the per-pass streaming of the WHOLE window at the measured per-chunk build cost) fill_s = stream_ms / 12 / 1000 (at the existing FACE_STREAM_BUDGET_MS = 12.0 — the lane spends at most 12 ms of build work per frame, so a full window fill takes stream_ms/12 frames at 60 fps) x_vs_6m = chunks(c, D) / chunks(6.136, D) (the trade: at the same view distance, c costs (6.136/c)^2 the chunks of the 6.136 m cell — 37.6x at 1.000 m, 8.58x at 2.094 m)

60 fps verdict inputs: frame constraint : M <= 16.7 ms (one build must fit one frame — the pacer budgets BETWEEN chunks, a single build runs to completion) budget constraint: demand(v) = 2*(v/60)/(16*c) * M <= 12.0 ms (chunk-boundary crossings per frame <= 2*(v/60)/(16c), the diagonal worst case, at the top speeds from player.gd: walk WALK 4.3 m/s, cruise-sprint SPRINT 5.6 * cruising_speed 6 = 33.6 m/s) The 12 ms budget PACES the fill (fill_s above), it does not cap the view — a window that needs 10 minutes of paced build still runs at 60 fps while it fills. The deciding numbers are bytes (resident memory) and fill_s (time to a full view), not the frame budget.

DEVIATIONS ---------- 1. The plan's "cover that disc" was implemented as the SQUARE window (2r+1)^2 — the shape the residency actually is (the plan's own 81-chunk radius-4 anchor is (2*4+1)^2). A geometric disc (pi*r^2) would hold (pi/4) the chunks; the square is the conservative (larger) side. The formula above is written out so either re-derives. 2. bytes_per_chunk is the MEASURED live-tree census (palettized slab payload p+i bytes for c.data AND c.fl + every slab mesh's ArrayMesh array bytes + the ConcavePolygonShape3D face bytes). The GDScript node/dict overhead (the per-slab Slab object, the slab dicts, the MeshInstance3D/StaticBody3D node overhead) is NOT byte-countable from the API — it is a labeled gap, not a hidden zero; it is small against the mesh arrays (the census reports the split, so the gap's size is bracketed by the mesh/collision share). 3. ms_per_chunk.build = gen_data_ms + mesh_build_ms — both parts MEASURED on this machine (the fresh data-only ensure; the sync build_mesh_face on band chunks with data-live in-line neighbours). The sum is DERIVED by addition, labeled as such in the RESULT. The warp sub-part is MEASURED from the chunk.gd accumulator delta around the mesh pass (warpcensus's own 0.42 ms figure is the warp only, as the plan states). 4. The timed gen ensures run on FACE 8's edge row (ccz = 63, along-edge ccx 47..62; the band mesh line is ccx 25..40 on the same row). The measurement had to move off face 4: face 4's far rows (ccx 0) sit on the far hemisphere, where face_cell_band's home_flat_ext reads d.y <= 0 and returns (INF, INF) — _face_chunk_min_dist then serves the 0.0 sentinel ("this face does not border the home patch") and EVERY ensure there builds the mesh (build on demand), so face 4 cannot produce a data-only chunk. The first arm attempt measured exactly that: the "fresh" face-4 cc 47..62 chunks came back resident+meshed from the settle, min_dist 0.0 (the arm keeps a gen_diag {key, resident_before, in_window, min_dist_m, mesh_built} in the RESULT so the data-only claim is evidence, not assumption). Face 8 is the clean side: _face_stream's edge-normal gate (edge_dist = hw - p.y ~ 3141 m > win) never streams it during the settle, and its edge row's distance to the stand is REAL (~3.1-3.9 km; gen_diag min_dist_m 3244.0, in_window 0, resident_before false, mesh_built 0 after the data-only ensure). The timed mesh builds read data-live in-line neighbours (the band line) but absent edge-normal neighbours (solid rings — ccz 62 is unstreamed, ccz 64 does not exist); steady-state streaming has all four neighbours present, so the mesh cost is expected to be a bound, not an exact steady-state value. 5. Render-side draw-call cost of a large resident set (251,001 meshed chunks at 1 m / 4 km is the address space, the resident set at a chosen view distance is what draws) is OUT OF SCOPE for this headless measurement — no rasterizer. The 60 fps verdict covers the CPU streaming/build budget as the plan defines it (16.7 ms frame, 12 ms face-stream budget). 6. The arm streams 34 extra face chunks at the fixed stand (18 band + 16 gen) and builds 16 meshes synchronously inside its own process — nothing persists (no save, no world file, no CELLS_PER_FACE, no policy, no key, no light). genhash 25/25 is the gate that proves the world is unchanged.
