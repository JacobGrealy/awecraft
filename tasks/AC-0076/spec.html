Root cause (AC-0075 finding 2, verify by instrumenting before fixing): every recenter re-inserts O(r) new entries through _insert_sorted which re-walks the WHOLE queue (O(n²) per crossing at r=50: ~101 new × 12 290), PLUS recenter eager-stubs EVERY chunk node in radius + both rings (≈10 609 bare Node3D creations) up front. Measure which dominates (timing prints in a scratch run), then fix BOTH. First-draw at r=50 (7 578 ms) is almost entirely this one recenter call.

Requirements (in priority order — if time/context runs short, land in this order and report honestly)

  1. Recenter must be O(k · log n) or O(n) with a tiny constant (k = new entries ≤ 2(r+1) ≈ 102 at r=50), NOT O(n²): existing queue entries keep their order; only new entries are inserted and freed-band entries removed. If the queue is a sorted Array, insert is O(n) each → either use a structure with cheap insertion (e.g. per-distance-band arrays / a simple heap / append + deferred stable re-sort at most once per recenter of the CHANGED entries only — your choice, prove it with the gate) or re-architect build_queue. The drain's per-frame step must stay cheap at n=13k: it currently walks forward for the first eligible entry — with ~13k entries mostlyineligible-that's the same trap; use an advancing cursor/skip-list or bucket-by-distance so a frame never scans the whole queue. Gate: recenter_ms < 100 at r=50 (baseline 7 397); ≤ 2 at r=4 (regression guard); perf r=50 first_draw_ms ≤ 600 (baseline 7 578).
