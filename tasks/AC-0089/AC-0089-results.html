AC-0089 — Analog tuning controls: look sensitivity, per-stick deadzones, invert X/Y

1. What was built, and where the controls live

Options > Controls > "Analog tuning (sticks)" group — the bottom section of the AC-0088 Controls tab (ui/menu.gd, code-built like the remap rows): one SpinBox row for Look sensitivity (right stick), one each for Deadzone — left stick (movement) and Deadzone — right stick (look), one row with the two invert CheckBoxes (Y, X) and a Reset analog to defaults button. SpinBoxes, not HSliders: the AC-0260 fix (the HSlider rows misbehaved in the tabbed options) — the ticket's "the project's equivalent control".

Convention copied from AC-0088, exactly: the five keys (look_sensitivity, deadzone_left, deadzone_right, invert_y, invert_x) are declared in Settings.DEFAULTS, _clamp-validated against the bounds, persisted through set_value (clamp + save in one step), read back by load_settings, shown on the tab, refreshed by _sync_controls, and asserted round-trip + row-present by the arms. No second mechanism. Two new pieces of code carry the logic, shared so the UI, the game and the instrument cannot drift (the controls_map.gd convention): godot/core/analog_tune.gd (pure-logic core: the math + the bounds) and the player's two input paths (below).

The values are APPLIED to the real input path, not merely stored (the failure mode the ticket warns about) — the player reads Settings.values live at both paths, so a slider change applies the next frame; no apply step exists to skip.

  • Look (right stick) — player.gd _process: the raw stored stick value (_pad_look, the AC-0087 value-event pattern) is tuned through AnalogTune.look_stick() (per-axis deadzone + renormalize, invert X/Y, the linear sensitivity multiplier) before it scales PAD_LOOK_SPEED.
  • Movement (left stick — "any analog movement") — player.gd _physics_process_impl: the four move_* reads switched from Input.is_action_pressed booleans to Input.get_action_strength, and the resulting vector goes through AnalogTune.move_stick() (the deadzone_left). Keyboard behaviour is unchanged (a held key holds at strength 1.0; the diagonal normalization is kept). Stated consequence: the movement model's speed is a constant (WALK/SPRINT/…), the input vector is normalized — the stick magnitude only feeds the DEADZONE filter (past the threshold = full speed). That is Minecraft parity (the stick is a direction, not a throttle) and the ticket's requirement (the deadzone affects analog movement); magnitude→speed scaling would be a new movement-feel change outside the ticket.

2. The decisions: bounds, curve, invert scope — stated and why

KnobDecisionWhy / what it buys
Sensitivity 0.25 … 2.0, default 1.0 LINEAR multiplier on the look delta (a multiplier, not a curve), look only One number the player can calibrate against the base PAD_LOOK_SPEED (2.5 rad/s); a curve would change low-deflection response in a way a single value cannot predict. The floor 0.25 keeps a full deflection at ≥ 0.625 rad/s (90° in ~1.4 s) — no legal value makes look unusable; the ceiling is fast-but-controllable. 1.0 = the shipped behaviour.
Deadzone 0 … 0.9 per stick, default 0.15 each Per-axis deadzone with renormalize: |v| ≤ dz → 0; above it (|v| − dz) / (1 − dz) Upper bound 0.9, not 1.0: a full deflection is EXACTLY full output at every legal dz ((1 − dz)/(1 − dz) = 1), so no legal setting can make look or movement unreachable — a player at the extreme still has a working stick, only shallow deflections die. dz = 1 is excluded because the renormalize divides by zero AND would filter even a full deflection (the game unnavigable — a bug, not a player choice). Lower bound 0.0 is legal and is the identity: finite math, no division by zero; a drifting stick at dz 0 reads as input — the player's reversible choice, visible in the UI. Renormalize keeps a full stick full at high dz (no hidden second effect on top speed). Default 0.15 keeps the shipped arms green (the gamepad arm drives 0.8 / 1.0 deflections — both pass with margin) and rejects typical stick drift by default. Movement: the engine's per-action deadzone (0.5, project.godot [input]) rescales the stick FIRST, the user value applies on top — so the effective raw threshold is 0.5 + 0.5·dz (dz 0.9 → raw > 0.95): the slider has a real, monotone effect, and drift can't reach movement even at dz 0.
Invert Y / X, default off Look-only (the right stick); flip the sign, keep the magnitude The left stick also drives the native GUI focus navigation (engine ui_focus_* bindings, untouched by design) and the sprint latch keys off the forward sign — inverting either would break both. Mirrors Minecraft's "Invert Y" being a look setting. Sensitivity is likewise look-only: movement speed is the game's, not a player knob.

6. Deviations & notes

  • Reset button added, not required: "Reset analog to defaults" (one Button, reuses the AC-0088 per-row reset convention; the "Reset ALL bindings" button stays bindings-only). No new Settings API — the handler sets the five keys from AnalogTune.defaults().
  • No apply step (stated, deliberate): the player reads the values live at its two input paths, so set_value (clamp + save) is the whole write path — an apply function to skip would be a second mechanism, the thing the ticket warns against.
  • The corrupt-cfg crash found by the arm's own test: bool("corrupt") raises "Nonexistent 'bool' constructor" in GDScript 4 (numbers only) and would abort the entire load_settings. The new keys use AnalogTune.sanitize_bool (garbage → false); the pre-existing bool settings (fullscreen, …) keep their plain bool(v) — a hand-edited string there is a pre-existing weakness outside this ticket's fence, noted here for the closeout harvest.
  • Engine deadzone (measured, not assumed): a temporary -s probe (removed in task) confirmed Godot 4.7 rescales the stick by the per-action deadzone (0.5) in project.godot [input] — raw 0.55 → strength 0.1, raw 1.0 → 1.0, raw < 0.5 → 0 — and that Input.get_action_strength exposes exactly that (keyboard holds at 1.0). The user deadzone composes on top; the arm's movement numbers are the proof.
  • Native lane untouched — no rebuild/re-stage needed (no C++ or data.gd change).
