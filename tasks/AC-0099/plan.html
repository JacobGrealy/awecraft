func _find_exit_button() -> Button:
	var stack := [menu_ui.main_box]
	while stack.size() > 0:
		var n: Node = stack.pop_back()
		if n is Button and (n as Button).text == "Exit":
			return n as Button
		for c in n.get_children():
			stack.append(c)
	return null
The press goes through pressed.emit() (not a direct call) so the signal wiring itself is exercised — the stronger check; the AC-0081 harness calls the handler directly (main.gd:4002) but that predates this button. RESULT is printed before the press because the desktop press ends the process: the RESULT asserts the preconditions (menu actually shown, button found), and the clean exit (RC=0, zero script errors) is the quit assertion itself. On precondition failure quit(1) → non-zero RC fails the gate loudly.

7. Risks/edge cases

  • D1 (spec typo): spec Scope says godot/gui/menu.gd; actual file godot/ui/menu.gd (menu code is in ui/, no gui/ dir exists). Run-2 edits godot/ui/menu.gd; coordinator to fix the spec line when committing.
  • D2 (spec G4 literal is partly vacuous): AWECRAFT_BATTERY="quitmenu;player" BATTSKIPs the quitmenu arm (HARNESS.md §3: “anything else prints BATTSKIP <mode> (no RESULT, no failure)”). Run the literal command (green, cheap) AND the standalone AWECRAFT_LOGIC=quitmenu (the effective AC-0081 regression). Do NOT add a quitmenu case to the battery (out of fence; it would kill the battery process).
  • Wrong dispatch location = wrong test: if Run-2 wires mainmenuexit inside _run_game (like quitmenu), the world boots first — that tests the pause-menu-adjacent menu, not the startup main menu, and adds 10–20 s of world gen. The _ready()-intercept placement in §2 is deliberate.
  • Headless quit semantics: get_tree().quit() default exit code = EXIT_SUCCESS (0) — RC=0 is the assertion. Any teardown-time script error would land on stderr → caught by the zero-SCRIPT ERROR grep. Precondition failure uses quit(1) so a missing button/menu never masquerades as a green run.
  • Menu-shown vs world (startup decision): menu-first boot is the default on every display platform (main.gd:103–106, AC-0033); Play continues the first occupied save slot else starts a new world (main.gd:332–342) — fresh-start vs loaded-save is irrelevant to Exit: from the main menu the handler touches neither world nor Save (Save.active_slot := -1, save.gd:7; auto-save lives only in quit_to_menu, main.gd:366–367, which Exit never calls). Spec fence “no save writes from Exit” satisfied by construction.
  • AC-0081 path intact: the new button/handler are additive; _on_quit_btn_pressed/on_quit_to_menu/quit_to_menu() are not touched. G4(a) re-proves it (ok:true).
  • In-game Exit press is N/A: the button exists only in main_box (visible only when _state == "main", menu.gd:45–52); the pause menu keeps its own "Quit to Menu".
  • Button discovery robustness: _find_exit_button walks main_box descendants matching Button.text == "Exit" — unique in that subtree (verified: no other "Exit" text in menu.gd). Fallback if Run-2 prefers explicit naming: set b.name = "ExitButton" at creation and use find_child("ExitButton", true, false) — either is acceptable; record which in continuity.md.
  • Web button stays enabled (unlike the web-disabled pack button): spec requires present + pressable-but-no-op; do not copy the disabled/tooltip pattern from menu.gd:430–432.
  • No comments in .gd edits (ARCHITECTURE.md §1); no world/* or data.gd edits; no git, no builds, no ~/.dsh, never kill python server pids (spec fences).
  • Doc drift (coordinator, post-Run-2): tasks/HARNESS.md §1 mode table gains a mainmenuexit row (36→37 modes) — coordinator update, not a Run-2 deliverable.
