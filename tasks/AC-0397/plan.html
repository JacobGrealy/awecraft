AC-0397 — plan: the band-A materialization fill stands on the carved top

Goal

The band-A materialization (the tier-1 draw, 80–128 m at the user's sim 4 / medium 8) runs generate_resl(skip=1), whose fill is solid 0..un-carved heightmap H. The far lane's reference (the far payload H) is already the full path's carved top (AC-0387, farab-gated). The defect: where the carve drops the top, the band-A plateau stands above the carved ground — the coordinator's census: 2,597 of 159,744 ring columns (1.63 %, 2.39 % outer band, max 91 blocks at (−91, 147, −48)). Fix per the recorded direction: fill band A to the carved top the far-lane reference already computes, not to the un-carved height. No toggle: (b) is a contract violation (the ticket's own switch analysis).

Shape of the change

  • Drive the fill from the resident far payload, do not re-derive. The mat dispatch (world.gd _mesh_dispatch_hslab band-A branch) already requires the column to be a far column with a 512-byte far_h; the handoff keeps the payload with the fill. AC-0388 established the pattern (reuse the resident bytes instead of re-deriving) and world/AGENTS.md forbids re-deriving a value another lane computes. The payload H is bit-exact the carved top (farab h_mismatch 0, negative-tested), so driving from it is driving from the carved top — at zero added generation cost (the alternative — re-running carved_top_pass inside the skip path — costs the AC-0387 price, ~3,258 µs/chunk, on every materialization, and re-derives bytes the lane already holds).
  • gen.cpp: gen_flat gains an optional 1024-byte far-payload pointer (used only on the skip path). Skip fill: he = payload H; the top row = the payload TOP id (the re-skin/top-row id the far emit draws — a rule re-derivation here would diverge on carved-into-deepslate columns); the water gate becomes the fill's own top (he < sea — the same rule the skip path and the far path already obeyed, AC-0342's comment, and it matches the far emit's St rule and the farab (2) reference exactly). The veg loop is untouched in logic: its in-column base already reads heff, which is now the payload H — matching the far lane's veg (gen_veg_cells, AC-0387: base = carved top, gate = pre-carve H2).
  • Binding: generate_resl gains an optional trailing p_pay (1024-byte far payload; ignored unless skip ≠ 0 and the size is right — a bad/absent payload falls back to the legacy un-carved fill, never a hard error). Existing callers (ladder's far race fallback, farab 3b codec round-trip) pass the payload they already have — data-source sync only, no assertion change in any arm.
  • world.gd: the mat entry carries "far_pay": c.far_payload(); the worker's mat branch passes it through. Nothing else in the dispatch/handoff moves.
