1. What was baked, and from what

Twelve 1024×1024 per-face satellite textures (satellite_face00.png … satellite_face11.png, RGB8 PNG, one file per face) were baked from the far column payload exactly as the streaming pipeline already produces it: a godot tool (.scratch/AC-0310/ac0310_far_dump.gd, run headless, 8 GB cap) instantiated AweGen via ClassDB and called generate_far(cx, cz, seed, 384, 126) for all 196,196 chunks — the same call the demotion path makes in world.gd:_demote_to_far — and wrote every 1024-byte payload to .scratch/AC-0310/far_dump.bin (203,259,100 bytes). The python bake (tasks/AC-0310/ac0310_bake_satellite.py) reads that dump; no generation logic lives in the bake itself.

Per chunk the payload is [H u16×256 LE][biome x256][top x256] (slot = lz·16+lx). The bake maps each texture pixel to one surface column and writes:

  • ocean (H < SEA): flat, unshaded water colour (the water surface is the plane S = max(H, sea), so no gradient shading);
  • land (H ≥ SEA): fcc top colour × lambert, where the colour is the far tier's own per-block top-face colour (the _lod_fcc_get convention: sRGB atlas-tile average → srgb_to_linear, dir = top; the atlas already carries the data.gd web tints for grass/water) and lambert = 0.45 + 0.55·max(0, N·L) with N = normalize(−∂H/∂u, 1, −∂H/∂v) (clamped central differences, 1 m spacing on the home pair, s·(1, ½ or ½, 1) on faces 2–11) and fixed sun L = normalize(0.4, 1.0, 0.2) in the (u, radial, v) frame. The stored PNG is linear_to_srgb(colour) — an unlit bake the later render tier modulates.

Pixel convention (the render tier maps a face's chart point here 1:1): pixel (i, j) = chart point ((i+0.5)/1024, (j+0.5)/1024); faces 2–11 have exactly one 16-cell face chunk per 16×16 pixel block (cell (iu, iv) = pixel (i, j), with the face_mirror_x lx flip on faces 2–5 and 8–9); faces 0/1 (the home pair, 1 m columns) sample the column whose centre lies at the pixel centre's flat position (floor of the SphereMath home inverse). Face 0: i-axis = flat +x (left = midline x=0, right = +3141 m), j-axis = flat z (top = −3141, bottom = +3141); spawn (0,0) sits at the left edge mid-height. Face 1: i = x from −3141 (left) to 0 (right).

Also emitted: ac0310_bake_stats.json (all numbers below), and — as a prerequisite probe — ac0310_fcc_probe.json (the fcc top colours the bake uses, measured from the real atlas, plus the flat data.gd palette for comparison).

5. Findings that change the design

  1. Chunk count, not chunk cost, breaks the 4.5 s claim. The estimate assumed 4,096 chunks per face; the home pair's 1 m columns need 155,236 (394×394). Measured: 17.9 s C++ for the far payloads at the standing 91.2 µs/chunk. The bake is fine as a one-time job, but the render tier must generate far payloads off the main thread (worker/sliced), keyed (planet_id, R, seed). (§3)
  2. Use the fcc colours, not the flat palette. The far tier's actual per-block top colours (atlas-tile averages with the data.gd web tints, linearized) differ materially from the data.gd flat C_* palette for the two most common surface classes: grass fcc (57,106,35) vs flat (109,173,67) — the fcc is markedly darker because the atlas grass tile's grey-average is ~34 % bright, and water fcc (35,76,165) vs flat (43,112,223). A bake from the flat palette would be visibly brighter/greener than the band the far tier actually draws. The fcc values are in ac0310_fcc_probe.json (and baked in). The flat palette is only the no-atlas fallback. (§2.4, §1)
  3. The home-edge blend band is not in the far payload. AC-0309 C1's blend band (generator.gd:_blend_face_chunk) is a GDScript post-process on faces 4–11 near the home-patch edge during streaming; generate_far is the canonical no-cave form without it. The satellite bake is therefore un-blended at those four strips — the far band (which draws from the same far payload) is equally un-blended, so the bake is consistent with what the far tier shows, but if the later piece blends the far band for the near-mid transition, the baked strip should match the blended look. Flag for the render-tier piece: decide blend-or-not for the satellite strip at the patch edge. (§1, §4)
  4. Seed 44 is a 99 %-land planet. 1.069 % ocean planet-wide (0–4.6 % per face, patchy veins), 0 deepslate surface anywhere (H ≥ 102 always > the 64 deepslate threshold), snow concentrated on the −Y faces. Whatever the render tier draws, the "satellite view" of the home world will be a green-white highland with sparse lakes — the ticket's framing should not promise a blue marble. Also worth a one-liner in the epic §6.3 context: ocean is a minority class on the current generator (post-AC-0288…AC-0360 re-bases), per the standing genhash/light-arm census notes. (§2.1)
  5. The 12-face chart is a great-circle partition. All 48 face edges are great-circle arcs (max plane deviation 2.8×10⁻¹⁷ R), the shared edges are gapless to 6.8×10⁻¹³ m, per-face solid angles are exactly 4π/12, and the round-trip map is exact to machine epsilon. Consequences for the render tier: (a) the visible limb at any camera distance is a perfect circle and the painted/empty terminator coincides with it — no "flat-square edge" artifact is possible at orbit view; (b) if the tier draws per-face quads and then warps vertices, edge vertices from both sides already coincide, so no seam-fixing pass is needed at the chart level; (c) any mip/LOD blend across an edge can be done in chart space without distortion worries. (§2.5)
  6. Per-face pixel counts are not equal-area in the naive sense. Each face is exactly 4πR²/12 in true surface area (the pre-warp makes the partition equal-area: 16,755,161 m² per face to 2×10⁻⁷), so a uniform 1024² texture gives a uniform m²/px = 16.0 m²/px on every face — the home pair's 1 m columns are simply supersampled 16× over that (256 columns per 16 m chunk). No per-face density correction is needed for the render tier; nearest-neighbour sampling of the textures is area-fair. (§2.5)

6. REPAIR — the v-invariant bake (piece 1, 2026-09-29)

6.1 Root cause — the v index was tiled along the u axis

Every row of every baked face was byte-identical to row 0 (coordinator's independent PNG decode: distinct rows = 1/256 on faces 00/03/05/10; face 10 read as a uniform green plain, face 3 as vertical bands). The cause, in ac0310_bake_satellite.py: a numpy row/column pattern error. The pixel index grids are built by tiling 1-D arrays: a u-axis (column i) array like cxi is a row pattern — each image row = the i-array — and np.tile(a_1d, (NPIX, 1)) makes exactly that (result [j, i] = a[i]). But the v-axis (row j) arrays — czj/lzj on the home pair, iv >> 4/iv & 15 on faces 2–11 — were also built with np.tile(arr, (NPIX, 1)), which puts arr[i] at [j, i] for every row. The sample therefore became a function of i only: faces 2–11 walked the chunk grid along the diagonal (ccz = ccx, local lz = lx-correlated) and the home pair along cz = cx of the flat grid — a one-dimensional slice repeated down all 1024 rows. The u arrays were correct by the same coincidence. No numeric check in the original run could see it: coverage, census, biome/colour correlation, limb and gaplessness all test the payload and the chart, not whether the image varies in two dimensions — and a machine diff of the dump data confirmed the far payload is fully 2-D (all 64 ccz rows distinct per face, all 64 ccx rows distinct), so the data was never the problem.

Fix: the v-axis arrays are now built as column patterns (np.broadcast_to(arr[:, None], (NPIX, NPIX))) in both the home-pair and faces-2–11 branches. The index rule is documented in the script header, and the guard in §6.3 makes the failure mode impossible to ship again.

Second defect found and fixed in the same code (would have survived the variance guard — it is not a variance defect): the lambert gradient terms were computed along the swapped axes. On the home pair dHdx/dHdz each differentiated along the other axis (the 4-D gradient grid is [cx, cz, lz, lx], so axis-2 differences are ∂/∂z); on faces 2–11 gx/`gz` took row/column differences the wrong way round and divided by the wrong spacing (du_m vs dv_m — a 2× scale error on the anisotropic faces 4–11). The shade was therefore lit as if the sun's in-plane direction were mirrored and the terrain stretched. Fixed: gx = column differences / du_m, gz = row differences / dv_m (home pair: dHdx = axis-3 differences). Effect: per-class mean brightness redistributed slightly between faces (0.91–0.95, was ~0.91 everywhere); planet-wide colour means unchanged to the displayed precision (§6.5).

6.3 The permanent check — per-face variance guard in the bake

The bake now asserts, for every face, on the bytes actually on disk (the written PNG is decoded back with a minimal filter-0 decoder in the script — not the in-memory array):

  • distinct rows and distinct columns — 256 sampled lines (every 4th) each, counted against the first; floors 64/64 of 256. The smear measured 1; the fixed faces measure 256 (4× floor margin, and a whole-axis smear can never be anywhere near the floor).
  • H-channel min/max spread over the face, floor 8 m (measured 74–110 m);
  • colour-channel min/max spread (stored bytes, per R/G/B, worst channel), floor 8 (measured 179–233).

Any floor failure prints the per-face table and sys.exit(1) — a smeared or constant bake can no longer pass. What each part catches: the distinct-row/column counts catch a dropped/fixed axis index (one-dim slice repeated — this defect), a constant/uniform face, and a degenerate PNG; the H spread catches a height-channel dropout or a face sampled from a single flat chunk; the RGB spread catches a dead colour channel or an all-ocean/all-land misclass. It is the same class of instrument as the four this project has already had to repair: a check that everything passes is worse than no check, because it looks like coverage. Negative test (run at repair time): the guard's counting logic applied to a rebuilt v-invariant replica of fixed face 00 returns rows = 1, cols = 230 → FAIL; the fixed face returns 256/256 → pass.
