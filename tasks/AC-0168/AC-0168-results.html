AC-0168 — r+1 hysteresis: retain mesh at the candidate (hide not kill)

User story: as a player walking near the edge of render distance, I want chunks at r+1 to stay on screen (fog hides them) so stepping back doesn't make the edge flicker or pop. AC-0080 hysteresis kept node+data+edits at r+1 but killed the mesh; stepping back re-queued a build and the worker re-mesh gap read as a flicker/pop at the distance line. Now the candidate keeps mesh_built and its slabs whole — the fog at fog_far=(R+1)*16*0.95 (already in place, daynight.gd:11-12, applied main.gd:1760-1761) covers the band — and true free stays at r+2 after the existing 2-recenter-event hysteresis.

What changed

  1. world.gd _enter_candidate — hide not kill. The two kill lines (mesh_built = false + chunk._enter_candidate_slabs(), which nulled every slab mesh/fluid/flora instance, freed collision bodies + occluders, and forced col_dirty) are gone. A candidate is now node + data + edits + mesh, whole; candidate=true; cand_since=0; lod_pending=false; clear_lod_cache() and the pending-mesh-work erases (light/fluid/tex/col) are unchanged. The pending-work erases stay correct: re-entry re-marks dirty via the normal paths, and a retained candidate that was marked dirty gets a fresher re-mesh through the existing flush loops (whose mesh_built gate now passes for retained candidates — previously the dead mesh skipped them).
  2. world.gd recenter re-entry guard. The in-set re-entry branch now calls _stage_check(c, key): if a band-0 chunk's collision body was still pending (un-staged) at the moment it became a candidate, the retained-mesh re-entry would never re-trigger the old kill→re-mesh path that used to re-stage it — so re-entry re-stages it explicitly (no-op when the body exists / col_dirty is clean). Free timing is byte-identical: two_out still increments cand_since per recenter event, free at ≥2, jitter at r+1 still resets it.
  3. chunk.gd — removed _enter_candidate_slabs() (20 lines; sole caller was the removed kill line).
  4. main.gd — edgeretain dispatch branch + probe (_edgeretain_test + _er_* helpers, R=8): boot core+edge build, fly the player east 1 chunk/step with the camera facing the trailing ring (yaw +π/2), 3 hold-still recenter events, step back 2 chunks; per-sample r+1/r+2 ring census (retained/visible counts), 3 tracked-chunk lifecycles (axial band-1 full / diagonal band-2 coarse free-path / diagonal band-2 coarse back-path), mesh-identity + per-frame back-phase hole/hidden sampling, fog-coverage check. Band-3 (data-only ring/collar) chunks are excluded from hole/kill/vis bookkeeping — a chunk re-created as band 3 on back-step never has a mesh by design.
  5. Comments — 3 stale pre-existing comments refreshed for accuracy (candidate doc, recenter hysteresis, cull-pass note that candidacy never hides). No comments in new code (ARCHITECTURE §1).

Deviations / notes for the coordinator

  1. D1 — pre-existing engine flake hit once (not a regression). One edgeretain run (2nd of 3) crashed SIGSEGV inside the threadmesh worker (_tm_worker_run at _tm_slots.get, world.gd:1289) with a propagate_notification-from-wrong-thread error on /root. Same signal-11 class appears in old logs (.scratch/AC-0143/g0.log, .scratch/AC-0108-gates/gates.log) on other trees, and the AC-0152 comment documents the _tm_slots racy window. Identical code re-ran green (ok:true, 80.7 s, 0 SCRIPT ERROR) — treated as the known flake. Worth an infra task (mutex or per-slot handoff for _tm_slots) but out of scope here.
  2. D2 — probe radius R=8, not 4. At R=4 every candidate is band-3 data-only (never meshed), so retention would be a no-op and the feature unobservable; the first meshed one_out candidates exist only at R≤12. R=8 gives band-1 (full) and band-2 (coarse) meshed candidates. The r4 baselines (boundary/perf) are structurally untouched: at R=4 the old kill path only ever touched data-only chunks, so retention changes nothing there (free timing, loads/unloads/flap, built_final all unchanged).
  3. D3 — band-3 exclusion in the probe. A tracked chunk freed at r+2 and re-created on the back-step re-enters as band-3 (ring, data-only) — it legitimately has no mesh; counting it as a "back hole" gave 28 false frames on the first green-feature run. Bookkeeping now skips band ≥ 3; the world code was not affected.
  4. D4 — extra ~300–400 cols at R=50 (accepted). Retained candidates add at most the meshes of chunks that would have been freed at r+2 anyway — one extra 2-recenter-event window of the edge arc. Memory grows only by those meshes; freed with the node on the unchanged schedule.
  5. D5 — ps is blind to other sandboxes. Each harness bash call runs in a fresh bwrap namespace, so ps does not list godot processes started by other calls; the .scratch/.godot_busy marker is the effective one-at-a-time lock (used for every invocation).
  6. D6 — lodswap timed its cross1 wait once (flake, re-run green). First lodswap run: cross1 atomic:false, retain_window:false, ok:false — T's coarse LOD rebuild did not land within the probe's 2400-frame (40 s) wait cap; the flip landed late (observed in the back phase; cross2 flip frame 3055 vs baseline 881; run 38.3 s vs baseline 28.4 s — the whole R=15 build-drain timeline was ~35% slower that window, shared machine with 8 users). no_hole:true/hole_frames:0 held throughout (retain-until-swap never emptied T). Identical code re-ran green at baseline values (D above). T is never a candidate in this probe, so the change cannot alter T's path; the fragility is the probe's fixed-frame wait cap under build-drain slowdown, not a behavior change. Coordinator may re-run on the heavy stage if desired.
