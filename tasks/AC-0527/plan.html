AC-0527 — the halo arm is red because the code got better

Coordinator contract. Medium builder applies it with tasks/templates/implement.md. Fix the expectation, and make the new assertion survive the next re-tune.

1. What changed and what is now stale

AC-0480 changed the far tier's halo sky from a BINARY lit/unlit split to THREE LEVELS: 15 above, 8 at the bottom-equals-terrain-top case, 0 below (world.gd _halo_sky_for). That turned a ~3.8× brightness step at every lit/unlit cell edge into graded 1.5× / 2.5× steps, which is what removed the visible line (the re-lit class measured 0.263 → 0.655).

The harness's halo arm at harness.gd:12800 still encodes the TWO-LEVEL rule and will therefore read RED. This is a test that is wrong because the code got better — the same class as AC-0326, AC-0327 and AC-0409, all resolved by correcting the expectation rather than the code.

2. The assertion to write — durable, not literal

Do NOT hardcode 15/8/0. Assert the invariant the fix was actually about:

  • MONOTONE: the halo value is non-increasing with depth below the terrain top (it can never rise as you go down).
  • BOUNDED STEP: the ratio between adjacent levels is bounded by a stated threshold — the fix's whole point is that no step is ~3.8× any more. Pick the threshold from the measured post-fix values (1.5× / 2.5×) with headroom, and say what you picked and why.

A monotonicity-plus-bounded-step assertion survives the next re-tune; a hardcoded triple does not, and would need this same ticket again.
