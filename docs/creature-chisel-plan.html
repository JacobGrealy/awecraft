Chiseled Creature & Character System

Reusable voxel rig built from the same micro-voxel + greedy + atlas stack as chiseled blocks (16×16×16 per block, multi-block parts) — with action-figure joints and animated decals for faces. Players and creatures share the same system. Templates are authored (human) or procedural, then spawned many times.

Goals

  • One system for players + creatures — same part format, same meshing, same save.
  • Chiseled parts, not sculpted meshes — reuse block chisel tech (palette + 512B bitset per 16^3 block).
  • Action-figure rig — independent part meshes connected by joints, moved by rotating parts, not skinning voxels.
  • Expressive faces via decals — mouth/eyes are animatable decals over the voxel texture, not voxels.
  • Author once, spawn many — saved templates + per-instance sliders (longer/thicker) for variety.
  • Editor is tooling — out-of-scope for v1, but system is built so a creature/object editor can drive it (separate tabs, same engine).
v1 ships without editor. Team authors templates in a dev tool / external editor; game only loads and spawns them. Part library + symmetry + joint limits are follow-ups.

Scope: What we decided

Players too

Player avatar is a rig (head/torso/arms/legs) built from chiseled parts, same as mobs.

Multi-block parts

A body part can be N blocks (e.g., 1×2×1 for a leg). All blocks baked into one mesh per part on finish.

Ball joints now, hinges later

Balls are the minimum; hinges and per-joint angle limits are a follow-up.

Decals animate

Eyes/mouth must be animatable — blink, talk — via frame swaps, not voxel edits.

Saved templates

Templates are pre-authored or procedurally generated; many instances share one template + per-instance tweaks.

Tool later

Creature/object editor is a separate tab of the same tool, not v1. System is editor-ready.

Architecture — at a glance

Data model

Template (saved asset)

  • template_id, name, bounds
  • parts[]: {id, name, blocks: [{pos: Vector3i, p:[id], bits:512B}], pivot: Vector3, joint: {parent, anchor, type:ball, limits?}}
  • decals[]: {part, name:"eye_L", rect:{u,v,w,h} in decal atlas, size, offset, anim:"blink"}
  • rig: {skeleton: parts tree, default_pose}

Per-instance override

  • sliders: {length:0.8..1.4, girth:0.9..1.2} — applied as non-uniform scale on the part’s MeshInstance or by resampling the micro grid before meshing (cheaper = node scale).
  • decal_frame: int + pose: {joint: quat} per frame (animation drives this).

Save layout

  • Templates live as res://creatures/templates/*.json (or .tres) — not per-world.
  • World save for a spawned creature stores {template_id, pos, sliders, decal_state} — not the voxles. So 100 goblins share one template + 100 tiny instance rows.
Forward-compatible: single-material chiseled blocks stored as p=[id] today; multi-material later just becomes p=[stone,wood] with no migration.

Meshing

  • For each part, build a dense occupancy over its multi-block volume (e.g., leg = 16×32×16 = 2 blocks tall).
  • Greedy pass: iterate faces, merge same-material quads where light/AO matches — but only inside the part. Never merge across parts (they’re separate meshes).
  • Chiseled blocks inside a part already excluded from “full block” greedy — they’re the micro greedy inside each 16^3 (now 16×16×16). Multi-block part just runs that micro greedy per block, then combines.
  • Result: one ArrayMesh per part. Flat walls still one quad, carved details stay detailed.
  • Texture: sample block atlas per micro-quad (repeat UV if merged). Decals are a second material pass — a QuadMesh child of the part with alpha.

LOD (follow-up)

  • Not v1. Later: distant creatures merge parts into one mesh (or billboard impostor) to cut draw calls for crowds.

Joints & animation

  • v1 joints: ball joints (3 DOF) at anchor micro-voxel — e.g., shoulder at (8,24,8) of torso. No limits yet; animator just sets quats.
  • Follow-up: hinge type + per-joint cone limits (min/max pitch/yaw) so elbows don’t bend backwards. Data lives on the joint: {type, axis, min,max}.
  • Animation drives part transforms + decal frames. No voxel re-mesh per frame. Walk cycle = swing leg parts ±30°, head bob, eye decal blink frame every few seconds.
  • Procedural creatures pick a template then randomize sliders + palette tints before spawn — so 10 goblins from one template look varied but share the mesh.

Decals

  • Decal atlas: small 256×256 with eye/mouth frames (e.g., 32×32 per frame, 4 blink frames, 6 mouth shapes).
  • Each decal is a Decal or Sprite3D-style quad pinned to a part face (offset + normal). Upper material, alpha-cut.
  • Anim: swap rect per frame; timer drives blink (random 2-5s) and lip-sync (phoneme → mouth frame). No geometry change.
  • Follow-up: additional decal layers (scars, paint) with tint — same system, just extra quads.

Tooling (out of scope, but design for it)

  • Separate creature/object editor — tabs share the same chisel backend. Object tab edits a single part (chair), creature tab edits a rig of parts.
  • Editor reuses in-game chisel tools: add/remove micro-voxels, box fill, symmetry mirror (follow-up).
  • Export button → writes templates/*.json with preview PNG.
  • Part library: save a chiseled arm to library, instantiate in another creature, tweak sliders per instance (longer/thicker).

Phased plan

Phase 1 — Core (v1)

  • Multi-block part format + single-material 16^3 storage + greedy per-part bake.
  • Ball joints as Node3D pivots, rig loader, pose driver.
  • Decal quad + animatable frame swap (eyes/mouth).
  • Template load + instance sliders (scale) — many spawns share template.
  • Player rig uses same path (swap current capsule for rig).

Phase 2 — Follow-ups

  • Symmetry mirror while chiseling a limb.
  • Part library + per-instance length/girth sliders that resample voxels (not just node scale).
  • Joint constraints (hinge + cone limits).
  • Extra decal layers (scars/paint, tint).
  • LOD: merge parts to one mesh at distance / crowd impostors.
  • Multi-material chiseled block (palette growth) — no save break.

Open answers captured

  • Players use the same rig — yes.
  • Editor not in v1; plan for a shared creature/object tool later.
  • Parts can be multi-block, baked to one mesh per part.
  • Balls now, hinges/limits later.
  • Decals must animate.
  • Templates saved, many instances share mesh; procedural generation picks template + randomizes sliders.
  • Symmetry → follow-up; part library yes + sliders; decal layers yes; LOD follow-up.

Risks

  • Too many parts → draw calls. Mitig: keep rigs to ~6-8 parts max for v1, batch by material.
  • Micro-mesh scale: 16^3 per block is heavier than 8^3 — ok for parts (small) but not for terrain slabs (keep terrain at 16^3 per block only where chiseled).
  • Decal Z-fighting on curved chiseled faces — offset decals slightly outward.
