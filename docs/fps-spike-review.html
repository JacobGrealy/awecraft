01

Answer in one page

You are seeing more FPS slowdowns because the last four performance tickets (AC-0283 → AC-0286 → AC-0312 → AC-0313) each traded tail latency for steady-state throughput and completeness, and every one of them was verified on a metric that cannot see a spike: the average frame time.

The mechanism is one sentence long: the unit of work got 24× bigger. Before AC-0313 the scheduler worked in windowed, partial-column units (the AC-0263 Y-window) and the drain was time-capped. AC-0313 deleted the window: a build "unit" is now a full 24-slab column, the load lane dispatches up to 16 of them per frame under a 300 ms budget, and a band-A column lands as one atomic 24-slab mesh attach. Mesh work moved to worker threads years ago — but three of the costs that ride behind a landing never did, and they are all per-slab, on the main thread.

The three main-thread costs that ride behind every landing 1. Collision rebuild — chunk.gd:_build_slab_collision does mesh.surface_get_arrays(0) (a full vertex+index copy), expands it into a triangle list, makes a ConcavePolygonShape3D and a StaticBody3D — for the destroyed and rebuilt mesh — then the physics server rebuilds the BVH. Measured cost in the gate logs: ~1 ms per slab, 101 ms worst frame at R4.
2. Mesh upload — apply_accs assigns a fresh ArrayMesh per slab instance; the render server uploads the vertex/index buffers synchronously.
3. Node churn — each _assemble_slab creates/frees up to four MeshInstance3Ds plus an OccluderInstance3D per slab.

None of those three is measured by the profiler the team has been steering with. The stage ring (World._wprof) has no COLLIDE stage at all — collision time lands in MISC, which is the residual bucket, so the only signal it can give is "the frame was slow and I don't know why".

The honest headline HARNESS.md already records the trade-off, in the boundary row: walking p95 22 → 39 ms, max 128 → 357 ms (later re-measured at 660 ms) as the price of AC-0313's full-column order — "the tail is the price of fewer/bigger dispatch units — an honest, user-directed trade-off (recorded, not smoothed)". So the regression was known; what it was never converted into is a budget. A 350 ms frame is a 25-frame hitch at 60 fps. That is the slowdown you feel.

The single most valuable next step is not an optimisation at all — it is a frame-time p99/max budget gate with per-cause attribution (§07), because right now nothing in the harness would fail if a change doubled the worst frame.

3.1 Collision rebuilds — the top hitcher

Read chunk.gd:1631 and the cost is self-evident:

# chunk.gd:1631 — runs on the MAIN thread, per slab, every time a slab's mesh changes
func _build_slab_collision(s: Slab) -> void:
    var mesh: ArrayMesh = s.mesh_instance.mesh
    var arrs := mesh.surface_get_arrays(0)              # full copy of verts + indices
    var faces := PackedVector3Array()
    faces.resize(idx.size())
    for i in range(idx.size()):
        faces[i] = verts[idx[i]]                            # de-index: 3 Vert3 per tri
    var shape := ConcavePolygonShape3D.new()
    shape.set_faces(faces)                                  # physics BVH rebuild
    var body := StaticBody3D.new() ... add_child(body)     # scene-tree insert

A dense 16³ slab can carry thousands of greedy-merged quads; a full column is 24 of them. The counters say the rest:

gate logcollision_ncollision_ms_totalcollision_max_msframe max
AC-0313 perf @R489358 ms17104 ms
AC-0314 perf @R4106350 ms15101 ms

Two structural problems compound it:

  1. It is per-slab. A full column landing runs the loop 24 times in one frame. At even 1 ms/slab that is 24 ms; on a real terrain column with a cave system (the 15–17 ms maxima observed) it is far worse. The AC-0313 commit message records editperf flush_frames 9 → 50 and perf build_ms 492 → 2483 — that second number is main-thread build time and it quintupled.
  2. It thrashes on band edges. _reband (world.gd:9712) calls drop_slab_bodies() when a column leaves the real band and mark_all_slabs_dirty() when it re-enters — all 24 slabs at once, re-derived from full mesh arrays. A player walking along the sim boundary oscillates columns across it. The staging lane can only rebuild 2 columns per frame (_col_drain_step, "<=2 staged bodies per frame"), which is exactly why staged_dropped went 707 → 1518–1678: the backlog is being dropped, not served.
Why this is the worst offender for perceived smoothness Collision is the one cost that lands on the exact frames the player is moving into new terrain — and unlike rendering, it cannot be amortised invisibly. Godot 4 runs physics on the main thread by default, and project.godot sets no physics/3d/run_on_separate_thread. So every one of these milliseconds is a main-thread stall.

Cheap, high-value fixes, in order

  1. Budget it. A hard per-frame collision-time cap (e.g. 4 ms) with a debt queue, the way drain_budget_ms already caps the build lane. This alone bounds the spike without changing any geometry.
  2. Stop re-deriving from mesh arrays. The worker already has the greedy quads; ship a compact triangle/box list to the main thread in the handoff result and build the shape from that, skipping surface_get_arrays + re-indexing entirely.
  3. Don't rebuild what did not change. A landing that only changed light (the remesh lane) or only one slab's geometry should not touch the other 23 bodies. Today any re-assembly sets col_dirty = true and re-requests the whole slab's body.
  4. Keep bodies across band edges. drop_slab_bodies() on demote plus full rebuild on re-entry is pure waste — the geometry does not change, only the band bookkeeping does. Only the collision_enabled flag needs to move.
  5. Consider a cheaper shape. ConcavePolygonShape3D is the most expensive option available. For greedy voxel terrain, per-slab ConvexPolygonShape3D/box decomposition, or a merged column-level body rebuilt incrementally, would be materially cheaper.

3.2 The scheduler scan floor

_low_scan_slabs and _low_pick walk band_buckets from index 0 and stop at LOW_SCAN_CAP = 2048 visited entries. At R50 the queue holds 5 300–5 500 entries (all of it data_only + build work), so the cap is hit essentially every frame, which also means the "no candidate" verdict can never be cached (the cache is only written on a full scan) and the scan repeats forever:

// world.gd:3014 — the verdict cache is only valid on a full scan
if best.is_empty() and not capped:
    _low_none_key = nk          # never reached at R50: always capped

Measured: LOW_PICK 4.1–4.7 ms, p95 5.2–5.6 ms, every single frame — while the wave's own pace (LOW_WAVE_PACE_MS 3.5) only permits ~0.3 slab dispatches per frame. That is roughly 7 000 queue entries examined per dispatch. The asymmetry is the bug: the scan is O(queue) but the work is O(1).

Fix: make the queue a real priority structure (the entries are already scored by _grid_score(entry) = taxi*10000 + layer), or maintain a per-band pending-slab index so the wave can ask "which column has a rank-0 pending slab" in O(1) instead of scanning for it. This is the highest ratio of removed-milliseconds to risk in the whole codebase, and it removes a cost from every frame rather than the tail.

3.3 Recenter: full rebuild per crossing

_rec_want_step walks a (2*(R+1)+1)² box — 10 609 cells at R50 — and _rec_merge_* re-buckets the entire existing queue by the new centre, at 2 048 units per frame under an 8 ms slice. Then, in the same recenter call, the loop over chunks (≈5 100 columns) runs per-column band flips: _star_halo_evict, _demote_high_band_exit, _reentry_flip_high, and on the way in _reband → mark_all_slabs_dirty → 24 collision rebuilds.

The comment at world.gd:9795 is honest about the design intent — "the queue is RECOMPUTED, not merged" — and it fixed a real stranding bug. But it makes every chunk crossing a multi-thousand-entry operation, and at R50 you cross ~9 columns per second while walking. The 36.5 ms RECENTER maximum is that work showing through. Two directions: (a) keep the recompute but make the per-column state a cheap predicate instead of an object walk, and (b) decouple the band flip from the collision rebuild (see 3.1.4), since that is what actually costs the frame.

3.4 Per-slab node and mesh churn

Measured at R16: 653 pooled columns holding 5 574 MeshInstance3Ds — 8.54 per column, with 4 287 instances grown during one build pass. Scale to R50's ~5 000 resident columns and the scene holds on the order of 45 000 instances plus fluid, flora, occluder and collision-body nodes. Each landing frees and re-creates a slab's instances (the pool softens but does not remove the churn), and the render server re-uploads buffers for every new ArrayMesh assignment synchronously.

The AC-0247 pooling work is good and should be extended, not replaced. The higher leverage idea is to stop having one instance per slab for the far draw tiers: the low/avg LOD already proves a MultiMesh-style batched path works in this codebase. The next question worth asking is whether band B/C (and even band A) can be a small number of MultiMeshInstance3Ds per ring rather than per-column MeshInstance3Ds — that would cut both node traversal and draw-call overhead at once.

3.5 Light-gate coupling

In the real band, _mesh_dispatch_hslab refuses to dispatch until star.box_settled(cx, cz, si-1, si+1) is true, and the light engine only gets 3 ms per frame (STAR_STEP_BUDGET_MS). starlight.cpp:396 shows what an edit does: it clears and re-seeds 9 columns × 16 sections (up to 144 sections ≈ 590 k cells) for a single block change — and that is per edit, not per column landing.

This is the mechanism most likely behind "it hitches when I mine/place". A promotion or a new real-band column also owes a whole-column seed. Because the gate is all-or-nothing per slab, one unsettled section holds up every slab in its 3×3×3 neighbourhood. This is a latency penalty rather than a direct frame spike, but when it collides with a crossing it presents as a freeze. Worth measuring before fixing: the profiler's STAR substage reads ~0.1 ms average, so the cost is bounded — it is the waiting that costs, and waiting is invisible to every counter currently recorded.

04

The physics: per-frame budget is the wrong controller

This is the generalisable lesson from the last four tickets, and it explains why "we made it faster" and "it stutters more" are both true at once.

The drain is governed by a web of averages:

// world.gd:127–155 — the pacing model
const DRAIN_FRAME_BUDGET_US := 30000      # 30 ms per frame
const DRAIN_UNIT_PACE_MS := 8.0           # ~2 units/frame at 60 fps
const DRAIN_UNITS_FRAME_CAP := 4         # commented "hitch spike guard"
var budget_us := int(drain_budget_ms * 1000)
...
while budget > 0:
    if Time.get_ticks_usec() - t0 > budget_us:   # checked BEFORE a unit
        break
    ... dispatch one unit ...                      # a unit is now a 24-slab column

The time check happens before the unit, so it bounds the number of overruns, not their size. When a unit was a single slab that was fine. When a unit became "one full 24-slab column mesh + 24 collision bodies + 24 instance assemblies", a single overrun can consume 100–350 ms — and the guard that was supposed to prevent hitches now merely guarantees you get at most four of them.

The reframing Perceived smoothness is a tail property, not an average property. 60 fps means "no frame over ~16.7 ms", not "frames average 16.7 ms". Every budget in this codebase is written against the average. The AC-0229 dynamic burst cap is the clearest example: it raises the per-frame handoff cap up to 72 during flight because "the ahead band fills well behind the player" — a throughput objective, purchased with the exact currency the user is now complaining about. The knob is documented as a tuning knob, not a frame-time budget.

Concretely, three controller changes would convert this from "trade-off" to "governed":

  • Check the budget after the unit too, and split units mid-flight. A column build should be resumable at slab granularity (it already is — the probe is per-slab), so the controller can stop between slabs instead of between columns.
  • Make the unit cost visible to the controller. last_build_us already exists and already feeds the pace selector — but it is the dispatch cost, not the landing cost. The landing (apply + collision + nodes) is what spikes, and it is paced by a separate, uncoordinated cap (stream_ho_cap).
  • Spend spikes as a budget across frames. A weighted moving average of recent frame time could throttle stream_ho_cap and the drain's budget jointly, which is what the chunks_per_frame slider is manually doing today.

Second tier: costs that scale with render distance

Your default render_dist is 50 (settings.gd:33), and a lot of the cost above is quadratic in it. The taxi-square geometry at the defaults (sim 4 / medium_start 8 / low_start 27 / render 50):

bandtaxi rangecolumnsrepresentationper-column cost

A5–8104full LOD, materialized (AC-0312)heavy — new since AC-0312
B9–27~1 4008×8 avglight
C28–49~2 8004×4 avglight
data collar50–51~200h-only, no drawcheap

Two observations worth acting on:

  • Band A is new heavy work in the draw path. AC-0312 restored full-LOD draw for taxi 5–8 by materializing each far column to the full 16×16×16 no-cave fill — a 24-slab mesh built from a generate_resl(skip=1) fill, landed in a single worker task. 144 columns of new high-detail geometry, each needing the full landing pipeline. It is the right call for the look (that was the user's decision), but it means the set of columns that can trigger a 24-slab landing grew from 40 to 144, and band-A columns are exactly the ones a walking player crosses constantly. This is a prime candidate for either a lighter landing (fewer slabs materialized above/below the surface) or the batched-instance treatment from §03.4.
  • The offscreen interior cannot be trimmed cheaply today. y_only-style vertical culling exists per column but the horizontal offscreen band is the same cost as the visible one, and the engine's occlusion culling is on (use_occlusion_culling, cull_3d). At R50 that means building and maintaining high-detail geometry the player cannot see. The in_render_circle scope is generous (the full taxi square), so a cheaper "keep the data, defer the mesh" tier for the behind-the-player half would cut real work.
06

Third tier: engine-side and structural

6.1 The unmeasured 33% of the frame

In the R50 profile, the bracketed stages sum to ~11 ms of a 17.2 ms frame. The remainder is MISC (5.6 ms average, 26 ms max) — and it is the residual bucket, so it silently absorbs every cost that was not explicitly bracketed. On this Linux box that includes physics, scene-tree work, and the render server; on your Windows build with forward_plus, real GPU-side and driver-side cost lands there too. Roughly a third of the frame is currently unattributed — that is the largest single blind spot in the whole investigation.

6.2 Physics is single-threaded on the main thread

project.godot does not set physics/3d/run_on_separate_thread. Given the collision evidence in §03.1, enabling it is a one-line experiment with a plausible large payoff — with the caveat that it changes CharacterBody3D behaviour timing, so it must be gated by the player/interact/fluids arms.

6.3 Two monoliths

scenes/harness.gd is 24 800 lines and world/world.gd is 11 900 (ARCHITECTURE.md §1 records this and tracks the split as AC-0115). This is not a runtime cost, but it is a real performance-engineering cost: the scheduler, the LOD lanes, the recenter walk, the light integration and the collision staging all live in one 11.9 k-line file, and every one of them is a per-frame loop over shared state. Splitting it is a prerequisite for making the scheduler's data structures changeable at all.

6.4 Fluid pass structure

tick_fluids runs at 20 Hz over the band-0 diamond and is gated by fluid_wet, which does keep the natural ocean free. But for each wet chunk it walks all 24 slabs and calls slab_flat() per wet slab, and set_block / _record_edit mark columns wet. During any water interaction this becomes a per-tick full-column decode. Cheaper: keep the flat decode on the slab object (invalidate on set_fl_at) rather than re-deriving it from the dictionary every tick.

6.5 Worker-pool sharing

threadgen_pool, threadmesh_pool and io_pool are the same WorkerThreadPool singleton, split by count, with the loading window raising the mesh cap to LOAD_TM_CAP = 64. The code comments already record a measured pathology here ("a 24-deep gen queue … starved the 2 ms mesh tasks", LOAD_TG_CAP 24 → 8). Two in-flight coordinates deep enough to starve each other remain a structural risk worth a dedicated review — particularly because the mesh tasks are the ones whose latency the player feels.
