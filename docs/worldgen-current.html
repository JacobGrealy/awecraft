01

The big picture

The current pipeline at commit 83cfcfe is a two-lane, worker-pool, main-thread-handoff machine driven by one bounded, always-current work queue. The whole lifecycle, in one place:

  1. Player chunk crossing — the player's floorf(pos/16) chunk index changes in x, z, or y (a Y-only crossing is a full recenter, AC-0234); camera-only moves never recenter (godot/player/player.gd:1611-1619).
  2. Recenter — World.recenter() moves the anchor (one chunk ahead on fast crossings, AC-0277), records the player Y (last_wy), re-bands / demotes / re-enters / frees chunk nodes, pre-warms the 5×5 queue, (re)fires the 5×5 gen burst, and starts a sliced walk that over the next frames recomputes the entire entry queue (WANT / STUB / MERGE_OLD / MERGE_WANT / MERGE_RING, atomic swap at finalize) (godot/world/world.gd:8321-8657, 8659-8703).
  3. The queue — one entry per chunk-column in band_buckets (bucketed by taxi); no score is ever stored — _grid_score is a pure function of the live anchor, live player slab, and live pending probes, so the very next pick after any recenter re-orders the whole queue for free (world.gd:4879-4890, 731-777).
  4. Per-frame pick — _drain_build_queue runs once per process frame: it draws a wall-clock-paced budget of units (1 unit = one gen enqueue or one slab mesh dispatch) and dispatches the lowest-scoring candidate to a lane (world.gd:6641-7035).
  5. Data lane — worker threads call C++ AweGen.generate_resl(cx, cz, seed, 384, 126, skip, keep) directly: a whole 384-column, all 24 slabs, in one call (the keep mask is always empty — the dormant AC-0237 seam); results land via threadgen_poll once per frame (world.gd:4936-4978, 5016-5098, 5195-5290).
  6. Banana pass + landing — on the main thread, after worker gen: the shore banana-tree post-process, then c.slabs_landed(...) — a reference handoff that bumps data_gen, which re-pends every slab in the build lane (world.gd:5272, 5281; godot/world/generator.gd:406-433; godot/world/chunk.gd:654-667).
  7. Build lane — one dispatch unit = exactly one slab of the picked column: _build_unit_hslab → _mesh_dispatch_hslab with its gates (no data → defer; in-flight dedup; TM cap; all 8 neighbors must hold data), the C++ snap_rings boundary snapshot, the scoped neighbor strips for y ∈ [si·16−1, (si+1)·16], then AweMesh.build_accs on the shared pool (world.gd:6446-6461, 6319-6395).
  8. Mesh handoff — threadmesh_poll (capped at stream_ho_cap landings per frame) attaches the slab's MeshInstance3Ds and stamps high_stamps[si] = data_gen — but the slab is hidden: the never-show-unlit rule (world.gd:5430-5603, 5706-5824).
  9. Lighting settle — every drain landing on an unsettled chunk re-marks light_dirty; the frame's flush loop re-meshes with settle=true (per-slab for partial columns, whole column when mesh_built); the flush landing sets flush_slabs[si] / light_settled and flips the slab visible. A landing in an already-settled chunk is late: un-settle, hide, re-arm (the 83cfcfe fix, KEEP) (world.gd:4403-4523, 5755-5779, 5752-5754).
  10. Visible at the right LOD — inside the high band the high-res slab shows (nothing renders while it is pending); outside it, the low wave paces coarse MED/LOW avg-color shells in the same (layer, taxi) disc order, and band crossings are free visibility flips (keep-all-LOD) (world.gd:3060-3199, 8261-8318).
  11. Persistence — a column is saved when it leaves the streaming set (evict) and on player save: worker-encoded AWCC v5 palettized blobs into 32×32 region files, main-thread-serialized commit, worker compaction on bloat; the read path is disk-first for every column (world.gd:8192-8204, 9194-9306, 9372-9490, 4939-4947).
Two structural facts the redesign turns on (1) Data is column-atomic — one generate_resl produces all 24 slabs and data lands only as whole columns (c.slabs_landed, world.gd:5281); the slab keep mask exists in C++ but is always passed empty (world.gd:5028-5031). (2) Meshing is already slab-granular end to end — worker scopes on si, the handoff attaches per slab, probes and stamps are per-slab (world.gd:631-654, 5731-5732). Everything downstream of the data lane is ready for a Y-disc; the data lane and the order shape of the queue are the two constraints (see §7).
02

Terrain generation

Terrain data generation is a single pure function of (cx, cz, seed) — plus hmax=384, sea=126, and two optional knobs: a lazy-skip flag and a per-slab keep mask. The entire generator lives in C++ as the AweGen GDExtension class (gdext/src/gen.cpp, 1022 lines). Since AC-0208 there is no GDScript generation path at all: the old ~370-line GDScript body was deleted, the AWECRAFT_GENCPP kill switch removed, and Game._ready fails fast if the C++ library is missing (godot/world/generator.gd:46-63). The GDScript WorldGen class is a thin facade: it forwards to AweGen.generate_flat, adds the per-face (sphere) transform generate_face, keeps the 2D proxy queries, and runs the post-generated banana-tree pass.

2.1 The AC-015 density model (the vanilla density router since AC-0347 P2)

The current terrain model is the coarse 3D density field with a vanilla density ROUTER (gdext/src/gen.cpp:1-91): one per-cell density field produces the surface, all caves, and the deep lava lakes from a single solid/air test (d > 0 solid — the vanilla convention too). Since AC-0347 P2 (THE STRUCTURE) the field is the Java 1.21.4 final_density router: with k = H − y (depth from the surface) and K_CUT = 10 (the switch cut = the ramp saturation depth): shallow (k < 10): d = min(S_ramp(H,y), 5·entrances) — the quintic surface ramp kept as-is, the entrance family carving the deliberate openings; deep (k ≥ 10): d = min(entrances, 4·layer_c² + clamp(−1,1)(0.27+cheese_c) + clamp(0,0.5)(1.5−0.64·k/10)) — the base terrain contributes nothing below the shallow band (the solid/air decision IS the cave router), the suppressor thins the caves toward the surface (0.5 at the cut, 0 by k≈23.4), and the squared layer term stacks the cheese caves into levels in absolute y. The old A(y)/DEEP_GROW/CAVE_AMP depth amplifier is gone; the “air for sure above H+11” margin is now structural (the ramp clamps −1 above H+10.5 → min(−1, 5·entrances) ≤ −1 for any noise). There is no heightmap-plus-carve anymore.

The field is built on a coarse lattice: 7×9×7 = 441 points per chunk (a grid of 4×8×4 cells = 4×48×4 BLOCKS per cell — 4-block horizontal / 48-block vertical, plus a 1-cell margin per axis so trees rooted up to 2 blocks outside the chunk can still grow leaves in; the “4×8×4” count is the number of cells, not a 4×8×4-block cell size), with 10 independent coarse fields sampled per lattice point (3 surface + 3 ore + the cheese + the 3 AC-0289 tunnel fields), then trilinearly interpolated per cell (gen.cpp:455-530). AC-0347 P2 adds TWO DENSE sources evaluated in the scan itself (they cannot ride the 48-block lattice): the layer (vanilla cave_layer AS-IS, seed+302 — the ~32-block vertical period) and the entrance family (vanilla caves/entrances minus its spaghetti min, seed+306 — the 0.37 offset makes entrances rare); the cheese stays coarse (P1’s field).

2.2 The surface formula (per column, 256 columns)

surface_h (gen.cpp:345-370): trilinear-sample the three surface fields at the sea-level slice gy = 126/48 = 2.625 (gen.cpp:349); affine-calibrate each sample onto the old AC-0091 2D distribution (gen.cpp:354-356: cc = 0.4219 + (c−0.3681)·(0.1280/0.0467), hc = 0.4964 + (h−0.5112)·(0.1361/0.1107), rc = 0.4292 + (r−0.5743)·(0.1366/0.1443) — constants measured over a 640×640 block area, seed 44); then the AC-0091 remap y = 105.2 + cc·36.4 + hc·52.0 plus the mountain boost if rc > 0.62: y += (rc−0.62)·390.0 (gen.cpp:357-359); then the exact spawn pad (gen.cpp:360-368): d≤6 from (8,8) ⇒ y = SPAWN_H = 136 exactly; 6<d≤10 ⇒ smoothstep blend back to 136; finally clampi(floor(y), 3, 300) (gen.cpp:369). Biome comes from two 2D fbm2s on the same 260-block scale: t = fbm2(x/260+900, z/260+900, seed+21, 3)·2−1, m = fbm2(x/260+1700, z/260+1700, seed+33, 3)·2−1 (gen.cpp:505-506) → bcode: 0 snow (t<−0.25), 1 desert (t>0.35 ∧ m<0.1), 2 forest (m>0.25), 3 plains (gen.cpp:508-515).

2.3 The density test and the top-down scan

Per column (gen.cpp:537-585): if skip ⇒ he = H, no scan, no cave field read, no lava pockets (gen.cpp:552-558). Otherwise allocate solidf[hmax] and scan top-down from top = min(H+11, hmax−1) down to y=1 (gen.cpp:568-571; the +11 bound is proven air above because the ramp clamps at ±1 and |CAVE_AMP·(cave−0.5)| < 1, comment gen.cpp:561-563); per y: skip ungenerated slabs (gen.cpp:573-574), cave = tril(f_cave, gx, y/48, gz), s = dens_at(H, y, cave, pad) > 0 (gen.cpp:575-576). he = topmost solid; a fully-caved column falls back to he = 0 (bedrock is the "surface", gen.cpp:581-582).

  • dens_at (gen.cpp:399-404) = density_ramp(H, y) + (non-pad only) cave_amp(H,y)·(cave−0.5).
  • density_ramp (gen.cpp:376-385): the quintic spline t = (H+0.5−y)/10 clamped to ±1, mapped through the same quintic as AweNoise._fade to [−1,+1] (solid below, air above, C² at the clamps).
  • cave_amp (gen.cpp:390-395) = 1.8 · (1 + max(0, H−y−10)/8) — deep caves widen downward (MC-1.18 cheese).
  • Params: CAVE_AMP 1.8, R_BAND 10.0, DEEP_GROW 8.0, SURF_YSCALE 64.0, GY_CELLS 8 (gen.cpp:230-235).

2.5 generate_flat vs generate_resl

The generator's two output formats: the flat column — a 98,304-byte PackedByteArray, index (y<<8)|(lz<<4)|lx (gen.cpp:520) — and the palettized slab form ("resl": an array of 24 slab entries, each null (all-air) or a dict {n, b, p, i, nz, nc, bs}). generate_resl (gen.cpp:994-1003) wraps gen_flat (gen.cpp:457-763) + palettize_slabs (gen.cpp:800-888) and returns [data_slabs(24), fl_slabs(24, all null — gen produces no fluid)] — the exact 2-element shape the threadgen handoff expects (world.gd:5209, 5233-5236). In the live game the flat form never reaches the main thread: workers call generate_resl directly (world.gd:5093, 5121, 5232-5290).

2.7 Determinism + the salt table

Everything is bit-deterministic. No RNG, no time, no iteration-order dependence, no cross-column state: every per-cell value comes from either trilinear interpolation of the coarse fields (pure fbm3 of world lattice coords + salt) or direct hash2i/hash3i of world coords + salt. A regenerated slab is bit-exact because "no cross-slab state exists" (gen.cpp:451-455); neighbor-chunk influence is input (the 1-cell field margin + the 20×20 tree neighborhood), not shared mutable state.

  • Bit-exact C++ port: hash2i/hash3i/fade/lerp/vnoise2/vnoise3/fbm2/fbm3 in gen.cpp:117-201 are bit-for-bit ports of godot/core/noise.gd:4-88 (same op order, f64, i64/i32 integer hash, lerp = a + (b−a)·t), compiled -ffp-contract=off so no FMA contraction (gen.cpp:55-59). Verified by the AWECRAFT_LOGIC=genprobe arm: 4700+ noise samples compared for exact f64 equality (harness.gd:16090-16184).
  • The genhash gate: AWECRAFT_LOGIC=genhash generates the 5×5 around the origin and prints MD5 per column (harness.gd:1024-1039). Current accepted baseline (post-AC-0261): GENHASH 0 0 = 80b904c0e5f085eef1e839459058c706 (godot/CONTINUITY.archive.md:357). Any terrain change must re-baseline it deliberately.
  • The keep-mask A==B gate: keep empty must produce output bit-identical to pre-AC-0237 generation (gen.cpp:441-444, 971-975; world.gd:5028-5030).
  • skip is not part of the terrain contract: skip=1 deliberately produces a different (cave-free) column for offscreen interior chunks — it's a fidelity knob, and those chunks are expected to be regenerated full later (gen.cpp:66-81).

No hash chains: no generated value feeds another salted hash — every field is an independent function of (world coords, seed+salt). The only "chain" is structural: he (scan output) drives surface/dirt/aquifer/flower placement, and heff (scan output) drives tree/flower bases.

2.8 The per-face (sphere) model

AC-0143 models the planet as a sphere of radius R partitioned into 12 faces = 6 axes × 2 sectors, face = axis·2 + sector (godot/core/sphere_math.gd:1-27). Each face has a 1024×1024 cell grid (CELLS_PER_FACE = 1024); (u,v) ∈ [0,1]² maps affinely to a rectangle on the unit cube, then normalize · R.

  • Home faces 0 and 1 (the +Y halves, split on X) stay the flat home world with 1-meter columns — they use the legacy "%d,%d" chunk keys and the normal streaming pipeline (world.gd:10402-10414, 10463-10464).
  • Non-home faces 2-11: a face chunk is 16×16 cells, keyed "%d:%d:%d" % [face, ccx, ccz]. generate_face (generator.gd:208-217) reuses the home-column pipeline with (1) a per-face salt seed ^ (face·1000003) and (2) a face-disjoint 2D domain face·64 + cx, face·64 + cz — each face is an independent flat world, salted by face. Seams policy: "No cross-face continuity in P1a (face-border terrain seams acceptable, documented)".
  • Generation trigger: on-demand, main-thread, synchronous — first get_block_key/set_block_key access to a non-home face position (world.gd:10460-10481 → _ensure_face_chunk, world.gd:10421-10454). Chunks are FIFO-capped at FACE_CHUNK_CAP = 512, pooled on eviction. Face chunks are never meshed or lit in the current phase (data-level only) and are not part of the streaming pipeline (world.gd:10390-10394).

2.9 The dormant AC-0237 keep mask — the slab-granularity seam

Dormant parameter, live machinery A slab-granularity escape hatch does exist in C++: the AC-0237 keep mask (a 24-byte PackedByteArray; slab si generated iff keep[si] ≠ 0; empty = full column) (gen.cpp:441-456, 971-975). It bounds the per-column scan and emit to selected slabs and encodes ungenerated slabs as null (no format change, gen.cpp:447-449). It is disjoint-set capable — "the window's kept set = the tower's terrain span UNION the player band — two intervals while the player flies high" (gen.cpp:444-448) — and the scan/emit/veg loops are already guarded by slab_kept (gen.cpp:573-574, 592-594, 711, 731, 752-753). The surface slab is always kept so the effective surface + vegetation always land (gen.cpp:455-456). What retired it: AC-0257 removed the vertical window — threadgen_enqueue now always passes an empty mask ("generation is ALWAYS the full column … bit-exact, gen is a pure f(world coords, seed)", world.gd:5028-5031). A Y-layer or cheap-far redesign is largely re-activating and generalizing this dormant parameter.

Cross-slab coupling inventory (what a per-slab design must handle): caves cross slabs freely but need no state (pure per-cell function of world coords + shared fields); the only column-scoped scan output is he, the effective surface — handled by always keeping the surface slab; trees cross slabs (handled by the slab_kept guards — ungenerated cells are simply not written, and a later slab generation writes the same cells bit-exactly); the aquifer is column-scoped (needs he); ores/obsidian/bedrock/lava are slab-local; the lazy-skip decision is XZ-only (world.gd:4990-5013) — the natural seam for a Y-aware skip.

03

The scheduler

The scheduler's job is to keep a bounded, always-current work queue of "what still owes work" around the moving player, and to feed that queue, at a wall-clock-paced trickle, into two worker lanes: the data lane (column generation / disk read, C++ AweGen on the shared WorkerThreadPool) and the build lane (per-slab high-res mesh + light, C++ AweMesh/AweStrips on the same pool). A third, separate lane — the low/placeholder wave (_low_step) — owns the visible band outside the high band and runs on its own pacing, fed by the same queue entries. The scheduler itself runs entirely on the main thread: the per-frame drain, the recenter walk, the polls/handoffs, the light flush, and the pick/scoring functions. Workers only ever execute one self-contained unit (a full-column gen, one slab mesh, one low emit, one IO op) and hand results back through the main-thread polls.

3.1 The queue structure

The queue is a flat list of entries — one per chunk-column that owes build or data work — held in band_buckets, an array of arrays indexed by taxi bucket (bucket b ≈ columns at taxi b, clamped; band_buckets[b].push_front(...) puts newest-first inside a bucket) (world.gd:4879-4890). data_only=false is a build entry (bands 0/1); data_only=true is a band-3 feed entry (the collar ∪ circle-ring data that feeds the circle edge's 8-neighbor build gate — never meshed). queued_keys maps key → "build"/"data" in lockstep (flag ⇔ entry invariant, rebuilt at finalize); queue_size counts all entries, _build_q_n counts build entries (the depth-cap counter); _qb maps key → bucket index for O(1) removal.

_recenter_slice (world.gd:8659-8703) runs every process frame while _rec_pending (paused during the spawn window — the rebuild walk is ~5 s of main-thread work at R50 and would race the burst/spawn handoffs):

So a recenter spans frames: each frame gets ≤ 8 ms of walk or ≤ 2048 unit-steps (whichever first). At R16 the whole walk is a single ~8 ms frame; at R50 (7845-entry circle) it takes many frames. The walk never discards partially — WANT/STUB are pure bookkeeping and the queue swap is atomic at finalize.

  • Phase 0 — WANT (8749-8797): walks the stream-set bounding box (half = maxi(render_radius+1, b1_eff()+1), cursor row-major). Skips out-of-set cells and band-3 cells (MERGE_RING owns those). For each in-set band 0/1 cell: if the existing chunk's band differs → _reband (sets c.band, drops/queues collision bodies — never rebuilds the mesh, keep-high) and, if the old queue held it as "data", _convert_data_to_build. Then the recompute: if c == null or not c.mesh_built: _rec_want[key] = {cx, cz, d: taxi} — i.e. every in-set column that still owes build work gets collected fresh, whether or not the old queue held an entry (an old "build" flag must not suppress the re-queue).
  • Phase 1 — STUB (8799-8819): same box walk; for every in-set cell with no chunk node → stub_chunk(cx, cz) (pooled node, band assigned, init_slabs()) — the data lane / build lane can now touch it.
  • Phase 2 — MERGE_OLD (8821-8855): walks the old band_buckets. For each old entry: out of the new stream set → drop; in _rec_want → drop (WANT re-queues it fresh); otherwise (a meshed column the recompute does not re-queue) → re-bucket by the NEW taxi at the bucket tail (carried entries sit behind the fresh push_front ones). Dropping the carry desynced flags/entries — measured 172 s stall in the lightstate arm.
  • Phase 3 — MERGE_WANT (8857-8876): for each WANT key: if the chunk is now mesh_built (a landing raced) → skip; else build the entry {key, cx, cz, data_only: false} + _tier_stamp and push_front into the new bucket — newest entries ahead of the re-bucketed carry.
  • Phase 4 — MERGE_RING (8878-8969): same box walk but only band-3 cells (collar ∪ circle ring): if already queued or already has data → skip; else data_only: true entry, push_front. These are the 8-neighbor gate's fuel — exempt from the depth cap.
  • Finalize (8886-8949): (1) stale sweep — the pre-warm queue ran in parallel with the walk, so an entry whose chunk FINISHED during the walk is dropped; (2) atomic swap — count entries, band_buckets = _rec_new_buckets, _pool_touch() (invalidate all cached picks), _rebuild_qb(), rebuild queued_keys from the live queue (flag ⇔ entry), reset drain window + cursors, re-apply the depth cap, _rescore_kick() (the column-cross rescore); (3) outrun escalation — if an escalation was parked and the player is still > REBUILD_COVER_L1(4) taxi chunks from this walk's center → chain the next walk immediately; if the player moved back inside, drop it.

The ahead lead's two time-based companions (AC-0277): the snap-back — in _process (world.gd:4377-4381): once the crossing stream is quiet for AHEAD_FAST_MS (3.5 s) AND the anchor still leads, recenter once onto the chunk under the player (this is the open question for the redesign — HANDOFF §5.1); and the settle (world.gd:4386-4390): when no walk is pending, not in the spawn window, > AHEAD_RING_DEBOUNCE_MS(1000) since the last recenter, not ahead-active, and the last walk center ≠ current anchor → one final rebuild at the resting center — the "fast-then-stop" fix: a 50× flight outruns the debounced rebuild by ~30 chunks and parks the standing queue behind the resting player. Walking never triggers it.

3.4 Scoring — _grid_score, the full formula

def _grid_score(e):                     # e = a queued entry dict
    dx = e.cx - last_pcx                # LIVE anchor (possibly ahead)
    dz = e.cz - last_pcz
    taxi = abs(dx) + abs(dz)
    c = chunks.get(e.key)
    layer = 0
    in_high = c is not None and (taxi < medium_start_r or is_tier0_col(dx, dz))
    if c is not None and not c.data.is_empty():
        si = _hslab_best_pending_cached(c) if in_high else _entry_best_pending_cached(c)
        if si >= 0:
            layer = _layer_rank_of(si)
        elif _lod_windowed_for(c):      # 83cfcfe Y-window (TO REMOVE, §3.6)
            return 1e30                # windowed -1 = NO CANDIDATE
    s = layer * 10000.0 + taxi          # LAYER-MAJOR bake order
    if is_tier0_col(dx, dz): s -= 1e10   # tier-0 SECTION prefix
    if loading_active and _loading_target_col(dx, dz): s -= 5e9  # AC-0274 load target
    return s

Verified line by line: dx/dz 732-733; layer=0 734; in_high 741; probe 742-745; the 1e30 rule 758-759 (rationale comment 746-757); the bake 760; tier-0 prefix 765-766; load-target prefix 775-776. An entry whose chunk has no data skips the probe block entirely — it scores at layer = 0 (taxi-only, with prefixes): a no-data column's "first owed slab" is treated as the player's slab.

The slab fan: _layer_rank_of(si) (world.gd:473-479): d = si − player_slab; rank 0 at d=0; d < 0 → −2d − 1 (1, 3, 5, …); d > 0 → 2d (2, 4, 6, …). So the fan around the player slab is: player slab (0), one BELOW (1), one ABOVE (2), two below (3), two above (4), … — the spec's "slab fan" (rule 2), exactly.

The score layer·10000 + taxi is LAYER-MAJOR: all columns' rank-0 slabs (in taxi order) before any column's rank-1 slabs, and so on — a global layer sweep, not per-column completion. The 10000 multiplier makes layer dominate taxi (taxi maxes well under 10000 at any R; the largest (layer, taxi) value in play is ~120k).

Worked example — the shape gap (matching HANDOFF §2):
a passed column's deep slab: layer 1, taxi 9 → 1·10000 + 9 = 10009
a fresh edge column's near slab: layer 2, taxi 50 → 2·10000 + 50 = 20050
10009 < 20050 → the passed column's DEEP slab outranks the fresh edge column's near slab — deep fill progresses in the gaps between recenters ("whole columns behind me").
Worse while flying high: a fresh column's terrain top (slab 8, player slab 18) makes its first pending slab rank 19 → 19000 + taxi, which loses to ANY passed column owing rank ≤ 18.

The prefixes: (1) tier-0 section −1e10 (765-766) — _is_tier0_col = Chebyshev ball maxi(|dx|,|dz|) ≤ tier0_r (world.gd:1628-1629; default 0 = the player's own column, max 8 = 289 columns) — every tier-0 slab scores −1e10 + layer·10000 + taxi, so the section (fanned from the player's Y) is fully complete before ANY ring slab starts; the build lane restricts itself to the high band + tier-0 set (world.gd:6516, 6786, 6918) and the low wave skips tier-0 entirely. (2) Load-target −5e9 (775-776) — only while loading_active; the target = Chebyshev ≤ tier0_r OR taxi < mini(band0_r, medium_start_r) (4702-4706) — "load tier 0 + simulation distance and then load the rest normally" (AC-0274 decision B); −5e9 sits below tier-0's −1e10 and above every (layer, taxi) value.

Live-anchor property — "rescore all slabs every recenter" is true today Nothing is cached about the score itself. The two caches that DO exist are (a) the pick cache — _pick_build_cached / _pick_data_cached store the last winning candidate under a key of (_pool_ver, maxb, spawn_fast, last_pcx, last_pcz, band0_r, ...) (world.gd:432-445, 6541-6553, 6589-6600) — and (b) the probe caches — fingerprints [data_gen, fl_gen, _player_slab(), _lod_tier_of(dx,dz), _lod_windowed_for(c)] (world.gd:593-595, 671-673). Both invalidation sources are live-state-derived: _pool_ver bumps at EVERY queue mutation; probe fingerprints move when the anchor, player slab, tier, window bit, or data changes. Both probe caches clear past 8000 entries. Consequence: the next pick after any recenter re-orders the entire queue — free. What is NOT re-derived is the order's shape: the (layer, taxi) layer-major form above.

3.5 The pick loop — _drain_build_queue

Called once per process frame (world.gd:4559). Guards and budget (6641-6721): first _startup_gen_apply() (land burst slots); edit-lane yield — if edit_inflight_count > 0: return (an edit handoff must land on a short frame, AC-0187); queue_size == 0 → only the collision stage; _rescore_step() (amortized tier/rank re-stamp); startup detection and the startup build-hold (if startup and _startup_gen_pending_n > 0: return); then the unit budget, wall-clock paced:

  • frame_dt_ms = min(now − _drain_last_t, DRAIN_DT_CLAMP_MS=100); unit_pace = DRAIN_UNIT_PACE_MS(8) if the last dispatch was fast (< BUILD_FAST_US(15000)) else DRAIN_UNIT_PACE_SLOW_MS(16) — fast dispatches bank units twice as fast.
  • loading_active → budget 1000000 (effectively unbounded, bounded by the 300 ms time budget); startup → 12; else _drain_acc_ms = min(acc + frame_dt, 4·unit_pace) and budget = min(4, int(acc/unit_pace)) — at 60 fps this reproduces 2 units/frame (fast) / 1 (slow); at 30 fps the accumulator banks 2×/frame.
  • Small-move trickle: 1.5 s after each recenter the budget is clamped to 1/frame.
  • Drain window: the pool scan admits buckets 0..maxb only; _drain_win_b starts at b1_eff()+2 then grows one bucket per DRAIN_WIN_PACE_MS(250) wall ms in steady state; loading uses the full window.

The steady-state loop, per unit (6876-7022):

  1. bpick = _pick_build_cached(maxb, include_fb=false, high_only=TRUE); if no candidate, the forward-lead pass (include_fb=true) additionally admits the forward band's data_only entries — the 2r+1 columns at cx = last_pcx + render_radius — so a ready lead chunk can pre-build before the general sweep reaches it (AC-0079 v3 C1) (6899-6904).
  2. High-band gate: a pick with taxi ≥ medium_start_r and not tier-0 is held (perf_high_gate_holds_n += 1) — the main build lane is the HIGH band only (6916-6920).
  3. sih = _hslab_best_pending_cached(candidate): if sih < 0 — a full −1 is genuine completion → _remove_entry (free the entry); a windowed −1 (83cfcfe) just holds the entry (6929-6940).   4. If no build unit, the data pass: _pick_data_cached(maxb) → _gen_unit(c, cx, cz) (disk-first read or threadgen_enqueue) (6969-6991); one disk read/frame cap; break when threadgen_inflight ≥ threadgen_max (pool saturated).

Loading-window drain (6740-6875): two independent feed phases per frame — Phase 1 (builds): fresh pool scan per iteration (re-pick keeps the order adaptive as landings land — a score-once snapshot raised churn 1.3×→1.94×), high-band only, best _grid_score; windowed −1 → break the pass (6813 class, the pick scored it lowest ⇒ no window-visible candidate exists); full −1 → remove + continue; deferred dispatch: TM-full → break, else per-column _lw_skip (the one-column-at-a-time load stall fix). Entry removal (7053-7089): fast path via _qb (O(bucket)), full-scan fallback on staleness; updates queued_keys, queue_size, _build_q_n, bumps _pool_ver.

This is the mechanism AC-0282 must remove (HANDOFF §3). It implements rule 4 ("passed discs stop building down while you keep moving") with a position-based moving state + a 3.5 s timer, which the user explicitly rejected: "3.5 s is a description of approximately what should happen based on our constraints, it in itself is not a constraint. So there should not be some kind of internal timer that changes what we do."

  1.   2. _lod_player_moving() (493-499): _lod_move_ms > 0 and now − _lod_move_ms < AHEAD_FAST_MS(3500) — "moving" = "the player moved ≥ 2 blocks at some point in the last 3.5 s". The 3.5 s window is SHARED with the ahead-lead fast predicate (same const, world.gd:3241).
  3. _lod_windowed_for(c) (513-522): c != null and _lod_player_moving() and not _is_tier0_col(...) — while moving, every non-tier-0 column is windowed; tier-0 is never windowed (full column even while moving — the band model).   4.   5.   6. The pick-site holds: a windowed −1 must never free the entry — steady build pass holds (u = 0, entry stays queued; removing on a windowed −1 stranded the spawn 3×3 — measured), load phase 1 breaks the pass.
  7. The cached-probe fingerprint coupling — the cached probes fingerprint the 5th element as the per-column window bit, and the probe CALL uses the SAME per-column predicate (world.gd:618, 703). This call↔fingerprint identity is the "soundness law" (HANDOFF §3): the r6 defect was the LOW cache fingerprint using the per-column bit while the probe used the GLOBAL moving bit → a windowed −1 was cached under the full-probe fingerprint and served forever → 50 ring holes through the whole lightstate settle.

Why it exists: it masks the layer-major shape gap (§3.4) — while moving, the probes can't see the deep slabs of any non-tier-0 column, so the (layer, taxi) order can't express "deep work behind the player" at all; only the player-slab ±1 window of every column plus the full tier-0 column are candidates. When the player stays still 3.5 s the window closes, the full probe resumes, and the queue reaches the deep disc on its own. Per HANDOFF §2, 83cfcfe's window is exactly what makes the user's in-game test pass — and exactly what the user now rejects on mechanism grounds. After removal, every probe is FULL and −1 is genuine completion (the hold/break sites collapse to _remove_entry on any −1).

4.3 The build lane, step by step

_build_unit_hslab (6446-6461) → _mesh_dispatch_hslab(c, cx, cz, si) (6319-6395):

  2. Gate 2 — in-flight dedup: _tm_inflight_keys.has(key) → return (one slab at a time per column; the entry stays queued and is re-picked next frame) (6328-6331).

  5. Snapshot: AweStrips.snap_rings — the 8 neighbors' relevant slab rows are copied into the task's neighbor_strips (a scoped strip: only y ∈ [si·16−1, (si+1)·16], the 3 slab rows the build actually reads) (6352-6372). This is what makes per-slab builds correct without holding the whole column.
  6. 4.5 Persistence — layout, write, read

Format: palettized slab blobs, codec version 4 on disk, v5 wire (chunk_io.gd:9-10: VERSION = 4, V5_VERSION = 5 — v5 adds the 24-bit gen_mask header recording which slabs exist, so partial columns round-trip). One blob = the 24-slab palettized form (§2.5) + header. The on-disk codec (gdext/src/chunk_io.cpp) shares palettize_slabs with gen, so disk and gen use identical bytes.

Region files: the world is partitioned into 32×32-column regions (regions/, one file each). A region file is a container of up to 1024 chunk slots. Write path — a column is saved when it leaves the streaming set (evict, _free_chunk_save, world.gd:8192-8204) or on player save; the encode runs on the shared pool LOW (_save_encode_worker, 3/frame cap), then a main-thread- serialized commit appends the blob to the region's in-memory copy and writes the file (the main thread owns file I/O ordering; workers only encode). Compaction: when a region file grows past its size budget, a worker (_compact_region_worker) rewrites it densely in the background; a bloat-triggered compaction is scheduled, never inline (9388-9490).

Read path — disk-first for EVERY column: on load and on any enqueue, if the column has a save on disk, the disk read wins (never regenerate what exists, world.gd:4939-4947, 9308-9338); the decode lands through the same threadgen_handoff as a fresh gen. Partial columns (regen-merge, world.gd:5273-5279, 9149-9171): a column whose gen_mask records only some slabs re-enters with the missing slabs re-queued — the v5 mask is what makes this possible; today it is exercised by the regen path (a disk column whose data was stripped) and is the seam a Y-disc or cheap-far design would reuse.

4.6 The late-landing fix (83cfcfe — KEEP)

Binding constraint — keep exactly A slab that lands (mesh or flush) into an already-SETTLED chunk must un-settle the chunk, hide the just-landed slab, and re-arm the light flush — never show an unlit slab in a settled region. Two sites:
  • Per-slab site (world.gd:5752-5754): a high-slab handoff into a light_settled chunk → light_settled = false, the slab stays hidden, light_dirty = true — the flush loop re-meshes it with settle=true on the next drain and re-shows it lit.
  • Full-column site (world.gd:5875-5882): a whole-column flush landing (settle re-mesh) into an already-settled neighbor region → same un-settle / hide / re-arm cycle at the column level (the E2 wave's boundary case).

Why it exists: the flush loop settles a column when it has no light-dirty slabs left; a concurrent landing (a slab dispatched before the settle, landing after it) would otherwise appear UNLIT in a settled region — the "bright flash then dark" pop the user saw. The dependency surface (what the redesign must preserve or replace deliberately): (1) the light_settled chunk boolean (chunk.gd:45); (2) the flush_slabs per-slab settle record (chunk.gd:40); (3) the show/hide flip in the flush landing (world.gd:5763-5779); (4) the never-show-unlit visibility rule (the slab's visible is a function of its flush state, not its mesh state); (5) the E2 wave's no-op proof (a settle that changed no eff frames re-marks no neighbors). A Starlight-style propagator would replace the settle/flush machinery with per-section nibble state — the un-settle / hide / re-arm SEMANTIC survives (a landing into settled light re-opens the queue for that section), the mechanism changes.

05

LOD, lighting, chunk state

5.1 The four acts of a column

Every column passes through four acts, each owned by a different part of the machine: (1) generation (the data lane — all 24 slabs at once, §4.2); (2) meshing (the build lane — slab by slab along the fan, §4.3); (3) lighting settle (the flush loop — slab-by-slab or whole-column re-mesh with settle=true, §5.2); (4) LOD display (the low wave and the band flips — which representation is visible, §5.3-5.6). The acts overlap in time (a column is being meshed while its neighbors are settling), and the queue is what keeps their order sane.

5.2 The never-show-unlit rule — the full chain

  1. A slab's mesh handoff attaches its instances but leaves them hidden (world.gd:5731-5732 stamps, the flip happens in the flush).
  2. The slab's light_dirty bit is set on: first mesh landing (no settled light yet), any edit in the 3×3 ring (_mark_light_around, world.gd:10, 9060-9068), any E2 wave re-mark (7822-7908), and any late landing (5752-5754).
  3. The flush loop (_flush_light_step, world.gd:4403-4523) runs each drain call: it picks the nearest light-dirty chunk (1 column/frame steady, EDIT_FLUSH_MAX_PER_FRAME = 1, world.gd:15; 6 during loading, 103; 40 ms time budget, 11), re-meshes it with settle=true — per-slab if the column is partial (high_stamps.keys(), 4506-4511), whole-column if mesh_built (4474-4476) — and on the flush landing sets flush_slabs[si] / light_settled and flips the slab visible (5763-5779).
  4. A column is settled (light_settled = true) when it has no light-dirty slabs left AND every slab ≤ top/16 is stamped (5763-5769).
  5. A landing into a settled chunk is late → un-settle, hide, re-arm (§4.6).
  6. The eff frame (the light data the mesh actually uses) is computed during the settle re-mesh from the settled-light state of the slab + neighbors; the E2 wave propagates eff-frame CHANGES to neighbors (a settle that changes nothing re-marks nothing — the no-op proof).

The chain's invariant: a slab is visible if and only if its light is settled. This is what makes the meshing and lighting acts separable — the mesh can land in any order; the light gates the show.

5.3 Keep-all-LOD — the stored tiers

When a column demotes out of the high band (band exit, §3.2 step 4), it does NOT discard its high-res mesh — keep-high: the high instances stay attached (hidden), the ready lows are flipped on, and the rest of the column's pending lows are re-opened to the low wave. A band RE-entry is a free visibility flip (the stored high is already meshed and lit; only show/hide changes, world.gd:8261-8318). A column can therefore hold up to 3 stored tiers (high + MED + LOW) — the cost of the keep-all policy, sized by _pool_mi_per_col ≈ 10 (world.gd:1104-1110, 1148-1169).

5.5 The low wave — pacing and order

_low_step (world.gd:2893-2973, 3060-3199) owns the visible surface OUTSIDE the high band (taxi ≥ low_start_r, default 27, clamped to [medium_start_r, render_radius] by apply_low_start, 1655-1671). The order is the SAME (layer, taxi) fan as the build lane: the wave picks the lowest-scoring entry outside the high band (the _entry_best_pending probe, NOT the high probe — it scans the full slab list, not the high-band window), dispatches one slab's avg emit, and the wave's pick is a (layer, taxi) disc fill — the far bands fill in the same player-slab-first, taxi-ordered disc the build lane uses for the high band. Tier-0 is excluded from the wave entirely (it's always high). The wave respects the band gate: if taxi < medium_start_r: skip (2916-2917) — the wave never touches the high band. And the high band itself renders NOTHING while pending (1604-1605, the AC-0261 decision) — a fast horizontal player sees HOLES in the high band until each slab's hslab + flush lands. The LOW_TASK_CAP = 64 (968) caps in-flight EMIT tasks (≈ 1.3 MB of slab copies); LOW_POLL_BUDGET_MS = 4.0 (973) caps per-frame wall clock on low handoffs (clamped to dt·0.25, min 1.0); LOW_UPGRADE_PER_FRAME = 1 (933) is the idle catch-up (low → high) after LOW_IDLE_GRACE_FRAMES = 10 (935); LOW_SCAN_CAP = 2048 (936) is the hard entry-visit cap for the pick scan.

5.8 Tier-0 — the section

The tier-0 section (default: the player's own column only, tier0_r = 0, max 8 = 289 columns, world.gd:1626-1629) is the one region that gets full-column, full-band treatment: its score gets the −1e10 prefix (it completes before ANY ring slab), its probes are NEVER windowed (the full column even while moving, §3.6), the build lane serves it (world.gd:6516, 6786, 6918), and the low wave skips it. 5.9 The lighting system — the two floods (what Starlight replaces)

The current lighting is two column-scale floods, both run by the flush loop's settle=true re-mesh:

  • The sky flood — the AweLighting pull-kernel (C++): for the slab being settled, the eff frame is computed by pulling sky-light from the neighbors' settled state (a per-section pull, not a global flood — but it re-meshes the whole column to apply it). This is the "sky + block one queue" target's first phase.
  • The block-light glow flood — the AC-0134 fix-6: torches/lava emit block light; the settle re-mesh computes the glow (distance-attenuated) from the slab's light sources + the neighbors' glow frames. The E2 wave (7822-7908) is the cascade that re-marks neighbors when an eff frame CHANGES on a landing.

The flush loop's 1 column/frame + 40 ms budget (world.gd:15, 11, 4435-4523) is the pacing that makes the two floods affordable — it also makes them the bottleneck for any design that settles more frequently (which Starlight's incremental propagation does NOT: it settles per-section, per-nibble, in the queue's own pace, not in a 1-col/frame flush).

07

Why this fights the flying disc

The user's end goal: a flying disc of full-quality terrain around the player — caves, light, everything — with the far horizon filling cheap and fast. The current architecture fights that goal in six ways (a–f), each verified against the code above.

a) Data is column-atomic — "cheap far" cannot be cheap

Every column in the render ring (5k-7k columns at R50) pays the FULL generation cost: 7 chunk-scoped coarse fields (3087 fbm3 ≈ 6174 vnoise3 samples) + the 384-block scan + all 24 slabs (§2.1, §4.2). The columns that only ever show as 4×4 avg shells (§5.4) are generated as if they were going to be meshed at full resolution. The C++ keep mask could in principle make a far column generate only its surface slab + evidence — but it is always passed empty (world.gd:5028-5031, the dormant AC-0237 seam, §2.9). As-is: a 1k-column far horizon costs ~1k × the full gen. That is the "far horizon < 50 ms" gate's blocker.

b) The (layer, taxi) layer-major order cannot express "fill the disc around me"

The score layer·10000 + taxi (§3.4) is a global layer sweep: all columns' rank-0 slabs before any rank-1, and so on. For a standing player that's fine. For a moving player it produces exactly the shape the user observed: passed columns' deep slabs (rank ≤ 18) outrank fresh columns' near slabs (a fresh column whose terrain top is at slab 8 while the player is at slab 18 starts at rank 19 — 19000+taxi, losing to ANY passed column owing rank ≤ 18). The worked example: 1·10000+9 = 10009 < 2·10000+50 = 20050 — deep work behind the player, holes ahead. The 83cfcfe Y-window papers over this (it hides the deep slabs from the probes while moving) but at the cost of the mechanism the user rejected. The shape itself — not the window — is the blocker to a disc that fills player-first, ring-by-ring.

c) The Y-window IS the rejected mechanism

User, verbatim (on the 83cfcfe timer) "3.5 s is a description of approximately what should happen based on our constraints, it in itself is not a constraint. So there should not be some kind of internal timer that changes what we do."

The window is a position-sampled moving state + a 3.5 s timer (§3.6): it decides what work EXISTS based on how recently the player moved 2+ blocks. That is a timer changing what the machine does — exactly the class of mechanism the user ruled out. And it is a band-aid on (b): it makes the deep work invisible to the scheduler while moving, rather than making the scheduler's order correct. Removing it without fixing the shape (b) restores the deep-behind-the-player behavior the window was hiding.

d) The lighting settle is a 1-column/frame flush of two column-scale floods

A slab can only become visible after its column's flush re-mesh (never-show-unlit, §5.2), and the flush is paced at 1 column/frame / 40 ms (world.gd:15, 11). Two consequences for the disc: (1) a fresh column that lands its 24 slabs in, say, 5 seconds then waits in a 1-column/frame flush queue before any of it is VISIBLE — the visible-disc lag is the flush lag, not the gen lag; (2) a landing into a settled column un-settles it (the late-landing fix, §4.6) — under a Y-disc that keeps landing long after the first settle, the chunk bounces settled → un-settled → settled for the entire fill, re-meshing neighbors along the way (the E2 wave, 7822-7908). Starlight's incremental per-section propagation is what replaces both the flush pacing and the two floods (§8.1, AC-0283).

e) Save-on-evict bloats the disk under flight

Every column that leaves the streaming set is saved (world.gd:8192-8204): encode on the pool, main-thread commit, region file. A 50× flight evicts thousands of full-quality columns per minute — each a full 24-slab palettized blob. The save IS the disk's memory of the world, so the disk grows with everything the player flew past, not with the region the player actually stood in. The v5 gen_mask (§4.5) already supports partial columns, but the save trigger is set-based, not content-based. AC-0287 (the save filter: only disc columns save) is the fix; the done-when gate is "a 10k-block flight doesn't bloat the save".

f) The queue's order shape is the only thing that is "expensive to change"

Everything else in the list above is a cost problem (a, d, e — too much work per unit) or a mechanism problem the user already ruled out (c). The (layer, taxi) BAKE (§3.4) is different: it is the ORDER in which the machine does its work, and it is correct for the walking regime the user accepted in-game. The redesign must not regress walking (done-when gate 5) while fixing flight — which is why the Flight-ready epic keeps the (layer, taxi) fan for the disc (player-slab-first is exactly "fill around me") and changes what the fan is FOR (the disc, not the ring) and what a column COSTS (the halo is dirt-cheap, §8.2). The "rescore all slabs every recenter" rule (HANDOFF §4) is already true — live scoring, free (§3.4) — so the redesign does not touch the recenter walk's contract at all.

Net assessment (a), (b), (c), (d), (e) are all solvable WITHOUT redesigning the substrate: the keep mask exists (dormant), the slab-granular build lane exists, the v5 partial-column disk exists, the live-scored queue exists, the flight-aware handoff budget exists. The epic's four tickets are the five enablers wired together: AC-0283 (Starlight) replaces (d), AC-0284 (cheap far data) re-activates (a)'s seam, AC-0286 (promotion) uses (b)'s fan correctly, AC-0287 (save filter) fixes (e). And (c) falls out: once the order (b) is correct and the halo (a) is cheap, there is nothing left for a moving-state timer to paper over — the window, and the 3.5 s, go away.
