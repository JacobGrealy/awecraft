03

Decision I — one light engine that settles (AC-0283, P1–P5)

Problem. The classic per-column light pull re-flooded on every landing; settled columns that received new data were un-settled (HID) and flushed through a per-column/frame wave — the late-landing churn (186 / 53 / 344 / 394 per phase in the baseline) and the flush-wave stage, and the cause of light popping on edits.

Decision. A single-queue C++ engine, AweStarlight (gdext/src/starlight.cpp): 16 level deques, per-section light nibbles, the sky column-pull that never crosses a chunk x/z edge; light settles into the engine and a slab's payload is captured at dispatch (epoch-checked at landing) instead of the mesh lane re-pulling. Around it: build-once-at-settle (the 3×3×3 box builds when the engine settles, not on every crossing), the remesh lane capped at 1 slab/key/frame (2 keys), the halo beyond the sim band (4×4 avg + heightmap sky, engine never seeded), and the star=false dispatch branch kept for the test arms. P4 re-classified AweLighting + the classic pull as TEST/REFERENCE (zero live game consumers); P5 made the tex-refresh dispatch star-native (real = settled payload, halo = h_avg_emit re-emit) and dropped c.last_eff from the path.

Rejected alternatives. (i) Keep the classic pull and only cache payloads — the un-settle/flush lifecycle is the churn, caching doesn't remove it. (ii) A GDScript engine — the per-cell fixed point is C++-speed territory; the equivalence gate (below) compares against the C++ legacy kernel anyway. (iii) Incremental per-slab re-seeding on far→full promotion — the whole-column top-down reseed is one operation and is the only seed order that cannot carry a stale sky (see §5).

Proof. starlighttest: engine ≡ legacy kernel, 0 / 5 308 416 cells (synthetic column + 3 edits + settled live region), re-run at every closeout. Post-P4 profile: late landings 0 in every phase, remesh flush down to 99 frames (flight) / 198 (walk), star work confined to 984 sections on the walk (exact confinement), frame 16.7 ms. P5's side finding, now a standing arm: Godot 4.7's ArrayMesh round-trip stores normals at 16-bit (1/65536 jitter) and vertex colours at 8-bit — vertices/indices/UVs byte-exact — so the tex-refresh arm compares at engine precision with a micro-probe every run.

04

Decision II — the far band costs 2 % of a column (AC-0284a/b)

284a — no caves out there. The halo band never shows caves (its light is a heightmap sky), so a far column doesn't need the cave field: generate_resl gained skip (0 full / 1 slab-skip / 2 far h-only), and 284a shipped skip=1 (solid 0..H slabs, no cave carve) for the far band.

284b — store nothing the mesh doesn't need. The 4×4 avg mesh is a function of (heightmap, biome, top block) — so the far column stores exactly that and no slabs at all: payload [H u16×256][biome×256][top×256] (1024 B raw, ≈ 198 B compressed on disk, v6 flag bit 1; bit 0 = no-caves from 284a; v1–v5 decode unchanged). The mesh is emitted by AweMesh.h_avg_emit, which shares its emit core with the slab path and is byte-identical to it (farab gate: 984/984 slabs). H is the heightmap (u16, no wrap) and stays bit-exact with the full path — that is the promotion consistency contract, so the surface fields are never coarsened.

Measured. Far column 92 µs (surface fields 57 + heights 34 + top 1) vs full 1678 µs — ≈ 18× per column; the heights-only pass (34 µs) meets the RP baseline's 32 µs line. The engine-seed contract fixed a real bug the arm exposed: a far column is never seeded as all air, and a far→full promotion re-seeds the whole column top-down (the stale all-air seam had been mis-carried sky 15 down through deep stone). A _far_promo_owed cap-drop retry (the enqueue returns bool) makes promotion lossless under queue pressure.

The honest gap on the <50 ms/1k done-when. The RP heights-only line (32 ms/1k) is met — but a far column that must stay bit-exact for promotion also carries the 3 surface fields (57 µs, the fbm physics floor — coarsening them would shift terrain on promotion) → 92 ms/1k single-threaded, 2× over the literal 50 ms. The win that actually matters: the far band is 1.7 % of what a full horizon cost (1.83 s/1k) and 198 B of what a full column costs on disk. Documented, not hidden.

Decision III — promotion that never pops (AC-0286)

The crossing itself was already detected (284a/b) and triggered a full regen; what was missing was the seamless part — the late-landing path HIDEs slabs during a re-bake, which reads as a fog-flash / hole while flying. The promotion contract, now in ARCHITECTURE.md:

ClauseDesignEvidence (halo (c) + flight profile)
DetectionThree points: the recenter walk, an in-band disk load, and a far data landing already inside the real band (gen-queue lag past the crossing — the bug found: such a column was never owed and sat low-detail forever). All funnel into _far_promo_owed; cap-drop = retry, not loss.181 landed promotions, enq == enq_final == 1 on every one (0 violations); demote + re-cross = new residency, also 1.
Retain-swapThe landing never hides/un-settles: the far low keeps showing, each slab flips high-on/low-off atomically behind the settled-payload gate. The old mesh's light (heightmap sky) is identical to the full path's sky for the surface — nothing is "wrong light", the caves are underground and invisible.0 hole-frames, 0 unlit frames in flight and walk; star_late_landings_promo = 0 (the hide path is never taken for promotions).
Single floodThe was_far branch re-seeds the whole column exactly once (top-down), one settle — never per-slab, never as air.seed-at-landing == 1 on every landed promotion; deterministic halo (c) confirms.
Burst_promo_build_step (per frame, beside the owed step) dispatches the landing column's best pending slab through the same _mesh_dispatch_hslab — all gates unchanged — bypassing only the build-queue score, so the conversion doesn't wait behind the flight's multi-thousand-deep backlog.Swap latency 350–361 ms at rest (~22 frames), 71–130 frames at flight cadence; final-state light vs converged reference: 0 mismatches.

Cost per promotion: full regen 2 ms (worker) + re-seed 2.6 ms + the swap above. The ticket's "~1 ms" was written before the h-only measurement — the regen alone is a hard floor; the incremental cost of the promotion on top of the gen is sub-ms main-thread.

06

Decision IV — what the save keeps (AC-0287 — pending)

The far band is now cheap in memory (198 B, no slabs) — the remaining waste is writing it to disk at all: a far column is re-derivable (92 µs of gen, no edits possible out there). AC-0287: the save filter writes only taxi ≤ sim or edited columns; the no-bloat proof is a 10 000-column flight whose save size must not grow with the far band. The RP baseline's IO lane was empty (0 reads/0 writes in all scenarios), so AC-0287 brings its own save-heavy scenario. It runs after the AC-0299 answers because the far band's data shape may change with the user's halo-look decision (§9) — the filter must know what a far column will look like before it decides what to drop.
